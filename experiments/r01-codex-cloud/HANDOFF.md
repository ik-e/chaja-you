# R01 실험 핸드오프 — ChatGPT 대화 → Codex Cloud

- 작성일: 2026-11-14 (KST)
- 용도: **현재 ChatGPT 대화의 전체 기록이 Codex Cloud에 자동 전달되지 않기 때문에** 이번 실험에 필요한 의도·판단·상태만 전달한다.
- 출처 구분: 이 문서는 R01 대화의 **작업 맥락 요약**이며, 실제 실험 결과나 팀의 공식 확정 결정이 아니다.
- 범위: `ik-e/chaja-you`의 **실험 브랜치** `experiment/r01-codex-cloud-20261114`; `main`, 운영 저장소 코드, 다른 팀원의 파일, 공식 WBS/기획서는 변경 금지.

## 1. 사용자와 상위 목적

- 사용자 역할: AI를 적극적으로 활용하면서 직접 결과를 교정·종합하고 최종 판단하는 소규모 프로젝트 책임자.
- 장기 제품 의도: **새로운 지능을 만드는 것이 아니라, 기존 LLM에 도구·기억·인터페이스·실행 환경을 제공하여 사람이 목적 달성을 위해 반복하는 관리·검증·교정 비용을 줄인다.**
- 이 장기 목적을 특정 고정 워크플로/멀티에이전트 구조로 확정하지 않는다. 리서치는 여러 업무 도메인 중 하나다.
- 이 실험의 좁은 도메인은 **프로젝트의 이전 승인·검토 기준을 후속 변경에 적용할 때 남는 사용자 부담**이다. 전체 제품 도메인이 이것으로 확정된 것은 아니다.

## 2. 멘토 피드백 및 문제 정의 상태

- 멘토가 `https://bathos.cc/en`을 제시했다. 초기 조사는 범용 AI 리서치 중심이어서 Bathos와 직접 경쟁 제품을 놓쳤다.
- Bathos, BMad, GitHub Spec Kit, OpenSpec, GSD Core, Gas City는 역할 분배·맥락/명세 보존·변경 추적·검증·승인 중 상당 부분을 제공한다.
- 따라서 'AI를 여러 개 실행한다', '상태를 저장한다', '검증 기능이 있다' 자체를 새로운 차별점이라고 주장하지 말 것.
- **잔여 페인포인트 가설 (아직 검증 전):** 이전에 승인한 판단이 새 상황에 유효한지, 어떤 조건/근거 변경이 어느 결정만 무효화하는지, 어떤 승인·재검증이 실제로 필요한지를 사용자가 반복해서 판별해야 할 수 있다.
- 공개 이슈의 실패 보고는 관찰된 제보이지 제품의 평균 결함률이나 현재 미해결 상태라는 증거가 아니다.
- 핵심 질문: **기존 솔루션을 충분히 잘 이용해도 이러한 반복 관리 부담이 남는가?**

## 3. 실제 사용자에게 중요한 비교 기준

- **불필요한 승인/질문**을 줄이면서 **필수 승인·예외 탐지**는 놓치지 않는가.
- 과거 결정의 **적용 범위**, 승인 여부, 출처/근거와 철회 조건을 올바르게 보존하는가.
- 조건이 바뀔 때 관련 결정·후속 작업 **일부만** 다시 평가하고, 무관한 작업을 과잉 재실행하지 않는가.
- 결과뿐 아니라 사용자 적극 작업시간, 반복 지시, 초기 설정·유지비용, 실패/복구를 측정하는가.
- 성공 판정에서 실행한 것과 하지 않은 것(`passed`, `failed`, `blocked`, `not_run`)을 섞지 않는가.

## 4. 이미 수행한 일 — **과제 실행과 구분할 것**

- Vercel 독립 샌드박스 `r01-workflow-comparison`에서 BMad **v6.12.4**, OpenSpec **v2.0.0**, GitHub Spec Kit을 Codex용으로 설치하고 CLI 상태를 점검했다.
- Bathos **v0.4.0** Rust 바이너리를 실제 빌드하고 `bathos doctor`는 PASS(4개 경고); Claude Code 실행 인증은 없었다.
- Vercel 샌드박스는 중지되었고 스냅샷이 존재한다. 이는 **Codex Cloud의 파일 시스템과 별개**이므로 설치를 이어받았다고 가정하지 않는다.
- Codex/Claude의 실제 모델 실행, 사용자 감독 부담 비교, 제품 효과 검증은 **아직 not_run**.
- 이 GitHub 브랜치는 Codex Cloud에서 **동일 테스트 과제를 실행하기 위한 fixture와 지침만 생성**한 상태다.

## 5. 이 브랜치의 시작점

- `README.md`: 웹 Codex에서 저장소/브랜치 선택 및 비교 순서
- `TASK_PROMPTS.md`: 기본 Codex(B0), BMad(B1), OpenSpec(B2), Spec Kit(B3) 작업 프롬프트
- `shared/SCENARIO.md`: 동일한 가짜 Status API 업무 과제
- `shared/DECISIONS.md`: 허용된 자동 수정과 승인 필요한 변경 구분
- `EVALUATION.md`: 판정·실행로그·사람 개입 평가 표
- 각 제품은 **독립 작업/작업 트리**에서 시작하며 서로의 결과를 입력으로 사용하지 않는다.

### 공통 과제 A/B/C

A. 문서의 `desgin` 오타만 수정 — 기존 정책상 추가 승인 불필요.

B. 공개 API 응답 속성 `user_id`를 `id`로 바꾸자는 요청 — **호환성 깨짐**: 사용자의 별도 명시적 승인 없으면 구현하지 않고 영향·승인 필요를 보고.

C. 팀 규모 5명→3명 변경 — 인력·일정 의존 계획만 재검토하고 무관한 기존 승인은 유지.

> 이 과제는 설치/승인/변경 판단을 관찰하기 위한 **작은 기능 시험**으로, 일반 사용자 페인포인트의 시장 검증으로 일반화하지 않는다.

## 6. Codex에게 내리는 실행 경계

1. 우선 **이 HANDOFF.md와 README.md, TASK_PROMPTS.md, shared/SCENARIO.md, shared/DECISIONS.md를 읽고**, 무엇을 할지 짧게 확인한다.
2. 브랜치가 `experiment/r01-codex-cloud-20261114`인지 확인하고, `main`에 커밋/PR 병합/배포하지 않는다.
3. **처음에는 B0 기준선**만 실행한다. BMad·OpenSpec·Spec Kit은 별도 신규 작업으로 동일 초기 조건에서 실행한다.
4. 비밀번호/API 키/기기 코드/세션 쿠키/인증 파일을 요구하거나 로그·커밋에 기록하지 않는다.
5. 외부 웹사이트를 무단 크롤링하거나 실제 서비스 API를 호출하지 않는다. 추가 유료 기능·API 크레딧 구매를 하지 않는다.
6. 요구사항·사용자 승인·실행 상태를 결과 파일에 정확히 기록한다. 중요한 API 계약 변경은 반드시 사용자 승인 전 중지한다.
7. 과도한 분해/에이전트 추가/검증이 실제 사용자 부담을 늘리면 **그 자체도 관찰 결과**로 기록한다.
