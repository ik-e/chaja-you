## 1. 먼저 탐색할 해결 능력(분류는 발견에 따라 수정 가능)

| 분야 | 기술이 제공하는 긍정적 해결 능력 | 확인할 입력→처리→결과 |
|---|---|---|
| **목적/요구 명세화** | 모호한 요청을 검토 가능한 요구·결정·변경 산출물로 만들고 구현 단계로 전달 | 자연어 요청·대화→명세/결정/작업 및 검증 기준 |
| **목표/조건 변경 관리** | 기존 명세·계획과 새로운 조건의 차이를 반영하고 영향을 국소화 | 이전 계획·승인 + 새 요구→변경안·영향 범위·새 작업 |
| **장기 문맥·기억** | 중요한 사용자 정보·이전 판단·문서/에피소드를 저장하고 유효한 맥락을 재제공 | 대화/경험/파일→저장·검색·갱신→후속 작업 입력 |
| **작업 분해·연결·인계** | 복합 목표를 담당 작업으로 나누고 출력·상태를 다음 단계에 전달 | 상위 요청→작업/위임→결과·인계·트레이스 |
| **실행의 지속·재개·예외 처리** | 긴 작업을 체크포인트하고 중단/승인 후 적절하게 이어감 | 작업 상태·이벤트→중단/복구/재개된 실행 |
| **권한·인간 결정권·검증** | 위험한 행동은 통제하고, 수행 여부/검증 결과를 근거와 함께 남김 | 행동 요청·승인 정책·산출물→허용/보류/검증/감사 기록 |

위 표는 기술 탐색용 분류다. 별도의 유의미한 기능(예: 대화 중 목표 수정, 정책 충돌 탐지, 계층적 검색, 사용자 선호 갱신)이 발견되면 추가한다. 이름이 비슷해도 다른 메커니즘이면 구별한다.

## 2. 우선 검토할 기존 기술·제품

깊게 조사할 핵심 후보(대략 8~10개, 문서·예제 확인이 불가능하면 축소 가능):
1. **ChatGPT Projects / Codex Cloud** — 사용자 맥락 유지와 비동기 작업/재개가 실제로 제공하는 것.
2. **OpenSpec** — proposal/spec/delta, tasks, verify/archive, 조건 변경 처리.
3. **GitHub Spec Kit** — specify/plan/tasks/analyze/implement 등의 사용자 의도→개발 산출물 연결.
4. **BMad Method** — 발견/계획/구현/리뷰에서의 목표·결정 보존과 right-sized workflows.
5. **Bathos** — 역할 분담, gating, audit, session restoration의 실제 보장.
6. **LangGraph** — 상태 그래프, checkpoint, interrupt/resume, human-in-the-loop와 선택적 경로.
7. **OpenAI Agents SDK** — handoffs, sessions, tools, guardrails, tracing, human review (지원 범위와 실제 API 확인).
8. **기억 계열 1~2개 대표** — 예: Letta와 Mem0 또는 다른 유지보수 중인 1차 구현. 지속 기억의 저장/검색/갱신/철회 방식.
9. **검증·권한의 실용 기준선** — GitHub Actions/required checks/PR review와 도구 승인 설정. 자체 프레임워크 기능과 구분.

추가 후보는 필요성이 드러난 경우만 2개 이내 포함. 이미 조사한 BMad/OpenSpec/Bathos를 다시 홍보식으로 요약하지 말고 **기능의 입력·출력·경계**를 새로 분석한다. 서로 성격이 다른 '제품 / SDK / 워크플로 방법론 / 인프라'를 동일 성능 랭킹으로 매기지 않는다.

## 3. 기술별 필수 분석 항목 — 기능 소개가 아니라 문제 해결 메커니즘

각 기술에서 실질적인 대표 기능 2~4개를 선택해 다음을 작성한다.

1. **사용 맥락 / 해결하려는 구체적인 작업:** 그 기술이 도입되기 전 무엇을 사람이 직접 관리했는가?
2. **입력 X, 결과 Y, 환경 E, 제약 C:** 기능을 실제로 호출하거나 운영할 때 필요한 것과 얻는 것을 예시로 작성. R4의 형식을 설명 도구로만 사용하고 모든 기술을 억지로 수학화하지 않는다.
3. **어떻게 해결하는가:** 명세 artifact, 체크포인트, 실행 상태, persistence, policies, gate, human interruption 등 메커니즘을 실제 파일/API/CLI 단계로 설명.
4. **확인 가능한 보장과 비보장:** 제품이 문서로 약속한 동작, 기계적으로 강제되는 것, AI 판단에 의존하는 것, 아직 미확인인 것 구분.
5. **작은 사용 예시:** 5~10단계 이내 재현 가능 시나리오나 공식 예제(가짜 고객 데이터만). 필요한 명령·설정·버전·환경을 적는다. 실제 실행하지 않았다면 `not_run`.
6. **운영 비용/제약:** 설치·권한·인간 승인·데이터 유지·호환·요금, 가능한 경우 현행 버전과 출시 성숙도.
7. **근거:** 공식 문서/공식 저장소/공식 example/기술 논문을 우선하고 URL·문서명·확인 시각(KST)·지원하는 주장·버전/커밋·반례를 표시.
8. **연구 활용 힌트(구현 아님):** 무엇을 *재사용 가능 구성 요소*로 배울 수 있는가. '우리만 가능하다/기존 것은 불가능하다'고 단정하지 않는다.

필수 **상태 구분**: `documented` (공식 문서로 지원) / `source_inspected` (소스/예제 열람) / `executed` (직접 실험과 로그) / `self_reported` (사용자/프로젝트 자체 주장) / `hypothesis` / `unknown`. 이 라벨은 `passed/failed/blocked/not_run` 작업 상태와 구분한다. 실제 실행·이용자 가치 측정이 없다면 반드시 기록.

## 4. 비교 방식과 핵심 산출물

`technology-capabilities/` 아래 다음 문서를 작성.

- `01-capability-map.md`: 기술 × 해결 능력 매트릭스(없는 기능은 '미제공'인지 '미확인'인지 분리), 가장 중요한 실제 구현 메커니즘, 해결 사례.
- `02-technology-cards.md`: 핵심 기술별 기능 2~4개의 X/E/C→Y, 메커니즘, 보장/한계, 공식 1차 근거, 버전.
- `03-patterns-and-reuse.md`: 공통 기술 원리 5개 이내(예: 명세-실행 분리, 체크포인트, 범위 있는 승인, 재검증, context retrieval), 서로 보완되는 조합, 기존 도구만으로 해결 가능한 사례. 근거 없는 신규 제품 아이디어는 별도 가설로 분류.
- `04-demo-candidates.md`: 기존 기술만으로 가능한 **작고 이해하기 쉬운 실증 2~3개**. 예: 목표가 바뀌었을 때 유지/수정할 작업 구별, 체크포인트 후 승인받고 재개, 이전 결정의 유효 범위를 수정 후 재적용. 각각 입력·기대 결과·필요 도구·성공/실패 조건·예상 작업 부담 포함.
- `STATUS.md`: 실제 읽은 출처·버전·관측, 파일별 작성 상태, 확인하지 못한 영역, 커밋 SHA, 다음 R01 판단 사항.

**중요:** P1~P6, 이전 경쟁 조사 목록은 참고 자료다. 이 목록을 모두 채우는 것보다 **현재 기술로 실제 무슨 일을 해결할 수 있는지 이해하기**가 우선이다. 문제 분류를 먼저 확정하고 거기에 제품을 강제로 대입하지 않는다.

## 5. 수행 순서

1. 기존 R01 R4, 선행기술 검토 R1, `discovery/03-existing-alternatives.md`, `discovery/06-existing-solutions-and-alternatives.md`를 중복 조사 방지용으로 읽는다.
2. 후보별 **공식 문서·예제·실제 API/파일 형식**을 확인하고 대표 기능과 작동 경계를 기록한다.
3. 기술 매트릭스를 작성하고, 설명이 겹치는 도구 간 다른 점과 함께 사용했을 때의 보완 관계를 분석한다.
4. 독립적이고 작은 실증 후보 2~3개를 제안한다. **실행은 별도 후속 단계**로 둔다.
5. 출처가 불명확한 주장은 삭제하거나 미확인으로 내리고, 모든 결과를 commit/push한다.

## 6. 작업 제한과 보고 형식

- 공개 자료는 공식 문서/저장소, 공식 API·허용된 열람 범위에서 수집한다. **대량 크롤링/무단 scraping 금지**. 계정·비밀키/권한 우회 금지.
- 새 외부 계정·유료 API·클라우드 인프라·Vercel sandbox 등을 개설/실행하지 않는다.
- 외부 사용자에게 연락하지 않는다. 실사용 시장성·고통 강도는 이번 조사 범위 밖이다.
- 새 아키텍처/프로토콜/제품을 만들지 않는다. 실제 기술이 **이미 어떤 문제를 해결하고 있는지**에 집중한다.
- 조사 비용이 커질 조짐이 보이면 후보 수를 줄이고, 우선 핵심 기능과 1차 출처를 확보한다.
- **완료 보고:** ① 주요 기술들의 실질적 해결 능력(가장 인상적인 3~5개), ② 기존 기술만으로 할 수 있는 것, ③ 기능의 보장/빈틈/미확인, ④ 실증 후보, ⑤ commit SHA 및 `passed/failed/blocked/not_run`별 실제 수행 상태.
- Cloud 작업 에이전트가 GitHub 결과를 작성한 뒤 이 ChatGPT 세션이 원문과 비교해 검토하고 R01이 다음 실증 우선순위를 고른다. Cloud UI 대화 내용이 자동 동기화되는 것은 아니므로 저장소 결과를 협업 인터페이스로 사용한다.
