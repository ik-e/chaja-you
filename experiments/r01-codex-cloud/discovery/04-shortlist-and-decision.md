# 04 — 최대 2개 타겟-문제 후보

- 날짜: 2026-11-16 (KST)
- 판정: 두 후보 모두 검증 전 가설. 공개 사례의 구체성은 보이지만 시장 문제나 고객군을 입증하지 않는다.
- 척도: 0 = 자료가 약하거나 해당 없음, 1 = 단일/제한적 자기 보고, 2 = 구체적 반복·실행 흔적이 있음. 점수는 우선 실험 순서를 돕는 휴리스틱이지 시장성 점수나 통계가 아니다.

## 후보 1 — 다중 저장소 변경을 조정하는 AI 활용 기술 책임자

> **여러 저장소를 가로지르는 변경을 주도하는 기술 책임자 후보**가 한 개의 계획을 여러 repo에 적용할 때 대상 저장소와 권한 범위를 직접 나누고 각 repo의 완료를 검증해야 하는 상황에서, 일부 대상이 빠져도 적용 완료로 보일 수 있다는 보고와 별도 repo 계획을 만드는 우회가 관측됐다. 현재 OpenSpec Store/workset은 중앙 계획과 여러 repo의 context를 제공하지만 보고된 현재 흐름에는 수동 라우팅과 부분 완료 확인이 남는다. **실제 누락 피해·반복 빈도·사용자 시간·2~5명 팀 여부는 미확인이다.**

- 근거: [OpenSpec #725](https://github.com/Fission-AI/OpenSpec/issues/725), [renatospaka의 실제 migration 보고](https://github.com/Fission-AI/OpenSpec/issues/725#issuecomment-5342286611), [partial apply 보고](https://github.com/Fission-AI/OpenSpec/issues/725#issuecomment-5447038536), [maintainer의 현재 Store/workset 한계 설명](https://github.com/Fission-AI/OpenSpec/issues/725#issuecomment-5573214645).
- 반증/한계: Rapoport의 OpenSpec 운영 보고처럼 저장된 proposal이 장기 인계에 도움이 된 사례가 있고 Store/workset도 중앙 계획과 context를 개선한다. 수동 라우팅이 몇 분이면 끝나고 누락 없이 작동한다면 새 문제는 약하다. m13v의 상태 표기는 실제 피해로 이어졌는지 확인되지 않았다.
- 해결되지 않은 의문: 사용자의 현재 도구는 무엇인가? 이런 변경이 월 몇 회 있는가? 부분 완료를 누가 어떻게 알아채나? 실제 누락/재작업이 있었나? 권한 경계를 열지 않고 현재 도구만으로 어떻게 운영하나? 같은 문제를 겪은 2~5명 팀의 연락 가능 사용자는 있는가?
- 점수: 반복 빈도 **1** (복수 repo가 필요한 작업은 있으나 사람별 재발 횟수 unknown); 실제 피해 **1** (부분 적용 완료 표시는 보고됐으나 실제 손실/시간 unknown); 기존 대안 뒤 잔여 **2** (Store/workset 이후에도 수동 라우팅/완료 확인을 maintainer와 사용자들이 지적); 연락·검증 가능 **1** (공개 issue 계정은 있으나 접촉/동의 없음); 8주 내 시험 **2** (격리된 3 repo fixture로 partial failure와 status 정확도 재현 가능). **합계 7/10, 탐색 우선 후보.**
- 10~15분 인터뷰 질문:
  1. 최근에 하나의 변경을 두 개 이상 저장소에 적용한 가장 최근 사례를 처음부터 설명해 주세요.
  2. 그때 각 저장소가 해야 할 일과 수정 권한은 어떻게 나누고 전달했나요?
  3. 일부 저장소가 실패하거나 늦게 반영된 것은 어떻게 확인했나요? 실제 후속 수정/재작업이 있었나요?
  4. 비슷한 일이 지난 한 달/분기에 몇 번 있었고 확인·조정에 직접 쓴 시간은 어느 정도였나요?
  5. 지금 쓰는 Store, worktree, project instruction, checklist로 충분히 해결된다면 무엇이 남아야 이 방식을 바꾸겠나요?
- 최소 기능 시험 1개: 계획 Store + 플랫폼/인프라/앱 3개 fixture에서 한 변경을 각 repo로 나누는 상황을 만들고 한 repo 실패를 주입한다. 잘 구성된 Codex 프로젝트 지침/decision log 기준선에서 대상 선택, 실제 수정 범위, repo별 성공 상태의 정확성, 사람의 라우팅/검증 시간과 반복 지시를 기록한다. 오늘은 fixture/실행 모두 만들거나 수행하지 않는다.

## 후보 2 — 로컬 MCP를 반복 사용하는 Codex CLI 사용자

> **Codex CLI와 로컬 MCP를 자주 쓰는 개인 개발자 후보**가 장시간 연속 작업에서 같은 도구를 다시 호출할 때 Allow always를 선택했는데도 승인 질문이 몇 번 호출마다 돌아와 작업이 멈추고 터미널을 지켜봐야 한다는 자기 보고가 있다. 현재 Codex는 Allow always 승인 선택지를 제공하지만 보고자들은 자신의 환경에서 반복 프롬프트를 경험했다. **정확한 원인, 최신 버전 상태, 총 감독 시간, 실제 반복률은 미확인이다.**

- 근거: [Codex #16911 원 보고](https://github.com/openai/codex/issues/16911), [Windows/local MCP daily use 추가 보고](https://github.com/openai/codex/issues/16911#issuecomment-6568876726).
- 반증/한계: 두 보고는 하나의 issue thread이며 조직 독립성을 확인하지 못했다. 버전별 오류일 수 있고 현재 릴리스에서는 사라졌을 수 있다. 승인 확인이 실제 위험을 막았던 사례·보안 이익도 함께 봐야 한다.
- 해결되지 않은 의문: 같은 도구·같은 세션에서 재발하는가? 허용 결정의 기대 scope는 무엇인가? 모델/서버/권한 모드별 차이는? 사용자는 무조건 허용 대신 어떤 경계(도구·인자·시간·횟수)를 원하나? 장시간 작업 중 실제로 몇 번 멈추고 얼마나 기다리나?
- 점수: 반복 빈도 **2** (원 보고의 “매 두 번째 호출처럼” 표현과 댓글의 daily use/몇 회마다라는 빈도); 실제 피해 **1** (작업 정지와 터미널 감시 보고, 시간 계측 없음); 기존 대안 뒤 잔여 **1** (Allow always가 있으나 자기 보고 환경에서 반복, 최신 상태 미확인); 연락·검증 가능 **1** (공개 계정, 메시지 발송·동의 없음); 8주 내 시험 **2** (로컬 mock MCP flow에서 승인·정지·반복률 계측 가능). **합계 7/10, 증거 제한 후보.**
- 10~15분 인터뷰 질문:
  1. 최근 같은 MCP 도구가 허용 뒤 다시 승인을 요청한 순간을 보여주거나 순서대로 설명해 주세요.
  2. 그 전에 어떤 Codex 버전·승인 선택·세션·도구를 쓰고 있었고 재발까지 몇 번 호출됐나요?
  3. 질문이 오면 하던 작업이 얼마나 멈추며 실제로 사람이 어떤 행동을 해야 다시 진행되나요?
  4. 현재 어떤 설정/버전 변경/도구 대체로 줄였고 그 대가로 잃은 기능이나 위험은 무엇인가요?
  5. 반복 프롬프트가 전혀 없도록 만드는 것과 범위가 넓은 자동 허용 중 무엇이 더 우려되며 어떤 증거가 허용 범위를 정하기에 충분한가요?
- 최소 기능 시험 1개: 실제 외부 서비스를 연결하지 않는 로컬 mock MCP 호출을 사용해 같은 세션에서 한 도구를 반복 호출한다. 수동 승인 수, 동일 작업의 대기/중단 시간, 의도한 scope 밖 호출 차단, 명시적 승인 후에도 반복되는 비율을 기록한다. 최신 Codex 버전과 승인 설정을 확인한 뒤 사용자 동의 아래 별도 시험으로 설계하며 오늘은 실행하지 않는다.

## 결정 제안

오늘은 두 후보를 우선 검증 목록에만 남긴다. R01은 다음 작업 전에 실제 연락 가능한 사용자군이 있는지와 어느 후보를 먼저 인터뷰할지 선택해야 한다. 실제 사용 사건·재발률·피해가 나오기 전에는 어느 후보도 제품 도메인으로 확정하지 않는다.
