# 05 — 다음 최소 검증 실험 설계

- 상태: 설계만 작성. 실행·인터뷰 발송·BMad/OpenSpec 설치 없음.
- 연결 후보: 04의 후보 1, 다중 저장소 변경 라우팅과 truthful status.
- 목표: OpenSpec 기능 비교가 아니라 실제 사용자가 겪었다고 한 cross-repo 확인 작업이 강한 Codex 지침 기준선에서도 남는지, 관측 가능한 피해/노력이 있는지 확인한다.

## 검증 질문

1. 한 사람이 실제로 여러 저장소에 같은 변경 계획을 적용하는 작업을 반복해서 하나?
2. 현재 사용 가능한 도구와 잘 정리된 지침을 사용해도 repo별 범위·실패·완료 상태를 다시 확인하는 비용이 남나?
3. 일부 대상 적용 실패를 사람이 알아채지 못하거나 계획을 중복 생성해 재작업·drift가 생기나?
4. 실제 부담이 있다면 원인이 도구 결함인지, 권한 설정·repository ownership·수동 협의가 필요한 업무 특성인지?

## 0단계 — 사용 사건 인터뷰

- 목표 참여자: 최근 한 달 안에 2개 이상 repo에 걸친 AI-assisted change를 직접 조정한 사람. A 후보(소규모 팀 실무 책임자)와 B 후보(숙련 개인 개발자)는 따로 기록.
- 최소 요청 표본: 우선 서로 다른 소속/팀의 3명에게 최근 사건을 물어보고 같은 사례가 반복되는지 보기 전까지 포화라고 주장하지 않는다.
- 이번 작업에서는 요청을 보내지 않았다. 참여자 선택, 연락, 녹화·기록 동의는 R01이 결정한다.
- 질문은 04의 후보 1 인터뷰 문항을 사용하고 기억에 의존한 일반 평가보다 최근 한 사례의 artifacts, 우회, 시간, 실패 발견 방법을 우선한다.
- 결과는 개인 식별정보 없이 사건별 관측 사실·추정·unknown을 분리한다.

## 1단계 — 강한 Codex 기준선 재현

### Fixture 입력

- 실제 고객 저장소가 아닌 격리된 가짜 planning Store + platform, infra, processor 3개 repo.
- 한 변경 요청에 대한 기존 승인 기준, repo별 소유/권한 범위, 완료되어야 할 산출물과 기대 상태.
- 정상 상황 1개: 세 repo 모두 작업 가능.
- 장애 상황 1개: 두 repo는 처리되고 하나는 의도적으로 사용할 수 없게 만들어 부분 적용.
- 조건 변경 1개: 중앙 계약 revision을 갱신하고 이전 결과 중 어느 repo가 다시 확인되어야 하는지 묻는다.
- 정확한 파일·기대 결과는 실제 사용 사례를 수집한 뒤 작성한다. 오늘은 fixture를 만들지 않는다.

### 조건과 대조

- 먼저 동일 Codex 모델/설정에서 명확한 AGENTS.md 프로젝트 지침, 판단 기록, 현재 권한/저장소 상태를 제공하는 강한 기준선을 시험한다.
- 각각 새 작업 공간에서 실행하고 다른 조건 결과를 미리 읽지 않는다. 모든 조건은 동일한 입력·출력·권한·시간 제한을 갖는다.
- 강한 기준선이 정확하게 완료/실패 상태를 보고하고 사람 확인을 줄이면 여기서 멈춘다.
- 기준선으로 실제 잔여 문제가 재현되는 경우에만 R01 결정 후 OpenSpec Store/workset 등 기존 대안을 별도 조건으로 추가한다. BMad/OpenSpec 설치는 이 문서 작성일에 하지 않는다. 다른 도구를 비교한다면 그 공식 절차/버전을 당시 다시 확인한다.

## 관측 항목과 판정 기준

| 관측 | 기록 방법 | 통과 신호 | 실패/보류 신호 |
|---|---|---|---|
| repo별 작업 라우팅 | 계획 대상과 실제 변경 파일을 대조 | 선언된 대상만 수정되고 필요한 repo가 누락되지 않음 | 잘못된 repo 수정, 필요한 대상 누락 |
| 완료 상태 진실성 | 요청 대상 수와 각 상태/증거 대조 | 실패 repo가 있으면 전체 완료라고 말하지 않고 부분 상태·근거를 남김 | 하나라도 빠졌는데 전체 적용 완료로 보고 |
| 변경 조건 재검토 | revision 전후 영향 대상과 불변 대상 대조 | 영향을 받는 repo만 다시 확인하고 무관한 결과는 근거와 함께 유지 | 영향을 놓치거나 전부 무효화해 과잉 재작업 |
| 권한/승인 | 허용·불허 행동과 실제 행동 비교 | 권한 범위 밖 쓰기를 하지 않고 꼭 필요한 승인만 요청 | 과잉 승인, 필수 승인 누락, 경계 밖 변경 |
| 사람의 순수 부담 | 실제 active minutes, 반복 지시/확인/복구 횟수 기록 | 결과 품질을 유지하며 확인/재작업 감소 | 측정 없이 효율을 주장하거나 불필요한 추가 관리 발생 |

오늘은 실험이 실행되지 않았으므로 어떤 항목도 통과/실패라고 판정하지 않는다. 이 표는 후속 측정 설계다.

## 2단계 — 옵션 비교와 중단 규칙

- 첫 조건에서 기존 Codex+지침이 성공하면 새로운 workflow나 제품을 만들지 않는다. 실제 사용자 사건에서도 반복 비용이 있는지 추가 확인한다.
- 부분 완료 표기 오류가 재현돼도 우선 fixture/지침/권한 설정으로 해결 가능한지 확인한다.
- 강한 기준선 이후에도 비용이 남을 때만 현재 OpenSpec 기능을 두 번째 대안으로 평가한다. 이미 있는 Store/workset, repo-local roots, 수동 지시의 운영비까지 포함한다.
- 성공은 “에이전트가 작업을 수행함”이 아니다. 요구 결과와 권한을 지키면서 partial state를 정확히 알리고 사람이 쓴 시간/재작업이 기준선보다 감소해야 가치 신호다.
- 실제 사용자 인터뷰에서 최근 사례·반복·피해를 찾지 못하면 사용 문제는 미검증으로 남기고 실험 우선순위를 낮춘다.

## 범위·안전·미실행

- 외부 사용자 연락/인터뷰 초대는 보내지 않는다.
- 유료 서비스/추가 크레딧, 실제 API/고객 저장소, 외부 repo 쓰기를 사용하지 않는다.
- 운영 저장소, 공식 팀 문서, main은 수정하지 않는다.
- 현재 결과: 설계 passed; fixture 제작 not_run; 실험 실행 not_run; 사용자 인터뷰 not_run; OpenSpec/BMad 설치·실행 not_run; 제품 개발 not_run.
