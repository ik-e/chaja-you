# R01 — AI 작업 위임 관리 문제 가설 P0~P6 및 기존 솔루션 대응 범위 (임시)

- 작성/확인: 2026-11-16 (KST)
- **상태:** 검증 전 가설 / R01 개인 실험 기준안. 타겟 사용자, 제품 문제, 핵심 기능, 공식 MVP를 확정하지 않는다.
- **작성 목적:** 추상적인 'AI에게 일을 맡겨도 안심할 수 없음'을 독립 검증 가능한 사용자 문제로 분해하면서 **기존 도구가 이미 해결하는 범위**와 **잔여 사용자 피해의 증거 부족**을 함께 기록한다.
- **범위:** 실험 브랜치의 조사 자료. main, 공식 프로젝트 INTENT·WBS·APP-A/C, 기존 B0 결과를 변경하지 않는다.
- **명명 주의:** 이 문서의 P0는 *AI 작업 위임 관련 중간 수준 가설*이다. 기존 R01 R4의 더 넓은 상위 P0(사용자 목적 달성 및 반복 관리 비용 절감)를 대체하지 않는다. 이 문서의 P1~P6도 임시 라벨이며 R4의 문제 트리를 재정의하지 않는다.

## 1. 상위 목표와 임시 사용자 문제

**R4의 더 넓은 제품 가치 가설:** 기존 모델의 지능을 도구·기억·인터페이스·실행 환경과 연결해 사용자 목적 달성 시 불필요한 인지적·관리적 비용을 줄일 수 있는가.

**이 문서의 위임 관리 P0(임시):** 사용자는 AI에게 실제 업무를 위임하지만, 중요한 실패·예외를 놓치지 않기 위해 실행 과정과 결과를 반복적으로 확인·교정해야 할 수 있다.

- **X:** 위임한 요청·목적·제약, 과거 판단, 실제 작업 상태, 새 정보
- **Y:** 허용 조건을 충족하는 실제 결과 또는 정확한 부분/중단 상태, 필요한 최소한의 사용자 판단 및 재개 정보
- **E:** 클라우드/로컬 AI 작업 환경, GitHub·코드 저장소·도구, 사용자 부재/마감 상황
- **C:** 사용자 승인권·보안/비용·실행권한, 무단 행동 금지, 미검증 결과를 성공으로 보고 금지
- **제품 가치 가설(증명 전):** 동일한 안전성과 결과 품질을 유지하면서 직접 감시·재설명·재검토·복구에 든 사용자 시간이 감소한다.
- **타겟 행동 조건(선정 전):** 30분 이상 걸리는 AI 작업을 반복 위임하고 결과 및 일정에 책임지는 개인 개발자 또는 작은 프로젝트의 실무 책임자. 사용 빈도·고통·직무는 아직 측정되지 않았다.

## 2. 하위 문제 — 사용자 행동과 비용을 중심으로

| ID/시점 | 정확한 발생 조건 X/E | 필요한 결과 Y / 보호 제약 C | 사용자가 겪을 수 있는 직접 피해(검증 전) |
|---|---|---|---|
| **P1 위임 전·실행 중: 범위 이탈** | 한정된 수정·조사를 지시했지만 실행 계획이 관련 시스템 전체로 확장 | 허용된 대상·범위 내 산출물; 범위 변경은 드러내고 필요하면 승인 | 예상보다 큰 재검토, 결과 지연 |
| **P2 실행 중: 불필요한 승인 중단** | 이전에 허용한 동일 범위 행동을 다시 승인하라고 요청 | 이미 유효한 허용은 재사용, 새로운 위험만 사용자 확인 | 작업 정지, 반복 클릭·상시 대기 |
| **P3 실행 중: 중단 사실 발견 지연** | 작업이 실패·승인 대기·자원 한도 등으로 정지했는데 사용자가 늦게 알게 됨 | 상태·원인·필요 행동을 적시에 알림, 실제 진행 여부를 숨기지 않음 | 자리를 비운 시간의 손실, 마감 차질 |
| **P4 실행 중: 자원/노력 통제 실패** | 특정 목적에 비해 지나친 탐색·하위 작업·토큰 사용 | 상한·중단 조건 내에서 유의미한 결과, 품질 하락은 표시 | 사용량/금액/시간 낭비와 미완료 |
| **P5 실행 후: 완료 상태와 실제 결과 불일치** | 일부 작업·저장소가 실패했는데 전체 완료로 보고하거나 테스트 미실행을 통과로 표시 | 대상별 passed/failed/blocked/not_run 및 산출물·테스트 근거 | 누락 발견을 위한 재검증, 배포·운영 위험 |
| **P6 실패 후: 복구/인계 부담** | 작업이 중단되거나 세션·담당자가 바뀌며 맥락·변경 이력·부분 산출물이 흩어짐 | 복구 가능한 상태와 재개 지점, 유효한 승인 범위 유지 | 처음부터 재설명·중복 실행·손상 복구 |

P1과 P4, P2와 P3은 연관되지만 서로 동일하지 않다. P1/4는 원인-비용 관계일 수 있고, P2가 완화되어도 다른 이유의 중단(P3)은 남는다. 이 분해는 사용자 문제의 분류이지 6개 제품 기능 목록이나 필수 실행 파이프라인이 아니다.

## 3. '해결 정도'를 측정하는 규칙

**두 축을 분리한다.**
1. **기능 대응(feature coverage)**: 기존 제품에 명세·상태·승인·복구 기능이 문서상 존재하는가?
2. **사용자 고통 감소(outcome effectiveness)**: 실제 사용자 상황에서 반복 확인 시간·재작업·피해가 얼마나 감소하는가?

이 문서의 '대응 수단 충분/일부/불명'은 1번에 대한 **정성적 잠정 판단**이다. 2번의 해결 비율(%)이나 시장 수요는 모두 **not_verified**다. 공개 issue는 해당 환경의 사용자 보고이지 제품 전체의 일반적 결함이나 발생률이 아니다.

| 하위 | 확인 가능한 기존 대응 수단 | 기능 수준 잠정 평가 | 기존 도구 사용 후에도 남는지 확인할 질문 |
|---|---|---|---|
| **P1** | Codex의 프로젝트 지침/AGENTS.md, BMad 명세·작업 범위 관리, OpenSpec proposal/spec | **폭넓게 존재** | 명확한 입력·지침이 있는데도 범위를 벗어나는가? |
| **P2** | Codex MCP/도구 승인 옵션, 검토/권한 게이트 | **부분 대응** | 같은 승인 범위에서 반복 요청이 재현되는가, 현재 버전/설정 문제인가? |
| **P3** | Codex Cloud의 독립 백그라운드 실행과 작업 상태, GitHub CI의 진행/실패 상태 | **일부 대응** | 작업 중단 또는 승인 대기를 사용자가 알아차릴 때까지 얼마 걸리나? 기존 알림/확인으로 충분한가? |
| **P4** | BMad right-sized workflow, Bathos 규모·동시성/쿼터 가이드, 지침상 자원 한도 | **부분 대응** | 좁은 목적에 과잉 조사·사용량 소진이 현재 버전에서도 발생하는가? |
| **P5** | GitHub 필수 CI·PR 검토, Spec Kit analyze/converge, OpenSpec verify/validate/archive, Bathos 검증 게이트 | **폭넓게 존재** | 검증하지 않은 대상/저장소를 완료 처리하는가? 대상별 실제 근거가 있는가? |
| **P6** | Codex Cloud 작업 이어가기·Git 커밋, OpenSpec 변경 기록/아카이브, Bathos save/resume | **폭넓게 존재** | 복구 시간과 재설명 비용이 실제로 남는가? 작업 상태·승인 범위가 유효하게 보존되는가? |

**중요한 비대칭:** '작업을 백그라운드에서 계속 수행 가능'(P3 관련) ≠ '모든 종류의 중단을 즉시 알려 줌'; '검증 기능이 존재'(P5 관련) ≠ '모든 작업 대상의 완료가 입증됨'; '세션 복원'(P6) ≠ '자동 원인 해결'.

## 5. 주요 대안의 문서로 확인된 기능

- **[Codex Cloud — 공식 도움말](https://help.openai.com/en/articles/20001545-using-codex-cloud)**: 준비된 환경에서 격리 작업을 실행하고, PC가 잠들어도 이어가며, 같은 작업으로 돌아가 계속 수정할 수 있다. 원래 작업의 미커밋 파일과 새 작업은 분리되므로 Git 기록이 중요하다. 이것만으로 임의의 중단을 감지·알림한다고 가정하지 않는다.
- **[OpenSpec workflow](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md) / [team workflow](https://github.com/Fission-AI/OpenSpec/blob/main/docs/team-workflow.md)**: 제안·명세·적용·검증·보관을 지원하고 변경 근거를 남긴다. 명세/검증 지원과 여러 repo의 완전한 실제 실행 상태 보장은 별개다.
- **[Spec Kit](https://github.com/github/spec-kit/blob/main/README.md)**: specify→plan→tasks→implement→converge, 분석·검증과 이슈 수정을 지원한다. converged 결과는 해당 절차·입력의 범위에서 해석한다.
- **[BMad changelog](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)**: 작업 규모 조정, 근거 있는 리뷰, 결정 로그를 포함한다. 특정 headless 사용자가 보고한 과다 실행을 일반화하지 않는다.
- **[Bathos README](https://github.com/taxideftis/bathos/blob/prod/README.md) / [FAQ](https://github.com/taxideftis/bathos/blob/prod/docs/FAQ-en.md)**: 역할·게이트·감사·저장/재개를 제공한다고 프로젝트가 문서화. v0.4.0은 early/dogfood 수준이므로 외부 사용자 효능이 입증됐다고 보지 않는다.
- **[GitHub status checks](https://docs.github.com/en/pull-requests/reference/status-checks) / [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)**: CI 진행/실패·필수 리뷰·병합 조건을 제시한다. CI 성공이 시험 범위 밖 업무 전체의 완료를 의미하지는 않는다.

## 6. 사용자 가치 검증 우선순위(임시)

- **고통의 즉시성 탐색:** P2+P3(위임한 작업이 장시간 중단되어 아무 성과가 없는 문제), P1+P4(작은 업무의 범위 확대로 사용량과 시간을 소진). 단, 구체 피해/빈도/현재 재현은 사용자 확인 필요.
- **업무 영향/신뢰성 탐색:** P5(일부 미완료를 완료로 보고). 실제 사고나 검증 비용이 측정되지 않으면 추상적인 '정확성 개선'으로 묶지 않는다.
- **기존 대응 강한 영역의 반증:** P6. 기본 Codex Cloud+Git+OpenSpec/Bathos로 이미 충분하다면 신규 기능은 보류한다.
- 기존 인터뷰 없는 공개 이슈 표본만으로 '타겟 사용자'를 확정하지 않는다. 더 넓은 P0를 곧바로 제품 서비스 문장으로 사용하지 않는다.

## 7. 다음 작업 계약 — 솔루션 비교를 먼저, 사용자 문제 검증과 병행

1. **타겟 행동 기준 선택:** 최근 한 달의 AI 위임 사례가 있고, 목표와 마감·결과 책임이 있으며, 실제 마지막 실패 사건을 설명할 수 있는 사람. 직함만으로 분류하지 않는다.
2. **실제 사건/피해 수집:** 최근 사건의 입력·실행 로그·중단 시각·사용자 발견 시각·복구 행동·재작업 시간, 사용 중인 설정을 기록. 외부 사용자 접촉은 별도 R01 결정 전 발송하지 않는다.
3. **강한 기존 대안 그대로 사용:** Codex Cloud+AGENTS.md+GitHub CI/PR, 필요한 경우 OpenSpec/BMad의 공식 절차. 현재 기능을 의도적으로 빼거나 약하게 설정하지 않는다.
4. **반증 실험:** P2/3은 작업 정지·승인 대기와 발견 지연을 측정; P1/4는 범위·사용량·완료까지 측정; P5는 부분 성공/실패 주입 후 대상별 상태와 증거 일치도를 확인.
5. **판정:** 실제 사용자 비용이 없거나 기존 제품만으로 충분하면 신규 기능 개발하지 않는다. 비용이 남는 경우에도 먼저 설정·운영 절차 개선으로 해결 가능한지 평가한다.
6. **다음 산출물:** 케이스별 (a) 기존 제공 기능, (b) 실제 사용한 설정, (c) 관측 결과, (d) 반복/사용자 적극 작업시간, (e) 잔여 문제, (f) 반증 및 제품 후보 여부. `passed / failed / blocked / not_run`과 **확인/자기보고/추론/미확인**을 분리한다.
