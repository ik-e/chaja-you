# R01 — P1~P6 기존 해결 방식과 현실적 대안 조사 R1

- 확인 기준: **2026-11-16 (KST)**
- 상태: **R01 개인 탐색 / 사용자 페인포인트·신규 제품 가치 미확정**
- 근거: [임시 문제 분해](2026-11-16-provisional-problem-tree-and-solution-coverage.md), [공개 사용자 사건 7건](02-user-incidents.md), [기존 제품 검토](03-existing-alternatives.md)
- 목적: 단순 결함 목록이 아니라 **기존 사용자의 대처 방식(AS-IS)** → **이미 출시된 해결 수단** → **현실적인 개선안** → **검증되지 않은 잔여 문제**를 연결한다.
- 범위: 모의 실험과 문서 조사. `main`, 공식 팀 자료, Codex B0 산출물, 외부 서비스 설정은 변경하지 않는다.

## 1. 해결 가능한 범위를 구분한다

1. **사용자 수동 운영**: 작업 단위 쪼개기, 체크리스트, 상태 확인, 담당자 리뷰, 재개 문서, 실패 복구.
2. **기존 제품 기본 기능**: Codex Cloud 작업 이어가기, 프로젝트 지침, 승인 설정, GitHub CI/PR, OpenSpec의 제안·검증·아카이브, BMad 규모별 워크플로, Bathos의 게이트·세션 복원.
3. **기존 도구 조합/설정**: 좁은 작업 스코프+허용 파일/예산+명시적 종료 조건, CI 및 상태 로그, 권한별 승인, 재개 체크포인트. *일부는 제품 기본 기능이 아니라 사용자가 직접 구성하는 운영 절차*다.
4. **추가 제품 기능 후보**: 이전 3개 접근으로도 남는 **반복적이고 비용이 큰** 사용자 문제에 한해 제안. 신규 오케스트레이터가 정답이라는 전제 없음.

**기능 대응과 성과를 구분:** 기능이 존재한다고 사용자의 시간·오류가 실제로 줄었다는 뜻이 아니다. 또한 공개 버그 제보 하나가 현재 모든 사용자에게 남는 결함을 입증하지 않는다.

## 2. 하위 문제별 AS-IS → 대안

| 문제 | 이전부터 사용한 사람 중심 해결 방식(AS-IS) | 이미 존재하는 제품/기능 | 지금 선택할 수 있는 저비용 대안 | 잔여 문제가 되려면 필요한 관측 |
|---|---|---|---|---|
| **P1 범위 이탈** | 작업 쪼개기, 담당자가 중간 결과 검토, 작업 범위 다시 설명 | Codex 프로젝트 지침/AGENTS.md, OpenSpec proposal/spec, BMad의 명세·프로세스 | 요청에 **대상/비대상/완료 조건/중단·승인 조건**을 명시하고 작업 결과를 파일 변경 목록과 대조 | 좋은 지침·좁은 작업 단위에서도 범위 이탈이 반복되고 사람 재작업이 남는가 |
| **P2 불필요한 승인 중단** | 터미널/승인 창 대기, 매 호출 수동 확인, 신뢰하는 작업만 승인 | Codex 승인 옵션, 도구·호스트 권한 설정, 기존 리뷰/권한 게이트 | 같은 **도구·행동·대상·권한 범위**에 대해 승인 규칙을 명확히 하고 환경·버전·반복 횟수를 기록. 모든 승인을 무제한 해제하지 않음 | 유효 승인 후에도 같은 범위의 프롬프트가 재현되는가; 버그 수정·설정으로 해결 안 되는가 |
| **P3 중단 발견 지연** | 주기적 상태 확인, 작업 완료 시 수동 연락, 작업 시간 추정 | Codex Cloud의 비동기 실행/작업 복귀, GitHub Actions의 작업 상태/실패 결과 | **실제로 얻을 수 있는 상태 이벤트**가 있다면 정지·승인 대기·실패에 한해 알림. 없다면 상태 기록과 점검 주기를 운영하고 알림 기능을 가정하지 않음 | 중단 발생 → 사용자 발견까지 시간과 손실이 충분히 큰가; 기존 상태/알림으로 줄어드는가 |
| **P4 과잉 탐색·자원 소모** | 작업을 작게 나눔, 사람이 시간/쿼터를 확인해 중단 | BMad 규모별 프로세스, Bathos 규모/동시성·쿼터 안내, 도구별 사용량 제한 기능(환경별 확인 필요) | **스코프·허용 하위 작업·시간/호출 예산·중단/부분보고 기준**을 입력과 실행 정책에 명시하고 실측. 실행 중 예산 제한이 지원되는지 별도로 확인 | 잘 설정한 기존 제품에서도 초과 탐색으로 비용/결과 손실이 반복되는가 |
| **P5 완료 보고 부정확** | 사람이 변경 파일·테스트·요구 항목을 일일이 확인 | GitHub PR/필수 status checks, OpenSpec verify·validate/archive, Bathos 독립 리뷰/게이트 | **각 대상별 actual evidence** (커밋, 테스트, 변경 diff, 미실행 표시)와 상태를 대조하고 부분 실패를 전체 성공으로 취급하지 않음 | 기존 CI+PR+현행 검증을 써도 ‘작업 전체’에 누락이 남는가; 추가 검증 부담이 큰가 |
| **P6 실패 복구·인계** | 회의/진행 메모, 작업 체크리스트, 변경 파일 보관·재설명 | Codex Cloud의 원래 작업 이어가기·Git, OpenSpec 변경 파일/아카이브, Bathos save/resume | checkpoint에는 목표/범위/승인 상태/마지막 근거/다음 작업/실패 이유를 남기고 **원래 작업을 재개**. 새 작업은 다른 미커밋 상태를 자동 상속하지 않음 | 일반적인 git+기록·세션 복원 후에도 실제 재설명/복구 시간이 반복적으로 큰가 |

**대체안은 제품 설계 확정이 아니라 관측 가능한 개입 후보**다. 특히 P2에 대해 위험한 모든 작업의 자동 승인을 권장하지 않는다. P5에서 CI 성공은 CI가 검사한 범위의 증거이지 비코드 업무/여러 저장소 전체의 성공 보장이 아니다.

## 3. 구체 상황별 3단계 대안

### A. 'AI에게 맡긴 작업이 밤새 멈춰 있음' (P2+P3)

- **기존 습관**: 밤새 작업 지시 후 다음 날 직접 확인, 중간에는 터미널을 지켜보거나 수시로 접속.
- **기존 제품으로 시도할 일**: Codex Cloud의 독립 실행과 동일 작업 재개, 현재 환경이 제공하는 상태/승인 표시, 필요한 범위의 승인 규칙. 백그라운드 실행은 *중단 제로*나 *즉각적 알림*을 보장하지 않는다.
- **기존 도구 조합**: 실제로 노출되는 작업 상태를 기준으로 ‘진행/승인 필요/실패/완료/불명’을 저장. 알림 채널이 존재할 때만 지연 측정 후 통지; 확인 불가능하면 `unknown`으로 기록.
- **추가 기능 후보**: 서로 다른 에이전트 런타임의 **진짜 개입 필요 이벤트**만 통합해 알려 주는 한정된 ‘주의 요구 큐’. 실제 상태 API·권한·기존 알림으로 충분하면 만들지 않음.
- **검증**: 중단 시각, 사용자가 발견한 시각, 불필요한 알림 횟수, 복구까지의 작업 시간, 긴급 승인 놓침을 측정.

### B. '엔드포인트 하나인데 조사와 호출이 폭증' (P1+P4)

- **기존 습관**: 프롬프트 다시 좁히기, 조사 즉시 종료, 남은 결과 수동 선별.
- **기존 제품으로 시도할 일**: Codex 지침 및 작업 범위·예산, OpenSpec의 좁은 변경 단위, BMad의 규모에 맞는 절차. BMad #3194는 특정 headless 모드의 과잉 조사 자기 보고일 뿐 일반 결과 아님.
- **기존 도구 조합**: 작업 선언서에 대상 1개, 제외 경로, 허용된 탐색 깊이, 단계별 산출물, 초과 시 중단·부분 보고. 모델에게 '예산을 지켜라'라고 적는 것과 실행기에서 하드캡을 집행하는 것은 다르다.
- **추가 기능 후보**: 기존 러너가 제공하지 않는 상황에서만 작업별 자원/범위의 관측·하드캡·안전한 종료. 단순 프롬프트 개선으로 해결되면 제품 기회 아님.
- **검증**: 결과 정확도, 계획 대비 스코프 이탈, 도구 호출/토큰/경과시간, 추가 사용자 수정 횟수.

### C. '세 저장소 중 두 개만 수정했는데 전부 완료 보고' (P5+P6)

- **기존 습관**: 사람의 저장소별 체크리스트/PR 리뷰, 실패 시 재실행 및 진척 업데이트.
- **기존 제품으로 시도할 일**: GitHub 보호 브랜치/필수 체크, OpenSpec 변경 기록과 verify, 사용자별 권한·수동 라우팅. OpenSpec Store/workset은 읽기 맥락을 공유하지만 저장소별 완전 적용을 자동 보장하지 않는다고 maintainer가 설명.
- **기존 도구 조합**: 선언된 대상 repo 리스트와 **실제 커밋/CI/배포 결과**를 비교하는 완료 표. 실패·미실행 대상이 한 개라도 있으면 전체 상태는 partial/blocked.
- **추가 기능 후보**: 단일 변경 요청의 repo별 상태와 근거를 합치는 경량 검증/보고 계층. 이미 CI/PR 체크리스트가 정확·저비용이면 불필요.
- **검증**: 누락된 repo의 발견률, 전체 완료 오보 건수, 보고 수집/검증에 쓴 사용자 active minutes, 추가 설정·운영 시간.

## 4. 다음 조사·실험의 우선순위

**솔루션 비교 실험을 신규 개발보다 먼저 한다.**

- **1번**: P2/P3의 실제 중단+발견 지연 사례 1개, P1/P4의 실제 범위 폭증 사례 1개, P5의 부분 성공 사례 1개를 사용자가 경험했는지 수집. 최근 사건·사용 환경·설정·실제 손실을 요청하되 외부 연락은 R01 승인 전 금지.
- **2번**: **강한 현재 제품 기준선**을 구성: Codex/Cloud 지침, 권한·범위, GitHub PR/CI, 필요시 공식 OpenSpec/BMad. 잘 되는 기능을 의도적으로 빼지 않는다.
- **3번**: 같은 입력/권한/시간에 대해 (a) 현재 사용자 관행, (b) 현재 제품의 강한 설정, (c) 기존 도구의 저비용 조합을 비교한다. 신규 시스템은 잔여 문제가 입증되었을 때만 (d)에 추가한다.
- **4번**: 사용자 실제 업무에서 active time/재작업/권한 위반/오보/설정·유지 비용을 함께 기록. 실사용 증거가 없으면 mock은 **기술 검증**만 할 수 있고 시장 문제를 확정하지 못한다.
- **중단 조건**: (b)/(c)가 품질·안전 기준을 지키면서 부담을 충분히 줄이면 신규 제품/범용 오케스트레이터 설계를 보류한다.

**후속 Codex Cloud 조사 지시(자동 실행 아님):** 이 문서를 읽고 P1~P6 각 도구별 실제 설정·공식 문서·사례의 사용 버전·한계·발생 증거를 링크/확인 시각과 함께 보강한다. '존재하는 해결 기능'과 '사용자 비용 감소'는 다른 열로 기록. 외부 메시지·결제·main 변경·실험 실행은 별도 승인 없이 하지 않는다.

## 5. 근거 (1차 공식 문서 및 사례)

- [OpenAI Codex Cloud 공식 도움말](https://help.openai.com/en/articles/20001545-using-codex-cloud): 격리 클라우드 작업, 같은 작업 재개, 새 작업의 격리, Git 저장 중요.
- [OpenAI Codex Cloud 환경 가이드](https://learn.chatgpt.com/docs/environments/cloud-environments): 워크스페이스 준비/재사용, 백그라운드 작업 및 상태 복귀.
- [OpenSpec workflows](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md): proposal→apply→verify→archive, 검증은 completeness/correctness/coherence를 표시하고 archive 자체를 항상 차단하지는 않음.
- [OpenSpec FAQ](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md): 변경 기록·아카이브를 Git에 남기고, 새 세션에서 진행 상태를 읽어 재개할 수 있음.
- [BMad Method](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/README.md): 작업에 맞는 역할·명세·검토를 제공(프로젝트 설명 기준).
- [Bathos README](https://github.com/taxideftis/bathos/blob/prod/README.md), [FAQ](https://github.com/taxideftis/bathos/blob/prod/docs/FAQ-en.md): 세션/게이트/할당량 관련 기능(early/dogfood 검증 단계).
- [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches): 필수 status checks/PR 리뷰/병합 게이트.
- [OpenSpec #725](https://github.com/Fission-AI/OpenSpec/issues/725), [maintainer 설명](https://github.com/Fission-AI/OpenSpec/issues/725#issuecomment-5573214645): 중앙 Store 및 수동 대상 지정, 강제 bounded repo apply는 미지원이라는 진술.
- [Codex #16911](https://github.com/openai/codex/issues/16911): 반복 MCP 승인 사용자 자기 보고(현재 사용 환경에서 재현 미확인).
- [BMad #3194](https://github.com/bmad-code-org/BMAD-METHOD/issues/3194): 과도한 범위·사용량 문제의 사용자 자기 보고(특정 모드/버전).
