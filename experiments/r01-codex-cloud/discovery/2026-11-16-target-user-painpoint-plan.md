## 1. 고정할 문제와 아직 열어둘 것

**상위 가치 가설(개인 제안):** 기존 LLM의 능력에 적절한 도구·기억·인터페이스를 연결해 사용자가 여러 작업에서 반복하는 설명·감독·검토·판단 비용을 줄인다.

**가장 좁은 최초 탐색 집단 A(후보):** 매주 여러 AI 코딩 도구를 직접 사용하고, 2~5명 정도의 작은 개발·기획 프로젝트에서 요청·리뷰·승인·진척을 직접 조정하는 실무 책임자. 이들이 어떤 구체적 작업에서 언제 고통을 느끼는지 조사한다. 'AI를 잘 쓰는 사람 전부'는 타겟이 아니다.

**반대 비교 집단 B(후보):** 혼자 반복 AI 개발/리서치 업무를 수행하는 숙련 개인 개발자. 팀 간 승인·리뷰 없이도 동일한 고통이 존재하는지 확인한다.

A·B 모두 **선정된 고객군이 아니라 탐색 가설**이다. 직책보다 사용 도구·작업 빈도·반복 행동·문제 사건으로 분류한다.

**페인포인트 후보(검증 전):**
- U1 — 여러 작업에서 합의된 목적·승인 범위를 반복 설명해야 해 결과 확인 시간이 늘어난다.
- U2 — 이전 판단을 새 작업에 적용할 때 유효 범위가 달라져 과거 결정을 다시 찾아 검토한다.
- U3 — 도구가 사소한 변경까지 승인·검토를 요청해 흐름을 멈추거나, 반대로 중요한 예외를 놓쳐 사람이 뒤늦게 발견한다.
- U4 — 조건·근거 변경 이후 어느 결정·후속 작업만 다시 검토할지 사람이 수동으로 추적한다.

'기억 부족', '멀티에이전트 부재', '오케스트레이터 필요' 같은 **솔루션 표현을 사용자 고통으로 쓰지 않는다**.

## 2. 오늘 작업 순서와 산출물

### A. 기존 자료에서 출발점 고정 — 우선

- 읽기: `docs/members/R01/workspace/2026-11-14_R01_BATHOS_직접경쟁서비스_잔여페인포인트_조사_R1.md`

- 이전 보고서의 공개 이슈는 단서로만 사용한다. 실사용 빈도·시장 수요의 증거로 격상하지 않는다.

### B. 실제 사용자 사건 수집 — 오늘 가장 중요한 작업

- 공식 GitHub Issues/Discussions, 제품 공식 커뮤니티의 공개 게시글, 허용된 사용자 후기를 우선하여 **구체적인 사건 5건 정도**를 찾되, 독립적인 사용자가 몇 명인지 구분한다. 찾지 못하면 부족한 그대로 보고한다.
- 사용자가 실제로 **어떤 일을 하려다 → 무엇 때문에 막혔고 → 어떻게 우회했으며 → 어떤 비용(시간, 재작업, 리스크)을 겪었는지** 원문 근거를 추적한다.
- 단순 기능 요청·마케팅 문구·AI의 추측·중복 인용은 실사용 고통과 분리한다.
- 모든 사건에 `source_url`, `title`, `published_or_updated`, `checked_at(KST)`, `user_role(확인/추정)`, `task_context`, `trigger`, `observed_problem`, `workaround`, `cost(evidenced/unknown)`, `existing_tool`, `evidence_strength`, `uncertainty`를 기록한다.
- **출력:** `02-user-incidents.md`. 함께 **반례/잘 해결된 사례 2건 정도**를 찾되, 없다면 미확보 표시.

### C. 경쟁 대안으로 반증 — '이미 있는 것'을 먼저 검토

- Bathos·BMad·OpenSpec 및 강한 Codex/ChatGPT 프로젝트 지침·기억을 최소 대조군으로 사용한다.
- 각 사건별 `현재 사용 가능한 기능` / `실제 사용자 우회 방식` / `그래도 남은 문제(증거 있음/가설)`를 분리한다.
- 기능이 제품 문서에 존재한다는 이유만으로 고통이 완전히 해결됐다고 단정하지 않는다. 반대로 실제 사용 검증 없이 해결하지 못했다고 단정하지 않는다.
- 가능하면 **기존 제품이 성공적으로 해결하는 반례**도 기록한다.
- **출력:** `03-existing-alternatives.md`. 근거 없는 '새 기능 차별화'는 쓰지 않는다.

### D. 페인포인트와 타겟 압축 — 오늘의 의사결정 자료

- 사건별로 타겟 A/B와의 일치 여부를 평가하고, 다음 5개 기준을 0~2점 또는 '자료 부족'으로 기록한다: (1) 작업의 반복 빈도 (2) 실제 피해 강도 (3) 기존 대안 이후 잔여 문제 (4) 사용자에게 연락/검증 가능한가 (5) 8주 과제에서 검증 가능한가.
- 낮은 근거는 높은 점수로 보정하지 않는다. 점수보다 **관측 사실과 미확인 이유**를 먼저 쓴다.
- 상위 후보 최대 2개에 대해 다음 문장으로 정리한다:
  - “**[누가]** [언제/어떤 작업]에서 **[구체적인 실패·반복 행동]** 때문에 **[관측된 피해]**를 겪고, 현재는 **[대안/우회]**를 쓰지만 **[잔여 문제 또는 미확인]**가 남는다.”
- 각 후보에 **근거 URL, 반증 사례, 해결되지 않은 의문, 10~15분 사용자 인터뷰 질문 5개, 최소 기능 시험 1개**를 붙인다.
- **출력:** `04-shortlist-and-decision.md`.
- 실제 사용자 인터뷰가 없다면 `user_interviews: not_run`, 공개 사례만으로 외부 사용자가 검증됐다고 주장하지 않는다.

## 3. 조사·실행 안전

- 공개 사이트의 **무단 크롤링·대량 자동 수집 금지**. 우선 공식 API, 허용된 열람, 제공된 문서의 인용 근거를 활용하며 사이트 정책·요청 제한을 준수한다.
- 외부 사용자에게 메시지·인터뷰 요청을 **발송하지 않는다**. 필요하면 연락 대상/질문안을 제시하고 R01이 결정한다.
- 유료 서비스, API 크레딧 구매, 추가 인프라 생성 금지. 접근 불가 자료를 우회하거나 토큰·쿠키를 기록하지 않는다.
- 출처마다 **직접 관측 / 게시자의 주장 / 해석 / 추정 / 미확인**을 구분한다. 원문 전체를 복사하지 않는다.
- 경쟁 제품 제공 기능이나 이슈의 *현재 해결 여부*가 확실하지 않으면 `unknown`으로 둔다.
- 표본이 약하면 솔루션을 만들지 말고 **자료 부족**으로 결론 내린다.

## 5. ChatGPT ↔ Codex Cloud 협업 계약

1. Codex Cloud는 위 파일들을 `discovery/` 하위에 작성하고 **실험 브랜치에 커밋·푸시**한다. 외부에 내용을 전송하지 않는다.
2. 이 ChatGPT 세션은 GitHub 결과와 원문 근거의 일치, 과대 일반화, 경쟁 대안 누락, 타겟·고통의 구체성을 독립 검토한다.
3. R01은 실제 사용자 접근, 인터뷰 진행 및 최종 문제 정의 채택을 결정한다.
4. **Codex 작업 대화 자체는 자동 공유되지 않는다.** 따라서 `STATUS.md`와 커밋을 필수 협업 인터페이스로 사용한다.
5. 예상보다 자료가 부족하면 추측으로 빈칸을 채우지 말고 결과를 먼저 커밋하고 미확인 상태를 남긴다.
