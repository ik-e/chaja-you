## 의도 또는 결정

첫 MVP는 **앱 리서치 도메인에서 버텀업으로 검증**한다. 범용 다중 도메인 프레임워크를 먼저 설계하지 않고, 앱 도메인에 필요한 역할·작업·출처 우선순위·검증 기준을 충분히 특화해 실제 흐름을 구현한다.

이번 MVP의 핵심 검증은 다음과 같이 둔다.

- APP-A: 지정 후보 비교의 첫 end-to-end vertical slice
- APP-C: 조사 중간 결과에 따라 후속 후보 발굴을 추가·생략·보류하는 핵심 동적 분기
- APP-B: 사용자 요청 자체에 후보가 없을 때 후보 발굴 작업이 필요해지는 요청 기반 구성 검증 사례로 유지하되, APP-A·C보다 구현 우선순위는 낮춘다.

공통 리서치 구조와 앱 도메인 특화 구조의 경계는 이번 구현에서 드러나는 것을 기준으로 잡되, 첫 도메인만으로 영구적인 범용 구조라고 확정하지 않는다. 일정과 구현 결과가 허용하면 후속 도메인을 추가해 확장 가능성을 검증한다.

## 이유

팀이 합의한 버텀업 개발 방향을 유지하면서도, 프로젝트의 장기 의도인 도메인별 리서치 특화와 요청·중간 결과에 따른 동적 구성을 MVP에서 실제로 검증하기 위해서다. 첫 도메인에서 실제 구현 근거를 만든 뒤 필요한 공통 구조를 추출하는 편이 선행 추상화보다 현재 일정과 검증 목적에 적합하다.

## 제약 / 반드시 지킬 것

- 앱 도메인을 제품의 영구 범위로 일반화하지 않는다.
- APP-A·C는 핵심 검증 범위로 유지한다.
- APP-B는 평가 사례에서 제거하지 않는다. 다만 최종 end-to-end 시연 포함 여부는 일정과 APP-A·C 통합 상태를 보고 조정할 수 있다.
- 미확인, 조건 미충족, 작업 실패를 구분하고 근거 없는 판정을 만들지 않는다.
- 핵심 판단은 source/evidence와 확인 시점에 연결한다.
- 문서 확인과 실제 기기 동작 확인을 구분한다.
- 공개 열람 가능 여부와 자동 수집·저장·재사용 가능 여부를 동일하게 취급하지 않는다.
- 동적 구성이 고정 workflow보다 우월하다고 실제 B0/D0 비교 전에 주장하지 않는다.
- 자유 역할 생성, 범용 workflow engine, 복잡한 자동 복구, 장기 기억/RAG/온톨로지, 다중 도메인 구현은 이번 핵심 MVP보다 후순위다.

## 재검토 조건

- APP-A vertical slice와 APP-C 조건부 분기 구현 결과가 현재 공통/앱 특화 경계를 유지하기 어렵게 만드는 경우
- B0/D0 비교에서 동적 구성의 추가 복잡성에 비해 유효한 차이가 나타나지 않는 경우
- 일정에 여유가 생겨 두 번째 도메인 적용으로 공통 구조를 검증할 수 있는 경우
- 실제 자료 접근·이용 조건 때문에 앱 리서치 자동화 범위를 크게 조정해야 하는 경우
