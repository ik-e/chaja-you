## 판단

R03가 정리한 공통 관리 구조 / 앱 도메인 특화 / 요청별 동적 구성의 구분과, 다중 도메인 실제 구현은 후속으로 두되 도메인별 특화 가능성 자체는 상위 의도로 유지한 방향을 승인한다.

APP-A·B·C와 요청 변형·판정 조합을 이용한 규칙 기반 모의 검사는 계획·분기 규칙의 일부를 확인한 근거로 인정한다. 다만 실제 LLM 계획, 실제 웹·앱 조사, 기기 시험, B0/D0 고정 흐름 대비 성능 검증의 근거로 확대 해석하지 않는다.

## 수정·정합 요청

- 일부 R03 문서에서 도메인 특화 의도의 출처를 `대화에서 전달된 상위 의도`로만 표현한 부분은 현재 GitHub 정본인 `docs/human/INTENT.md`, `PROJECT.md`, `docs/human/task-intents/TASK-005.md`를 직접 근거로 갱신한다.
- TASK-006과의 정합에서는 필드명 자체를 먼저 고정하지 말고 공통 의미와 ID 연결을 우선 맞춘다.
- 계획·실행 연결에는 최소한 request/task 식별자, 역할, 선행 관계, 명시적 실행 조건(run_if), 상태와 변경 이유가 추적되어야 한다.
- 판정은 앱 후보 하나에 단일 verdict를 붙이는 것으로 끝내지 않고 `조사 대상 × 조건`별 판정과 이를 직접 지지하는 evidence ID가 연결되는 의미를 맞춘다.
- APP-C에서 미확인 상태는 미충족으로 바꾸지 않는다. 확인 한도에 도달하면 무한 보류하지 않고 확인된 내용과 남은 미확인을 부분 결과로 종료할 수 있게 한다.
- R05와 해석 차이가 생기면 임의로 한쪽 설계에 맞추지 말고 차이, 영향, 제안을 기록해 R01 검토로 올린다.

## 유지할 방향

- 현재 역할·작업 목록은 앱 리서치 도메인의 첫 후보군이며 모든 도메인의 영구 고정 목록이 아니다.
- 공통 관리 구조와 앱 도메인 특화 규칙, 요청별 동적 구성을 분리해 기록한다.
- APP-A는 지정 후보 비교의 기본 흐름, APP-C는 중간 판정에 따른 추가·생략·보류의 핵심 검증 사례로 유지한다.
- 모의 검증과 실제 실행 검증의 증거 범위를 구분한다.
- 기획서와 WBS는 이번 정합 작업에서 직접 수정하지 않는다.

## 현재 근거

- R03 규칙 기반 원형: APP-A·B·C, 요청 변형, APP-C 판정 조합을 포함해 18건 통과, 0건 실패.
- 의도적으로 넣은 오류 4건은 검사에서 모두 탐지됨.
- 위 결과는 수동 구조화 입력과 가상 판정·가상 출처 유형을 사용한 모의 검사이며 통계적 성능 증거나 실제 서비스 검증이 아니다.
