## R01이 중요하게 보는 의도

이번 작업에서는 현재 팀원에게 기능을 먼저 나누는 것보다 **사용자 요청에서 근거가 연결된 결과까지 실제로 이어지는 시스템 구조를 먼저 찾는 것**이 중요하다.

구성요소, 주고받는 데이터, 의존 관계와 최소 통합 순서를 먼저 명확히 한 뒤 현재 팀 역할에 작업을 배치한다. 특정 기술 스택을 선택하는 것보다 팀이 병렬로 구현해도 마지막에 연결될 수 있는 최소 계약을 만드는 것이 우선이다.

또한 이번 앱 리서치는 **도메인별로 특화된 리서치가 공통 시스템 위에서 실제로 동작하는 첫 사례**로 본다. 모든 도메인을 하나의 고정된 조사 방식으로 처리하는 구조가 아니라, 공통적인 조사·근거·실행 구조는 재사용하면서도 도메인마다 필요한 역할·작업·출처 우선순위·검증 방법을 특화할 수 있어야 한다.

## AI가 실행 기준으로 해석한 내용

다음 순서로 구조를 도출한다.

1. 사용자 요청부터 결과까지 필요한 구성요소
2. 각 구성요소의 최소 입력·출력 데이터
3. 구성요소 간 선행 관계와 조건부 실행
4. 실패·미확인·근거 부족 상태의 전달 방식
5. 요청 하나가 끝까지 통과하는 최소 vertical slice
6. 구현·통합 순서
7. 마지막으로 현재 R01~R05 역할에 담당 제안

정상 흐름뿐 아니라 검색 실패, 출처 접근 실패, 근거 부족, 조건 미확인, 부분 결과와 재시도도 데이터 흐름에서 표현할 수 있어야 한다.

구조를 제안할 때는 다음 두 층을 구분한다.

- **공통 리서치 구조**: request, task, 역할, 의존 관계와 실행 조건, source, evidence, claim/verdict, 실행 상태, uncertainty/failure, report 등 도메인이 바뀌어도 유지될 수 있는 의미와 연결 관계
- **앱 리서치 특화 구조**: 오프라인 사용, 계정 필요 여부, 무료 기능, 권한·호환성, 앱스토어·개발사 등 출처 우선순위, 문서 확인과 실제 기기 동작 확인의 구분, 앱 비교·후보 발굴에 필요한 작업과 검증 기준

이번 단계의 목표는 범용 도메인 프레임워크를 완성하는 것이 아니라, **앱 리서치를 충분히 특화하면서 그 특화가 공통 리서치 구조에 하드코딩되지 않도록 경계를 찾는 것**이다.

## 과도하게 확장하지 않을 것

- 사람 수에 맞춰 소프트웨어 모듈을 억지로 분할
- 전체 시스템을 처음부터 완성형 아키텍처로 설계
- 필요성 검증 전 프레임워크·DB·검색 공급자 확정
- 구현하지 않은 실패 복구나 성능을 완료된 기능처럼 표현
- 아직 두 번째 도메인 검증도 하지 않은 상태에서 범용 플러그인·도메인 프레임워크를 먼저 설계·구현
- 앱 도메인 전용 조건·출처·검증 규칙을 공통 리서치 구조에 고정

## 담당자가 자율적으로 판단해도 되는 것

- 구성요소의 구체적인 경계
- 최소 I/O 필드 초안
- vertical slice 구현 순서
- 역할별 담당 제안
- 기술 후보와 이를 선택할 조건
- 공통 리서치 구조와 앱 도메인 특화 구조의 구체적인 경계 초안

## R01에게 돌려줄 결정

- MVP에서 반드시 구현할 구성요소와 후순위 구성요소
- 팀 간 최소 데이터 계약
- 부분 실패·미확인 결과를 어느 수준까지 MVP에서 지원할지
- 특정 기술이나 프레임워크를 지금 선택해야 할 충분한 이유가 있는지
- 앱 리서치에서 드러난 공통 구조와 도메인 특화 구조 중 무엇을 MVP의 안정된 계약으로 둘지
