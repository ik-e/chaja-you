## A. 사용자 스토리 — 서비스 기능 범위의 근거

- F01~F29 전체, E01~E05는 조건부 별도 검토. 정상·오류·예외·반복(최초/재이용/추가 등록/수정/갱신/조회)과 필요한 지원 행동을 도출한다.
- 단일 행동을 사용자 + 동사 + 대상(SVO)으로 정의한다. UI 버튼·화면·API에 종속되지 않는다. 내부 시스템 행동은 별도 supporting_system_events로 연결한다.
- 스토리별 목적/피처, 발생 조건, 선행 상태/인증/권한, 대상·입력, 사용자가 관찰하는 결과, 분기/후속 행동, 상태·오류·종료, 범위 후보(기본/조건부/제외/미결정), 근거를 남긴다. 승인 거절·재시도·부분 성공·결과 미확인도 검토한다.
- 기획에서 명확하지 않은 계정·삭제·취소 등은 필요한 이유와 결정 요청을 제시한다. 자동 편입 금지. 각 F/E ID의 행동 연결 또는 내부 기능/해당 없음 사유를 coverage에 표시한다.

## B. 플랫폼 조사 — DB 및 후속 설계 입력

대상 7개: 크몽 · 탈잉 · 숨고 · 프람피 · 뮬 · 힙합플레이야 · 힙합LE. 각 플랫폼별 신규/추가 등록, 조회, 수정, 갱신, 상태 확인, 오류·반려 대응의 존재 여부 및 업무별 조건을 모두 조사한다.

| 항목 | 핵심 내용 |
|---|---|
| 업무·사용자 행동 | 단계·분기·선행 조건·인증·승인·실제 결과·오류·후속 대응 |
| 객체·식별 | 실제 관리 객체의 의미, 소유자/계정, 식별자·URL, 수명주기 |
| 데이터 사전 | 입력·반환·노출 구분, 실제 필드 표시명, 의미·자료형·필수/조건부·단위·값·길이·반복·첨부·공개 범위·수정 가능성 |
| 관계·제약 | 객체 관계·다중성·소유권·조건부 필드·가격/시간/옵션 차이 |
| 상태·결과 | 시도/접수/심사/반려/공개 등 실제 명칭·변화·확인 근거, 오류/미확인·중복 위험 |
| 권한·정책 | 웹 경로, 인증·자격 및 업무별 접근/대행 허용 여부(별도 판단) |
| 후속 연결 | 추가 사용자 스토리 후보, 저장 필요 데이터/근거, 업무 이벤트·입출력·상태·오류·승인 등 API 설계 입력 |

**근거 규칙:** 직접 관찰·공식 문서·기존 조사·추론·미확인 구분. 출처·확인 날짜·화면/절 위치 및 ID 연결. 모르는 항목은 미확인 이유와 추가 확인 방법 기록. 웹에서 게시물이 보인다고 웹 등록·자동화가 가능하다고 간주하지 않는다. 내부 DB/API 추정 금지.

**권한 제한:** 기존 mock-only 유지. 기존 조사 및 허용된 공개 자료의 필요한 최소 개별 조회. 실제 계정 로그인, 인증정보 수집, 실제 등록/수정/갱신, 자동화 실행 금지. 확인할 수 없는 경로는 미확인으로 기록하고 별도 승인/대체 후보를 요청한다.

## 제출·완료 기준

[work-contract.json](work-contract.json)의 record_fields 및 acceptance A1~A5가 상세 기준이다. 각 담당은 초기 원본에 실제 결과를 채우고 TASK result에 경로·commit·자체 검토·미확인·결정 요청을 기록한다. 양식만 있거나 성공을 주장할 근거가 없으면 완료 아님. 7개 플랫폼과 전체 F/E 검토 자체를 누락하지 않는다.

R01은 기존 세 독립 조사 결과 및 R03의 사용자 스토리 검토를 비교·병합해 사용자 행동 범위를 확정하고, 플랫폼 객체·데이터·상태·제약을 논리 데이터 모델과 ERD/스키마로 연결한다. 7개 표현 가능성, 기존 DB/API/구현 영향, 이후 API·프로토콜 입력을 검증하고 남은 불확실성을 명시한다. UI 상세, API 엔드포인트, 기술 스택·신규 구현은 이번 독립 조사 범위가 아니다.
