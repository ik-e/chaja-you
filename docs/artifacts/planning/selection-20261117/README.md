## 필수 제출 7항목

**타깃 사용자**(상황·목적·현재 행동) → **실제 Pain**(시간/비용/반복/실패) → **현재 대안**(가장 강한 서비스·수작업) → **기존 대안 이후 남은 Pain** → **문제 정의 한 문장** → **Painkiller 기능 2~3개** → **근거/반대 근거/미확인 + 8주 MVP/검증 계획**.

### 1차: 필수 조건(점수와 별개)

G1 사용자·상황·고통이 실제 업무/생활 맥락으로 특정되는가. G2 이용 정책을 지키는 자료·실험 경로가 있는가. G3 8주 내 최소 제품과 기존 대안 대비 비교 실험이 가능한가. **권한 없는 자동 크롤링·보안 절차 우회 등을 당연히 허용된 실행 경로로 전제하지 않는다.** 불확실하면 조건부·미확인, 실행 가능한 합법 대안이 없으면 중단 위험을 표시한다.

### 2차: 공통 100점 기준

| 코드 | 기준 | 배점 | 심사 질문 |
|---|---|---:|---|
| A | 실제 사용자 페인포인트 강도 | 25 | 시간·금전·반복·위험·빈도에 근거가 있는가 |
| B | 기존 대안 이후 남은 문제 | 25 | 가장 강한 대안을 인정한 뒤 의미 있는 손실이 남는가 |
| C | Painkiller 핵심 피처 | 15 | 피처 2~3개가 남은 손실을 직접 줄이는가 |
| D | 8주 구현·검증 가능성 | 20 | 적법한 데이터·실험·비교 기준선·축소 경로가 있는가 |
| E | 근거·반증 계획 | 10 | 확인/추정/반대/미확인을 구분하고 검증할 수 있는가 |
| F | 실제 사용·도입 가능성 | 5 | 누가 사용하고 승인·구매하며 어떤 흐름으로 쓰는가 |
| **합계** | | **100** | |

**등급:** 0(반증/조건 불충족), 1(주장 중심), 2(초기 근거), 3(설득력 있는 근거·검증), 4(강한 실증·비교). 각 항목 점수는 `배점 × (등급/4)`. **미평가는 0점이 아닌 null**이며, 일부만 점수화한 후보를 100점 완성 후보와 같은 총점으로 순위 매기지 않는다. 항목마다 근거/반대 근거를 표시한다.

### 3차: 두 후보와 보류 세 후보의 이유

- 가능하면 제안자를 제외한 나머지 팀원이 **독립 채점**하고, 어려우면 최소 2명 이상 교차 검토한다. 같은 항목이 2등급 이상 차이나면 근거를 다시 본다.
- **2개 선택은 점수순 자동 확정이 아니다.** 필수 게이트, 치명적 제약, 가장 짧은 검증 방법을 함께 검토하고 선정/보류 이유를 남긴다.
- R01 안이라고 가산하지 않고, 기존 연구나 멀티에이전트 구조를 그대로 활용할 수 있다는 이유만으로도 가산하지 않는다.
- 자료 부족 시 미확인으로 남긴다. 최종 후보 선택은 **[TASK-021](../../tasks/TASK-021.json)의 R01 결정·검증 근거**로 기록한다. 기존 제품 범위·WBS·제출용 기획안을 자동 변경하지 않는다.

## 관리 방법

1. 팀원은 자신의 작업 원본(TASK-016~020)에 최신 기획안과 근거를 남기고, 이 페이지의 **[제출 템플릿](submission-template.md)** 순서대로 1페이지로 정리한다.
2. R01은 [submissions.json](submissions.json)에 각자의 실제 제출본 경로·버전·수합 상태를 업데이트한다. 본문을 옮겨 복제하지 않는다.
3. 평가자는 [score-template.json](score-template.json)을 복사해 평가자/대상별 별도 JSON에 근거를 남긴다. 아직 점수는 없다.
4. R01은 다섯 안의 공통 기준 비교 후, **선정 2개·보류 3개** 각각의 이유, 주요 반대 근거, 확인할 다음 실험을 TASK-021 결과에 기록한다. 멘토 피드백 후 최종 주제를 별도 결정한다.
