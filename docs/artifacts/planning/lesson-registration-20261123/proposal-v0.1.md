## 1. 서비스 개요와 목표

**서비스:** 기존 레슨 공고·사진·수업 조건을 가진 개인 음악 강사가 새 모집 채널에 최초 등록할 때, 공통 정보를 재사용하고 플랫폼별 입력·결과 확인을 지원한다. 최종 등록 대행은 플랫폼의 허용 경로에서만 수행한다.

**1차 목표:** 강사의 직접 등록 시간·추가 개입을 줄이면서 실제 게시·심사 접수 등 완료 상태를 구분한다. 수강생용 근거리 지도는 정보 재게재 권한이 확인되지 않아 확장 가설로 보류한다.

**현재 상태:** 초안 · **담당:** R01

**추가 확인:** 첫 Pain(최초 등록 vs 반복 게시)·첫 플랫폼 확정

**완료 기준:** 업무 대상·가치·제외 기능을 명확하게 설명

## 2. 타깃 사용자와 이용 상황

**첫 타깃:** 한 곳 이상에서 개인 음악 레슨을 모집한 경험이 있고, 기존 소개글·사진·가격 조건을 갖고 있으며, 다른 플랫폼으로 모집을 넓히고 싶은 강사.

**이용 순간:** 새 플랫폼을 선택하고 첫 공고를 등록하려는 시점. R02 본인과 동료 강사 1명의 사례가 있으나 표본은 제한적이다. 강사의 범용 AI 숙련도와 사용 장벽은 확인 전이다.

**현재 상태:** 기존 근거 보유 · **담당:** R02

**추가 확인:** 다른 강사 인터뷰·기술 사용 방식 확인

**완료 기준:** 첫 타깃·업무 트리거·미대상 사용자를 구별

## 3. 페인포인트와 실제 근거

| --- | --- | --- |
| 최초 등록 | 당근 약 15분, 크몽 약 20분(R02 회상) | 양식·사진·제출 반복, 채널 진입 지연 |

**현재 상태:** 실측·우선순위 보완 · **담당:** R02

**추가 확인:** 업무별 실측/빈도, 실제 위임 의향, 최우선 Pain 비교

**완료 기준:** 근거·빈도·손실·반대 설명이 함께 기록됨

## 4. 기존 해결 방식과 한계

수동 복사·템플릿, 범용 AI/Codex의 문안/브라우저 작업, Browser Use 같은 도구, 유료 대행·플랫폼 자체 기능을 비교한다. **기술적으로 가능하다는 사실과 강사가 쉽게 사용할 수 있다는 사실을 분리**한다.

대안별로 설정·로그인·자료 준비·가격 입력·사진 첨부·최종 제출·결과 확인·실패 복구에 누가 관여하는지, 서비스 가격은 무엇인지 조사한다.

**현재 상태:** 보완 대기 · **담당:** R04

**추가 확인:** 대표 대안 3~5개와 실제 잔여 불편

**완료 기준:** 기존 서비스의 해결 범위·가격·출처와 남는 사용자 부담이 구분됨

## 5. 문제 정의와 발생 원인

**문제 정의 초안:** 이미 모집 자료가 있는 음악 강사도 새 플랫폼에 처음 등록하려면 플랫폼별 필수 항목·사진·가격 구성·제출 절차를 다시 처리해야 하므로 업무 부담이 생기고, 일부는 경제적 조건과 함께 추가 채널 진출을 미룬다.

**C1** 플랫폼별 입력 구조 차이(기존 사례 확인). **C2** 문안 작성 이후에도 인증·첨부·심사 접수 조작이 남음(기존 사례 확인). **C3** 범용 AI 설정·지시·복구 자체가 강사에게 부담일 수 있음(**미검증**).

**현재 상태:** 가설 · **담당:** R01

**추가 확인:** 채널 포기의 경제적 이유 vs 입력 부담 구분, C3 사용자 검증

**완료 기준:** Pain과 원인·근거 수준이 분리됨

## 7. 서비스 이용 시나리오

**정상 흐름:** ① 강사가 원본 공고·사진·대상 플랫폼·공개 조건 제공 → ② 서비스가 정보 구조화·필수 조건 점검 → ③ 누락 값은 강사에게 확인 → ④ 허용된 방식으로 강사가 인증하고 승인 범위 안에서 등록 진행 → ⑤ 게시 확인/심사 접수/실패/미확인 결과 제공.

**예시:** 월 4회·회당 90분·월 30만 원의 1:1 랩 레슨. 1회 체험 판매가는 주어지지 않았으므로 임의로 정하지 않는다.

**예외:** 세션 만료·자료 누락·파일 업로드 실패·제출 결과 불명확·취소·중복 위험.

**현재 상태:** 대표 사례 기반 · **담당:** R03

**추가 확인:** 각 단계 사용자/서비스 책임과 승인 조건 정리

**완료 기준:** 정상 흐름과 실패 시 종료·복구 상태를 구분

## 8. 비즈니스 모델

**인과 흐름:** 강사의 신규 채널 등록 필요 → F1~F3로 재입력·직접 조작 감소 → 등록 업무 위임의 편의·시간 가치 → 강사의 지불 동기.

| 요소 | 현재 가설/근거 | 확인할 내용 |
| --- | --- | --- |
| 고객·결제자 | 개인 음악 강사 | 고객 규모·구매 조건 |
| 판매 가치 | 등록 준비·실제 제출·완료 상태 확인 | 어느 단계까지 돈을 내는가 |
| 과금 | 건당/플랫폼 수별 묶음 | 가격·구매 실험 |
| 반복 매출 | 공고 갱신·후기 재게시 추가 서비스 | 실제 반복 이용 필요성 |
| 핵심 비용 | AI/API, 서버/브라우저, 플랫폼 변경, 실패 처리·지원, 보안 | 등록 1건당 원가 |
| 유입 채널 | 강사 커뮤니티·소개(가설) | 고객 획득 가능성 |

동료 강사 1명이 **10개 플랫폼 최초 등록 총 5만 원** 지불 의향을 밝혔지만 실제 결제·2곳만의 가격은 미확인이다. 5천 원/플랫폼 가격으로 단순 환산하거나 구독 매출을 전제하지 않는다.

**현재 상태:** 수익 가설·검증 전 · **담당:** R01

**추가 확인:** 지불 의향·단가·운영비·재이용 빈도 실증

**완료 기준:** 고객→가치→지불→수익·비용 흐름과 리스크 명확

## 10. 기술 실현 가능성과 제약

**대안:** 공식 API/제휴, 강사 기기 로컬 브라우저, 서버 일회성 브라우저, 범용 AI·Browser Use. 기술 성공·플랫폼 허용·안전한 인증은 **별개의 통과 조건**이다.

R02는 10개 플랫폼의 공개 안내·약관을 조사했지만 당근 모임·크몽에서 외부 AI가 최종 게시·심사 접수까지 수행하는 허용 경로를 확인하지 못했다.

일회성 비밀번호를 삭제해도 인증 세션·쿠키가 남을 수 있다. 서버/로컬 결정에는 사용자 편의, 세션 격리·폐기, 구현 비용, 플랫폼 권한을 함께 고려한다.

**현재 상태:** 제약 조사 완료·실증 대기 · **담당:** R05

**추가 확인:** 플랫폼별 허용 경로, 원격 인증, 작업 종료·세션 폐기

**완료 기준:** 가능/허용/안전/미확인을 분리한 기술 판단표

## 11. MVP와 개발 범위

**첫 검증 범위:** 기존 공고 1건을 첫 플랫폼 1곳의 요구사항에 맞춰 준비하고 직접 작업을 얼마나 줄이는지 평가한다.

**포함 후보:** 원본 정보 재사용·누락 검증·플랫폼별 변환·작업 상태 구분. **조건부:** 외부 플랫폼에 대한 실제 자동 제출(허용 경로·인증 안전성을 확보한 경우). **제외:** 수강생용 지도, 무단 수집/등록, 10개 플랫폼 동시 지원, 반복 업무·상담 자동화의 무조건적 포함.

허용된 자동 게시 경로가 없으면 등록 보조 등 축소형의 사용자 가치·지불 의향을 다시 확인하며, 자동 대행 서비스가 실현됐다고 보고하지 않는다.

**현재 상태:** 조건부 제안 · **담당:** R01

**추가 확인:** 첫 Pain·첫 플랫폼·MVP must/conditional/out 결정

**완료 기준:** 8주 안에 검증할 하나의 완결된 시나리오와 제외 범위

## 12. 검증 계획과 성공 기준

**사용자 확인:** 강사의 업무 빈도·실제 손실·기존 도구 활용 장벽·가격/위임 의향을 검증한다.

**대조 설계:** 동일한 원본·사진·조건·초기 상태에서 ① 직접 등록/템플릿 ② 충분한 지시의 범용 AI+브라우저 ③ 전용 서비스 비교. 우선 모의 양식에서 시험한다.

**측정:** 등록 정보 정확도와 최종 완료 건수, 강사 직접 작업 시간, 추가 클릭·지시·수정, 세션 만료·실패 복구, 불명확한 결과의 중복 게시, 비용·선호·지불 의향.

**실제 플랫폼:** 운영상 허용 근거가 확인된 뒤 제한적으로 검증. 측정 전 정량 합격선·AI 우위를 임의로 확정하지 않는다.
