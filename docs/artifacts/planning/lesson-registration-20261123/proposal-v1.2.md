# 음악 레슨 강사 다중 플랫폼 등록·관리 지원 서비스

**기획안 V1.2 | 2026.11.26 | 보완 검토안**

## 1. 서비스 개요

개인 음악 레슨 강사가 여러 플랫폼을 통해 수강생을 모집하는 과정에서 발생하는 반복적인 레슨 정보 등록 및 관리 업무를 대행·지원하는 서비스이다.

사용자가 제공한 레슨 정보를 기반으로 플랫폼별 정보 변환, 검증, 등록, 수정, 갱신, 결과 확인 및 상태 관리를 수행한다.

사용자가 직접 수행해야 하는 반복 업무를 줄여 수업과 창작 등 본업에 집중할 수 있도록 하는 것을 목표로 한다.

**핵심 가치 흐름**

타깃 사용자 → 페인포인트 → 문제 원인 분석 및 문제 정의 → 핵심 피처의 작동 → 반복 업무 감소 → 사용자 가치 발생 → 지불 동기

## 2. 타깃 사용자

### 2.1. 핵심 타깃

여러 플랫폼을 통해 수강생을 모집하고 레슨 모집 정보를 관리하는 개인 음악 레슨 강사.

### 2.2. 초기 고객의 특성

- 기존 레슨 소개글, 사진, 수업 조건 등을 보유하고 있다.
- 하나 이상의 플랫폼에서 수강생을 모집하고 있거나 모집 채널을 확대하려 한다.
- 수업 및 창작 활동과 모집 정보 관리 업무를 병행하고 있다.
- 플랫폼별 반복적인 등록 및 관리 업무에 부담을 느낀다.

### 2.3. 사용자 목적

여러 플랫폼을 통해 잠재 수강생과의 접점을 확대하고, 정확한 레슨 모집 정보를 지속적으로 유지하면서 모집 정보 관리에 필요한 시간과 수고를 최소화하는 것이다.

## 3. 페인포인트 및 근거

### 3.1. 페인포인트

| ID | 페인포인트 | 사용자 행동 |
|---|---|---|
| P01 | 반복적인 정보 준비 부담 | 플랫폼마다 레슨 정보를 재작성하고 검수한다. |
| P02 | 반복적인 업무 실행 부담 | 플랫폼마다 정보를 입력·첨부하고 등록·수정·갱신한다. |
| P03 | 반복적인 확인 및 대응 부담 | 플랫폼마다 등록 정보와 상태를 확인하고 문제에 대응한다. |

이러한 업무는 강사의 시간과 주의력을 소모하고 본업과 병행하는 데 부담을 발생시킨다.

### 3.2. 사용자 조사 근거

| 업무 | 확인된 사례 |
|---|---|
| 최초 등록 | 크몽 최초 작성 및 제출에 약 1~2시간 소요 |
| 반려 대응 | 수정 및 재제출에 약 5~10분 소요 |
| 공고 갱신 | 뮬 공고 갱신에 회당 약 2~3분 소요 |
| 추가 플랫폼 등록 | 등록 업무의 번거로움과 창작 시간 침해를 이유로 한 채널만 이용한 강사 사례 |
| 반복적인 콘텐츠 게시 | 동일한 후기·영상을 추가 4개 채널에 게시하는 데 약 20분 소요 |
| 기존 AI 활용 | 문구 작성 부담은 감소했으나 사실 검수·입력·첨부·제출 업무가 남은 사례 |

위 수치는 R02의 사용자 경험에 대한 회상이며 실측 결과가 아니다. 조사 표본은 직접 사용자 1명과 동료 강사 2명의 간접 진술을 중심으로 구성되어 있다.

### 3.3. 조사 근거의 한계

- 최초 등록과 공고 갱신, 반려 대응 부담은 실제 사용자 경험을 통해 확인되었다.
- 복수 플랫폼의 기존 게시 정보 수정 빈도와 실제 누적 부담은 추가 검증이 필요하다.
- 기존 플랫폼에서 심사 승인 알림을 제공한 사례가 있으므로, 추가적인 상태 관리 기능이 어느 정도의 잔여 문제를 해결하는지 확인해야 한다.
- 후기·영상 재게시와 상담 업무에서도 반복 부담이 관찰되었으나, 초기 서비스의 모집 정보 관리 범위와는 구분한다.
- 가격 경쟁을 이유로 플랫폼 입점을 원하지 않는 사례도 존재한다. 이러한 문제는 등록·관리 업무 자동화만으로 해결할 수 없다.

## 4. 문제 원인 분석 및 문제 정의

### 4.1. 문제 발생 배경

잠재 수강생은 여러 모집 플랫폼에 분산되어 있다. 강사는 모집 기회를 확대하기 위해 자신이 이용하려는 여러 플랫폼에 레슨 정보를 등록하고 유지한다.

그러나 각 플랫폼의 정보 구조, 업무 절차, 정보 및 상태 관리 방식은 서로 독립적으로 구성되어 있다.

### 4.2. 문제 발생 원인

| ID | 문제 원인 | 발생 메커니즘 | 관련 Pain |
|---|---|---|---|
| C01 | 플랫폼별 정보 구조의 이질성 | 플랫폼마다 필수 항목, 입력 형식, 가격 표현, 사진 규격 등이 달라 기존 레슨 정보를 그대로 재사용하기 어렵다. | P01 |
| C02 | 플랫폼별 업무 절차의 독립성 | 하나의 플랫폼에서 수행한 등록·수정·갱신이 다른 플랫폼에 반영되지 않아 동일한 목적의 작업을 개별적으로 수행해야 한다. | P02 |
| C03 | 플랫폼별 정보 및 상태의 분산 | 등록 정보, 접수 결과, 심사 상태, 게시 상태 등이 각 플랫폼에서 독립적으로 관리되어 개별적인 확인과 대응이 필요하다. | P03 |

### 4.3. 원인 간 관계

플랫폼의 정보 구조가 동일하더라도 등록 절차가 독립적이면 반복적인 업무 실행이 필요하다.

등록 업무를 자동화하더라도 플랫폼별 입력 조건에 맞지 않는 정보가 존재하면 정보 준비와 검수 부담이 남는다.

등록을 완료하더라도 각 플랫폼의 정보와 상태가 분산되어 있으면 이후 확인 및 대응 부담이 남는다.

따라서 정보 구조, 업무 실행, 상태 관리의 세 가지 문제를 구분하고 이에 대응하는 해결 기능을 도출한다.

기존 AI의 잘못된 정보 생성, 문구 생성과 실제 실행의 단절, 범용 도구의 설정 부담은 사용자가 원래 겪는 문제의 원인이 아니라 기존 해결 방식의 한계로 구분한다.

### 4.4. 문제 정의

여러 플랫폼을 통해 수강생을 모집하는 개인 음악 레슨 강사는 플랫폼별 정보 구조와 업무 절차가 다르고 모집 정보 및 상태가 분산되어 있어, 동일한 레슨에 대한 정보 준비·등록·수정·갱신·확인·대응 업무를 반복적으로 수행해야 한다.

이로 인해 시간과 수고가 소모되고, 원하는 모집 채널을 확대하고 유지하는 데 부담이 발생한다.

### 4.5. 해결 목표

플랫폼별 레슨 정보 등록 및 관리 업무를 대행·지원하여 강사가 직접 수행해야 하는 반복 업무를 최소화한다.

플랫폼 자체의 통합이나 규칙 변경을 목표로 하지 않으며, 수강생 모집 증가 및 매출 증가를 직접 보장하지 않는다.

## 5. 핵심 피처

핵심 피처는 서비스가 문제를 해결하기 위해 수행하는 행동 단위로 정의한다. 각 행동은 구분되는 목적과 확인 가능한 결과를 가진다.

핵심 피처에는 사용자의 문제를 직접 해결하는 행동과 해당 문제 해결을 성립시키는 데 필요한 정보·인증·권한·승인 확보 행동을 포함한다.

### 5.1. 원본 정보 확보 및 관리

| ID | 핵심 피처 | 수행 결과 |
|---|---|---|
| F01 | 사용자로부터 원본 레슨 정보를 입력받는다. | 소개글·사진·수업 조건 등의 원본 확보 |
| F02 | 저장된 원본 레슨 정보를 불러온다. | 재사용할 원본 확보 |
| F03 | 원본 레슨 정보를 구조화한다. | 근거와 연결된 레슨 사실 및 항목별 정보 |
| F04 | 사용자가 기존 원본 정보를 수정할 수 있도록 한다. | 변경된 원본 정보 |
| F05 | 원본 레슨 정보를 저장한다. | 재사용 및 버전 관리가 가능한 원본 |

원본 정보의 수정은 외부 플랫폼에 게시된 정보의 자동 수정을 의미하지 않는다.

원본의 변경 내용을 기존 게시물에 적용하려면 적용 대상과 변경 정보를 별도로 확인하고 승인받아야 한다.

### 5.2. 업무 지원 범위 확인 및 대상 선택

| ID | 핵심 피처 | 수행 결과 |
|---|---|---|
| F06 | 플랫폼별 지원 가능한 업무와 제약을 사용자에게 제공한다. | 등록·수정·갱신·조회 가능 여부 및 선행 조건 |
| F07 | 사용자로부터 작업 대상과 업무 종류를 선택받는다. | 대상 플랫폼 및 수행하려는 업무 범위 |

플랫폼별 지원 범위는 확인된 업무 절차와 운영사 정책, 기술적 실현 가능성을 근거로 제공한다.

특정 플랫폼의 신규 등록이 가능하더라도 수정·갱신·상태 조회까지 가능하다고 가정하지 않는다.

업무 대행의 허용 근거가 확인되지 않은 경우 자동 실행을 제공하지 않는다.

### 5.3. 플랫폼별 업무 준비

| ID | 핵심 피처 | 수행 결과 |
|---|---|---|
| F08 | 원본 정보를 대상 플랫폼에 맞게 변환한다. | 플랫폼별 입력안 |
| F09 | 입력안의 정확성과 유효성을 검증한다. | 누락·불확실·충돌·규격 위반 확인 |
| F10 | 부족하거나 불확실한 정보를 사용자에게 요청한다. | 추가 정보 및 확인된 사실 |
| F11 | 플랫폼 제약과 충돌하는 정보에 대한 해결 방안 및 선택지를 제공하고 사용자 결정을 요청한다. | 승인된 대체 조건 또는 업무 수행 불가 판단 |

정보 보완과 플랫폼 제약 충돌을 구분한다.

정보 부족은 필요한 사실을 확보하면 해결할 수 있지만, 제약 충돌은 기존 사실을 그대로 표현할 수 없는 문제이므로 사용자 결정이 필요하다.

예를 들어 실제 수업이 90분인 경우, 플랫폼에서 이를 그대로 입력할 수 없다면 임의로 60분 또는 120분으로 변경하지 않는다.

사용자가 실제로 제공할 수 있는 대체 조건을 선택한 경우에만 다시 변환하고 검증한다. 유효한 대안이 없으면 해당 업무를 수행하지 않는다.

### 5.4. 사용자 인증 및 작업 대상 확인

| ID | 핵심 피처 | 수행 결과 |
|---|---|---|
| F12 | 대상 플랫폼에 대한 사용자 인증을 요청한다. | 사용자가 직접 수행한 인증 결과 |
| F13 | 인증된 계정과 작업에 필요한 접근 권한을 확인한다. | 확인된 계정 및 접근 가능 범위 |
| F14 | 기존 게시물을 조회하고 관리할 대상을 식별한다. | 확인된 기존 게시 객체 및 원본과의 연결 |
| F15 | 기존 게시 정보와 변경 예정 정보를 비교하여 사용자에게 제공한다. | 변경 대상·변경 전후 정보 및 변경 범위 |

외부 플랫폼에 접속하기 전에 해당 접근 및 업무 대행 방식이 허용되는지 확인한다.

사용자가 플랫폼에 직접 로그인하고 필요한 인증을 수행한다. 계정 가입, 전문가 자격 확인, 약관 동의, 정산 계좌 설정 등 사용자가 직접 판단하거나 수행해야 하는 업무는 자동 대행 범위에 포함하지 않는다.

기존 게시물의 수정·갱신은 정확한 게시 객체가 식별된 경우에만 수행한다. 신규 등록의 경우에도 기존 등록 여부를 확인하여 중복 등록 위험을 방지한다.

사용자가 서비스 이용 전에 직접 등록한 게시물도 권한과 대상이 확인되면 관리 대상으로 연결할 수 있도록 한다.

### 5.5. 사용자 승인 및 실행 조건 확인

| ID | 핵심 피처 | 수행 결과 |
|---|---|---|
| F16 | 사용자에게 최종 등록·변경 정보의 승인을 요청한다. | 사용자가 승인한 최종 정보 |
| F17 | 사용자에게 업무 실행 범위의 승인을 요청한다. | 승인된 플랫폼·계정·게시 객체·업무·실행 범위 |
| F18 | 현재 실행 조건과 사용자 승인 내용의 일치 여부를 확인한다. | 실행 가능 또는 실행 제한 판단 |

정보 보완, 제약 충돌에 대한 결정, 인증, 권한 확인, 정보 승인, 실행 승인은 서로 다른 목적을 가진다.

정보 승인은 무엇을 등록하거나 변경할지에 대한 동의이고, 실행 승인은 어디에서 어떤 업무를 수행할지에 대한 동의이다.

두 승인은 논리적으로 구분하되 사용자가 한 번의 승인 과정에서 처리할 수 있도록 한다.

승인 이후 계정, 대상, 변경 범위, 플랫폼 제약 또는 게시 정보가 달라져 승인한 업무에 영향을 주는 경우 기존 승인을 그대로 사용하지 않는다.

### 5.6. 플랫폼별 업무 실행

| ID | 핵심 피처 | 수행 결과 |
|---|---|---|
| F19 | 승인된 레슨 정보를 플랫폼에 신규 등록한다. | 신규 등록 실행 결과 |
| F20 | 기존 게시물의 정보를 승인된 내용으로 수정한다. | 정보 수정 실행 결과 |
| F21 | 기존 모집 공고를 승인된 방식으로 갱신한다. | 공고 갱신 실행 결과 |

사용자가 승인한 정보와 범위 내에서 플랫폼이 허용하는 업무만 수행한다.

추가 플랫폼 등록은 저장된 원본을 재사용하여 새로운 플랫폼에 신규 등록하는 방식으로 지원한다.

수정은 기존 게시 객체의 내용 변경을 의미하며, 갱신은 플랫폼에서 제공하거나 허용하는 공고 유지·갱신 절차를 의미한다.

기존 게시물을 삭제하고 새로운 게시물을 생성하는 행위를 수정 또는 갱신으로 임의 대체하지 않는다. 재등록이나 삭제는 별도 업무이므로 기존 승인만으로 수행하지 않는다.

### 5.7. 업무 결과 확인 및 관리

| ID | 핵심 피처 | 수행 결과 |
|---|---|---|

| F23 | 업무 실행 및 결과 이력을 저장한다. | 작업 대상·승인·실행·관측 결과의 추적 기록 |
| F24 | 수행한 업무의 결과를 사용자에게 전달한다. | 플랫폼별 작업 결과와 필요한 후속 조치 |
| F25 | 플랫폼별 마지막 확인 정보와 상태를 통합하여 제공한다. | 확인된 등록 정보·상태·확인 시점·게시 링크 등의 관리 정보 |

업무 이력에는 외부에 영향을 주는 작업의 실행 전 정보와 실행 이후의 관측 결과를 모두 포함한다.

등록 시도, 접수 확인, 심사 승인, 게시 완료는 서로 구분한다. 플랫폼별 업무의 완료 조건을 사전에 정의하고 근거가 없는 성공 판정을 하지 않는다.

여러 플랫폼에 대한 업무는 각각 독립적인 결과를 관리한다.

## 8. 서비스 이용 시나리오

### 8.1. 최초 등록

1. 사용자는 서비스에 진입한다.
2. 사용자는 기존 레슨 정보를 제공한다.
3. 사용자는 지원 가능한 플랫폼과 업무를 확인한다.
4. 사용자는 등록할 플랫폼을 선택한다.
5. 서비스는 원본 정보를 구조화하고 플랫폼별 정보를 변환·검증한다.
6. 사용자는 필요한 정보를 보완한다.
7. 사용자는 플랫폼 제약과 충돌하는 정보에 대한 해결 방안을 선택한다.
8. 사용자는 대상 플랫폼에서 직접 인증한다.
9. 서비스는 인증된 계정과 등록 권한 및 기존 등록 여부를 확인한다.
10. 사용자는 최종 등록 정보와 실행 범위를 확인하고 승인한다.
11. 서비스는 승인된 조건과 실제 실행 조건을 대조한다.
12. 서비스는 승인된 등록 업무를 수행한다.
13. 서비스는 실제 업무 결과를 확인하고 이력을 저장한다.
14. 서비스는 업무용 인증 세션을 폐기한다.
15. 사용자는 플랫폼별 결과와 필요한 후속 조치를 확인한다.

### 8.2. 추가 플랫폼 등록

사용자는 저장된 원본 레슨 정보와 새로운 플랫폼을 선택한다.

서비스는 기존 원본과 플랫폼별 설정 정보를 활용하여 필요한 정보를 준비하고 신규 등록 절차를 수행한다.

### 8.3. 기존 레슨 정보 수정

사용자는 변경할 원본 정보와 적용할 플랫폼을 선택한다.

서비스는 필요한 인증을 요청하고 수정 대상 게시물을 식별한다. 실제 게시 정보와 변경 예정 정보를 비교하여 사용자에게 제공한다.

사용자는 변경 내용과 대상, 실행 범위를 승인한다.

서비스는 승인 이후 변경된 외부 상태와 충돌하지 않는지 확인하고 수정한다. 이후 실제 변경 결과를 확인하여 제공한다.

### 8.4. 공고 갱신

사용자는 갱신 대상 게시물과 갱신 업무를 선택한다.

서비스는 해당 플랫폼에서 허용하는 갱신 방식이 존재하는지 확인한다.

사용자의 승인 범위에서 갱신 업무를 수행하고 결과를 확인한다.

### 8.5. 등록 이후 상태 관리

사용자는 통합 관리 화면에서 플랫폼별 마지막 확인 정보와 상태를 조회한다.

사용자가 상태 갱신을 요청하면 서비스는 허용된 조회 방법을 사용한다. 인증이 필요한 경우 사용자에게 직접 인증을 요청한다.

서비스는 새로 확인한 상태와 확인 시점을 저장하고 필요한 대응을 안내한다.

### 8.6. 조건부 자동 모니터링

공개 정보 기반 조회 또는 사용자가 위험성을 인지하고 별도로 승인한 인증 유지 방식이 허용되는 경우에만 제공한다.

사용자는 관리 범위와 기간을 설정하며 언제든 종료할 수 있다.

### 8.7. 대표 예외 상황

| 예외 상황 | 처리 원칙 |
|---|---|
| 정보 부족 또는 불확실 | 필요한 사실만 사용자에게 요청 |
| 플랫폼 제약 충돌 | 대안 제공 및 사용자 결정 요청 |
| 유효한 입력 대안 없음 | 해당 업무 수행 불가 안내 |
| 인증 실패·만료 | 사용자 인증 요청 또는 업무 종료 |
| 잘못된 계정·대상 불명확 | 실행하지 않고 대상 확인 |
| 사용자 승인 거절 | 해당 업무 실행하지 않음 |
| 승인 이후 중요 조건 변경 | 실행 보류 및 필요한 재검증·재승인 |
| 실행 중 오류 | 영향을 받은 업무 중단 및 확인된 결과 반환 |
| 실행 결과 미확인 | 무조건적인 재실행 금지, 기존 외부 효과 확인 |
| 일부 플랫폼만 완료 | 플랫폼별 독립 결과 제공 |

| 상태 조회 실패 | 마지막 관측 상태와 현재 조회 불가 상태 구분 |
| 인증 유지 승인 철회 | 자동 접근 중단 및 인증 세션 폐기 |

사용자 스토리는 이러한 정상·예외·반복 흐름을 기반으로 주어·동사·목적어 형태의 행동 목록으로 상세화한다.

## 9. 기능 요구사항 및 데이터 설계 원칙

### 9.1. 정보 관리 원칙

| 정보 구분 | 의미 |
|---|---|
| 원본 레슨 정보 | 사용자가 제공한 기본 레슨 사실과 자료 |
| 플랫폼별 설정 정보 | 특정 플랫폼에 적용하기로 결정한 정보와 조건 |
| 플랫폼별 변환 정보 | 플랫폼의 정보 구조와 제약에 맞게 준비한 입력안 |
| 승인 정보 | 특정 업무에서 사용자가 최종 승인한 정보와 실행 범위 |
| 실제 게시 정보 | 외부 플랫폼에서 관측한 게시 내용 |
| 관측 상태 | 외부 플랫폼에서 확인한 업무 상태 및 확인 시점 |

원본 정보와 플랫폼별 게시 정보가 항상 동일해야 한다고 가정하지 않는다.

강사가 플랫폼별로 서로 다른 가격이나 수업 조건을 운영할 수 있으며, 해당 차이는 사용자의 확인과 승인을 근거로 관리한다.

원본 변경 시 과거 승인과 실행 이력을 보존한다. 기존 게시물에는 별도로 승인된 변경만 적용한다.

외부 플랫폼에서 확인하지 못한 정보를 최신 실제 게시 정보로 취급하지 않는다.

### 9.2. 업무 실행의 필수 조건

다음 조건을 충족한 경우에만 외부 플랫폼 업무를 실행한다.

- 플랫폼에서 해당 업무 및 접근 방식을 허용한다.
- 필요한 사용자 인증과 계정 권한이 확인되었다.
- 업무 대상이 정확하게 식별되었다.
- 입력 정보가 원본 또는 사용자가 확인한 플랫폼별 조건과 일치한다.
- 플랫폼의 필수 입력 조건을 충족한다.
- 최종 정보 및 실행 범위가 사용자에게 승인되었다.
- 실제 실행 조건이 승인 범위와 일치한다.
- 기존 작업의 미확인 외부 효과로 인해 중복 실행 위험이 발생하지 않는다.

위 조건 중 하나라도 충족하지 못하면 해당 업무를 실행하지 않으며 이유와 필요한 조치를 사용자에게 제공한다.

### 9.3. 실패 및 결과 관리 원칙

- 외부 효과를 발생시키는 작업은 실행 전 대상과 승인 범위를 기록한다.
- 실패·미확인·부분 성공을 구분한다.
- 접수 응답을 받지 못한 경우 등록되지 않았다고 단정하지 않는다.
- 미확인 외부 효과가 있는 경우 중복 등록이나 변경을 방지한다.
- 기존 게시물의 외부 변경을 확인하지 못한 상태에서 오래된 정보로 덮어쓰지 않는다.
- 외부 플랫폼의 변경 취소나 원상 복구를 보장하지 않는다.

### 9.4. 인증 및 접근 권한 관리

기본 업무 실행과 사용자 요청 기반 조회에서는 작업에 필요한 기간 동안만 인증 세션을 활용한다.

업무 완료·실패·권한 철회·만료 이후 서비스가 관리하는 작업용 인증 세션을 폐기한다.

외부 플랫폼의 비밀번호와 인증코드를 서비스 데이터로 수집하거나 저장하지 않는다.

인증 중 민감한 화면이나 입력 내용이 불필요하게 기록되거나 AI에 전달되지 않도록 한다.

사용자별·계정별 인증 세션을 분리하고 다른 사용자의 세션을 사용할 수 없도록 한다.

지속 인증 유지 방식은 조건부 자동 모니터링의 별도 승인 및 보안 조건을 충족하는 경우에만 허용한다.

### 9.5. 개인정보 및 정보 보호

- 업무 수행에 필요한 정보만 수집한다.
- 개인정보, 인증 정보, 업무 데이터의 접근 범위와 보관 기간을 구분한다.
- 사진·영상 등 제3자 권리와 관련된 자료는 사용 권한을 확인한다.
- 외부 AI로 전달하는 정보를 최소화한다.
- 외부 웹페이지와 사용자 자료의 내용은 처리 대상 데이터로 취급하며 서비스의 실행 권한을 변경하는 지시로 취급하지 않는다.
- 사용자가 보관된 원본 정보의 삭제 및 외부 게시물 관리 연결의 해제를 요청할 수 있도록 한다.
- 서비스 내부 데이터 삭제나 관리 연결 해제는 외부 플랫폼 게시물의 삭제를 의미하지 않는다.

사용자 한 명이 여러 레슨과 플랫폼 계정을 관리하거나, 하나의 레슨 정보가 여러 상품·클래스·게시물로 표현될 수 있는 관계를 조사하고 설계에 반영한다.

실제 조사에서 확인된 공통점과 차이점을 근거로 저장 방식과 데이터 관계를 결정하며, 특정 데이터베이스 구조를 사전에 확정하지 않는다.

기존 보고서의 화면 및 절차는 조사 당시의 근거로 활용한다. 플랫폼의 최신 세부 필드, 실제 완료 증거, 업무 대행 허용 범위는 추가 확인이 필요하다.

### 10.3. 7개 플랫폼 조사 및 확장성 확보

**조사 목적**

초기 저장소 및 서비스 계약이 일부 플랫폼의 구조에 종속되는 것을 방지하고, 향후 지원 플랫폼의 확대에 따른 데이터베이스 및 공통 기능의 변경 부담을 최소화한다.

이를 위해 초기 설계 과정에서 7개 플랫폼을 조사한다.

**조사 대상**

| ID | 플랫폼 | 주요 조사 대상 | 데이터 및 업무 구조의 검토 사항 |
|---|---|---|---|

| PL02 | 탈잉 | 레슨 클래스 | 커리큘럼·회차·시간·일정·심사 상태 |

| PL04 | 프람피 | 전문가 프로필 및 레슨 분야 | 전문가별 제공 분야·프로필과 서비스 간 관계 |

조사 대상은 R02의 실제 이용 경험과 기존 조사 결과를 바탕으로 선정하며, 상품형·클래스형·전문가 프로필형·커뮤니티 게시물형 등 서로 다른 구조를 고려한다.

초기 조사 후보 중 당근과 소모임은 현재 고려 중인 PC 웹 기반 등록·관리 경로가 확인되지 않아 우선 조사 대상에서 제외한다. 향후 해당 경로가 확인되거나 모바일 환경 지원을 검토하는 경우 다시 조사할 수 있다.

프람피의 유료 제안서 발송 등 고객별 상담·견적 업무는 조사 대상에서 제외한다.

조사 대상의 실제 웹 등록·수정 가능 여부는 확인 과정에서 검증하며, 등록 경로가 존재하지 않거나 서비스 대상 업무에 적합하지 않은 경우 다른 플랫폼으로 대체한다.

## 11. 제품 범위 및 MVP

### 11.1. 기본 제품 범위

개인 음악 레슨 강사의 다중 플랫폼 모집 정보 등록 및 관리 업무를 지원한다.

- 원본 정보 저장 및 재사용
- 플랫폼별 정보 변환·검증 및 사용자 정보 보완
- 업무 대상 확인·직접 인증·권한 확인·사용자 승인
- 신규 등록 및 추가 플랫폼 등록
- 기존 게시 정보 수정
- 플랫폼에서 허용하는 공고 갱신
- 업무 결과 확인 및 이력 관리
- 플랫폼별 통합 상태 조회
- 사용자 요청에 따른 상태 갱신
- 오류·반려·정보 불일치 대응 안내

개별 플랫폼에서 실제로 제공하는 업무는 허용 범위와 기술적 실현 가능성에 따라 제한한다.

### 11.2. 조건부 확장 범위

- 공개 정보 기반 자동 모니터링
- 사용자가 위험성을 인지하고 명시적으로 승인한 인증 유지 기반 자동 모니터링
- 자동 모니터링에서 확인한 상태 변화의 알림

자동 모니터링은 기본 제공 범위와 필수 MVP에서 제외한다.

### 11.3. 제외 범위

- 사용자 승인 없는 등록·수정·갱신·재등록·삭제
- 기본 업무의 종료 이후 불필요한 인증 세션 유지
- 플랫폼 정책상 허용되지 않은 접근이나 자동화
- 본인인증 또는 보안 절차 우회
- 수강생 상담·유료 견적 발송
- 수업 일정 관리·출결·결제·수업 자체의 운영
- 별도 후기·영상 콘텐츠 제작 및 마케팅 업무
- 이용자에게 실제 모집 인원 또는 매출 증가를 보장하는 행위

### 11.4. 단계별 개발 범위 제안

| 단계 | 목표 |
|---|---|
| 플랫폼 및 데이터 조사 | 7개 플랫폼의 데이터 구조 및 업무 분석 |
| 공통 설계 | 플랫폼별 차이를 수용할 수 있는 공통 데이터 모델·저장소·서비스 계약 설계 |
| 기술 검증 | 단일 플랫폼에서 정보 준비부터 승인된 등록 및 결과 확인까지 전체 흐름 검증 |
| 제품 MVP | 복수 플랫폼에서 동일 원본의 재사용, 신규·추가 등록, 대표적인 기존 정보 수정 및 통합 결과 확인의 사용자 가치 검증 |
| 제품 확장 | 지원 플랫폼 확대, 추가 수정·갱신 업무 및 사용자 요청 기반 상태 관리 확대 |
| 조건부 확장 | 수요·권한·보안·운영 비용이 검증된 자동 모니터링 제공 |

제품 MVP는 최소 2개 플랫폼에서 반복적인 등록 및 관리 업무 부담을 줄이는 경험을 검증하는 방향으로 제안한다.

7개 플랫폼 조사는 초기 저장소 및 공통 설계의 확장성을 확보하기 위한 범위이며, 7개 플랫폼의 모든 기능 구현을 MVP 필수 조건으로 설정하지 않는다.

공고 갱신과 상태 갱신의 세부 구현 범위는 실제 사용 빈도와 권한을 확인하여 결정한다.

기존 개발 일정 및 구현 상황은 공수 판단의 근거로 사용하되, 문제 정의나 필요한 기능을 기존 구현에 맞추어 제한하지 않는다.

MVP 범위, 일정 및 업무 분담은 기획 검토 이후 재결정한다.

### 12.3. 비교 실험

동일한 원본 정보, 사진, 사용자 조건, 플랫폼 규칙 및 업무 완료 기준을 사용하여 다음 세 가지 방식을 비교한다.

1. 사용자의 직접 업무 수행 및 템플릿 활용.
2. 충분한 자료와 재사용 지시를 제공한 범용 AI 및 브라우저 에이전트 활용.
3. 전용 서비스 활용.

정확성과 업무 완료 수준이 동일한 조건에서 사용자 직접 업무 시간, 개입 횟수, 오류, 재작업 및 비용을 비교한다.

모의 환경의 성공, 실제 플랫폼 업무의 성공, 실사용자의 업무 절감 효과를 각각 구분한다.

R02가 제시한 3개 플랫폼 이용 시 사용자 직접 작업 시간 20~30분 이내는 희망 기준이며, 아직 달성된 성과가 아니다.

### 12.4. 데이터 및 플랫폼 확장성 검증

7개 플랫폼의 조사 결과를 공통 데이터 모델 및 저장소 설계에 연결하고, 서로 다른 플랫폼 구조를 수용할 수 있는지 검증한다.

| 검증 항목 | 확인 기준 |
|---|---|
| 정보 표현 가능성 | 플랫폼별 필수 정보와 고유 제약을 의미 손실 없이 표현할 수 있는가? |
| 객체 관계 | 상품·클래스·프로필·게시물의 서로 다른 관계를 표현할 수 있는가? |
| 상태 표현 | 플랫폼마다 다른 업무 결과와 상태를 구분하여 관리할 수 있는가? |
| 정보 재사용 | 새로운 플랫폼에 등록할 때 기존 원본 정보를 활용할 수 있는가? |

| 기존 기능 영향 | 플랫폼 추가 및 규칙 변경 이후 기존 플랫폼의 업무와 데이터가 정상적으로 유지되는가? |

설계 검증 방법으로는 7개 플랫폼 중 일부를 공통 모델 도출에 활용하고, 나머지를 독립적인 확장 사례로 활용하는 방식을 고려한다.

예를 들어 서로 다른 객체 유형을 포함한 5개 플랫폼으로 초기 모델을 구성한 후 나머지 2개 플랫폼의 조사 결과를 적용하여 설계의 변경 필요성을 확인한다.

발견된 설계 한계는 공통 모델 및 저장소 설계에 반영하고 전체 7개 플랫폼의 데이터 표현 가능성을 다시 검증한다.

실제 업무 자동화의 성공 여부와 데이터 모델의 확장성 검증 결과는 구분한다.

### 12.5. 실제 사용자 확보 및 개선

실제 타깃 강사를 확보하여 서비스의 이용 가능성과 반복 업무 절감 효과를 확인한다.

사용자 피드백을 수집하고 실제 문제를 해결하는 데 필요한 부분을 개선한다. 개선 이후 동일한 지표를 다시 측정한다.

사용자 수, 반복 이용, 만족도, 지불 의향 및 실제 구매와 운영 비용을 기록하여 사업성을 검토한다.

### 12.6. 기획 및 설계 진행 순서

문제 정의 및 원인 분석 → 핵심 피처 정의 → 사용자 스토리 → 7개 플랫폼 데이터 및 업무 분석 → 공통 논리 데이터 설계 → ERD 및 API 프로토콜 → 확장성 검증 및 설계 보완 → 상세 설계 및 구현 → 사용자 검증 및 개선.

사용자 스토리와 플랫폼 조사는 독립적으로 수행할 수 있는 부분을 병행하고, 양쪽 결과를 공통 논리 데이터 및 서비스 설계에 연결한다.
