## L0~L2 · 이번 수직 검증의 목표와 Done

**검증 질문:** 기존 레슨 소개글·판매 조건·사진이 있는 강사의 최초 등록 1건을, 임의 조건을 만들어내지 않고 **정보 준비 → 사용자 승인 → 모의 양식 입력/첨부 → 결과 확인**까지 처리할 수 있는가?

- 대상: 가상 1:1 레슨 1건, 크몽 **모의** 등록 양식. 실제 상품/계정/인증/제출은 사용하지 않는다.
- Must(FR-01~03, FR-05~06): 사실 구조화·변환, 조건 충돌/누락 감지, 승인한 초안 버전과 실행 권한 연결, 모의 등록 기록 및 분명한 mock 결과, 실패·unknown·중복 방지.
- Conditional(FR-04): 실크몽 접수/입력은 운영사 허용, 강사 인증·명시 승인, R05 기술 검증과 별도 R01 결정 이후.
- Out: 실제/가짜 상품 무단 게시, CAPTCHA·로그인 우회, 비밀번호/OTP 수집, 타 플랫폼 실등록, 상담/후기/수강생 지도.
- 11/27 목표: **모의 전체 흐름을 실행**하고 실행 로그와 실패 원인을 남긴다. 12/08 MVP: 이 흐름을 사용자가 구동할 수 있는 통합 결과로 제시. 모의 성공은 실서비스 완료가 아니다.

## L3 · 업무 객체 및 변경해서는 안 되는 규칙

| 업무 객체 | 최소 의미 | 보유/변경 책임(제안) |
| --- | --- | --- |
| SourceLesson | 출처/버전, 승인받은 판매 사실(가격·회당 분·횟수·비용·일정·제공 범위), 이미지 권한 | R02 사실 fixture, R03 규칙 |
| RegistrationDraft | 대상 플랫폼, 원본 버전, 매핑값, 해결되지 않은 질문, 초안 버전 | R03 |
| Approval | 초안 버전, 승인 주체·시각, 허용된 실행 동작(입력/첨부/제출 별도), 적용 환경(mock/live) | R03 의미, R04 사용자 동작 |
| RegistrationJob / Event | 작업 ID, 승인 참조, 실행 대상·환경, 단계별 시도·오류, 증거 참조, 재시도 제한 | R05 실행/기록, R03 상태 규칙 |
| RegistrationResult | 증거로 확인된 상태, 미확인 사유, 다음 사용자 조치 | R03 판정, R04 표시 |

필수 불변식:
1. 원문에 없는 판매 조건(가격, 할인, 체험가, 취소/변경, 추가 혜택)을 **임의로 확정하거나 추가하지 않는다**.
2. F2는 승인된 **정확한 초안 버전과 허용 동작**만 실행한다. 변경 시 재승인이 필요하다.
3. mock과 live의 결과/증거는 분리한다. 모의 제출 또는 버튼 클릭은 크몽 심사 접수의 증거가 아니다.
4. 제출 결과가 unknown이면 **자동 재제출하지 않는다**. 먼저 확인 또는 사용자 개입이 필요하다.
5. 미확인 필수 필드, 사진 권한, 실제 플랫폼 허용은 확인 전까지만 **미확인**이다. 가상 데이터의 성공으로 승격하지 않는다.
6. 실제 계정 비밀번호·OTP·세션 쿠키·개인 연락처는 저장소, fixture, 로그에 기록하지 않는다.

## L4 · 컴포넌트와 단독 코드 책임 (제안)

| 코드 경계 | 소유 제안 | 구현 책임 | 외부 공유 입력/출력 |
| --- | --- | --- | --- |
| fixtures | R02 | **합성** 정답 원본, 오류 데이터, 크몽 공식 필드의 근거 수준 | SourceLesson + 기대값 |
| core | R03 | F1 구조화·매핑/검증, 승인 일치 검사, F3 상태 판정·중복 차단 | I-01/I-02, I-03 검사, I-04 판정 |
| ui | R04 | 강사 원본 입력, 필드 검토, 버전 승인, mock 진행/오류/unknown 표시 | I-02/I-03/I-04 |
| adapters/mock-kmong | R05 | **오프라인/로컬 모의 양식만** 입력·사진 첨부·모의 응답/실패 주입 | I-03 → 실행 이벤트(I-04) |
| application/API/record | R05 | 위 컴포넌트 연결, 작업 ID/이벤트/증거의 전달·기록 | I-01~04 연결, 상태 조회 |
| 통합 인수 | R01 | Must/Out/Done 판정, 합의 불일치·가치 검증 결정 | 실행 로그/검증 증거 |

R03이 업무 데이터·상태 **의미의 정본**을 맡고, R05가 호출·실행·저장 **기술 계약**을 맡는다. 공유 필드 이름이나 의미를 바꾸는 경우 R03/R04/R05 간 합의하며, 제품 목표·Must/Done 충돌만 R01이 결정한다. Python/React/Playwright·API 실행 위치는 **미채택**이며 R05의 TASK-030과 비교 후 정한다. 당장은 새 의존성을 강제하지 않는다.

| 케이스 | 시험 입력 | 성공 조건 | 실제 실행 상태 |

| C02 | 필수 값 미확인·가격/시간 충돌 | 임의 완성하지 않고 보류·확인 요청 | 미실행 |

## L7 · 작업 착수 조건과 전달 순서

1. R01: 모의 환경에 한정한 설계·PoC 착수 여부 및 범위/완료 기준을 결정하고 현재 Phase Intent/ADR/TASK를 수정해 정본으로 기록한다. 이 문서 작성만으로 승인하지 않는다.
2. R03 + R05: I-01~04의 최소 필드·오류·상태·버전 검사 규칙을 합의한다. R04는 승인 화면의 사용자 행동과 상태 표시를 확인한다.
3. R02: 오전 부재 중에는 합성 fixture만 사용. 이후 R02는 실제 판매 조건/사진 권리/실플랫폼 필드 사실과 테스트 데이터의 차이를 확인한다. **실제 등록 자료 제출을 요구하지 않는다**.
4. R03/R04/R05: 각자 소유 디렉터리에서 최소 코드·단위 검증을 진행, 계약 변경 시 소비자에게 전달한다.
5. R01: C01/C03/C05/C06의 실행 증거와 차단 조건을 통합 확인한다. 첫 통합은 mock 전용으로 유지한다.

## 미결정 / 다시 검토할 근거

- R01: 실제 MVP Must/Done 채택 및 모의 코딩 착수 승인 여부.
- R03/R05: 공통 스키마 버전·상태 이름·오류, 구현 책임 세분화 및 공통 계약 채택.
- R05: 로컬/서버/혼합·기술 스택·실제 플랫폼 권한 검증과 예상 공수.
- R02: 크몽 실제 폼 필드/사진·권리, 원본 가격 버전의 정확한 적용 범위.
- R01: 모의 완료만으로 사용자 가치가 입증됐다고 간주할 수 없음. 범용 AI 대비 시간·개입 비용은 후속 실측.
