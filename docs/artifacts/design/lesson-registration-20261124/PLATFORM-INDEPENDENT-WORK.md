## 두 플랫폼이 공유할 내용과 공유하면 안 되는 내용

- **공통:** 가상 사용자 승인, 입력값/사진 권리 확인, 오류·미확인 구별, 중복 제출 제한, mock/live 분리 및 증거 기록.
- **플랫폼별:** 등록 대상 객체(크몽 레슨 상품 / 숨고 고수 프로필·서비스 후보), 필수 필드, 인증·심사/공개 단계, 화면 위치와 실행 기술.
- **R03 test-harness는 R04·R05의 개발 방식에 간섭하지 않는다.** 입력 데이터·테스트 사례·결과 비교를 담당한다. R04와 R05는 각자 기술 스택/패키지/코드·개발 경로를 자율 설계하며 **서로 코드 복사나 공통 인터페이스 변경을 강제하지 않는다**.
- 반드시 공유할 최소 어휘: `environment` mock/live, `platform` kmong/soomgo, `source_version`, `approved_draft_version`, `actions`, `result_state`, `evidence_refs`, `retry_blocked`. 구체적인 타입·오류 코드는 착수 후 R03/R04/R05가 합의한다.

## 실행할 최소 시험

| 케이스 | 공통 검증 | 플랫폼별 해석 |
|---|---|---|
| T1 | 합성 입력 1건, 사용자 승인 후 모의 필드 입력과 이미지 첨부 | 크몽: 레슨 상품 / 숨고: 근거로 확인한 객체 1개 |
| T2 | 가격·시간·필수 조건 누락 또는 불일치 | 임의 값 생성/변경 없이 중단·확인 |
| T3 | 승인 버전 불일치·미승인 실행 | 모의 실행 거절 |
| T4 | 이미지/폼 입력 오류 | 실패·재개 조건, 성공 오판 방지 |
| T5 | 제출 결과 유실 | unknown, 확인 전 자동 재제출 금지 |
| T6 | live 허용 미확인 | 외부 사이트 실행 차단 |

모든 시험은 **실제 크몽·숨고 계정 없이** 실행하며 mock 성공이 심사 접수/게시 성공이라는 증거가 될 수 없다. 정답/실행 결과/확인되지 않은 플랫폼 세부를 분리해서 보고한다.

## 최소 설계→실행 순서

1. R03: mock 범위·모의 페이지·fixture·정상/오류/unknown 예제 공개. 숨고 폼은 R04 공식 등록 객체 조사 전까지 **가설**로 표시.
2. R04·R05: 각자 독립 브랜치에서 `design.md`에 사용자 시나리오, 외부 경계, 컴포넌트, 데이터/오류, 검증 명령 기재 후 최소 구현.
3. 두 팀원의 초기 코드 결과로 R03이 mock 적합성을 점검하고 시험 데이터를 조정하되, 성공 기준을 특정 구현에 맞춰 변경하지 않는다.
4. 11/26 동일 유형의 정상/오류/unknown 시험을 실행. 11/27 R01은 **각 플랫폼의 충족 범위와 불확실성**을 검토한다. 서로 다른 플랫폼이므로 단일 점수 경쟁이 아니라 플랫폼별 가능성과 재사용 경계를 판단한다.

## 오늘 범위와 안전

- 기존 `main`의 제품 프레임워크는 추가하지 않는다. `pyproject.toml` 및 `uv.lock`은 최소 상태로 유지하고, 새 의존성은 담당자의 독립 브랜치에만 먼저 도입해 영향·용도·라이선스/버전 기록.
- 실제 웹 서비스 로그인, 비밀번호/인증코드/세션 수집, 무허용 자동화·실제 제출, 플랫폼 보호 우회는 불가.
- 미확인 허용 범위를 '가능'으로 적지 않는다. 실서비스 동작 확인 필요 사항을 명확히 남긴다.
- 기존 TASK-038~042와 PR #41은 **미병합·대체**. 이번 정식 TASK는 TASK-043~045.
- GitHub는 지속적인 결정·검증 기록의 정본. **현재 사용자 지시대로 PR은 만들지 않는다**. 팀원별 작업 브랜치는 독립 유지하고, main 병합 전 필요시 통합 검토한다.
