## 확정 결정

정본은 [상위 논리적 데이터 계약 결정](logical-data-contract-decision-v1.json)이다. R01의 직전 제안에 대한 합의 및 GitHub 반영 지시를 기록한다.

| ID | 결정 | 이유 |
|---|---|---|
| LD-01 | 공통 업무에서 사용하는 정보의 의미와 전달만 공통 계약으로 정의하고 플랫폼별 항목·타입·필수/조건부 제약·절차·완료 조건은 플랫폼 프로필이 정의한다. | 등록 업무의 공통 구조를 유지하면서 지원 플랫폼마다 달라지는 필드를 보존한다. 지원 플랫폼 추가 시 공통 계약 수정이 원칙적으로 불필요해야 한다. |
| LD-02 | 원본(Source), 플랫폼 프로필(Profile), 등록 요청(Registration)의 3개 핵심 논리 구조를 유지한다. 준비·인증·승인 범위·진행·결과는 등록 요청에 속하는 정보이며 독립 업무 자원을 강제하지 않는다. | 원본은 여러 등록에서, 프로필은 여러 사용자에게 재사용되고 등록 요청은 독립적으로 수행된다. 분리는 수명주기와 재사용 여부에 근거한다. |
| LD-03 | 동일 의미의 정보는 동일 타입을 사용하며 데이터의 생성·수신·변경·검증 책임을 명시한다. | 컴포넌트마다 다른 의미로 해석하거나 책임이 누락되지 않도록 한다. |
| LD-04 | 등록값은 해당 프로필의 계약으로 검사한다. 공통 식별자는 특정 플랫폼 열거형에 묶지 않고 서버의 지원 프로필 조회 및 유효성 검사로 제한한다. | 모든 필드의 공통화와 무검증 자유형 JSON의 단점을 피한다. 미지원/미확인 실제 플랫폼에 대한 실행 허용을 뜻하지 않는다. |
| LD-05 | 준비 결과는 등록값·정보 근거·문제를 전달한다. 준비 완료 여부는 필수 조건 충족 및 해결되지 않은 차단 문제 여부에서 도출하며 별도 독립 상태로 관리하지 않는다. | 완료 표시와 실제 검사 결과 간 불일치를 방지하고 사용자에게 필요한 정보만 질문한다. |
| LD-06 | 실행 범위는 승인된 등록값·원본/프로필 버전·인증된 계정 및 대상·확인된 연결을 결합하여 고정한다. 승인 참조는 등록 요청 내 고정 범위를 식별하며 별도 계획 생성이나 승인 관리 자원을 추가하지 않는다. | 사전 확보 절차로 수행 가능한 업무이며 승인 내용과 실제 실행을 일치시키기 위함이다. 원격 연결 참조는 서버 내부에서만 전달하고 세션/자격증명 자체는 공통 업무 데이터에 넣지 않는다. |
| LD-07 | 등록 결과는 목표 판정·확인된 수행/효과·관측 대상과 방식이 포함된 근거·오류를 제공한다. 목표 달성은 해당 프로필의 완료 조건으로 판정한다. | 제출 응답과 독립 재조회 등 관측 방식을 구분하고 신뢰할 수 있는 근거가 충분하면 불필요한 조회를 강제하지 않는다. 오류 중단 및 미확인 효과 보존 원칙 유지. |
| LD-08 | 공통 타입·플랫폼 규칙·업무 관계·실행 조건·결과 검사를 각 책임 경계에서 수행한다. 논리 계약과 물리적 저장 및 코드 구조를 구분한다. | 타입이 맞는 것만으로 업무 유효성을 보장할 수 없으며, 검증 책임 구분은 별도 검증 서비스 5개를 의미하지 않는다. |

### 정보 흐름

| 전달 정보 | 생성 책임 | 수신 책임 | 의미 |
|---|---|---|---|
| 플랫폼 프로필 | KNOW | CO/PREP/EXEC/RESULT | 동일 고정 프로필의 정보 및 규칙 |
| 준비 결과 | PREP | CO | 등록값, 근거, 문제; 프로필과 원본 관계 검사 |
| 인증·대상 확인 | EXEC | CO | 신뢰할 수 있는 계정/대상과 서버 내부 연결 참조 |
| 승인된 실행 범위 | CO | EXEC | 승인된 값과 대상·프로필·연결 고정; 실행 전 조건 검증 |
| 실행 관측 | EXEC | RESULT | 수행 결과·대상·관측 방식·근거·오류 |
| 등록 결과 | RESULT | CO | 프로필 완료 조건에 따른 판정 및 근거; CO가 저장/제공 |

## 검증 및 미해결 항목

[논리 모델 V5](logical-behavior-v5.json), [논리 검증 결과](logical-validation-v5.json), [인터페이스 검토 근거 V3](interface-review-evidence-v3.json), [검토 코드](validate-interface-review-v3.mjs)를 보존한다. 논리 모델 탐색 114개 상태/276개 전이, 선정한 불변식 위반 0건. 기본 타입 사례 18/18과 스키마 내부 참조 173/173은 직접 작성한 JavaScript 검사기에 대한 결과다. 표준 JSON Schema 엔진 검증과 실제 구현 실행은 수행하지 않았으며 의미 검사 규칙의 실행 가능성과 연결 계약은 아직 보완해야 한다.

| ID | 상세 설계에서 해결할 사항 | 상태 |
|---|---|---|
| P1 | 인증 출력→실행 입력의 내부 연결 참조 및 동일 연결 바인딩 계약 | 미해결 |
| P2 | 완료 근거의 관측 방식 및 대상과 증거 연결 계약 | 미해결 |
| P3 | 플랫폼 ID/종류/목표의 공통 스키마 고정 열거형을 지원 프로필 기반 계약으로 정리 | 미해결 |
| P4 | 의미적 검사 규칙의 책임·실행 가능한 검증과 정상/비정상/확장 예시 | 미해결 |
| P5 | 상세 데이터 타입·필수/조건부 필드·참조·제약과 인터페이스/API의 정합성; 구현자 통합 가능 수준 검증 | 미해결 |

상위 계약을 충족하는 상세 계약의 검증 기준:
- 동일 원본으로 서로 독립된 크몽/숨고 등록 요청을 처리할 수 있다.
- 새로운 지원 플랫폼을 추가할 때 공통 업무 구조와 계약의 수정이 원칙적으로 필요하지 않다. 플랫폼별 등록 계약 및 검증·실행 구현은 추가한다.
- 필수 정보 누락·충돌·제약 위반이 있을 때 필요한 사항만 확인하고 임의의 값으로 실행하지 않는다.
- 승인된 값과 실제 확인된 계정·대상·연결로만 실행한다.
- 정상 완료와 오류 중단, 확인된 결과와 미확인 결과를 구분하고 근거를 제공한다.
