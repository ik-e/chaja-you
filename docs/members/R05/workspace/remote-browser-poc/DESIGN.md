# 원격 브라우저 기반 인증 및 서버 실행 검증 — 최소 설계

- 작성: R05 임다혁 · 2026-11-24
- 범위: 자체 모의 사이트 + 가상 계정. 실제 크몽·숨고 계정과 사이트는 사용하지 않음.
- 기존 팀원 구현 코드와 공통 루트 의존성은 변경하지 않음. 이 폴더 안에서만 의존성을 관리함.

## 1. 구조

```
[사용자 웹 브라우저]                         [서버]
 뷰어 페이지(canvas)  ── WebSocket ──▶  제어 서버 (FastAPI)
   ▲ JPEG 프레임                           │  세션마다 BrowserContext 1개
   │                                       │  (쿠키·저장소 분리)
   └──── 마우스·키보드 이벤트 ─────────────▶│  Chrome (headless, 서버 1개 프로세스)
                                           │       │
 등록 내용 맡기기(REST) ────────────────────▶│  서버 작업(asyncio Task)
                                           │       ▼
                                           └──▶ 모의 레슨 사이트 (FastAPI, 가상 계정)
```

| 구성 요소 | 파일 | 역할 |
| --- | --- | --- |
| 모의 사이트 | `mock_site/app.py` | 가상 계정 로그인, 인증된 레슨 등록 폼(제목·설명·가격·이미지), 저장, 결과 페이지, 시험용 통계 |
| 제어 서버 | `control_server/app.py` | 세션 생성·조회·종료, 화면 중계, 입력 중계, 제어권 관리, 서버 등록 작업, 감사 로그 |
| 뷰어 | `control_server/viewer.html` | 원격 화면 표시, 마우스·키보드 전달, 작업 맡기기·제어권 회수·세션 종료 버튼 |
| 시험 | `tests/test_remote_browser.py` | 사용자 브라우저를 따로 띄워 뷰어를 조작하는 종단 시험 T01–T11 |

## 2. 흐름

1. 사용자가 `POST /api/sessions`로 세션을 만든다. 서버는 BrowserContext를 새로 열고 모의 사이트 로그인 화면으로 이동한다. 응답은 세션 ID와 세션 토큰이다.
2. 사용자는 `/view/{세션}#t={토큰}`을 연다. 토큰은 URL 해시로 전달되어 서버 접속 로그에 남지 않고, 페이지가 읽은 뒤 주소창에서 지운다. WebSocket은 연결 직후 첫 메시지로 토큰을 보내 인증한다.
3. 서버는 CDP `Page.startScreencast`로 받은 JPEG 프레임을 뷰어에 보낸다. 뷰어의 마우스·키보드 이벤트는 Playwright `mouse`·`keyboard`로 원격 브라우저에 재생된다.
4. 사용자가 원격 화면에서 가상 계정으로 직접 로그인한다. 서버 프로그램은 아이디·비밀번호를 받지 않는다.
5. 사용자가 등록 내용을 `POST /api/sessions/{id}/handoff`로 맡긴다. 제어권이 `server`로 바뀌고, 같은 BrowserContext(같은 쿠키)로 서버 작업이 실행된다.
6. 서버 작업은 WebSocket과 무관한 asyncio Task라서, 사용자가 뷰어를 닫아도 계속 실행된다.
7. 작업은 폼 열기 → 텍스트 입력 → 이미지 첨부(메모리 버퍼) → 저장 → 결과 페이지 값 검증 순서로 진행된다. 끝나면 제어권은 자동으로 사용자에게 돌아간다.
8. `DELETE /api/sessions/{id}`나 유휴 시간 초과가 발생하면 BrowserContext를 닫는다. 이때 쿠키도 메모리에서 함께 폐기된다.

## 3. 결과 판정

팀 공통 모의 계약의 상태 이름에 맞췄다.

| 상태 | 조건 |
| --- | --- |
| `mock_success` | 결과 페이지의 제목·설명·가격·이미지 SHA-256이 요청 값과 모두 같음 |
| `needs_confirmation` | 저장은 됐으나 값이 다름 |
| `failed` | 사이트가 오류를 표시했거나, 제출 전에 예외가 발생함 |
| `unknown` | 제출 후 결과를 확인하지 못함(타임아웃·중단). 중복 제출 위험이 있어 재시도하지 않음 |
| `needs_login` | 인증되지 않은 세션. 서버는 재로그인을 시도하지 않음 |
| `cancelled` | 제출 전에 사용자가 제어권을 회수함 |

## 4. 기술 선택 근거

| 선택 | 이유 | 대안과 비교 |
| --- | --- | --- |
| Chrome + Playwright | 사용자 조작과 서버 자동화를 같은 브라우저 객체로 다룰 수 있음. 팀이 이미 검토한 도구임 | Selenium은 CDP 화면 중계를 별도로 붙여야 함 |
| 화면 중계: CDP `Page.startScreencast` | X 서버·VNC 없이 Chrome만으로 페이지 화면을 프레임으로 받을 수 있음. 이 검증 환경에는 Docker 데몬이 없어 Xvfb+x11vnc+noVNC 컨테이너 구성을 실행할 수 없었음 | noVNC는 바탕화면 전체(브라우저 UI·파일 선택창 포함)를 보여 줄 수 있어 더 범용적이지만, Xvfb·x11vnc·websockify와 컨테이너 운영이 필요함 |
| 세션 격리: 세션마다 BrowserContext | 쿠키·로컬 저장소가 분리되고 생성 비용이 낮음 | 컨테이너(또는 브라우저 프로세스) 1개씩 쓰면 격리 수준은 높지만 자원 비용이 큼 |
| 서버: FastAPI + WebSocket | 비동기 Playwright와 같은 이벤트 루프에서 동작함 | — |
| 이미지 첨부: 메모리 버퍼 | 서버 디스크에 사용자 파일을 남기지 않음 | 임시 파일 방식은 삭제 누락 위험이 있음 |

## 5. 보안·민감정보 처리

- 비밀번호는 사용자가 원격 화면에 직접 입력한다. 제어 서버 API로는 전달되지 않는다.
- 감사 로그에는 이벤트 종류만 남긴다. 키보드 입력은 건마다 기록하면 비밀번호 길이가 드러나서 기록하지 않는다. 시험 첫 실행에서 이 문제를 발견해 고쳤다.
- 세션 토큰은 URL 해시와 WebSocket 첫 메시지, `X-Session-Token` 헤더로만 오간다. 접속 로그(access log)는 끈다.
- 상태 API는 경로(쿼리 제외)·제어 주체·작업 결과만 돌려주고, 쿠키는 내보내지 않는다. `storage_state`도 파일로 저장하지 않는다.
- 증거 스크린샷은 서버 작업의 결과 페이지만 찍는다. 화면 프레임은 마지막 1장만 메모리에 두고 세션 종료 때 지운다.

## 6. 알려진 제약

- **격리 수준:** 세션들이 Chrome 프로세스 하나를 공유한다. 쿠키·저장소는 분리되지만, 브라우저 취약점이 있으면 세션끼리 영향을 줄 수 있다. 운영 단계라면 사용자별 컨테이너가 필요하다.
- **화면 범위:** 화면 중계는 페이지 영역만 보여 준다. 파일 선택창, 인증서 경고, 브라우저 메뉴 같은 페이지 밖 UI는 보이지 않는다. 그래서 이미지는 원격 파일 선택창 대신 맡기기 API로 전달한다.
- **한글 입력:** 한글 조합 입력(IME)은 키 이벤트로 재생되지 않는다. 뷰어는 붙여넣기로 대체한다.
- **실제 플랫폼 적용 시 위험(미검증):**
  - 서버 IP에서 로그인하면 새 기기 인증이나 보안 알림이 뜰 수 있다.
  - headless 브라우저 탐지, CAPTCHA·2단계 인증, 세션 만료 정책이 걸릴 수 있다.
  - 플랫폼 약관상 자동 등록 금지 조항이 있다. 크몽은 운영사 문의 중이고, 탈잉 약관에도 같은 조항이 있다.
- **확장성:** 동시 사용자 수에 따른 메모리·CPU 부하는 측정하지 않았다. 지금은 세션 1–3개만 시험했다.
