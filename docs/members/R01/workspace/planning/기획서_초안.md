## 2. 배경과 문제 정의

앱을 고를 때 사용자는 앱스토어·검색엔진·리뷰·개발사 페이지 등 여러 곳을 오가며 조건에 맞는 후보를 찾고, 각 앱의 기능·광고·가격·지원 환경을 비교해야 한다. 검색 상위나 유명 앱 중심으로 살펴보면 조건에 더 잘 맞는 덜 알려진 대안을 놓칠 수 있다. 이전에 확인한 출처와 선호 조건이 다음 조사에 이어지지 않으면 비슷한 탐색을 되풀이하게 된다.

기존 AI 검색과 리서치 도구도 웹 검색·요약·인용 기능을 제공하므로, “AI가 여러 에이전트를 쓰고 링크를 붙인다”만으로 차별성을 주장하지 않는다. 본 프로젝트는 앱 찾기를 첫 도메인으로 삼아 사용자의 성향과 탐색 의도에 맞는 출처 경로를 구성하고, 주장별 근거와 검토된 경험을 기억해 다음 조사에 참고하는 시스템을 구현·평가한다.

**문제 가설:** 앱 선택을 위한 온라인 조사는 여러 출처를 찾아 조건을 비교하고 정보의 근거와 최신성을 확인하는 수작업을 요구한다. 익숙한 선택지만 반복 확인하거나 과거 조사 맥락을 재사용하기 어려운 상황이 있는지 사용자 과제와 시험으로 확인한다.

**해결 가설:** 도메인 출처 지도, 앱 개념 관계, 확인된 사용자 성향과 승인된 조사 기억을 검색 계획에 활용하면, 익숙한 후보 비교와 새로운 대안 발굴을 더 설명 가능하게 지원할 수 있다.

두 가설은 아직 사용자 조사로 검증된 사실이 아니다. 기획서·발표에서는 검증 전까지 가설로 표시한다.

## 3. 목표와 완료 기준

### 3.1 목표

1. 사용자 요청을 이해하고 필요한 조건을 확인한 뒤 조사 계획을 세운다.
2. 익숙한 대상·출처를 중심으로 앱을 찾는 모드와, 낯선 대안까지 탐색하는 모드를 제공한다.
3. 도메인별 출처 경로와 앱 개념을 구조화한 인터넷 지도를 조사 계획·검색에 활용한다.
4. 사용자가 확인·수정할 수 있는 성향 정보와 출처가 연결된 과거 조사 기억을 후속 조사에 참고한다.
5. 앱 후보와 핵심 비교 주장을 근거 출처와 함께 제시하고, 미확인·오래된 정보·충돌을 드러낸다.
6. 기능별 기준선과 비교해 조사 품질·시간·검색량에 미치는 영향을 확인한다.

### 3.2 완료 기준 초안

- 입력한 앱 탐색 요청이 조건 확인 → 모드 선택 → 계획 → 조사 → 근거 확인 → 비교 결과까지 이어지는 시연 가능한 흐름으로 동작한다.
- 익숙한 탐색과 새로운 방향 탐색의 목적·검색 전략·결과 구분이 UI에서 드러난다.
- 결과의 앱별 핵심 정보에 출처 링크와 확인 시점이 연결되고, 확인하지 못한 속성은 미확인으로 표시된다.
- 사용자는 개인 성향 정보를 확인·수정·삭제할 수 있고, 시스템은 어떤 성향이 추천·정렬에 사용됐는지 설명한다.
- 인터넷 지도, 최소 앱 온톨로지, RAG 기억이 하나씩 실제 흐름에 연결된다. 기능이 단순 저장에만 머물면 완료로 보지 않고 해당 데이터가 검색/계획/설명에 쓰이는 것을 확인한다.
- 검토 세트의 결과와 실패 사례, 품질·시간·검색량 비교, 알려진 제한과 후속 조치가 문서로 남는다.
- 핵심 기능이 작동하고 시험 기록 및 서비스 준비 판단을 남기면 프로젝트 완료 기준을 충족한다([팀 헌장](../../../../charter/팀_헌장.md)).

수치형 품질 목표와 표본 수는 1주 PoC에서 기준선을 측정한 뒤 팀이 정한다. 사전에 근거 없는 정확도 수치를 약속하지 않는다.

## 4. 대상 사용자와 주요 사용 상황

### 4.1 대상 사용자 초안

앱을 선택해야 하지만 앱스토어의 검색 순위만으로는 자신의 조건에 맞는 앱을 고르기 어렵고, 여러 출처를 직접 비교할 시간이나 조사 방법이 부족한 사용자다. 실제 대상 사용자와 문제 빈도는 인터뷰 또는 사용 과제로 확인한다.

### 4.2 사용 시나리오

**시나리오 A — 익숙한 방향에서 찾기**

> “안드로이드에서 쓸 가계부 앱을 비교하고 싶어. 무료이고 자동 입력이 되는 앱 위주로, 알려진 앱부터 확인해줘.”

사용자는 알고 있는 카테고리나 앱·출처를 중심으로 검색한다. 시스템은 요청을 구조화하고, 익숙한 출처 지도와 후보를 이용해 비교한 뒤 핵심 조건을 뒷받침하는 출처를 붙인다.

**시나리오 B — 새로운 방향에서 찾기**

> “복잡한 기능보다 기록이 간단한 앱이 필요해. 유명하지 않아도 괜찮으니 다른 선택지도 찾아줘.”

사용자는 앱 이름이나 익숙한 검색어보다 해결하고 싶은 목적·제약을 중심으로 요청한다. 시스템은 온톨로지의 관련 개념·동의어와 지도에 등록된 출처를 활용하고, 일반 검색으로 지도 밖의 후보도 탐색해 덜 알려진 대안을 포함한다. ‘새로운’은 시스템의 검색 결과와 출처 범위에서 기존 상위 후보 외에 추가로 발굴한 후보를 뜻하며, 시장의 모든 앱을 찾았다고 보장하지 않는다.

## 5. 서비스 흐름

```text
사용자 요청
  → 앱 탐색 모드 선택 또는 추천
  → 목적·조건 구조화, 부족한 조건 질문
  → 사용자가 조사 계획 확인/수정
  → 인터넷 지도 + 온톨로지 + 허용된 사용자 성향/기억 검색
  → 익숙한 경로 또는 새로운 방향 검색 수행
  → 앱 후보와 근거 자료 수집·정규화
  → 주요 주장·출처 연결 및 최신성/상충 확인
  → 조건별 비교, 개인화 이유와 한계 설명
  → 사용자가 결과/성향 정보를 수정·평가
  → 검토가 필요한 기억만 승인 후 재사용 후보로 저장
```

상위 오케스트레이터가 흐름과 상한을 관리한다. 논리 역할은 요청·계획, 검색·출처 수집, 근거 검증·결과 통합으로 제한하며 모든 단계를 독립 LLM 에이전트로 만들 필요는 없다. 시작은 작은 결정적 흐름으로 두고, 중단·분기·재개 이점이 확인되면 LangGraph 등 워크플로 도구를 비교한다([기술 방향 조사](기술_방향_6AI_협의_종합.md)).

## 6. 두 가지 검색 모드

| 구분 | 익숙한 것 찾기 | 새로운 방향 탐색 |
|---|---|---|
| 사용자의 시작점 | 알고 있는 앱·카테고리·출처·조건 | 해결할 목적·선호·제약 또는 기존 선택에 없는 요구 |
| 탐색 전략 | 등록된 주요 출처와 알려진 후보를 빠르게 확인·비교 | 검색어·동의어·연관 개념을 넓히고 출처 지도 밖 후보도 탐색 |
| 온톨로지 사용 | 후보와 비교 속성을 같은 분류로 정규화 | 인접 카테고리·기능·동의어로 새로운 검색 경로 생성 |
| 결과 표현 | 알려진 후보의 조건별 비교와 근거 | 추가로 발견한 후보, 발견 경로와 적합성 이유, 검색 범위 한계 |
| 주요 위험 | 인기·기존 목록에 편중, 최신 정보 누락 | 무관한 후보 증가, 새로움 과장, 더 넓은 검색에 따른 비용·시간 증가 |
| 평가 질문 | 알려진 조건의 핵심 정보를 빠르고 근거 있게 비교하는가? | 널리 알려진 후보 외에 조건에 맞는 새 후보를 근거와 함께 발견하는가? |

사용자가 직접 모드를 고를 수 있게 하는 것이 초안이다. 요청이 분명하면 시스템이 모드를 추천할 수 있으나, 사용자의 선택 없이 더 넓은 검색으로 전환하는 동작은 확인을 받도록 설계한다.

## 7. 차별화 방향과 기억 구성

차별화는 각각의 기술 이름보다 **사용자의 익숙한 탐색과 새로운 탐색에 지식이 실제로 이어지는 구조**에 둔다.

### 7.1 인터넷 지도 — 도메인 출처 카탈로그

인터넷 지도는 웹 전체의 복제본이나 완전한 그래프가 아니라, 앱 정보를 찾고 검증하는 데 도움이 되는 출처·경로 카탈로그다.

- 출처 이름/도메인, 유형(앱스토어·개발사 공식 페이지·공식 도움말 등), 언어, 주요 제공 정보
- 관련 앱 카테고리와 기능/정보 유형
- 접근 방식, 검색 가능한 조건, 공개 접근 여부, 이용 조건 확인 상태
- 최종 확인 시각, 갱신 주기 메모, 검색 성공/실패 기록
- 해당 출처를 쓰는 이유 및 연결된 주장/조사 기록

익숙한 모드는 등록 출처의 빠른 경로를 우선 활용한다. 새로운 방향 모드는 등록 출처를 쓰되 일반 검색도 열어 두며, 새 출처를 자동으로 신뢰하거나 지도 기준 정보로 승격하지 않는다. 사람이 출처와 이용 조건을 확인한 뒤 지도에 반영한다.

### 7.2 사용자 성향 기억 — 사용자 통제형

사용자 성향에는 우선 앱 선택과 직접 관계되는 선호만 담는다. 예: 광고 허용 여부, 무료/유료 선호, 단순함과 기능성 중 우선순위, 플랫폼, 개인정보 권한 민감도.

- 현재 요청에만 적용하는 조건과 장기 선호를 분리한다.
- 대화에서 추출한 장기 선호는 확정된 사용자 사실처럼 저장하지 않고 확인받는다.
- 사용자가 확인·수정·삭제할 수 있고, 결과 화면에 어떤 선호가 사용됐는지 보여준다.
- 타인의 대화 기록이나 원본 대화 내보내기는 MVP에서 자동 가져오지 않는다. 필요하면 사용자가 제공한 프로필을 직접 검토·입력하는 방안을 먼저 평가한다.
- 사용자 성향 데이터는 공개 도메인 출처 지도 및 팀 공용 조사 기억과 분리한다.

### 7.3 RAG — 출처가 붙은 조사 기억의 검색·재사용

RAG는 저장된 문장을 정답처럼 복사하는 기능이 아니라 현재 조사에 맞는 출처 메타정보, 승인된 과거 조사 계획·주의사항을 찾아 참고하는 기능으로 정의한다.

- 실행 기록: 요청, 모드, 계획, 검색어, 출처, 주장·근거 연결, 도구 상태, 실패, 날짜
- 승인된 경험: 재사용 가능한 조사 순서, 효과가 확인된 출처 경로, 실패 회피법, 검토일·적용 조건
- 검색결과/앱의 변동 정보(가격, 기능, 지원 버전, 평점 등)는 오래된 기억만으로 답하지 않고 현재 출처를 다시 확인한다.
- 과거 결과를 참고했는지와 최신 출처로 다시 검증했는지 결과에 구분해 표시한다.
- 관련성 낮거나 오래된 기억은 제외하고, 만료·정정·폐기할 수 있도록 한다.

### 7.4 온톨로지 — 작은 앱 도메인 개념 지도

온톨로지는 MVP에 포함하되, 범용 지식 그래프가 아니라 검색과 비교에 직접 쓰는 작은 검토 가능한 개념·관계 집합으로 제한한다.

- 개념 예시: 앱 카테고리, 앱, 기능, 운영체제, 가격 유형, 광고/추적 특성, 사용자 조건, 정보 출처
- 관계 예시: `앱은 카테고리에 속함`, `앱이 기능을 지원함`, `앱이 플랫폼에서 동작함`, `출처가 속성을 확인함`, `카테고리가 다른 카테고리와 관련됨`
- 용어·동의어, 상위/하위 범주, 비교 속성을 사람이 검토해 관리한다.
- 새 방향 탐색의 검색어 확장과 후보 정규화, 결과 비교에 실제 사용한다.
- 자동 추론·대규모 지식 그래프 저장소·완전한 도메인 모델은 이번 범위에서 제외한다. 단순 관계 테이블/JSON 등 구현 방식은 기술 PoC 뒤 결정한다.

### 7.5 기억 계층과 권한

| 기억 종류 | 내용 | 공유 범위 | 기본 갱신 방식 |
|---|---|---|---|
| 인터넷 지도 | 공개 출처·접근 경로·갱신 정보 | 프로젝트 공용 | 출처 담당자가 확인 후 수정 |
| 앱 온톨로지 | 앱 분류·속성·기능·관계 | 프로젝트 공용 | 검토된 용어/관계만 추가 |
| 사용자 성향 | 사용자가 확인한 개인 선호 | 해당 사용자 | 사용자 편집·삭제, 추출값은 확인 후 저장 |
| 조사 실행/RAG 기억 | 출처와 연결된 조사 기록·승인 경험 | 공개 가능한 도메인 조사와 개인 조사 분리 | 초안 기록 → 검토 → 승인/만료/폐기 |

개인 선호를 팀 공용 경험에 넣지 않는다. 개인 기록이 외부 모델·검색 API로 전송될 수 있는 경우 데이터 최소화와 사용자 통제를 별도로 적용한다.

## 8. 기능 요구사항 초안

모든 요구사항은 기획 초안이며, 범위 결정 회의와 1주 PoC 결과에 따라 조정한다.

| ID | 우선순위 | 요구사항 | 초안 수용 기준 |
|---|---|---|---|
| FR-01 | Must | 앱 탐색 요청과 모드를 받는다. | 익숙한 탐색/새로운 방향 중 모드를 표시하고, 요청의 조건·목적을 확인할 수 있다. |
| FR-02 | Must | 부족한 조건을 질문하고 조사 계획을 구성한다. | 조사 전 하위 작업/출처 경로를 사용자에게 제시하며 수정 또는 시작을 선택할 수 있다. |
| FR-03 | Must | 인터넷 지도 출처를 검색 계획에 활용한다. | 시험 요청에서 어떤 출처를 선택했는지 출처 유형/선정 이유가 실행 기록에 남는다. |
| FR-04 | Must | 두 탐색 모드별 검색 전략을 실행한다. | 익숙한 모드는 등록 출처/후보 비교를 우선하고, 새 방향 모드는 연관 개념 및 지도 밖 검색을 시도한 흔적을 남긴다. |
| FR-05 | Must | 앱 온톨로지의 기본 분류·관계를 사용한다. | 앱 후보와 비교 속성을 공통 개념으로 정규화하고, 새 방향 모드에서 적어도 하나의 연관 개념/동의어 경로를 활용한다. |
| FR-06 | Must | 결과를 주장·근거·출처로 연결한다. | 핵심 속성별 출처 링크/확인 시각을 보여주고, 미확인은 미확인으로 표시한다. |
| FR-07 | Must | 개인 성향을 사용자가 관리한다. | 성향 보기·수정·삭제가 가능하며, 결과에 사용된 선호와 영향을 설명한다. |
| FR-08 | Must | RAG로 출처가 연결된 경험을 검색한다. | 기록의 출처·검토 상태·날짜를 함께 반환하고, 미승인 경험은 승인된 지식처럼 제시하지 않는다. |
| FR-09 | Must | 변동 정보의 현재성을 확인한다. | 가격·기능 등 변경 가능한 속성은 현재 출처를 재조회하거나 오래된 값으로 표시한다. |
| FR-10 | Must | 검색 실패·충돌·근거 부족을 표시한다. | 일부 자료 접근 실패나 근거 부족 상황에서 이를 숨기지 않고 결과의 한계로 출력한다. |
| FR-11 | Should | 결과에 사용자 평가를 받아 개선 자료로 남긴다. | 피드백이 선호 프로필 또는 승인 대기 경험 중 어디에 반영되는지 사용자에게 표시한다. |
| FR-12 | Could | 지도 밖 신규 출처를 발견해 등록 후보로 제안한다. | 자동 승격은 하지 않고, 검토 대기 목록에 출처와 발견 근거를 남긴다. |

### 8.1 비기능 요구사항 초안

- **근거성:** 앱의 핵심 비교 주장마다 출처와 확인 시각을 추적할 수 있어야 한다.
- **개인정보 통제:** 사용자가 개인 성향을 조회·수정·삭제할 수 있어야 하며, 비밀값·개인식별 정보를 검색 질의나 로그에 포함하지 않는다.
- **범위 통제:** 검색, 외부 호출, 하위 작업, 재시도에 팀이 정한 상한을 둔다. 한도 초과는 명시적인 부분 결과로 끝낸다.
- **최신성:** 현재 상태가 중요한 앱 정보는 기록 시점과 재확인 여부를 보여준다.
- **설명 가능성:** 검색 모드, 선택된 출처 경로, 개인화 이유, 기억 사용 여부를 결과에서 확인할 수 있어야 한다.
- **복구 가능성:** 실행 상태와 오류를 기록해 최소한 실패 원인과 미완료 작업을 확인할 수 있어야 한다.
- **접근·이용 준수:** 데이터 원천별 접근 조건과 API 공급자 약관을 확인하고, 저장·재배포 가능한 범위를 지킨다.

## 9. MVP 범위

### 포함 범위

- 첫 도메인: 앱 탐색·비교, 시작 카테고리와 대표 과제는 팀이 우선 선정
- 익숙한 탐색과 새로운 방향 탐색 두 모드
- 요청 조건 확인, 제한된 계획·조사·검증 흐름
- 앱 탐색용 출처 지도 시드와 사람이 관리하는 최소 개념·관계
- 사용자가 확인·수정·삭제하는 소수의 개인 선호
- 출처가 연결된 조사 실행 기록 및 승인된 과거 경험을 검색하는 초기 RAG
- 앱별 핵심 비교 항목, 근거 링크, 확인 시각, 미확인/충돌 표시
- 한 가지 시연 가능한 UI와 기준 과제 평가

### 제외 또는 후순위

- 모든 도메인을 처음부터 지원하거나 인터넷 전체를 크롤링하는 기능
- 앱 설치·구매·로그인 대행, 비공개/유료 정보 수집
- 검색 순위와 시장 전체를 완전하게 파악한다고 주장하는 기능
- 검토 없이 개인 대화 전체를 불러와 장기 보관하는 기능
- 승인 없이 과거 기억을 최신 사실처럼 재사용하는 기능
- 자동 온톨로지 생성/대규모 추론, 전체 지식그래프 구축
- 근거 없는 사용자 성향 추론의 자동 저장
- 상시 자율 에이전트 증식·무제한 토론·무제한 웹 탐색
- 평가 없이 다른 도메인까지 확장

## 10. 기술 방향과 검증 계획

### 10.1 기술 선택 원칙

현재까지의 조사로 최종 기술 스택이 결정되지는 않았다. 다음 기본안을 1주 PoC에서 비교한다.

- 워크플로: 순수 Python 기준 흐름과 LangGraph 동일 흐름 비교, 한 가지만 채택
- 검색·추출: 검색 API 후보와 직접 추출/관리형 추출을 실제 앱 출처로 분리 비교
- 데이터: 관계형 정본. SQLite/FTS5로 시작할지 PostgreSQL로 갈지는 동시 사용·배포 조건을 확인한 뒤 결정
- RAG 검색: 구조화 메타데이터 + 키워드 검색을 먼저 검증하고, 임베딩 검색은 필요성이 보일 때만 비교
- 온톨로지: 작은 수작업 분류/관계 데이터로 시작, 특수 그래프 DB는 PoC에서 채택 필요가 확인될 때 검토
- 모델/API: 공식 가격·호출 상한·데이터 처리 조건을 확인하고 팀이 사용할 공급자·예산을 정한 뒤 실험

### 10.2 평가 설계

평가 세트는 앱 탐색 모드 각각에 대해 대표 요청을 만들고, 익숙한 앱 비교·조건 불충족·새 후보 탐색·상충/미확인 정보를 포함한다. 기준 정보와 필수 근거를 실행 전에 작성한다. 최종 과제와 표본 수는 1주 PoC에서 고정한다([PoC 설계](PoC_선행조사_4AI_종합.md)).

| 비교 | 확인할 질문 |
|---|---|
| 인터넷 지도 없음/있음 | 지도 사용이 관련 출처를 더 빨리 찾거나 출처 누락을 줄이는가? 지도 관리 비용은 얼마인가? |
| 개인 성향 없음/사용 | 성향이 결과 정렬과 이유에 실제 영향을 주며 사용자가 결과를 수정할 수 있는가? |
| 익숙한 모드/새로운 방향 모드 | 검색 경로·후보 구성이 다르고 각각의 목적에 맞는 결과를 내는가? |
| 기억/RAG 없음/승인 경험 제공 | 출처가 연결된 경험이 품질을 낮추지 않으면서 검색량·시간을 줄이거나 결과를 개선하는가? |
| 온톨로지 미사용/최소 온톨로지 사용 | 관계·동의어가 새로운 후보 탐색 또는 속성 정규화에 실질적으로 기여하는가? |
| Python 흐름/LangGraph | 상태·분기·재개가 팀의 구현·오류 처리에 주는 실제 이득이 있는가? |

**공통 측정:** 핵심 주장 근거 커버리지, 인용과 실제 페이지 정보의 일치, 관련 후보 비율, 유효 근거까지 걸린 시간, 검색/페이지 수, 오류·접근 실패, API 비용, 개인화 이유의 적절성, 새 후보의 조건 부합률, 기억의 유용/무관/오류 사례.

작은 비교 실험 결과는 MVP 기술·제품 방향 결정에만 사용한다. 통계적 우월성이나 시장 전체 성능을 증명했다고 표현하지 않는다. 효과가 없거나 운영 부담이 큰 기능은 저장·기록 기능만 남기고 자동화 수준을 낮춘다.

| 오래된 기억/출처가 잘못 재사용됨 | 부정확한 앱 비교 | 정보 시점·검토 상태·만료를 기록하고 변동 속성은 현재 출처 재확인 |
| 온톨로지 설계가 과도하거나 분류가 부정확함 | 개발 지연·검색 누락 | 앱 비교에 필요한 핵심 속성과 관계만 수작업 정의하고, 사용/미사용 비교로 효용 판단 |
| RAG가 과거 내용이나 검색 문구의 지시를 신뢰 | 환각·잘못된 동작 | 과거 자료는 참고 데이터로 취급, 출처 검증과 현재 정보 재조회, 명시된 실행 흐름·도구 권한 제한 |
| 검색/LLM API의 데이터 보존·비용 조건 불명확 | 민감 정보 노출·예산 초과 | 일반화된 공개 질의만 전송, 개인·비공개 값 제외, 선택 요금제의 약관·비용 확인, 요청 상한 적용 |
| 프레임워크/에이전트 역할이 늘어 통합 복잡도 증가 | 일정 지연 및 장애 증가 | 역할을 논리적으로 고정하고 단계별 통합, 동일 기준 PoC로 프레임워크 선택 |
| 시연 데이터가 실제 사용자 수요를 대표하지 않음 | 가치·차별성 과장 | 실제 과제 테스트/피드백을 기록하고, 사용성 관찰을 시장 수요 근거로 일반화하지 않음 |

## 12. 8주 일정 제안

공식 가이드의 제출 일정이 우선이다. 11월 13일 기획서(요구사항 포함)와 WBS 제출은 확인된 첫 마감이며, 아래 주별 구현 일정은 팀 확인이 필요한 초안이다([최종 프로젝트 가이드](../../../../guidelines/README.md)).

| 기간(제안) | 초점 | 완료 산출물 |
|---|---|---|
| 11/10~11/13 | 비전·사용자 문제·요구사항·MVP/WBS 초안 | 기획서 및 WBS 1차 제출본 |
| 11/16~11/20 | 앱 시연 범위, 데이터 원천, 공통 스키마와 기술 PoC | 대표 과제, 출처 시드, 실행 가능한 기준 흐름 |
| 11/23~11/27 | 익숙한 앱 탐색 수직 슬라이스 | 요청부터 근거 연결 비교까지 end-to-end 동작 |
| 11/30~12/04 | 새로운 방향 탐색과 최소 온톨로지 | 연관 개념 검색과 새 후보 발견 경로 시연 |
| 12/07~12/11 | 사용자 성향 입력·편집·삭제와 개인화 | 동의 기반 프로필 및 설명 가능한 결과 정렬 |
| 12/14~12/18 | 출처 지도·승인 경험 RAG 연결 | 출처/기억 검색, 최신 정보 재확인, 갱신 흐름 |
| 12/21~12/25 | 통합·품질·오류 처리·사용자 과제 평가 | 핵심 요구사항 평가표, 오류/리스크 조치 기록 |
| 12/28~01/04 | 배포·QA·시연·제출 마무리 | 서비스 가능성 판단, 최종 문서·발표·제출물 |

기간 중 교육 일정과 공식 마감에 맞춰 조정한다. 일정 변경은 영향을 받는 작업과 줄이거나 미룰 범위를 함께 기록한다([팀 헌장](../../../../charter/팀_헌장.md)).

## 13. 역할별 산출물 제안

기존 팀 역할을 기준으로 한 WBS 분해용 제안이다. 세부 작업·담당·기한은 팀이 WBS에서 확정한다.

| 역할 | 기획안/WBS에 연결할 산출물 제안 |
|---|---|
| R01 팀장·통합·배포·QA | 요구사항·완료 기준 통합, 주간 범위 조정, 통합 시나리오·QA 및 최종 준비 판단 |
| R02 인프라 | 실행·배포 환경, 데이터 저장/백업·보안 조건, 환경 설정 가이드 |
| R03 에이전트 | 요청 구조화·모드 선택·계획·검색/검증 역할, 프롬프트 및 오케스트레이션 |
| R04 프론트엔드 | 모드 선택, 조건 확인, 계획 확인, 개인 성향 관리, 비교·근거 표시 UI |
| R05 백엔드 | 검색·추출 어댑터, 출처 지도·온톨로지·기억 저장/조회, 결과 API |

## 14. 팀에서 확인할 결정 목록

1. **대표 사용자와 앱 범위:** 첫 시연에서 다룰 카테고리와 사용자 문제는 무엇인가?
2. **두 모드의 경계:** “익숙한 것”의 기준을 알려진 앱 목록, 등록 출처, 사용자의 익숙함 중 무엇으로 정할까? “새로운 방향”에서 어느 정도 검색 확장을 허용할까?
3. **인터넷 지도 범위:** 어떤 출처를 초기 등록하고, 지도 밖 신규 출처를 어떤 절차로 검토할까?
4. **사용자 성향 정보:** 어떤 항목만 수집하며 저장 전 확인·수정·삭제는 어떻게 제공할까?
5. **기억/RAG:** 어떤 기록을 승인된 경험으로 올리고, 최신 정보를 언제 다시 확인할까?
6. **온톨로지 최소 범위:** 앱 카테고리·기능·플랫폼·가격 외 어떤 개념과 관계가 첫 시연에 필요할까?
7. **기술·데이터 조건:** 언어, 모델/API, 검색·추출 서비스, 저장 방식, 비용·호출 상한은 무엇인가?
8. **수용 기준:** 기준 과제와 품질·효율 지표를 무엇으로 고정할까?
