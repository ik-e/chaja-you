# 기존 기술 재사용 심화 조사

- 조사일: 2026-11-11
- 목적: `chaja-you`의 8주 MVP에서 에이전트 구성·워크플로·검색·기억을 직접 발명하지 않고 기존 기술로 조합하는 방안을 검토한다.
- 상태: 기술 조사와 후보 권고안. 팀의 확정 스택이나 승인된 제품 설계가 아니다.
- 프로젝트 맥락: 5명, 2026-11-10~2027-01-04. 사용자 목적과 도메인에 맞는 공개 웹 조사를 수행하고, 출처 메타정보와 검토된 조사 경험을 다음 작업에 활용하는 시스템을 구상 중이다.

## 1. 조사 범위와 AI 자문 진행 상태

이번 후속 자문은 기술 영역을 나눠 요청했다. 현재 6개 중 5개 후속 응답을 회수했다. Grok은 이전 조사 차수의 답변은 있지만 이번 질문 답변은 받지 못했다.

| AI | 담당 영역 | 결과 |
|---|---|---|
| Claude | 검색부터 근거 검증·승인 저장까지 통합 구성, 교체 가능한 모듈 경계, 보안 | 응답 완료 |
| Perplexity | 출처 메타정보, RAG·기억 유형, 갱신·삭제·계보 | 응답 완료 |
| DeepSeek | 프레임워크와 직접 구현 경계, 후보 구성 | 응답 완료. 일부 비교·가격 주장은 원문 검증 필요 |
| Gemini | 세션·체크포인트·SQL·벡터 검색·기억 제품 비교 | 응답 완료. 일부 내용은 비공식 2차 출처에 의존하므로 공식 근거를 추가 확인해야 함 |
| ChatGPT | LangGraph·OpenAI Agents SDK·CrewAI 비교 | 응답 완료. 세 후보 모두 승인·재개 기능이 있으며 비교 기준을 고쳐야 한다고 지적 |
| Grok | 통합·시간·비용 위험 레드팀 검토 | 미회수. 초안 `x`를 정리했으나, 현재 Edge 탭이 허용 도메인으로 판별되지 않아 요청/응답 확인이 차단됨. 이전 조사 차수의 Grok 의견은 별도 참고 자료 |

### 회수한 자문별 핵심 의견

- **ChatGPT — 프레임워크 비교:** LangGraph·OpenAI Agents SDK·CrewAI 모두 사람 승인/중단/재개 기능을 제공하므로 승인 기능만으로 LangGraph를 확정하면 안 된다고 지적했다. LangGraph는 상태 그래프, Agents SDK는 agent/tool/handoff, CrewAI는 역할 기반 Flow가 중심이다. 조사 실행 흐름 하나를 세 후보로 같은 방식으로 구현해 비교하라고 권고했다.
- **Claude — 통합 설계와 보안:** 검색·수집·추출·근거 검증을 교체 가능한 어댑터로 나누고, LLM 출력은 URL 대신 `evidence_id`를 쓰도록 하며 렌더러가 출처 정보를 붙이는 방안을 제안했다. 외부 웹 텍스트는 신뢰할 수 없는 데이터로 다루고, 읽기 전용 도구·인용 검증·사람 승인·호출 상한을 권고했다.
- **Perplexity — 기억과 계보:** 대화 기록, 실행 상태, 출처 메타정보, 에피소드(조사 실행), 검증된 지식, 정책/용어집을 분리하자고 했다. 벡터 검색 전 도메인·자료 유형·날짜·유효기간 필터를 적용하고, 정정·삭제·대체 이력이 파생 검색 인덱스에도 반영되어야 한다고 강조했다.
- **DeepSeek — 직접 구현 경계:** Python 가정에서 LangGraph·Pydantic·SQLite와 검색/추출 API를 조합하는 안을 권고했다. 출처 지도, 경험 승인/만료, 재사용 힌트, 주장-근거 스키마는 프레임워크가 대신해주지 않는다고 구분했다. Tavily/Firecrawl/Langfuse 등 특정 제품·가격 제안은 후보일 뿐 팀 결정으로 보지 않는다.
- **Gemini — 기억 저장소:** SQLite 구조화 테이블과 FTS5 검색으로 시작하고, 벡터 검색은 키워드 검색 실패가 확인된 뒤 추가하자는 안을 제안했다. Mem0/Letta 관련 답변 일부는 2차 자료에 의존해 이번 결론의 확정 사실로 쓰지 않았다.
- **Grok — 이전 차수 답변만 참고:** 새 후속 요청은 회수하지 못했다. 이전 위험 검토에서는 한 도메인·고정된 두 역할·중앙 흐름으로 제한하고, 기억 재사용을 무기억 기준선과 비교할 것을 제안했다. 이는 이번 프레임워크 비교 요청의 응답으로 간주하지 않는다.

AI 답변은 후보와 가설을 찾는 데 사용했다. 아래의 기술 기능은 공식 문서에서 직접 확인한 항목만 사실로 적었고, 적합성 판단은 권고 또는 추론으로 표시한다. AI들이 언급한 제품 가격, 프레임워크 간 우열, 메모리 제품의 내부 기능은 팀 의사결정 전에 해당 공식 원문에서 다시 확인해야 한다.

## 2. 핵심 결론

기존 조사에서 빠진 것은 “기술이 존재한다”는 인식이 아니라 **구체적으로 어떤 기존 제품을 조합하고, 어느 부분만 프로젝트가 구현할지 비교하는 단계**였다. 8주 MVP에서는 다음 원칙으로 보완한다.

1. 오케스트레이션 프레임워크는 하나만 선택하고, 에이전트 역할은 고정된 소수로 둔다. LangGraph를 유력 후보로 두되, 승인·재개 기능만으로 선택을 확정하지 않는다.
2. 실행 상태를 저장하는 체크포인트와, 여러 조사에 걸쳐 재사용할 프로젝트 지식을 분리한다.
3. 출처 목록·주장-근거 관계·검토 상태는 구조화 데이터로 저장한다. 벡터 DB나 온톨로지는 효용이 확인되기 전 필수가 아니다.
4. 웹 검색·본문 추출 제공자는 어댑터 뒤에 두어 교체 가능하게 만든다. 검색 API의 결과 저장 약관과 원문 이용 조건을 먼저 확인한다.
5. 시스템의 고유 가치는 에이전트 수가 아니라 도메인 출처 지도, 조사 정책, 근거 검증, 승인된 경험을 적절히 다시 쓰는 규칙에 둔다.

## 3. 프레임워크 비교에서 바로잡은 점

ChatGPT의 비교 결과를 공식 문서와 대조하면서 앞선 초안의 LangGraph 편향을 수정했다. **LangGraph만 사람 승인과 재개를 제공하는 것은 아니다.** 세 후보 모두 승인/사람 피드백 흐름을 갖고 있어, 최종 선택은 같은 조사 시나리오의 구현 시간·재개 동작·데이터 경계 비교로 해야 한다.

| 후보 | 공식 문서에서 확인한 기능 | 이 프로젝트에 대한 판단 |
|---|---|---|
| LangGraph | `interrupt`로 실행을 멈추고 체크포인터에 상태를 저장한 뒤 재개할 수 있다. 기억 문서는 thread 상태와 교차 thread 장기 store를 구분한다. | 조사 단계를 상태 그래프로 드러내고 중간 승인/분기/재시도를 조정하기 편한 후보. 저수준 그래프 구성을 과하게 세분화하지 않도록 주의한다. |
| OpenAI Agents SDK | 도구 승인 요청은 실행을 중단하고, `RunState`로 저장·직렬화한 뒤 승인/거절 후 원래 실행을 재개할 수 있다. 에이전트 handoff와 session 기록도 제공한다. | 빠르게 전문가 에이전트와 도구를 묶는 데 매력적이다. 조사 워크플로의 비즈니스 상태와 장기 지식 모델은 앱에서 별도로 설계해야 한다. |
| CrewAI | Flow는 상태·조건 분기·이벤트 흐름을 제공한다. `@human_feedback`으로 멈춰 피드백을 받고 결과에 따라 route하며, checkpointing은 실행 복구를 지원한다. | 역할 기반 협업 데모와 Flow를 한 생태계 안에서 구성할 후보. memory/checkpoint 기능이 있다는 사실만으로 검증된 조사 경험이 자동 관리되는 것은 아니다. |
| AG2 1.x `dynamic_agent()` | 호출 에이전트가 작업별 임시 하위 에이전트의 이름·지침·도구 일부를 구성한다. 자식은 새 실행 스트림에서 작업한다. | 동적으로 전문가를 구성하려는 목표와 가까운 PoC 후보. 실행 간 기억은 별도 저장·전달 설계가 필요하다. |
| AG2 Classic CaptainAgent | AutoBuild를 호출해 복잡한 작업을 하위 과제로 나누고, 전문가 그룹 대화를 시작한다. | 동적 전문가 생성의 참조 사례로 유용하다. 다만 AG2 1.x `dynamic_agent()`와 동일 기능/패키지가 아니므로 구분해 평가해야 한다. |

**선택 제안:** LangGraph는 출처 수집→근거 검증→재조사/승인→합성의 명시적 상태 흐름에 가장 잘 맞는 유력 후보지만, 이번 조사만으로 우승을 확정할 수 없다. 1주 PoC에서 같은 시나리오를 LangGraph·Agents SDK·CrewAI로 비교하되, 팀의 실제 언어·숙련도와 재개·중복 실행 방지까지 확인하고 하나만 남긴다. 세 프레임워크를 한 시스템에 결합하는 방식은 첫 수직 슬라이스 이후에도 필요성이 드러날 때만 검토한다.

**CaptainAgent 팀 조사 반영 및 보완:** 팀원이 공유한 조사에서는 CaptainAgent를 AG2 Classic의 AutoBuild 기반 전문가 생성·그룹 협업 사례로 다루고, 최신 AG2 1.x와 API를 혼용하지 말라고 경고했다. 이는 공식 문서의 구분과 일치한다. 다만 이 심화 비교의 최초 버전은 팀 자료에 있던 CaptainAgent/AG2 후보를 프레임워크 표와 PoC 범위에 포함하지 못했다. 이번 개정에서 이를 보완해 AG2 1.x `dynamic_agent()`와 AG2 Classic CaptainAgent를 별도 후보로 기록한다.

팀 조사는 **기술 후보 발굴 및 버전 구분을 위한 예비 조사로는 타당**하다. CaptainAgent가 동적으로 전문가를 구성할 수 있다는 점은 확인했지만, 우리 시스템의 웹 출처 탐색·근거 인용 검증·승인된 경험의 장기 재사용까지 해결한다는 증거는 제시하지 않았다. 따라서 CaptainAgent를 바로 채택할 근거는 아직 부족하다. 구현 판단은 같은 조사 과제를 두고 단일 에이전트 기준선, AG2 1.x `dynamic_agent()`, (필요하면) 다른 프레임워크를 동일 모델·검색 도구·호출 예산으로 비교해 검색 성공률, 출처/주장 연결 정확성, 재계획·종료 동작, 시간·비용을 측정한 뒤 내린다.

## 4. 기능별 재사용과 직접 구현의 경계

| 기능 | 재사용 후보와 확인된 기능 | 프로젝트가 직접 정할 부분 | 8주 MVP 권고 |
|---|---|---|---|
| 워크플로·상태 전이 | LangGraph는 interrupt/checkpoint, Agents SDK는 승인 중단과 직렬화 가능한 RunState 재개, CrewAI는 Flow routing·human feedback·checkpointing을 문서화한다. | 요청 정규화, 허용 도구·예산, 종료/실패 상태, 승인 후 재개 의미 | 셋 중 하나로 같은 PoC를 구현해 선택한다. 승인 기능만으로 LangGraph를 확정하지 않는다. |
| 에이전트 팀 | Agents SDK는 handoff 및 agents-as-tools 패턴을, CrewAI는 역할·Crew/Flow 구성을 제공한다. LangGraph는 역할 구성을 고정하지 않고 노드/하위 그래프로 표현한다. | 역할별 입력/출력 계약, 어떤 상황에 위임하는지, 오류 전파 방지 | 검색·근거 수집과 주장 검증·정리의 고정 역할 2개부터 구현한다. 단순한 단계는 별도 에이전트가 아니라 일반 코드로 둔다. |
| 웹 검색 | Tavily 등 검색 API가 후보이며 검색 결과 반환은 기존 서비스에 맡길 수 있다. | 공급자 어댑터, 도메인/기간 필터, API 약관과 저장 정책, 검색 예산 | 공급자 1개로 시작하되 `SearchProvider` 인터페이스를 둔다. 스니펫·결과 저장 권리는 약관 확인 전 가정하지 않는다. |
| 페이지 가져오기·본문 추출 | 로컬 파서나 호스티드 추출 API를 조합할 수 있다. 검색 API와 추출 API는 서로 다른 기능이다. | 허용 도메인, robots/약관 기록, 리다이렉트·내부망 차단, 실제 대상 페이지의 추출 품질 | 도메인을 고른 뒤 대표 페이지 15~20개로 로컬 파서와 API 후보를 비교한다. 수집 원문 전체를 저장할 수 있다고 가정하지 않는다. |
| 구조화 출력 | Pydantic 등 스키마 검증 라이브러리와 모델의 구조화 출력 기능을 재사용할 수 있다. | `Source`, `Evidence`, `Claim`, `ResearchCase` 스키마 및 유효성 규칙 | 모든 핵심 출력에 타입·필수 필드를 둔다. 출처가 없거나 인용이 검증되지 않은 주장은 확정 결과에서 분리한다. |
| 실행 상태 저장 | LangGraph checkpointer, Agents SDK RunState, CrewAI checkpointing은 각각 해당 프레임워크 실행 상태의 보존·재개 기능을 제공한다. | 보존 기간, 민감정보 제외, 재시도 시 중복 부작용 방지 | 선택한 프레임워크의 저장 구현을 우선 사용하되, 체크포인트를 장기 지식 저장소로 취급하지 않는다. |
| 출처 카탈로그·조사 이력 | SQLite 등 관계형 저장소가 출처·실행·주장·근거 간 관계 저장을 담당할 수 있다. SQLite FTS5는 전문 검색 기능을 제공한다. | 도메인 출처 목록, 출처 최신성, 주장-근거 링크, 검토/폐기/만료 규칙 | SQLite 구조화 테이블과 키워드/태그 검색부터 검증한다. 한국어 검색 적합성은 실제 용어 데이터로 확인한다. |
| 장기 기억·RAG | 프레임워크 store, 전문 검색, 벡터 인덱스 등은 저장·검색 기반을 제공한다. | 어떤 조사를 유효 경험으로 승인할지, 언제 재검증할지, 상충·삭제를 어떻게 다룰지 | 승인된 구조화 조사 사례만 “참고 힌트”로 제공한다. 벡터 검색은 FTS/태그 검색 실패 사례가 모인 뒤 추가 여부를 결정한다. |
| 추적·평가 | Langfuse는 트레이스, 데이터셋·실험, 모델/사용자 정의 평가 기능을 문서화한다. | 출처 커버리지, 주장 지지율, 미검증 비율, 비용·시간의 기준선 | 처음부터 도입하지 않아도 되며, JSONL/수동 점검으로 시작 가능하다. 추적 도구 도입 시 민감 데이터 마스킹과 보존 정책을 먼저 정한다. |

## 5. 기억은 서로 다른 네 가지 저장 대상으로 나눈다

“기억 기능”은 하나의 벡터 DB를 뜻하지 않는다. 프로젝트에서 필요한 데이터와 수명은 다르다.

| 대상 | 무엇을 저장하나 | 제안 저장 방식 | 새 조사에서의 사용 |
|---|---|---|---|
| 대화/세션 | 현재 사용자 대화의 문맥 | 프레임워크 세션 또는 짧은 대화 저장 | 같은 대화의 후속 질문에 사용. 장기 지식으로 자동 승격하지 않음 |
| 실행 체크포인트 | 현재 작업의 단계, 검색 진행 상태, 대기 중 승인 | 워크플로 프레임워크 checkpointer | 중단·오류 후 현재 실행을 이어감 |
| 출처 카탈로그 | 기관/사이트, 자료 종류, 도메인, 언어, 갱신·접근 정책, 마지막 확인일 | SQLite의 `sources` 테이블 | 새 조사 계획에서 후보 출처를 찾고 오래된 메타정보를 재확인 |
| 조사 사례·검증 경험 | 질문, 계획, 검색어, 사용·제외 출처, 주장-근거 판정, 실패/수정, 검토 상태 | SQLite의 `research_cases`, `claims`, `evidence` 및 FTS5/태그 검색 | 유사 사례를 계획에 참고로 제시. 사람이 수락·수정·거부 |

이렇게 하면 프레임워크의 대화 기억이 프로젝트의 검증된 지식인 것처럼 취급되는 일을 막을 수 있다. 검색 기록이 있다는 사실만으로 다음 판단이 좋아진다고 가정하지 말고, 기억이 들어간 조건과 없는 조건을 비교해야 한다.

## 6. 권장 구성안 — 팀 기술 스택 확인 전 후보

```text
요청
  → 구조화된 조사 계획
  → [사람 승인]
  → 출처 카탈로그 + 웹 검색 어댑터
  → 페이지 가져오기/본문 추출 어댑터
  → 근거 ID와 원문 인용 구간
  → 인용 문자열·출처 메타 검증
  → 결과 렌더링(주장 ↔ 근거 링크)
  → [사람 검토]
  → SQLite에 실행 이력과 승인된 사례 저장
  → 다음 조사에서 FTS/태그로 유사 사례를 참고 제안
```

### 우선 PoC 후보

- 워크플로: **LangGraph·OpenAI Agents SDK·CrewAI 중 하나**로 같은 승인·재개 시나리오를 구현해 비교한다.
- 역할: 검색/근거 수집과 검증/통합의 두 단계. 둘 중 일부는 일반 함수로 구현한다.
- 기록: SQLite에 `sources`, `research_runs`, `claims`, `evidence`, `research_cases`를 둔다.
- 기억 검색: 키워드·태그·기간 조건을 먼저 적용하고 FTS5 전문 검색을 실험한다. FTS5 자체는 전문 검색 기능을 제공하지만 한국어 토큰화/동의어 성능은 별도 검증이 필요하다.
- 검색·추출: provider 인터페이스만 먼저 정하고, 비용·키·약관 확인 후 하나씩 연결한다.
- 추적: 우선 구조화된 로그와 평가 체크리스트. 팀 시간이 허용되면 Langfuse를 선택적으로 붙인다.

**이 구성은 확정 스택이 아니다.** 현재 저장소에는 애플리케이션의 백엔드/프런트엔드 의존성 manifest가 없어 Python 사용 여부, LLM 공급자, 배포 환경을 확인할 수 없다. LangGraph는 명시적 조사 흐름에 맞춘 유력 후보지만, 최종 선택은 세 후보의 같은 시나리오 PoC와 팀의 언어·숙련도 비교 후 결정한다.

## 7. 무엇을 직접 만들어야 하나

기존 프레임워크로 대체하기 어려운 프로젝트 고유 부분은 다음과 같다.

- **출처 지도:** 이 도메인의 어떤 출처가 어떤 질문/자료에 적합한지, 마지막으로 언제 검토했는지 관리한다.
- **조사 정책:** 출처 유형, 최신성, 상충 자료, 미확인 사실, 인용 조건을 어떻게 처리할지 결정한다.
- **근거 검증:** 주장은 `evidence_id`만 참조하게 하고, 렌더러가 근거 레코드에서 URL·제목·접근일을 채운다. 인용문이 가져온 본문에 실제로 존재하는지 검사한다.
- **경험 승인과 만료:** 실행 결과를 무차별 저장하지 않는다. 검토 상태, 출처 유효성, 수정/폐기 이력에 따라 재사용 후보를 정한다.
- **재사용 정책:** 예전 답을 복사하는 대신 계획·출처 후보·주의점을 제안하고, 사용자에게 확인받는다.
- **효과 측정:** 기억 없음/기억 참고 조건에서 근거 커버리지, 인용 정확성, 조사 시간·호출량, 오래된 근거 재사용을 비교한다.

## 8. 우선순위와 기술 스파이크

### 1순위 — 오케스트레이션 작은 실험

계획 생성 → 사람 승인으로 멈춤 → 승인 입력으로 재개 → 검색 함수 1회 실행 → 종료/실패 기록의 흐름을 만든다. LangGraph를 우선 검증하되, 같은 동작을 구현하는 순수 Python 상태 머신과 구현 시간을 비교한다. 실행이 재개될 때 검색이나 저장이 중복 실행되지 않는지도 확인한다.

### 2순위 — 검색·본문 추출 교체성

동일한 고정 질의·페이지로 후보 검색/추출을 비교한다. 결과 URL 정확성, 자료 최신성, 한국어 본문 추출 성공률, 호출 시간, 예상 비용, 저장·캐시 조항을 기록한다. 약관과 권리가 미확인인 원문/스니펫은 장기 사례 데이터로 저장하지 않는다.

### 3순위 — 기억의 최소 효용

우선 같은 도메인의 비슷한 질문 몇 개를 선정한다. A는 기억 없이 조사하고, B는 이전에 검토된 계획·출처 후보를 참고로 받는다. 품질 체크리스트를 동일하게 두고 근거 커버리지, 조사 시간/호출 수, 오래된/무관한 기억 주입을 비교한다. 임계치는 파일럿 후 팀이 정하며, 외부 AI가 제안한 수치를 확정 기준으로 복사하지 않는다.

## 9. 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 프레임워크가 해결해 준다고 생각해 업무 규칙이 비어 있음 | 체크포인터와 별개로 승인·종료·재사용 정책을 애플리케이션에 명시 |
| 외부 페이지의 프롬프트 인젝션·오염된 메모리 | 외부 본문을 지시가 아닌 데이터로 취급하고, 추출 모델에는 도구 권한을 주지 않으며, 검토된 사례만 저장 |
| 인용 주소/내용이 모델 생성 중 바뀌거나 틀림 | 안정된 evidence ID와 수집 시점 원문 위치를 사용하고 인용 검증 후 렌더링 |
| 검색 공급자 결과를 약관과 다르게 저장 | 공급자별 검색 결과·스니펫·원문 저장 조항을 확인하고 데이터 종류별 보존 정책 분리 |
| 오래된 사실이 다시 사용됨 | 접근일, 발행/갱신일, 재검토일, superseded/expired 상태를 기록 |
| 벡터 DB와 메모리 제품 통합으로 일정 소진 | 먼저 SQL/FTS/태그 검색을 측정하고 실제 실패가 있을 때만 확장 |
| “에이전트가 많다”는 것이 품질 개선으로 오해됨 | 고정된 역할 최소 구성과 단일 에이전트 기준선을 비교하고 품질·비용을 함께 평가 |

웹 검색의 `robots.txt` 준수만으로 원문 사용·저장 권리가 생기는 것은 아니다. 로봇 배제 프로토콜과 이용약관/라이선스는 별도로 관리한다.

## 10. 이번 조사에서 아직 확정하지 않은 것

- 팀이 선택할 언어·백엔드·배포 방식과 기존 팀 숙련도
- 프로젝트 도메인과 공개 출처 시드
- 사용할 검색·추출 제공자, 예산, 키 발급 가능성 및 보관 약관
- 수집 원문·검색 스니펫·파생 요약을 어디까지 저장할 수 있는지
- FTS5 한국어 검색의 품질과 벡터 검색을 추가할 필요성
- LangGraph와 OpenAI Agents SDK/CrewAI의 실제 구현 시간·운영 단순성 비교
- 과거 조사 사례를 승인·재검증할 책임자와 구체 절차

각 AI 답변의 비용, 플랜 한도, AutoGen 유지보수 상태, 특정 제품의 우열은 이 문서의 확정 근거로 사용하지 않았다. 공식 문서에서 다시 확인하고 기술 스파이크에서 검증한다.
