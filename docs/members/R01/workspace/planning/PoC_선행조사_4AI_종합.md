## 요약 결론

지금 확정할 것은 프레임워크나 검색 업체가 아니라 **비교할 도메인, 평가 과제, 공통 데이터 계약**이다. 도메인과 기준 과제를 고정한 다음, 순수 Python 흐름과 LangGraph를 같은 조건으로 비교하고, 검색·추출·기억은 각각 분리된 실험으로 평가한다. AI 자문은 LangGraph와 Tavily를 유력 후보로 들었지만, 도메인 적합성·팀 숙련도·서비스 약관이 확인되기 전에는 채택 결정으로 간주하지 않는다.

2개월 MVP에는 고정된 세 논리 역할(계획, 조사, 근거 검증/편집)을 두고, 복잡한 자율 에이전트 팀은 기본 흐름에서 제외한다. 출처·주장·근거·검토된 경험을 관계형 데이터로 관리하고, SQLite/FTS5를 우선 실험한다. 벡터 데이터베이스와 온톨로지는 사용성 개선이 측정될 때까지 보류한다.

## 도메인과 평가 과제부터 정하기

도메인 후보는 2~4개를 모아 아래 통과 조건을 확인한다. 하나라도 큰 접근·권리 장벽이 있거나 팀이 결과를 판정할 수 없으면 우선 후보에서 뺀다.

- 공개적으로 접근 가능한 1차 자료와 보완 자료가 있다.
- 팀원이 결과를 약 10~20분 안에 판정할 수 있다.
- 단순 사실 검색 외에 비교·종합·최신성·상충·근거 부족 등 서로 다른 요청이 존재한다.
- 비슷한 출처나 자료 구조가 반복되어 출처 지도 또는 검토된 경험의 재사용을 시험할 수 있다.
- 개인·민감정보 수집 없이 대표 과제를 만들 수 있고, 사이트 접근 조건과 콘텐츠 이용 조건을 확인할 수 있다.

통과한 후보는 평가 가능성 25%, 출처 접근성과 반복성 25%, 이용 조건의 명확성 20%, 과제 다양성 15%, 최신성 요구 10%, 개인정보 위험이 낮은 정도 5%로 1~5점 비교하는 방안을 제안한다. 가중치는 초안이며, 점수만으로 도메인을 자동 선택하지 않는다. 후보별 대표 질문 3개로 짧은 파일럿을 한 뒤 팀이 하나를 고른다.

선정 도메인에는 다음 6개 과제를 준비한다.

1. 공개 1차 출처로 확인 가능한 단일 사실
2. 복수 출처를 비교하는 종합 질문 2개
3. 기준일 또는 최신 정보가 중요한 질문
4. 출처 간 차이·불일치를 찾아 설명하는 질문
5. 자료가 부족할 때 불확실성을 밝히고 답을 보류해야 하는 질문

질문마다 기대 핵심 주장, 허용되는 출처 유형, 근거 판정 기준, 정답을 모르는 경우의 처리 방법을 실행 전에 기록한다.

## 1주 PoC 설계

세 실험을 분리해 수행한다. 제품·모델·프롬프트 선택을 한꺼번에 바꾸는 조합 실험은 원인 파악이 어려우므로 피한다.

### A. 워크플로 비교

- A군: 도구 호출과 상태 전이를 명시한 순수 Python 기준 흐름
- B군: 같은 흐름을 LangGraph로 구현
- 두 군은 모델, 프롬프트, 데이터 스키마, 검색·추출 어댑터, 초기 출처 지도와 승인 경험, 도구 호출·시간 상한을 동일하게 둔다.
- 6개 과제 × 2회씩, 총 24회 실행을 1차 계획으로 삼는다. 결과 편차가 큰 과제만 1회 추가해 최대 30회로 제한한다. 시간이 충분하면 전 과제 3회(36회)를 수행한다.
- 워크플로 비교와 별도로 중단, 재개, 재시도 상한, 사용자 승인 거부 후 외부 호출 없음 등 5개 결정적 동작을 확인한다.
- LangGraph는 지속 상태, 분기, 중단·재개가 구현 부담을 줄이는지 본다. 차이가 작거나 팀이 더 빠르게 구현하는 기준 흐름이 있으면 프레임워크를 쓰지 않는다.

### B. 검색·페이지 추출 비교

- 선정 도메인의 검색 의도 15~20개를 고정해 Tavily와 Exa 등 후보를 같은 질의로 비교한다.
- 결과 순위·관련성, 1차 출처 비율, 필요한 출처 누락, 한국어 결과, 요청 시간·비용, 실패를 기록한다.
- 대표 URL 12~20개(정적 HTML, JavaScript 렌더링, PDF, 표 포함)를 골라 직접 HTTP/HTML 추출과 Firecrawl 등 관리형 추출을 비교한다.
- 모든 검색/추출 제품 조합을 시험하지 않는다. 각 단계에서 후보를 좁힌 뒤 최종 워크플로 평가에 고정한다.
- 도메인 사이트별 접근 정책 및 콘텐츠 이용 조건을 별도로 확인한다. API가 결과 저장을 허용한다는 사실만으로 원문 콘텐츠의 재배포 권한이 생기지는 않는다.

### C. 경험 재사용 비교

- 초기 자료로 사람이 검토하고 승인한 경험 4~6건을 준비한다.
- 비슷하지만 보류해 둔 요청 4~6개를 평가용으로 둔다.
- A군은 경험을 제공하지 않고, B군은 승인된 계획·출처 식별자·주의 사항을 참고 힌트로 받는다. 두 군의 모델, 검색·추출 도구, 호출 상한은 같게 유지한다.
- 경험을 그대로 답으로 복사하지 않고 현재 출처를 다시 확인하게 한다. 검토 결과에 따라 수용·수정·거부할 수 있게 한다.
- 주장 근거 커버리지와 인용 일치, 적합한 출처 수, 검색/수집 횟수, 첫 유효 근거까지 걸린 시간, 유용/무관한 경험, 오래된 경험으로 인한 오류를 기록한다.
- 잠정 통과 기준은 근거 품질이 나빠지지 않고 검색/수집 횟수 또는 첫 유효 근거 시간이 20% 이상 개선되며, 중대한 오래된 정보 오류가 없는 것이다. 이 수치는 팀이 파일럿 결과를 보고 조정할 가설이다. 개선이 없으면 경험 이력 저장만 남기고 자동 재사용은 미룬다.

### 공통 평가표

| 영역 | 기록할 지표 |
|---|---|
| 답변 품질 | 핵심 주장 근거 커버리지, 인용과 실제 본문 구간 일치, 상충·불확실성 처리, 무근거 응답 여부 |
| 검색 | 관련 결과 비율, 1차 출처 비율, 누락, 중복·실패 질의 수 |
| 효율 | 유효 근거까지 시간, 전체 시간, 페이지 수, 모델/API 사용량과 비용 |
| 흐름 안정성 | 오류 종료, 재시도 상한, 중단 후 재개, 승인 거부 동작 |
| 경험 재사용 | 유용·무관한 힌트 비율, 편집·거부, 오래된 힌트로 인한 오류, 조사량 변화 |

이 표본은 제품 방향을 결정할 초기 엔지니어링 PoC이지 통계적 성능 보증은 아니다. 데이터 세트와 판정 기준을 먼저 고정하고, 결과와 실패 사례를 함께 보관한다.

## 최소 데이터·기억 설계

관계형 레코드를 정본으로 두고, 검색 인덱스는 재생성 가능한 보조 인덱스로 취급한다.

- `Source`: URL, 제목, 발행자, 자료 유형, 발행/접근 시각, 콘텐츠 해시, 도메인 태그, 접근·이용 조건 메모
- `ResearchRun`: 요청, 정규화된 의도/범위, 계획, 실행 상태, 시각, 도구 사용량
- `Query`: 검색어, 공급자, 실행 시각, 결과 URL과 순위
- `Snapshot`: 출처에서 수집한 허용 범위의 텍스트 또는 필요한 발췌, 해시, 수집 시각
- `Claim` / `Evidence`: 주장, 근거 출처·위치, 지지/부분 지지/반박/미확인 상태
- `Review`: 검토자 판단, 수정·거부 사유, 검토 시각
- `Experience`: 승인 상태, 적용 조건, 참고 계획/출처, 마지막 검증일, 만료·폐기 상태

출처 신뢰도를 하나의 숫자로 합치지 않는다. 최신성, 발행자 유형, 해당 주장에 대한 직접성, 충돌 여부, 사람 검토 상태를 구분해 저장한다. SQLite와 FTS5는 소규모 단일 사용자 PoC의 시작 후보이며, 한국어 토큰화 품질을 실제 데이터로 확인한다. 동시 접속형 배포·권한 분리·운영 복구 요건이 MVP에 포함되면 PostgreSQL을 다시 평가한다. 벡터 검색이나 온톨로지는 필수 과제가 키워드 검색으로 해결되지 않는다는 근거가 생긴 뒤에만 추가한다.

## 외부 서비스에 보내는 질의와 데이터 조건

검색 API에 보내는 요청 문구 자체가 서비스 제공자에게 전달되는 데이터다. 확인한 현재 약관·개인정보 문서상 Tavily는 입력/출력을 서비스 개선 및 제3자 AI 공급자 처리에 사용할 수 있다고 안내하며, Exa는 기본 Query Data를 개선·모델 학습에 활용한다고 설명한다. Exa는 엔터프라이즈용 Zero Data Retention을 별도로 안내하므로, 선택한 계약에 실제 적용되는지 확인해야 한다. 따라서 PoC에는 공개 정보만을 바탕으로 한 일반화된 질의를 사용하고, 사용자·팀원 식별자, 비공개 조사 내용, 키·토큰, 개인 정보는 외부 검색어에 넣지 않는다. 보존·학습 조건은 실제 사용할 요금제와 계약 문서를 확정 전에 다시 확인한다.

Tavily 도움말의 출력 보존 안내는 API 출력에 관한 것이며, 그 출력이 바탕으로 삼은 웹 게시물의 저작권·이용 조건을 대신하지 않는다. Exa의 결과 장기 저장·재사용 범위는 확인한 공개 자료만으로 확정하기 어려우므로 계약 조건 확인 항목으로 남긴다. Firecrawl 등 추출 공급자의 보존·학습 조건도 도입 전에 별도 확인한다.

## AI 자문 간 의견과 종합 판단

| 주제 | 회수된 의견 | 이번 문서의 판단 |
|---|---|---|
| LangGraph | ChatGPT는 기술 선정을 미리 정하지 말고 Python 기준선과 비교하라고 강조. Gemini는 빠르게 결정할 후보로, Perplexity는 필요 기능을 분리한 선택지로 제시. | 동일 조건 PoC 후 선택. 기존 [기술 방향 문서](기술_방향_6AI_협의_종합.md)의 비교 원칙 유지. |
| 검색·추출 | Tavily와 Exa를 비교하고, 직접 추출과 관리형 추출을 실제 도메인으로 평가하자는 의견. Gemini는 Tavily+Firecrawl 조합을 빠른 후보로 제안. | 검색과 추출 벤치마크를 분리. 제품 조합을 선결정하지 않음. |
| 기억 데이터 | DeepSeek이 최소 Source/Run/Query/Snapshot/Claim/Evidence/Review/Experience 필드와 승인·만료 상태를 구체화. 다른 답변도 검토된 경험의 제한된 재사용을 지지. | 관계형 정본 + FTS5 시작, 승인된 힌트만 A/B로 검증. 저장과 자동 재사용을 별도 결정. |
| 실험 규모 | ChatGPT는 과제별 반복과 실패 테스트를 구분. Gemini는 작은 기능 세트의 반복 실행을 제안. | 작은 팀의 1주 일정에 맞춰 24회 1차 실행 + 고편차 사례만 추가. 수치적 성능 보증으로 해석하지 않음. |

자문은 도메인, 언어, 배포 형태, 모델 예산을 알지 못하므로 어떤 업체나 프레임워크의 채택을 확정할 수 없다. 특히 자문이 언급한 가격·무료 한도는 시간이 지나며 달라지므로 여기서는 확정 수치로 옮기지 않았다.

## 공식 자료 확인

- LangGraph [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts): 체크포인트·실행 재개가 실제 요구와 맞는지 평가할 때 참고.
- AG2 [Subagents / dynamic_agent](https://docs.ag2.ai/docs/user-guide/subagents/), CaptainAgent [Classic 문서](https://classic.docs.ag2.ai/latest/docs/user-guide/reference-agents/captainagent/): 현재 dynamic-agent API와 CaptainAgent AutoBuild 사례의 구분을 확인할 때 참고.
- Tavily [Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search), [출력 저장·보존 안내](https://help.tavily.com/articles/1612400809-storing-caching-retaining-output), [서비스 약관](https://www.tavily.com/terms): 검색 옵션·출력 보존 및 입력/출력 처리 조건 확인.
- Exa [가격·제품 페이지](https://exa.ai/pricing), [개인정보 처리방침](https://exa.ai/privacy-policy), [Enterprise](https://exa.ai/enterprise), [서비스 약관 PDF](https://exa.ai/assets/Exa_Labs_Terms_of_Service.pdf): 가격 변동, Query Data 처리, 엔터프라이즈 ZDR, 결과 이용 조건을 실제 계약과 대조.
- Firecrawl [Scrape 문서](https://docs.firecrawl.dev/features/scrape): 페이지 추출 능력 비교용 기능 문서. 콘텐츠 이용 권한을 뜻하지 않는다.
- SQLite [FTS5](https://www.sqlite.org/fts5.html): 전문 검색 후보 기능. 한국어 품질은 별도 벤치마크 대상.

## 팀이 정하면 진행할 수 있는 항목

1. 2~4개 도메인 후보와 최종 평가 책임자
2. PoC가 단일 사용자 로컬 시연인지, 동시 사용 웹 앱까지 포함하는지
3. 사용할 언어·모델/API 공급자 및 호출·비용 상한
4. 외부 검색 공급자에 일반화된 공개 질의를 보내는 데 대한 팀의 데이터 처리 기준
5. 1주 실험이 끝났을 때 기술 선택을 승인할 기준과 최종 결정 기록 위치

이 다섯 항목이 정해지면 팀은 1일차 작업을 시작하고, 결과에 따라 기획서·WBS의 기술 및 리스크 절을 갱신할 수 있다.
