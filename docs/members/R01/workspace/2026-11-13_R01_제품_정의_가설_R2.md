- **문서 경계:** 팀원 독립 기획안의 최종 통합·승인이 아니며, 현재 INTENT/PROJECT/MVP·제출 기획서·WBS의 권위 있는 변경을 의미하지 않는다.

## 0. 요약

**제품 비전:** 찾아you는 더 똑똑한 AI 모델을 만드는 것이 아니라, **기존 프론티어 모델의 지능을 사용자의 목적에 효과적으로 활용하도록 도구·인터페이스·지속 기억·작업 상태·실행 제어를 제공하는 AI 협업 시스템**이다.

**해결할 사용자 문제:** AI를 능숙하게 활용하고 스스로 결과를 검토·교정할 수 있는 사용자가 유사한 문제 해결 과정에서 이미 내린 판단과 설명, 작업 지휘, 검증을 불필요하게 반복하는 부담을 줄인다.

**핵심 원칙:** **이미 확인한 판단은 적합한 조건에서 재사용하고, 새로운 판단이나 중요한 예외에만 사용자 주의를 요청한다.**

**8주 검증:** 큰 업무 도메인은 **리서치**, 첫 하위 도메인은 **앱 탐색·비교·검증**으로 제한한다. 한 번 승인한 조사 판단을 다른 앱 조사에 안전하게 재사용하는지, 예외를 잘 구분하는지, 사용자 노력 감소가 있는지 검증한다.

## 1. 시스템·도메인 계층

| 수준 | 범위 | 이번 프로젝트에서의 의미 |
| --- | --- | --- |
| 상위 시스템 | AI 협업 및 목적 중심 문제 해결 | 기존 지능의 활용을 돕는 도구·기억·인터페이스·판단/실행 관리 |
| 큰 업무 도메인 | 리서치(Research) | 질문 구성, 하위 조사 문제 분해, 출처 탐색, 검증, 결과 통합 |
| 하위 도메인 | 앱 리서치(App Research) | 앱의 기능·조건·사용 환경 비교, 출처·미확인 상태 판정 |
| 첫 실험 단위 | 연속된 앱 조사 2~3건 | 첫 판단 확인 → 유사 과제 재사용 → 변경 조건/예외 검토 |

리서치는 시스템 전체와 동의어가 아니다. 기획·설계, 개발, 운영 등은 **후속 큰 도메인 후보**이며 이번 8주 안에 구현한다고 약속하지 않는다.

실제 설계에서는 ‘리서치’라는 업무 과정과 ‘앱’이라는 대상 도메인을 조합하는 방식도 고려한다. 아직 범용 도메인 분류나 공통 프레임워크를 고정하지 않는다.

## 2. 타겟 유저

### 2.1 1차 타겟

**AI를 업무에 자주 활용하고, 결과를 분석·교정할 수 있으며, 반복되는 지시·검토·판단의 인지적 비용을 줄이고 싶은 사용자.**

처음 검증할 구체 집단은 **AI를 사용해 조사·기획·개발을 반복하는 개인 개발자와 소규모 기술 프로젝트 리더**로 제안한다.

- 자신의 목적이나 판단 기준을 설명하고 AI의 잘못된 전제를 교정할 수 있다.
- 도구 사용·프롬프트 설계 등 모델의 능력을 이미 어느 정도 활용한다.
- 같은 기준을 여러 작업에 반복 적용하거나 다른 문제에 재활용할 일이 있다.
- 중요한 결정은 직접 내리되, 저위험·반복적인 관리 작업은 위임하고 싶어 한다.

타겟은 AI 활용 능력이 부족한 사람이 아니다. **능력이 있지만 그 능력을 반복적인 관리에 소모하고 싶지 않은 사람**이다.

### 2.2 관찰 사실과 검증되지 않은 확장

R01과 AI의 실제 대화에서 의도를 수정·발전시키고 문제 구조를 교정하는 상호작용이 일어났다. 이는 해당 능력이 **이 대화 조건에서 가능했다는 관찰**이지, 대부분의 사용자에게 지속적인 제품 부담 감소가 확인되었다는 증거는 아니다.

사용자 집단의 크기, 문제 빈도, 재사용 요구, 기존 도구 대비 추가 가치는 **검증 전**이다.

## 4. 문제 정의

> AI를 능숙하게 사용하는 사람은 프론티어 모델의 추론·조사·문제 분해 능력을 활용할 수 있지만, 복잡하거나 반복적인 업무에서는 이미 설명한 의도·승인한 기준·작업 방식의 적용 여부를 다시 판단하고, AI가 놓친 예외를 교정하며, 변화한 목적에 따라 결과를 연결하는 데 주의를 계속 투입해야 할 수 있다.
>
> **찾아you는 이 협업 관리 부담을 줄여 사용자가 새로운 문제와 중요한 결정에 집중하도록 돕는다.**

이는 LLM 자체의 지능을 높이는 문제가 아니다. **지능을 활용하는 환경과 협업 프로세스를 설계하는 문제**다.

## 5. 제품 가치 제안과 책임 경계

### 5.1 사용자에게 약속하려는 가치

- **반복 설명 감소:** 이미 확인된 목적·조건·기준을 매번 재입력하지 않는다.
- **반복 판단 감소:** 이전에 승인한 절차와 기준을 유효한 범위에서 재사용한다.
- **예외 중심 개입:** 기존 규칙으로 해결하지 못하는 중요한 부분만 사용자에게 보여준다.
- **변화 대응:** 새로운 정보가 사용자 의도를 발전시키거나 바꾸면 기존 문제 구조와 작업을 갱신한다.
- **검증 가능한 결과:** 무엇을 왜 적용했는지, 어디까지 확인했는지 되짚을 수 있다.

### 5.2 기존 LLM과 시스템의 책임 분리

| 구성 요소 | 맡길 역할 |
| --- | --- |
| **기존 LLM(지능)** | 요청·맥락 해석, 의도 가설, 문제 분해, 대안 생성, 증거 평가 및 계획 제안 |
| **도구(Tools)** | 허용된 정보 탐색·조회, 자료 읽기, 작업·파일·외부 시스템의 권한 있는 실행 |
| **기억(Memory)** | 사용자가 확인한 의도·판단·적용 범위, 이전 실행 결과와 근거의 지속 보존 |
| **인터페이스(Interface)** | 탐색적 출력, 수정, 승인, 충돌·예외 확인, 결과·상태 표시 |
| **제어·실행 계층(Control/Execution)** | 적용 조건 검사, 작업 상태·이력, 권한 경계, 재계획·중단·재시도 및 사용자 개입 시점 관리 |

ChatGPT·Work·다른 에이전트 제품도 이 기능의 일부 또는 다수를 이미 제공할 수 있다. **기억과 도구를 붙이는 행위 자체는 차별화가 아니다.** 동일 업무에서 사용자 부담과 오류를 줄일 때만 제품 가치가 입증된다.

## 6. 상위 문제 해결 모델

사용자가 처음부터 자신의 의도를 완벽히 표현하거나, 심지어 완전한 선호를 이미 형성했다고 가정하지 않는다. AI는 **질문뿐 아니라 탐색적 정보·선택지·부분 결과**를 제공하여 사용자가 자신의 목적을 발전시키도록 도울 수 있다.

**현재 의도/문제 ↔ 탐색적 출력·사용자 피드백 ↔ 문제 분해·정보 확보·검증 ↔ 결과 통합**

- **의도 추론:** 명시/추론/미확인을 분리한다.
- **의도 형성 지원:** 새로운 대안과 근거를 제공하되 특정 선택으로 유도하지 않는다.
- **동적 문제 분해:** 하나의 상위 문제를 필요한 하위 문제들로 구성·수정한다.
- **근거 확보와 통합:** 결과를 합쳐 원래 목적에 충분한지 판단한다.
- **지속 상태와 재사용:** 과거 판단이 새 상황에 적합한지 확인하고 유효한 경우 재사용한다.

문제 분해는 고정된 한 번의 단계가 아니라, 의도와 결과 변화에 따라 다시 수행될 수 있다. 다만 이 전체 구조의 범용성은 장기 가설로 남기고 **첫 구현에서는 제한된 앱 리서치로 관찰**한다.

## 7. 핵심 피처

### F1. 의도·맥락 형성 및 유지

사용자의 명시적 요구, AI의 추론, 미확인 가정, 사용자가 실제 승인한 목적을 구분하고 기록한다. 중요한 불확실성은 질문할 수 있고, 일부는 정보·대안을 먼저 제시해 사용자의 반응을 받는다. 새 피드백을 기존 문제와 연결한다.

**대응:** P1, P5, P6

### F2. 도메인별 동적 문제 분해·실행·근거 통합

상위 요청을 앱 기능 확인, 후보 탐색, 사용 조건 검증 등의 하위 문제로 나누고 필요한 작업만 실행한다. 중간 결과에 따라 작업을 추가·생략·보류한다. 근거·출처·확인 시점·충족/미충족/미확인·실패를 구분하여 결과를 통합한다.

**대응:** P2, P4, P6

### F3. 승인된 판단의 조건부 재사용과 예외 중심 개입

과거 판단을 **내용 + 적용 대상 + 유효 조건 + 예외 + 승인 권한 + 재검토 조건**으로 보존한다. 다음 과제에서 조건이 충족되면 재사용하고, 모호하거나 충돌하거나 권한 밖이면 보류·질문한다. 결과와 적용 이력을 남긴다.

**대응:** P1, P2, P3, P4

**가장 중요한 경계:** ‘공식 출처를 우선한다’ 같은 업무 방법은 재사용 가능하지만, ‘지난번 앱은 오프라인 타이머가 필수였다’ 같은 과제별 조건은 새 과제에 자동 승계하지 않는다. **판단의 재사용과 결론의 무조건 재사용을 구별**한다.

## 8. 제품·MVP 입출력 계약

### 8.1 상위 시스템 수준

- **입력:** 자연어 문제, 사용자의 현재 목표·제약, 선택적 문서·도구 접근, 기존 승인 판단과 이전 작업 상태.
- **중간 상호작용:** 의도 해석, 질문 또는 탐색적 출력, 확인·수정·승인, 하위 문제와 작업 선택.
- **출력:** 현재 목적에 맞는 결과와 근거, 미해결 사항, 재사용한 판단의 범위, 새로 결정해야 할 예외, 후속 행동.
- **후속 입력/출력:** 제약·의도 변경 → 영향받은 판단·작업·근거의 변경과 필요한 재실행 결과.

최종 산출물은 문제에 따라 다르다. 보고서 한 가지 형식으로 고정하지 않는다.

### 8.2 앱 리서치 3회 연속 사용 시나리오

| 회차 | 예시 사용자 입력 | 시스템이 해야 할 일 | 검증할 출력 |
| --- | --- | --- | --- |
| **1. 최초 협업** | “안드로이드 공부용 앱을 찾고 싶어. 오프라인 사용이 중요해.” | 필요 시 타이머/차단 등 사용 목적 탐색, 앱별 근거 조사. 사용자가 ‘공식 자료 우선, 확인 안 된 기능은 미확인’이라는 **재사용 기준을 승인**하면 범위와 함께 저장 | 앱 조건별 판정·근거·미확인·승인 기준 기록 |
| **2. 유사 작업** | “무료 사이트 차단 앱도 찾아줘.” | 기존의 **조사 방식**은 적합하면 재사용하되, 지난번 ‘오프라인 타이머’ 조건을 새 작업에 잘못 적용하지 않음 | 불필요한 반복 질문 없이 조건별 결과와 적용된 기준 표시 |
| **3. 중요한 예외** | “공식 문서에 기능이 없는데 다른 곳에서는 된다고 해.” | 근거 충돌을 인식해 단정하지 않고, 추가 공식 확인 또는 미확인 유지 등 허용된 선택지를 제시 | 중요 예외·보류 이유·사용자 판단 요청·이력 |

**성공 예시:** 동일한 업무 기준을 다시 설명하지 않아도 되고, 예외에서는 무리하게 결론을 내지 않는다.

**실패 예시:** 과거 과제의 오프라인 조건을 현재 앱에 자동 적용하거나, 정보 충돌을 숨기고 지원한다고 확정한다.

기존 APP-A(지정 앱 비교)와 APP-C(중간 판정에 따른 대안 추가·생략·보류)를 F2 기술 검증 자산으로 활용한다. 위 연속 사용 시나리오는 **추가 제품 가치 검증 후보**이며, 기존 Must 범위를 문서만으로 변경하지 않는다.

## 9. 8주 MVP 범위와 최소 상태

**8주 목표:** 하나의 앱 리서치 하위 도메인에서 **최초 의도/기준 확인 → 실행 → 다음 유사 과제의 판단 재사용 → 예외 처리·수정**이라는 완전한 한 사이클을 재현하고 비교한다.

**Must 후보**
1. 첫 조사에서 명시된 의도/추론/미확인을 구분하고 제한된 질문 또는 대안을 제공한다.
2. APP-A/C 수준의 작업 분해·조건 판정·근거 연결을 실행한다.
3. 사용자가 승인한 조사 판단 **최소 1~3개**를 범위·예외와 함께 저장한다.
4. 두 번째 유사 조사에서 재사용 여부와 이유를 기록한다.
5. 세 번째 예외 상황에서 오적용을 피하고 필요한 경우 사용자 판단을 요청한다.
6. 실제 평가에서 사용자 개입과 결과 품질을 기준선과 비교한다.

**후순위/제외:** 여러 큰 도메인의 범용 엔진, 자유로운 에이전트 생성, 자동 정책 일반화, 전체 저장소 수정, 무제한 자율 실행, 대규모 기억·RAG·온톨로지, 복잡한 정보가치 최적화, 다수 외부 서비스 통합.

**최소 상태 후보(기술 명세 확정 전):**

| 상태 | 필수 정보 |
| --- | --- |
| Goal/Intent | 명시·추론·미확인/확인, 목적·제약·변경 이력 |
| Decision Policy | 판단 내용, 적용 범위, 승인 여부·권한, 조건·예외·재검토 |
| Problem/Task | 상위/하위 문제, 선행 관계, 실행 조건과 상태 |
| Evidence/Result | 주장·출처·확인 시점, 조건 판정·미확인·충돌·실패 |
| Run/Review | 실제 적용·생략·예외·사용자 교정·최종 결과 |

저장소·프레임워크·모델은 구현 검증과 필요에 따라 선정한다. 장기 정본(승인 판단, 검토 근거)과 일시적인 실행 상태를 혼동하지 않는다.

## 10. 관찰된 능력과 검증 가설 구분

**현재 대화에서 관찰:** 프론티어 모델은 사용자 피드백에 맞춰 의도 해석·대안·문제 분해를 수정할 수 있다. R01은 실제로 이를 활용하면서 반복적으로 상위 목표와 해석 오류를 교정했다.

**검증하지 않은 것:** 다른 숙련 사용자에게도 같은 관리 부담이 반복되는가, 구조화된 판단 재사용이 실제로 그 부담을 줄이는가, 범위를 잘못 적용하지 않는가, 다른 제품보다 유리한가.

| ID | 제품·기술 가설 | 최소 실험 | 지표 |
| --- | --- | --- | --- |
| H1 우선 | 승인된 판단 기준의 조건부 재사용이 반복 설명·교정을 줄인다. | 첫 앱 조사에서 기준 승인 → 다른 앱 조사에서 재사용 | 중복 지시, 사용자 교정, 적극적 작업 시간 |
| H2 우선 | 적용 조건·예외를 검사하면 부적절한 재사용을 줄일 수 있다. | 과제별 조건 불일치·출처 충돌 주입 | 잘못된 적용, 놓친 중요 예외, 불필요한 확인 |
| H3 보조 | 탐색적 출력이 사용자의 의도 구체화에 도움이 된다. | 초기 요청에서 질문만 제공 vs 소규모 대안·부분 결과 제공 | 목적 수정의 명확성, 근거 있는 선택, 편향된 유도 |
| H4 보조 | 중간 판정에 따른 작업 추가·보류가 고정 흐름보다 적합하다. | APP-A/C 고정 흐름 vs 조건부 작업 | 필수 조건 누락, 근거 정확성, 시간·호출·비용 |

**기준선:** 동일한 모델과 가능한 한 동등한 자료·권한을 사용하여 ChatGPT를 능숙하게 활용하는 방식(잘 작성한 프롬프트, 프로젝트 맥락, 사용 가능한 기억·연결 기능)과 비교한다. 필요한 경우 고정형 조사 흐름도 비교한다.

**성공은 사용자 질문 횟수 감소만으로 판정하지 않는다.** 잘못된 판단 재사용·중요 예외 누락·근거 품질 저하가 나타난다면 효율 개선으로 간주하지 않는다. 정량 합격선은 초기 실행과 평가 기준을 확인한 뒤 정한다.

## 12. 주요 위험과 반증·축소 조건

- **기존 ChatGPT도 이미 충분한 경우:** 전용 제품 우월성을 주장하지 않고 어떤 상태·예외 기능만 의미 있었는지 분리한다.
- **판단 재사용의 과잉 일반화:** 승인되지 않았거나 적용 조건이 불명확한 규칙은 자동 적용하지 않는다.
- **과도한 질문:** 되돌리기 쉬운 선택은 조건·가정을 기록하고 진행하되 높은 영향·권한 문제는 사용자에게 돌린다.
- **의도 형성에 대한 과도한 유도:** 여러 대안·반대 근거를 제시하고 AI의 제안과 사용자 선택을 구분한다.
- **동적 구성 과잉 복잡성:** 고정 흐름으로 충분하면 자유 역할 생성·다단계 재계획을 늘리지 않는다.
- **권한·안전:** 공식 API·승인 데이터·허용된 최소 개별 페이지 조회를 우선하며 무단 크롤링에 의존하지 않는다.
- **일정 초과:** H3/H4의 고급 기능은 축소하고 H1/H2의 완전한 연속 사용 실험을 우선한다.
- **사용자 근거 부족:** R01 경험은 시작점이며 외부 숙련 사용자 관찰과 실제 비교가 필요하다.

## 13. TASK-015와 제품 확정의 경계

본 문서는 **R01 독립 제품 정의 개정안**이다. R02·R03·R05 기획안과의 비교는 TASK-015에서 같은 기준으로 진행하며, 단일 사용 사례의 기술적 편리함만으로 제품 방향을 자동 확정하지 않는다.

현행 INTENT는 리서치와 APP-A/C를 현재 검증 대상으로 두고 있다. **이 문서가 시스템 비전을 확장했다고 해서 기존 확정된 제출 범위, 앱 MVP Must, WBS를 직접 수정하지 않는다.** 변경 시에는 R01의 명시적 판단과 별도 기록이 필요하다.

## 14. 결론

**찾아you의 지향점은 새로운 ‘지능’이 아니라 기존 ‘지능’을 사용자가 편리하게 활용할 수 있게 만드는 환경이다.**

가장 우선 검증할 제품 가치는 **AI를 잘 쓰는 사람조차 반복해서 수행하는 판단·교정·관리 작업을, 승인된 기억과 도구·실행 상태를 통해 안전하게 줄이는 것**이다.

리서치는 첫 큰 도메인, 앱 리서치는 그 첫 하위 도메인이다. 8주 프로젝트에서는 판단의 **재사용과 예외 처리**를 중심으로 하나의 완전한 연속 작업을 구현하고, 실제 사용자 노력과 오류를 측정한다.
