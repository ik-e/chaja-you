## 0. 요약 판정

기존 R01의 상위 가치 가설은 기존 LLM을 도구·기억·인터페이스와 연결하여 사용자의 **불필요한 반복 감독·검증·교정 비용**을 줄이는 것이다. 종전 선행기술 조사는 SDK, 일반형 AI 조사 제품을 먼저 봤고, **BATHOS처럼 제품 기획~개발~검증의 전 과정을 AI 팀으로 운영하는 직접 경쟁군을 누락**했다. 이는 경쟁 조사 범위의 오류이며 이 문서에서 보완한다.

**현재 확인:** BATHOS·BMad Method·Spec Kit·OpenSpec·GSD Core·Gas City는 역할 분담, 의도/명세 보존, 지속 상태, 변경 기록, 작업 분배, 검증과 사용자 승인 중 상당 부분을 이미 제공한다. 따라서 'AI 팀/상태/기억/품질 게이트를 제공한다'는 것만으로 차별화할 수 없다.

**현재 미확인:** 이러한 기능의 조합이 실제 목표 달성까지 사용자 작업 시간·재확인·과잉 차단·중요한 누락을 얼마나 줄이는지. 외부 사용자의 반복 수요와 찾아you의 추가 가치는 **not_run / not_verified**다.

**잠정 방향:** 새로운 범용 오케스트레이터보다, (1) 변경된 목적·판단 적용 범위의 정확한 재사용, (2) 필요한 경우에만 개입하는 검증/승인, (3) 여러 AI·출처의 주장 충돌 및 의사결정 영향을 좁은 업무에서 비교한다. 어느 것도 고유성이나 사용자 수요를 확정하지 않는다.

### 1.1 BATHOS에서 직접 확인한 중요한 사실과 불일치

- 소개 페이지는 **v0.3.0**, 현재 연결된 GitHub 기본 브랜치 README는 **v0.4.0**으로 표기한다. 최신 버전/현재 기능 판단은 버전이 표시된 개별 문서별로 구분한다. [S01, S02]
- 사이트는 Claude/Codex/GLM 혼합을 홍보하지만, GitHub v0.4.0 README는 **Claude Code v2.1.32+ 및 실험적 Agent Teams**를 기본 실행 요구조건으로 적는다. 포터빌리티 문서는 GLM 백엔드 교체와 Codex 런타임 포팅을 구분하며 Codex의 완전한 게이트/종료 훅 이식은 후속으로 기록한다. **혼합 모델 실행이 모든 런타임에서 검증되었다고 단정하지 않는다.** [S01, S02, S04]
- BATHOS는 자신이 **BMad Method 선행 작업을 검토한 독립 재구현**임을 FAQ에 밝힌다. 따라서 BMad가 직접 경쟁군의 우선 비교 대상이다. [S03]
- 'zero-context-loss', 품질 보증, 테스트 수 등은 프로젝트의 주장/자체 검증 기록이다. FAQ에 **v0.4.0은 production-ready가 아니며, 자체 도그푸딩만 거쳤고 외부 파일럿은 다음 단계**라고 적혀 있다. 이것이 제품 가치가 없다는 뜻은 아니지만 제3자 실증으로 바꿔 말하지 않는다. [S03]
- 이미 자기 문서에서 **토큰 비용 증가, 할당량으로 인한 팀원 멈춤, 재실행과 재검증 비용**을 운영상 한계로 설명한다. [S10]

## 4. 재정의할 사용자 문제 후보 — 확정 전

> 소규모 프로젝트의 AI 활용 책임자는 이미 다양한 AI 개발/조사 워크플로와 상태·검증 도구를 이용할 수 있지만, 여러 과제에 걸쳐 **승인된 판단을 언제 재사용·철회해야 하는지**, **어떤 검증·승인이 실제로 필요한지**, **새 정보가 어느 결정·후속 작업만 바꾸는지**를 여전히 직접 판별할 수 있다. 이 부담이 기존 도구의 강한 설정을 사용해도 반복되는지, 그리고 부담 감소가 추가 설정·운영 비용보다 큰지는 아직 검증이 필요하다.

이 문장은 **기존 R01 문제 정의의 경쟁군 검토를 반영한 후보**다. '기존 제품은 이 기능이 없다'는 주장이나 팀 제품 변경 결정이 아니다.

## 5. 강한 비교 실험 — 문서에서 구현으로 옮기기 전에

### 기준선

- **B1:** 능숙한 사용자 + ChatGPT/Claude 프로젝트 지침·기억·동등한 자료·도구.
- **B2:** 같은 작은 업무를 BATHOS 또는 BMad로, 각 공식 가이드와 적정 규모 설정에 따라 수행. 필요시 OpenSpec/Spec Kit를 변경 추적 기준선으로 사용.
- **D0:** R01이 제안한 최소 판단 적용 범위·예외·변경 영향 연결만 추가. 새 범용 멀티에이전트 엔진 구현은 제외.

### 최소 과제 2종

1. **기술 선택/리서치:** 5명/8주 기술 선택 과제를 조사·결정한다. 이후 팀 인원/제약을 바꾸고 독립 원출처 중복이나 충돌을 한 건 삽입한다. 어떤 결정·근거를 유지/보류/재확인하는지 측정.
2. **프로젝트 변경/검토:** 이전 승인 기준을 적용 가능한 정상 변경, 부분 적용 변경, 중요한 예외 변경에 각각 실행한다. 불필요한 검증/승인 요청과 위험 누락, 실제 작업 소요를 함께 측정.

### 관측 항목

- 정확한 사용자 목적 반영; 중요한 누락/예외 탐지; 거짓양성 게이트·쓸데없는 승인 수.
- 원출처까지의 근거 추적, 중복 독립성 착각, 충돌 여부, 실제 수행/실패/미실행의 구분.
- 사용자 적극 작업 시간 및 반복 지시 횟수; 초기 설정·업데이트·문서 관리 비용; 총 경과시간/호출량·토큰비용.
- 동일 사례 최소 2회 반복과 중요한 제약 변경 1회. **품질·권한이 악화되면 시간 절약만으로 성공 판정 금지.**

**검증 중단 조건:** 강한 B1/B2가 이미 충분하거나 D0의 추가 설정/유지 비용이 절감보다 크면 신규 기능 범위를 줄이고 기존 솔루션 조합을 우선한다. 현재 적정 도메인과 사용자 가치는 미결정.
