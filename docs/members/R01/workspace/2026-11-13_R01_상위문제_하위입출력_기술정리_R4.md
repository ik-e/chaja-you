## 0. 결론부터

**제품의 상위 목표:** 더 높은 지능을 개발하는 것이 아니라 **기존 LLM의 지능에 적절한 도구·기억·인터페이스·실행 환경을 제공하여 사용자가 목적을 달성하기 위해 지불하는 불필요한 인지적·관리적 비용을 줄이는 것**이다.

**문제 정의 방식:** 문제는 P = (X, Y, E, C)로 표현한다. X는 입력, Y는 요구 출력, E는 환경, C는 제약이다. 주어진 환경·제약 아래 **X를 Y에 대응시키는 문제가 존재한다**는 뜻이지, **변환 함수·알고리즘·상태 전이·검증 함수를 문제 정의에 적어야 한다는 뜻이 아니다.**

**문제 분해 방식:** 상위 문제 P0의 **입출력이 하위 문제들의 입출력으로 나뉘거나 재구성**되며, 어떤 하위 문제의 출력은 다른 하위 문제의 입력이 된다. 상위 입출력의 만족에 필요한 연결만 지정한다. 하위 문제와 연결의 구성은 고정 4~6단계 파이프라인이 아니다.

**기술적 1순위:** 문제 입출력 계약과 연결 관계를 최소한으로 보존하고, 기존 LLM·도구를 활용하며, 사용자와 확인한 판단·맥락을 적용 범위에 맞게 재사용하고 예외를 드러내는 작동 가능한 한 사이클.

**첫 도메인:** 제품의 정체성과 분리하여 검증력으로 선택. 프로젝트 변경·TASK 리뷰는 사용자 문제와 판정 근거가 있어 **값싼 후보 실험**으로 권장하지만 최종 선정된 도메인은 아니다. 기존 APP-A/C는 공식 개발 자산으로 유지한다.

## 1. 사용자 가치, 문제, 해결 전략은 별도 계층

| 구분 | 정의 | 이번 논의의 내용 |
| --- | --- | --- |
| **제품 목적/가치** | 왜 해결하는가 | 숙련 AI 사용자의 불필요한 반복 설명·판단·관리 부담을 줄임 |
| **상위 문제** | 어떤 X에서 어떤 Y가 요구되는가 (E, C 포함) | 사용자의 현재 목적·맥락·조건에서 그 목적에 부합하는 결과와 필요한 결정 정보를 얻음 |
| **하위 문제** | 상위 문제의 입출력을 나누어 무엇을 다룰 것인가 | 상황에 따라 목적 파악, 관련 기존 상태, 필요한 중간 결과, 결과 통합 등의 문제 |
| **해결 전략** | 실제로 X를 Y에 대응시키는 방법 | 기존 LLM, 검색/파일 도구, 기억, UI, 작업 조정, 규칙 등 |
| **구현·운영** | 무엇을 코드/설정으로 만들고 실행하는가 | 문제 연결 표현, 도구 어댑터, 승인·이력 상태, 오류 처리 |
| **검증** | 그 방법의 작동성과 사용자 가치가 있는가 | 허용 결과·예외 품질, 부담·시간·정확도, 기준선 비교 |

**중요한 정정:** R3.0의 R(x,e,c,y), 정책 π, 상태 전이 T는 문제 정의를 명확히 하기 위한 필수 요소가 아니다. 그것들은 각각 별도의 평가 관계·실행 방법·상태 모델을 표현할 때 **필요에 따라** 도입할 수 있다. 문제 정의가 충분히 추상적이라는 이유만으로 함수가 빠졌다고 평가하지 않는다.

## 2. 문제의 추상화 계층

### 2.1 상위 P0 — 의도적으로 추상적

**P0: AI와의 협업으로 사용자 목적에 필요한 결과를 얻고, 반복적인 관리 부담을 줄여야 하는 문제**

| 요소 | 상위 추상 명세 |
| --- | --- |
| **입력 X0** | 사용자의 요청·목적·현재 맥락과 새로 주어지는 정보·피드백 |
| **출력 Y0** | 사용자의 현재 목적에 부합하는 결과/행동 또는 해결 불가능한 부분의 정보, 이후 필요한 사용자 판단 |
| **환경 E0** | 사용자가 AI를 이용하는 실제 업무 환경, 이용 가능한 모델·자료·도구·시간 |
| **제약 C0** | 사용자 목적·권한·통제권, 자원 한계, 신뢰성과 정보 이용 제한 |

상위 P0에는 특정 도메인, 데이터베이스, 워크플로, 메모리 구현, 화면 구조를 주입하지 않는다. **도구·기억·인터페이스의 제공은 P0를 해결하기 위한 시스템 전략**이지 P0의 정의에 강제로 포함된 전제가 아니다.

사용자의 피드백 때문에 목적 자체가 발전할 수 있으므로 출력은 단일 최종 보고서로 고정하지 않는다. 정답이 유일하다는 가정도 필요 없다.

### 2.2 하위 문제 분해의 일반 구조

어떤 분해 D에서 **P0 → {P1, …, Pn}**이며, 각 **Pi = (Xi, Yi, Ei, Ci)** 이다.

- 상위 X0 중 일부가 여러 하위 Xi에 반복 투입될 수 있다.
- 하위 Yi가 다른 하위 Xj가 될 수 있다. **Yi → Xj** 연결을 기록한다.
- 상위 문제에 명시되지 않은 중간 입출력도 하위에서 도입할 수 있다.
- 하위 문제의 결과를 통합·비교하는 과정 자체가 다른 하위 문제일 수 있다.
- 상위 C0 중 관련 제약은 하위 Ci에서도 유지해야 하고, 필요하면 구체 제약이 추가된다.
- 서로 독립적인 문제는 병렬로 다룰 수 있고, 결과에 따라 다른 문제를 추가·생략할 수 있다.
- 여러 대체 가능한 분해 구조가 존재할 수 있다. **한 개의 표준 문제 트리를 가정하지 않는다.**

단지 '하위 작업을 수행했다'는 것과 '상위 요구 출력이 얻어졌다'는 것은 구분한다. 반대로 문제를 분해할 필요가 없는 경우에는 바로 하나의 문제로 다룰 수도 있다.

### 2.3 예시: 프로젝트 변경 영향 검토 문제

**상위 사례 문제 PM0**
- **X0:** 변경 요청·실제 변경 내용·검토 목적·현재 승인 기준
- **Y0:** 변경의 영향 및 필요한 검토에 관한 결과
- **E0:** 프로젝트 코드·문서·작업 기록에 접근 가능한 환경
- **C0:** 승인 범위, 검토 기준, 누락·근거 부족에 관한 제한

| 하위 문제 | Xi: 요구 입력 | Yi: 요구 출력 | 연결 |
| --- | --- | --- | --- |
| **PM1 변경 요소 파악** | 변경 내용, 기준 revision | 실제로 변경된 계약/구성 요소 | PM1의 Y → PM2 및 PM3의 X |
| **PM2 영향 대상 파악** | 변경 요소, 기존 의존 관계 | 영향 후보와 확인되지 않은 영향 | PM2의 Y → PM3의 X |
| **PM3 검토 요구 파악** | 변경 요소·영향 대상·현재 검토 기준 | 필요한 담당 검토, 불필요한 확인, 미확인 항목 | PM3의 Y → PM4의 X |
| **PM4 결과 구성** | PM1~PM3의 결과, 사용자 목적 | 상위 검토 결과와 필요한 사용자 결정 | PM4의 Y가 PM0의 Y를 구성 |

이는 특정 도메인의 **가능한 문제 분해 예시**다. PM1~PM4가 실제 실행 단계와 1:1 대응하거나 각각 별도 에이전트여야 한다는 뜻은 아니다. 어떤 문제는 하나의 모델 호출로 복수 하위 입출력을 채울 수 있다.

## 3. 기술적 구현에서 분리할 최소 책임

| 영역 | 책임 | 처음부터 만들지 않는 것 |
| --- | --- | --- |
| **Problem/Link** | 각 하위 문제의 Xi/Yi/Ei/Ci와 상위·하위·입출력 연결 기록 | 범용 추론 언어, 임의의 문제를 보편적으로 분해하는 알고리즘 |
| **Tool/Capability** | 기존 모델/도구가 어떤 입출력을 제공하는지 표현, 실행 권한·오류 관리 | 새 검색엔진·범용 브라우저·도구 생성 엔진 |
| **Memory/Decision** | 확인된 의도·승인된 기준·과제 제약·이전 결과를 구분하여 적용 범위와 변경 이력 보존 | 모델의 내부 기억 복제, 자동 정책 일반화, 대규모 벡터 지식베이스 |
| **Run/Review** | 실행/미실행/보류, 근거, 사용자 교정, 실패·부분 상태와 revision 기록 | 처음부터 복잡한 멀티에이전트 오케스트레이션 |
| **Interface** | 현재 결과, 재사용한 판단, 중요한 변화·예외, 상세 근거를 선택적으로 제공 | 모든 내부 상태를 한 화면에 노출하는 대시보드 |

기능 계층과 데이터 저장 방식은 구분한다. 각각을 별도 서버·에이전트·DB로 분리하라는 뜻은 아니다. **한 프로세스+작은 저장소에서도 충분히 구현 가능**하다.

### 3.1 최소 데이터 계약 제안

- **Problem**: id, parent_id, X_desc, Y_desc, E_ref, C_ref, status
- **Link**: source_problem, source_output, target_problem, target_input, reason
- **Memory**: id, kind(preference/policy/task_constraint/conclusion/experience), content, scope, authority(confirmed/inferred/proposed/revoked), provenance, review_condition
- **Run**: problem_id, input_revision, tool_or_method, outcome, evidence_refs, applied_memory_ids, exceptions, permission_status
- **Feedback**: run_id, user_action(accept/revise/reject/defer), change_scope, resulting_revision

각 필드는 **첫 시연에서 필요한 정도만** 유지한다. 후보 구조이므로 저장소/스키마 확정으로 간주하지 않는다. Problem에는 실제 알고리즘이나 매핑 함수 필드를 필수로 두지 않는다.

### 3.2 판단 재사용의 임시 운영 규칙(문제 정의가 아닌 해결 전략)

1. 명시적으로 승인된 판단과 AI가 추론한 판단을 분리한다.
2. 현재 문제와 해당 기록의 적용 범위를 대조한다.
3. 기존 판단이 유효하면 적용 근거를 기록한다.
4. 범위 이탈·충돌·근거 부족·새 권한 요구는 **자동 적용을 제한하고 필요한 부분만 확인**한다.
5. 사용자 수정은 해당 범위의 다음 작업에만 반영하며, 승인되지 않은 일반 규칙으로 확장하지 않는다.

어떤 경우에 사용자 질문이 최선인지, 대안 제시가 최선인지, 보류가 최선인지는 문제·권한·위험에 따라 달라질 수 있다. **질문 자체를 필수 출력으로 고정하지 않는다.**

### 3.3 도구·권한

도구는 입력 스키마, 출력/오류, 요구 접근 권한, 실행 조건을 명시하는 어댑터로 시작한다. 읽기와 외부 변경을 구분하고 실제 쓰기·승인·병합·전송은 사용자 권한 밖으로 확대하지 않는다. 외부 자료 수집은 기존 공식 데이터 정책을 준수한다.

### 3.4 인터페이스 최소 단위

**결과 / 기존 판단을 반영한 이유 / 새 판단이 필요한 예외**를 중심으로 보여준다. 반복적인 정상 처리에서는 내부 실행 로그를 기본으로 숨기고 필요할 때 펼친다. 새 의도를 형성하는 과정에서는 질문만 아니라 대안·부분 결과를 제시할 수도 있다.

## 4. 도메인은 실험 대상으로 선정한다

**선정의 기준이 되는 가설:** 기존 LLM으로 처리 가능한 문제에서도, 도구·기억·인터페이스와 상태 연결이 **사용자의 반복 관리 비용을 실제로 낮추는가?**

**선행 조건:** 실제 반복 사용자 문제 / 분명한 입력·출력·환경·제약 / 필요한 데이터·권한 접근 / 중요 예외의 판정 가능성 / 8주 구현 가능성.

| 후보 | 핵심 장점 | 결정적 약점 | 기술 정리상의 우선 사용 |
| --- | --- | --- | --- |
| **프로젝트 변경·TASK 검토(A)** | 실제 프로젝트 기록, 반복 검토 기준, 권한·영향 예외, 이력 | 팀 특화/일반화 불확실, 간단한 규칙 기반 자동화로 충분할 수 있음 | **첫 주의 제품 가치 실험 우선 후보** |
| **반복 문서 리뷰(B)** | 적은 비용으로 입력·출력 반복 가능 | 단순 프로젝트 지침으로 이미 해결될 수 있음 | 반대 비교/저비용 대조 |
| **앱 리서치(C)** | APP-A/C 명세·도구/근거 구조를 재사용 가능 | 타겟이 같은 앱 판단을 반복할지 불명확, 외부 정보 변동 | **이미 승인된 기술 PoC 보존** |
| **기술 선택·설계(D)** | 목적 형성·조건 변경의 실제 문제 강도가 높을 가능성 | 객관적인 수용 기준과 반복 횟수 확보가 어려움 | 사용자 문제 수집·수동 고난도 검증 |

**내 기본 실행 제안:** A의 실제 반복 사례 2~3개로 빠르게 제품 가치 테스트를 시작한다. 동일 방식으로 C의 APP-A/C 자산에 적용 가능한 가설도 대조한다. A가 가치 신호가 약하거나 구현이 과도하면 A에 투자하지 않고 C를 유지한다. **두 도메인을 제품 수준으로 동시에 완성하지 않는다.** B/D는 각각 반증/사용자 사례 수집에 제한적으로 사용한다.

**중요한 권한 경계:** 현재 팀이 확정한 MVP는 APP-A/C다. A로 공식 개발 주제를 바꿀 결정은 별도 R01 승인 대상이다. 나는 1주 가치 실험에 필요한 가벼운 입력 사례 설계까지 기본값으로 진행하고, 팀 목표·제출 범위를 변경하는 조치는 진행하지 않는다.

## 5. 첫 가설 검증 시나리오 — A 후보

**PM-TEST-01: 승인된 검토 기준의 범위 있는 재사용**

| 차례 | X(입력) | Y(요구 출력) | 관찰할 기술 |
| --- | --- | --- | --- |
| **T1 기준 확인** | 공유 인터페이스 검토 기준을 사용자가 승인한 작업 | 승인된 기준의 내용·범위와 현재 결과 | 확인된 기억만 저장 |
| **T2 정상 반복** | 공유 영향이 없는 별도 변경 | 불필요한 검토를 요구하지 않는 현재 결과 | 적용 가능한 기준의 재사용 |
| **T3 자동 예외 발견** | 공유 계약을 바꾸는 변경, 사용자의 예외 힌트 없음 | 영향과 검토 필요성이 드러난 결과 | 충돌/범위 영향 탐지 |
| **T4 목표·기준 수정** | 시스템의 중간 결과를 본 사용자가 범위를 수정 | 갱신된 기준으로 후속 사례의 입출력 | 의도 형성·상태 변경의 실제 연결 |

이 표는 **입력·출력 문제 사례**다. 각 행을 어떤 도구/알고리즘으로 해결하는지는 다음 단계에서 선택한다. T3의 중요 예외 탐지는 단순히 사용자가 준 '예외가 있다'는 문장을 반복하는 것과 구분한다.

**실험 fixture 최소 3종:** 정상 적용 / 과제별 제약이 있어 부분만 재사용 / 기존 승인과 충돌하거나 새 승인이 필요한 경우. 예시가 너무 쉬워서 규칙만으로 가능하다면 그것도 중요한 관찰 결과다.

## 6. 검증: 문제 정의와 분리해서 설계

**기능 검증:** 해당 도메인의 구체 입력에서 필요한 결과가 나오고, 중요한 예외·권한 위반·근거 누락이 발생하지 않는가?

**제품 가치 검증:** 결과 품질을 유지하면서 사람의 **불필요한** 설명·교정·검토·상태 연결 비용을 줄이는가? 중요한 숙고와 의도 수정의 기회는 보호되는가?

**기준선과 후보:**
- **B1(핵심):** 능숙한 사용자 + 동일 LLM + 잘 관리된 프로젝트 지침·기억 + 동등한 입력 자료·도구
- **B2(적합할 때):** 작은 규칙/체크리스트 자동화(기계적 판정만으로 충분한지)
- **D0:** 동일 LLM + 찾아you의 상태 연결·판단 범위·예외 관리
- **B0(참고):** 직접 ChatGPT 사용(기억 정리가 약한 조건을 부당하게 강요하지 않음)

**측정:** 잘못된 판단 재사용, 사용자의 힌트 없이 중요한 예외 발견, 불필요 확인과 필요한 승인 구분, 반복 지시 횟수, 사람의 실제 작업 시간, 초기 설정·유지 비용, 결과의 정확성과 설명 가능성, 사용자 통제감.

**특히 반복 사용의 총비용:** 초기 기준 설정 시간 + 각 작업의 사용자 입력·검토·재작업 시간. **몇 번 반복해야 초기 투자비를 회수하는지**도 기록한다.

**반증:** B1/B2보다 결과가 나아지지 않거나 중요 예외를 놓치고 확인 부담을 키운다면 현재 도메인·설계를 재검토한다. 질문 수가 적다는 것만 성공 근거로 삼지 않는다.

실험 성공을 위한 수치 임계값은 실제 기준선 파일럿에서 측정 가능성을 확인한 뒤 본 평가 전에 고정한다. 사용자 가설과 제품 경쟁력은 아직 실증되지 않았다.

## 7. 기술 선택·개발 우선순위

**최초 구현 기준:** 실행 환경은 가능한 한 작은 **단일 오케스트레이션 + 상태 저장소 + 기존 모델/도구 어댑터**로 시작한다. 특정 프레임워크·에이전트 수를 먼저 고정하지 않는다.

- **먼저:** 하나의 문제 → 필요한 하위 입출력 → 기존 도구로 결과 확보 → 승인 판단 적용/예외 → 사용자 피드백 반영까지의 세로 단면.
- **그다음:** 실제로 필요해진 경우에만 일시중지·재개, 분기, 작업 병렬화, 상태 복구와 추가 도구를 강화한다.
- **보류:** 무제한 자기 분해, 동적 에이전트 생성 자체의 성능 과시, 범용 메모리 지식그래프, 모든 도메인을 위한 추상화.
- **실행 근거:** 입력·출력·조건과 실제 적용한 기록을 남기되, 별도 엔진을 새로 만들기 위한 형식화 작업으로 확대하지 않는다.

## 10. 핵심 정리

**상위 문제는 추상적이어도 엄밀할 수 있다.** 상위 X/Y/E/C가 넓게 정의되는 것은 의도적인 추상화이고, 이를 분해할수록 Xi/Yi/Ei/Ci가 구체화된다. **구체화할 대상은 문제의 입출력 구조이지 그 매핑을 구현하는 함수가 아니다.**

찾아you의 기술 목표는 '동적으로 에이전트를 만든다'거나 '많이 기억한다'는 기능의 완성이 아니다. 기존 LLM·도구·기억을 이용해 하위 문제들의 출력을 연결하고, 이전에 확인한 판단을 유효한 범위에서 재사용하며, 사용자에게 필요한 개입만 남기는 협업 결과를 보이는 것이다.

장기 목표는 계속 추상적으로 유지하고, 단기 구현은 하나의 구체적 하위 문제와 도메인에서 검증 결과로 수정한다.
