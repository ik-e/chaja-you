## 0. 의사결정자를 위한 요약

### 지향하는 제품

> 찾아you는 새로운 '지능'을 만드는 것이 아니라, **기존 LLM의 지능이 도구·인터페이스·기억·작업 상태를 활용해 사용자의 목적을 더 적은 인지적 노동으로 달성하도록 돕는 AI 협업 시스템**이다.

첫 번째 사용자 집단은 AI를 어느 정도 능숙하게 활용하고, 자신의 목적·결과를 메타 수준에서 검토·교정할 수 있지만 **유사 작업에서 반복되는 설명·판단·지휘·검증에 시간과 주의를 소모하는 사람**이다.

**8주 동안 구현·검증할 가장 작은 사용자 가치:** 사용자가 승인한 판단의 유효 조건을 저장하고, 유사 과제에서 그 판단을 적절히 재사용하며, **기존 판단을 적용해서는 안 되는 중요한 예외를 발견·보류·보고**함으로써 사용자 개입 비용을 줄이는 것.

**도메인 선정 원칙:** 리서치는 큰 업무 도메인 후보, 앱은 그 안의 대상 도메인 후보일 뿐이다. APP-A/C는 기존 기술 자산으로 보존하되 최적의 **제품 가치 검증 환경이라고 선결정하지 않는다**. 1주차에 여러 도메인을 동일 기준으로 비교하고 선택한다.

**핵심 확인 질문:** 강한 ChatGPT 기준선(프로젝트 지침·기억·도구 포함)에 비해 추가 제어·판단 상태 계층이 **결과의 안전성과 품질을 유지하면서 실제 사용자 부담을 줄이는가?**

## 2. 타겟 사용자와 페인포인트

### 2.1 첫 검증 타겟

**AI를 업무에 반복적으로 사용하는 사람 중, AI 결과를 비판적으로 평가하고 의도를 교정할 수 있으며, 유사한 판단·검토를 여러 번 수행하는 사용자.**

우선 관찰 집단 후보: 개인 개발자, 소규모 프로젝트 리더, AI로 문서·계획·작업 검토를 반복하는 실무자.

타겟의 핵심은 직업명보다 **행동 조건**이다. 일주일에 비슷한 판단을 여러 번 반복하고, 기존 모델과 도구를 직접 운용할 수 있으며, 반복 지시·검토 시간을 줄이려는 사람이 실험에 적합하다.

### 2.2 사용자 문제 후보

| ID | 사용자가 실제로 하는 일 | 검증할 비용/오류 |
| --- | --- | --- |
| U1 | 이미 합의한 목적·판단 기준을 후속 작업에 다시 제공 | 반복 입력 횟수·시간 |
| U2 | 새 작업에서 과거 판단을 적용할 수 있는지 직접 대조 | 적용 검토 시간·오적용 |
| U3 | AI 작업의 누락·충돌·승인 범위 이탈을 발견해 교정 | 직접 발견한 중대 예외·교정 |
| U4 | 새 정보·대안을 보고 목적을 수정한 뒤 작업 구조를 다시 지시 | 재설명·재계획 비용 및 목적 충족 |
| U5 | 결과·근거·상태를 문서와 다음 작업에 다시 연결 | 재구성 시간·누락 |

**주의:** 반복된 모든 사용자 개입이 낭비는 아니다. 새로운 목적을 발견하거나 중요한 결정을 승인하는 행위는 보호해야 한다. 줄이려는 것은 **불필요하게 반복되는 관리·교정**이다.

## 3. 문제 정의의 형식과 책임

### 3.1 엄밀한 문제 명세

문제를 다음처럼 표현한다.

**P = (X, E, C, Y, R)**

- **X — 입력 집합:** 요청·자료·이전 상태·확인된 판단·후속 사용자 피드백
- **E — 환경:** 사용 가능한 LLM, 도구, 자료원, 권한이 부여된 연결, 시간/작업 맥락
- **C — 제약 조건:** 승인·권한, 정보 접근/수집 정책, 품질, 가용 시간·비용, 재사용 범위, 실패 처리
- **Y — 출력 집합:** 사용자 결과, 판단/근거, 예외, 다음 사용자 결정과 갱신된 상태
- **R — 허용 입출력 관계:** 주어진 (x,e,c)에 대해 어떤 y가 문제를 만족하는지 판정하는 조건

**R(x,e,c,y)=true**이면 그 출력은 해당 입력·환경·제약에서 허용된다. 답이 여러 개 있을 수 있으므로 모든 문제를 단일 정답 함수로 억지 정의하지 않는다. **R은 구현 알고리즘이 아니라 요구되는 매핑/검증 조건**이다.

특정 도메인의 실제 요구를 넣지 않은 'AI가 목적을 달성한다'는 문장만으로는 R을 충분히 정의할 수 없다. 상위 수준에서는 공통 계약과 안전 제약을 명시하고, **도메인·사례별로 구체적인 정답/수용 기준을 인스턴스화**해야 한다.

### 3.2 상호작용 문제의 시간적 구조

사용자 의도는 고정된 숨은 정답이라고 가정하지 않는다. 중간 출력이 사용자의 다음 선택·목적 형성에 영향을 줄 수 있다.

- 시점 t의 입력: **x_t = (현재 요청, 관측 가능한 상태 s_t, 새 증거, 사용자 피드백)**
- 시스템의 행동·출력: **(a_t, y_t) = π(x_t, E_t, C_t)**
- 새 입력 및 상태: **s_(t+1) = T(s_t, a_t, y_t, 사용자 피드백_(t+1), 새 정보)**

여기서 π와 T는 **구현하려는 정책·상태 갱신 방식**이다. 문제의 허용 관계 R과 구별한다. 사용자는 출력에 반응해 선호를 수정할 수 있으므로 최초 발화에 모든 목적을 고정하지 않는다.

### 3.3 상위 사용자 문제 P0의 계약

| 항목 | 명세 |
| --- | --- |
| **입력 X** | 사용자의 현재 문제/요청, 명시된 목적·조건, 접근 가능한 도구와 자료, 이전에 승인한 판단과 범위, 이후 피드백 |
| **환경 E** | 기존 LLM, 문서·파일·외부 업무 도구, 지속 상태 저장소, 인터페이스, 사람이 참여할 수 있는 환경 |
| **제약 C** | 승인되지 않은 외부 변경 금지; 미확인을 사실로 단정하지 않음; 판단 적용 범위 준수; 개인정보·수집 정책; 시간·자원 한도; 사용자의 거절·수정 가능성 |
| **출력 Y** | 현재 목표에 유효한 해결 결과 또는 부분/차단 상태, 근거·수행 내역, 재사용 판단과 적용 이유, 해결에 필요한 새로운 사용자 결정, 변경된 작업/판단 상태 |
| **허용 관계 R** | 결과가 **사용자가 현재 확인한 목적과 제약**을 충족하거나, 불충분하면 이유·미해결 항목을 드러내야 함. 승인 범위 밖 판단을 실행하지 않고 재사용 조건을 위반하지 않아야 함 |

**제품 최적화 목표(결과 허용 조건과 별개):** 품질·안전·권한을 악화시키지 않는 범위에서 **사용자의 적극적 작업 시간, 불필요한 재설명·교정·판단 요청 및 상태 연결 비용**을 줄인다. 이 비용은 제품 가치의 측정 대상이지, R의 모든 내용을 대체하는 단일 점수가 아니다.

### 3.4 구현 문제와 사용자 문제의 분리

- **사용자 문제:** 같은 품질의 목적 달성에 필요한 인간의 반복 관리 부담을 줄일 수 있는가?
- **시스템 구현 문제:** 어떤 메모리 표현과 실행 제어가 판단 재사용/예외 구분을 보장하는가?
- **검증 문제:** 실제 반복 과제에서 사용자 시간과 실수가 감소하는가?

'기억을 만든다', '에이전트를 동적으로 생성한다'는 기술 솔루션이지 문제 정의가 아니다.

## 4. 상위 문제의 하위 문제 분해 및 계약

| 하위 문제 | 입력 | 요구 출력 | 환경·제약의 핵심 | 허용/실패 조건 |
| --- | --- | --- | --- | --- |
| **P1 의도·목표 형성 지원** | 현재 요청·이전 맥락·대안·피드백 | 명시/추론/미확인으로 나눈 목표·수정 내용 | 사용자 자율성, 확인되지 않은 의도를 확정하지 않음 | 사용자 반응 없이 새로운 목표를 '승인' 처리하면 실패 |
| **P2 문제 분해** | 현재 목표·완료 조건·자료/도구 능력 | 필요한 하위 문제, 의존성, 종료/보류 조건 | 접근 범위·자원 한도 | 필수 하위 문제 누락 또는 불필요 작업 강행은 실패 |
| **P3 승인 판단의 재사용** | 새 작업·기존 판단과 승인 범위·현재 조건 | 적용/미적용/보류 판단과 근거 | 과제 조건, 유효 범위, 규칙 충돌 | 과제별 사실을 일반 규칙으로 오적용하면 실패 |
| **P4 도구·자료 실행** | 하위 작업·허용된 도구/자료·예산 | 결과·근거·실패/미확인 상태 | 권한·수집 정책·timeout | 무권한 실행·출처 없는 단정은 실패 |
| **P5 예외 발견 및 대응** | 실행 자료·기존 규칙·현재 관측 | 발견된 충돌/범위 이탈/미확인과 보류·확인 요청 | 위험도·사용자 결정권 | 사용자가 알려주기 전에 검출해야 하는 예외를 놓치거나, 발견 후 무시하면 실패 |
| **P6 상위 결과 통합·재계획** | 각 하위 출력·변경된 의도·기존 결과 | 상위 목표의 해결/부분/차단 판정, 후속 작업, 변경 영향 | 증거 충돌·완료 조건 | 작업들이 완료됐다는 이유만으로 상위 문제를 완료 처리하면 실패 |

각 하위 문제는 다시 분해할 수 있다. 그러나 첫 실험에서 범용 재귀 분해기를 구현할 이유는 없다. **선택한 도메인에서 실제 필요한 깊이와 분기만 구현**한다.

## 5. 판단의 종류와 재사용 계약

'판단' 하나로 묶지 않고 적어도 다음을 구분한다.

| 종류 | 예시 | 권장 저장·적용 원칙 |
| --- | --- | --- |
| **사용자 가치·선호** | 현재는 구현 속도가 중요함 | 적용 맥락·수정 가능성 보존. 새로운 목표에 자동 확정하지 않음 |
| **지속 작업 정책** | 검토 결과에서 미확인을 명시 | 승인 범위와 조건이 같으면 재사용 후보 |
| **평가 기준** | 공유 인터페이스 변경은 관련 담당자 확인 필요 | 구체 입력에서 충족 여부 검증 후 사용 |
| **과제별 제약** | 이번 TASK는 금요일까지 | 새 TASK에 자동 승계하지 않음 |
| **과거 결론·결정** | 이전에는 설계 A를 채택 | 근거·전제·현재성 확인, 현재 결론으로 자동 치환 금지 |
| **검토된 경험** | 이전 작업에서 충돌하던 자료 유형 | 유사 상황 탐색에 참고, 사용자 규칙으로 자동 승격하지 않음 |

**DecisionPolicy 최소 계약(예시):**
`{id, type, statement, scope, applicability, exceptions, authority, source_revision, review_when, status}`

**적용 결과 최소 계약:**
`{policy_id, task_id, applied: true|false|"deferred", rationale, checked_conditions, missing_conditions, exception_ids}`

실제 MVP에서 모든 종류를 완전 구현하지 않고, **평가 기준 1종 + 과제별 제약의 오적용 방지**를 우선한다.

## 6. 실험 도메인 선택 — 리서치 고집하지 않음

### 6.1 원칙

도메인은 제품의 전제가 아니라 **H1~H4를 식별하기 위한 실험 변수**다. 선택 기준은 '흥미로움'이나 기존 코드 양만이 아니라 **같은 판단이 실제로 반복되는지, 적용 가능한 경우와 금지되는 경우를 구별할 수 있는지, 사용자 부담과 출력 품질을 측정할 수 있는지**다.

**선행 게이트(하나라도 실패하면 제외):**
1. 해당 타겟 사용자가 **실제로 반복하는 과제**인지 최소 사례 확보
2. 접근 가능한 입력·상태·도구/자료와 허용된 이용 조건 존재
3. 정상 적용·부분 적용·적용 금지/예외를 **독립적으로 판정**할 수 있음
4. 8주 내 구현·비교·시연 가능, 잘못된 자동 실행을 통제 가능
5. 동일 모델을 충분히 잘 활용한 **강한 기준선**을 구성할 수 있음

**통과 후보 평가(사전 가중치 제안, 추정 점수를 사실로 기록하지 않음):**
- 반복 판단의 실제 빈도·부담 **25%**
- 재사용 경계/예외가 관찰되는 정도 **20%**
- 입출력·정답/수용 기준의 판별 가능성 **20%**
- 합법적 도구/자료 접근 및 권한 안전성 **15%**
- 8주 구현·통합 비용 **10%**
- 강한 AI 기준선 대비 추가 효과 검증 가능성 **10%**

1~5점 점수는 **후보별 실제 2~3개 사례의 자료와 팀 평가**를 확보한 뒤 부여한다. 외부 관측 전 임의 숫자로 우승자를 만들지 않는다. 동점이면 적은 구현 비용과 더 좋은 검증 가능성을 우선한다.

### 6.2 도메인 후보 비교 — 현재는 정성 가설

| 후보 | 유효한 핵심 실험 | 장점 | 문제·위험 | 임시 판단 |
| --- | --- | --- | --- | --- |
| **A. 프로젝트 문서·TASK 검토/변경 영향 관리** (비리서치) | 반복 검토 기준 재사용, 공유 인터페이스 변경 예외, 승인 경계, 목표 변경 시 영향 추적 | 실제 팀 워크플로가 존재하고 버전·검토 기록이 있음; 판정 가능한 fixture 생성 가능 | 사용자 본인 팀에 과적합 위험, GitHub 변경/권한·통합 부담 | **1차 검증 후보** |
| **B. 반복 문서 리뷰·수정** (비리서치) | 문체/요건/검증 체크 기준 재사용, 과제별 예외 | 입력·출력 비교 쉬움, 낮은 구현 비용 | 문제 분해·예외 판단이 지나치게 단순할 위험; 지침 파일만으로 해결 가능 | **저비용 대조 후보** |
| **C. 앱 리서치(현 APP-A/C)** | 조건 분해, 공식 근거·미확인, 분기/보류 | 기존 요구사항·기술 자산 존재, 근거 검증 훈련에 적합 | 숙련 사용자에게 반복 앱 비교가 실제 고통인지 미확인, 출처 접근·최신성 변동 | **기술 PoC·대조/예비 후보** |
| **D. 기술 선택·설계 의사결정** (리서치+기획) | 의도 형성, 조건 변화, 판단 근거와 재사용 | R01의 실제 고통과 가까움, 장기 가치 검증에 적합 | 과제별 판단이 덜 반복되고 정답·품질 판정이 주관적일 수 있음 | **인터뷰·수동 실험 후보** |

**잠정 권장:** 실험 첫 주에는 **A·B·C**로 동일한 간단한 시험 과제를 구성하고, **D**는 실제 사용자 사례로 수요·문제 강도를 확인한다. A의 반복 판단/검증 자료가 충분하다면 첫 제품 가치 실험으로 선택하고, 그렇지 않으면 B나 C를 채택한다. **아직 어느 것도 확정하지 않는다.**

즉, *APP-A/C를 계속 보유하되 새로운 가설 때문에 앱만 고집하지도, 새롭다는 이유로 기존 기술 자산을 버리지도 않는다.*

## 7. 임시 1순위 도메인 A의 구체 입출력 예시

**문제 ID: PM-REVIEW-01 — 팀 프로젝트 변경/TASK 검토에 기존 승인 기준을 재사용**

### 7.1 입력·환경·제약·출력·매핑

| 요소 | 구체 명세 |
| --- | --- |
| **입력 X** | 검토 요청, 현재 TASK/설계 요약과 변경 내용, 기준 리비전, 이전 승인된 리뷰 기준과 예외, 사용자 피드백 |
| **환경 E** | GitHub에 존재하는 파일·PR/TASK·검토 기록, LLM, 읽기 도구, 비교 UI, 제한된 상태 저장소 |
| **제약 C** | 읽기·검토 중심; PR 승인/병합·정본 변경은 별도 명시적 권한 필요; 원본 revision 추적; 타 TASK의 승인 기준 자동 일반화 금지; 민감정보 비노출 |
| **출력 Y** | 검토 결과(충족/미충족/미확인), 적용/비적용한 기존 판단과 이유, 발견된 중요 예외, 사용자 확인 항목, 후속 작업 제안 |
| **관계 R** | 변경이 공유 계약에 영향을 미치면 담당 검토를 요구하며, 영향 없는 단순 변경에는 불필요한 승인을 요청하지 않음; 사용자가 확인하지 않은 새로운 정책은 확정 적용하지 않음; 각 판정은 입력 revision 및 확인 가능한 근거에 연결 |

### 7.2 최소 연속 과제

- **T1 최초 검토:** 사용자가 PR/TASK 검토에서 '공유 인터페이스 변경은 관련 담당자 확인 필요', '미확인 항목은 합격으로 처리하지 않음'을 **명시적으로 승인**. 이력을 저장.
- **T2 반복 검토:** 변경 범위가 다른 비공유 TASK를 제공. 기준을 적용하되 **공유 인터페이스 검토를 불필요하게 요구하지 않아야 함**. 재설명 없이 결과 제공.
- **T3 예외 탐지:** 기존과 비슷해 보이나 실제로는 공유 인터페이스에 영향을 주는 변경을 제시. **사용자의 힌트 없이** 예외를 발견하고 추가 검토를 요청. 자동 병합/승인 금지.
- **T4 선택적 확장:** 중간 출력에서 새 위험·대안을 제시해 사용자가 검토 기준을 수정하면, 확정한 변경만 이후 판단에 반영.

여기서 T1~T3는 같은 사용자·같은 평가 기준의 반복이라는 점이 핵심이다. T4는 의도 형성과 문제 재계획을 위한 보조 실험으로, 일정 부족 시 수동 진행한다.

### 7.3 예상 사용자 화면(세 영역)

1. **현재 검토 결과:** 대상·버전·충족/미충족/미확인 및 근거
2. **판단 재사용 근거:** 적용한 기준, 적용하지 않은 기준과 이유
3. **주의가 필요한 예외:** 새 충돌·범위 이탈·승인 필요 결정과 다음 행동

정상 처리에서 2번은 접고, 3번이 없으면 불필요한 추가 질의를 요구하지 않는다.

## 8. 제품 가설과 검증 계약

**이미 관찰 가능한 LLM 능력:** 의도 해석, 대안 제시, 문제 분해, 피드백에 따른 수정. 이것을 다시 'LLM이 가능한가'라는 실험으로 만들지 않는다.

| ID | 가설 | 비교할 조건 | 관측/반증 |
| --- | --- | --- | --- |
| **H1 주가설** | 조건부 판단 재사용이 불필요한 반복 지시·교정·사용자 시간을 줄인다 | 동일 사용자의 연속 T1~T3 | 중복 지시/적극적 시간 감소가 없거나 설정 비용만 늘면 반박 |
| **H2 주가설** | 범위/권한/예외 검사가 오적용을 방지하고 중요한 예외를 표면화한다 | 정상 재사용·부분 재사용·금지 사례 | 중요 예외 누락·무권한 변경이 있으면 합격 불가 |
| **H3 보조** | 탐색적 출력과 피드백이 사용자 목표 형성에 유용하다 | 질문만 vs 대안/부분 결과 + 질문 | 사용자가 선택 이유를 설명하지 못하거나 편향 유도 |
| **H4 보조** | 변화한 조건에 따라 하위 문제만 재구성하는 편이 적합하다 | 고정 계획 vs 조건부 변경·재실행 | 필수 작업 누락, 과잉 작업, 중복 검증 |
| **H5 사업성/수요** | 숙련 사용자에게 반복 판단 관리가 실제로 빈번하고 부담스럽다 | 실제 최근 업무 기록/인터뷰 | 반복 문제 강도·빈도/재사용 의향 낮으면 도메인 재선정 |

### 8.1 강한 기준선

- **B0:** AI를 능숙하게 활용하는 사용자의 직접 ChatGPT 사용(충분한 프롬프트/수동 검토 포함)
- **B1:** 동일 모델 + 프로젝트 지침/저장된 판단·기억 + 가능한 동일 자료·도구. **가장 중요한 경쟁 기준선**
- **D0:** 동일 LLM + 찾아you의 명시적인 판단 상태·적용 조건·예외/실행 관리

B1이 D0와 실질적으로 같다면 전용 상태 엔진의 가치가 약할 수 있다. 단순 저장된 텍스트 규칙도 제대로 활용하도록 **B1을 고의로 불리하게 만들지 않는다**.

같은 입력 사실·자료·권한·모델 버전·과제 예산을 최대한 맞춘다. 연결 기능 차이가 있으면 별도로 기록하고, 사전 준비/기억 입력 비용까지 총 사용자 시간에 포함한다.

### 8.2 정확성/시간/인지적 부담 측정

- **매핑 적합성:** 사전 작성한 과제별 수용 기준 및 독립 리뷰어 검토(충족/실패/불명확)
- **안전·권한:** 금지된 판단 적용, 누락된 중요 예외, 승인되지 않은 작업 변경
- **사용자 개입:** 반복 지시, 불필요한 확인 요청, 사용자가 새로 발견한 오류, 반드시 필요했던 승인 **구분**
- **비용:** 적극적 사용자 시간(도구 대기 제외와 포함 모두 기록), 초기 설정·정책 유지 비용, 모델 호출·토큰·실행 시간
- **주관 지표:** 인지적 부담과 사용자가 결과를 통제할 수 있다고 느끼는 정도(간단한 비교 설문)

**예외 발견**(자료만 보고 감지)과 **예외 대응**(감지 후 처리)을 따로 평가한다. 사용자가 이미 예외를 설명한 사례로 '자동 발견 성공'을 주장하지 않는다.

### 8.3 실험 설계와 잠정 합격 원칙

- 서로 다른 정상/부분/금지 사례 **8~12개**를 먼저 작성하고 예상 출력/판정 근거를 기록한다.
- 소수의 숙련 사용자 **3~5명**에게 기존 작업과 원형을 비교하게 하되, 일반화 가능성을 과장하지 않는다.
- 가능한 경우 과제 순서와 조건 배정을 교차해 학습·순서 효과를 완화한다.
- **중대 무권한 실행·중대한 예외 누락이 관찰되면 기능 범위를 줄이거나 중단**한다.
- 사용 시간/반복 개입의 정량 기준은 첫 기준선 파일럿에서 측정 가능성과 변동폭을 보고 **본 평가 전에 확정**한다. 결과를 본 뒤 임계값을 사후 변경하지 않는다.
- 사용자 개입이 적더라도 결과 품질이 저하되거나 의도 형성·중요한 숙고 기회가 억제되면 성공으로 보지 않는다.

**담당 제안(미확정):** R01 사용자 과제/판정/통합, R02 자료·도구·접근 정책, R03 문제/작업 구성, R04 피드백·예외 UI(복귀 후), R05 승인 판단 상태/API. 개인 PR 검증과 공유 인터페이스 검증은 담당자를 나누고, R01이 모든 PR을 단독 승인하는 구조를 만들지 않는다.

## 11. 주요 위험과 보류 판단

1. **도메인을 바꿔 기술 자산을 잃는 위험:** APP-A/C는 폐기하지 않고 독립 PoC로 보존한다. 전환 비용을 도메인 선정 점수에 반영한다.
2. **기존 LLM 활용만으로 충분한 위험:** B1과 차이가 없으면 복잡한 기억/판단 제어 엔진을 필수로 주장하지 않는다.
3. **사용자 개인 워크플로 과적합:** R01 본인 기록으로 정답표를 만들더라도 다른 사용자·다른 과제에서 확인한다.
4. **형식화의 과신:** 상위 추상 계약의 R은 모든 입력을 수학적으로 판정 가능한 완전한 규칙이 아니다. 최소 도메인 과제에서 판별 가능한 부분을 명시한다.
5. **예외 판단의 오류:** 자동 허용의 실수 비용이 크면 보류·사용자 확인을 선택한다. 무조건 확인을 남발해 부담을 늘리지 않는다.
6. **수집·권한:** 공식 API·허용된 자료·실사용자 승인 범위 준수. 외부 사이트 무단 반복 크롤링을 실험 도구로 사용하지 않는다.
7. **장기 비전과 현재 정본의 차이:** 공식 INTENT는 여전히 **리서치와 앱 MVP를 우선**한다. 본 문서의 비리서치 도메인 후보 선정은 R01의 변경 판단 전까지 설계 제안이다.

## 12. 후속 결정 요청과 즉시 실행 가능한 다음 작업

**결정할 것(아직 확정하지 않음):**
1. 8주 제품 가치 검증에서 **도메인 선택을 다시 열지**, 기존 APP-A/C 위에서 검증을 우선할지
2. A/B/C 후보의 실제 사용 사례·판정 가능한 입력을 확보했는지
3. 결과에 따라 공식 INTENT/Target Design/MVP/평가·WBS를 개정할지
4. 사용자 판단을 자동 재사용할 수 있는 **최초 권한 범위**를 어디까지로 제한할지

**다음 작업의 실제 입출력 계약:**
- **입력:** A/B/C의 동일한 평가 항목, 각 도메인의 반복 작업 2~3개, 승인 규칙·예외 사례, 사용 가능한 도구/자료, 초기 구현 비용
- **출력:** 선정/보류/기각 도메인과 근거, 최소 3회 연속 시나리오, 해당 도메인의 `X/E/C/Y/R`, B1 기준선 실행 자료, 도메인 전환 영향과 수정이 필요한 현재 정본 목록
- **완료 판정:** 근거 없는 점수 대신 관측 자료로 후보를 비교하고 R01이 명시적으로 선정 여부를 결정했을 때

### 최종 결론

**찾아you의 목표는 '리서치를 잘하는 AI'도, '기억이 있는 챗봇'도 아니다.** 기존 지능이 사용자의 확정된 판단과 맥락을 적절하게 활용하고, 새로운 의도와 예외를 다루도록 **도구·기억·인터페이스·실행 상태를 구성함으로써 반복적인 사용자 관리 노동을 줄이는 것**이다.

첫 도메인은 그 비전을 표현하는 분야가 아니라 **문제의 입출력 매핑을 명확하게 정의하고, 무엇이 작동하고 실패했는지 가장 분명하게 검증할 수 있는 실험 환경**으로 선정해야 한다.
