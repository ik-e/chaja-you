# 크몽·탈잉·숨고에서 강사 계정으로 레슨을 등록하려면

2026-11-23 · R02 조사 · R05 TASK-030 참고 자료

**1차 검증안은 서버에서 사이트별 초안을 준비하고, 강사의 기기에서 로그인과 등록을 진행하는 혼합 방식이다.** 설치가 첫 등록을 어렵게 한다면 강사가 서버의 원격 브라우저에 직접 로그인하는 방식도 비교한다. R02가 확인해 준 전제는 세 곳 모두 레슨 등록용 공식 제휴 API가 없다는 것이다. 강사가 직접 인증한 뒤 화면을 계속 지켜보지 않아도 되는 것이 목표다. 강사의 PC를 끌 수 있어야 하는지는 미확인이다.

## 플랫폼마다 어디까지 확인했나

| 플랫폼 | 강사가 들어가는 방법 | 로그인 후 등록 대상과 R05 확인 사항 |
| --- | --- | --- |
| 크몽 | 이메일 또는 기존에 연동한 SNS로 로그인한다. 처음 판매하는 강사는 전문가 인증 상태를 확인한다. | 전문가 계정의 **서비스 판매글**을 작성해 심사를 요청한다. 접수와 실제 게시 사이에 크몽 승인이 있다. 판매 이용약관 제9조는 비정상적인 방법의 등록과 실질적으로 동일한 글의 중복 등록을 제한한다. 로컬·서버 각각에서 초안 입력·사진 첨부·심사 요청·결과 확인 중 어디까지 보조할 수 있는지 확인한다. | 탈잉 | 기존 튜터 계정에 쓰던 이메일·카카오·네이버·Apple 등의 방식으로 로그인한다. 같은 이메일이나 전화번호여도 로그인 방법에 따라 다른 계정이 열릴 수 있다. | **PC 탈잉 스튜디오의 클래스**가 대상이다. 튜터 등록에는 프로필 이미지·전화번호 인증·튜터 소개가 필요하다. 기존 튜터 프로필을 확인한 뒤 클래스 작성·첨부·등록 신청·결과 확인 중 로컬·서버 각각에 허용되는 단계를 묻는다. 예전 가이드의 페이스북 항목은 지원 종료 공지가 있다. [로그인 안내](https://talingtutorguide.oopy.io/26341f37-bd7f-8049-b2dd-cdc835b14a19) · [튜터 등록](https://talingtutorguide.oopy.io/tutorprofile) · [PC 클래스 관리](https://talingtutor.oopy.io/talingone2) · [공지](https://taling.oopy.io/) |
| 숨고 | 공식 웹 로그인 화면에서 이메일·비밀번호, 카카오, 네이버를 확인했다. 휴대폰 본인인증을 할 때는 강사 본인 명의 번호를 사용한다. | 우선 대상은 **고수 프로필에 레슨 서비스·소개·사진을 등록하는 일**이다. 고객별 견적 발송은 숨고캐시가 필요한 별도 작업이다. 고수 프로필 화면에서 소개·사진 입력, 저장, 공개 결과 확인을 보조할 수 있는지 문의한다. ## 강사가 직접 로그인할 때 등록은 어디에서 실행할까

| 비교 항목 | 로컬 실행 | 서버 실행 |
| --- | --- | --- |
| 첫 이용 | 강사가 평소 브라우저에서 로그인한 뒤 등록 화면에서 확장을 켠다. 같은 프로필의 유효한 로그인 상태를 활용할 수 있다. 지원하지 않는 브라우저라면 브라우저 전환·설치·재로그인이 첫 이용 시간에 더해진다. | 강사가 웹에서 자기 작업용 원격 브라우저를 열어 플랫폼 공식 화면에 직접 로그인한다. 확장 설치는 생략할 수 있지만 평소 PC의 로그인 상태는 이어지지 않는다. 소셜 로그인·휴대폰 인증이 그 환경에서 가능한지는 플랫폼별 실험이 필요하다. |
| 자리를 비우는 경우 | 승인 후 다른 일을 하는 동안 진행하도록 설계할 수 있다. PC가 잠자기에 들어가거나 등록 탭이 닫히면 중단한다. | 사용자 연결이 끊겨도 서버가 작업을 유지하도록 설계할 수 있다. 원격 세션이 유효하고 추가인증이 필요 없을 때만 PC 종료 후에도 진행할 수 있다. |
| 계정과 사진 | 로그인 상태와 인증 입력은 강사 기기에 둔다. 승인된 사진을 강사가 선택하면 그 기기에서 첨부한다. | 비밀번호를 서비스 양식으로 수집하지 않아도 로그인 입력·화면과 세션은 원격 환경을 거친다. 첨부할 사진도 그 환경으로 전송한다. 강사별 격리, 인증 중 녹화·로그·AI 화면 접근 차단, 종료 후 세션·임시 사진 폐기가 필요하다. |
| 팀 운영 | OS·브라우저 조합별 설치·권한·사진 첨부를 시험하고 확장을 배포·갱신한다. Chrome·Edge는 코드 재사용 여지가 있고 Safari는 별도 배포·검증이 필요하다. | 실행 브라우저는 통일할 수 있다. 대신 동시 작업 수에 따른 브라우저 실행 비용, 화면 연결, 인증 대기, 시간 초과와 복구를 팀이 부담한다. |

Chrome의 임시 탭 권한과 AWS의 사용자 조작형 원격 브라우저는 두 구조의 기술 사례다. 두 자료에서 크몽·탈잉·숨고의 자동 등록 허용이나 로그인 성공까지 확인할 수는 없다. [Chrome 탭 권한](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) · [Edge 확장 호환](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/port-chrome-extension) · [Safari 확장 배포](https://developer.apple.com/safari/extensions/) · [AWS 원격 브라우저](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-dcv-integration.html)

**혼합 방식의 작업 경계.** 서버는 강사가 제공한 자료를 사이트별 문구로 정리하고 강사가 승인한 버전과 사이트별 결과를 관리한다. 확장은 인증을 마친 강사 계정에서 허용된 항목만 입력·첨부·제출한다. 서버로는 접수·심사·게시 등 확인된 상태, 링크와 필요한 다음 행동을 보낸다. 강사 기기의 로그인 쿠키를 서버로 옮기지 않는다. 사용자가 일반 웹사이트에서 다른 사이트를 열기만 한 경우에는 직접 입력·제출할 수 있도록 문구와 사진을 제공하고 결과는 사용자 확인으로 표시한다. [브라우저 동일 출처 정책](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) · [Playwright 인증 상태](https://playwright.dev/docs/auth)

**비밀번호 복호화 대행.** 로컬과 서버 모두 강사가 직접 인증할 수 있다. 강사가 비밀번호를 맡기고 우리 프로그램이 복호화해서 로그인하는 경우, 복호화한 기기가 원문을 사용할 수 있고 소셜 로그인이나 추가인증도 남는다. 강사 기기에서 복호화해도 확장 설치·기기 유지 부담은 그대로다. 서버에서 복호화하면 운영팀이 원문 처리와 로그인 세션을 함께 보호해야 한다. 직접 인증이 가능하다는 사용자 조건을 고려해 두 실행 방식 모두 직접 인증을 우선한다. [OWASP 비밀번호 보관 지침](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [R02 사용자 검증](2026-11-23_lesson-pain-priority.md)

## 조사에서 남은 질문과 비교 기준

아래는 오늘 조사에서 나온 검증 후보와 측정 방법이다. 후속 확인 항목과 담당은 11월 24일 회의가 끝난 뒤 정한다.

1. **운영사에 물어볼 수 있는 질문.** “강사가 귀사 화면에서 직접 인증한 뒤, 외부 유료 서비스가 강사가 승인한 문구 입력, 사진 첨부, 최종 제출, 결과 조회를 할 수 있나요? 강사 기기의 브라우저 확장과 강사가 직접 인증한 서버 원격 브라우저 각각에서 보조할 수 있는 단계, 강사가 직접 눌러야 하는 단계, 시험 계정 제공 여부를 알려주세요.” 크몽은 심사 요청·반려 확인, 탈잉은 기존 튜터 계정 식별·클래스 등록 신청, 숨고는 견적 발송 없이 고수 프로필만 편집하는 권한을 특정한다.
2. **같은 모의 공고로 비교할 때의 관측값.** 맥·윈도우에서 평소 쓰는 브라우저를 기록하고, 확장 설치·권한 승인과 원격 브라우저에서의 재로그인에 드는 직접 시간을 각각 잰다. 다른 계정, 동의 취소, 세션 만료에는 제출을 멈춘다. 제출 직후 응답이 끊기면 ‘제출 여부 확인 필요’로 두고 기존 접수부터 조회한다. 강사에게는 확인된 상태, 게시 링크가 생긴 경우 그 링크, 본인이 해야 할 다음 행동을 표시한다.
3. **운영사 허용 후 실험할 경우의 기준.** 동의한 기존 강사가 자료 제공·초안 승인·로그인·본인인증·추가 질문에 직접 쓴 시간을 합산한다. 세 곳 합계 **20~30분은 R02의 희망 기준**이다. 첫 이용의 확장 설치·브라우저 전환·권한 승인도 직접 시간에 포함한다. 신규 전문가 가입, 기계 처리, 플랫폼 심사 대기는 따로 기록한다. 설치로 포기한 사람, 추가인증 횟수, 결과가 확인된 등록 한 건당 서버 비용도 비교한다. 인증을 마친 뒤 화면을 지켜보지 않아도 되는지도 별도로 확인한다.

로컬 설치 부담이 크거나 PC 종료가 실제 이용 조건이고 원격 로그인·제출이 허용되며 시험을 통과하면, 그 플랫폼에는 서버 실행을 우선 검토한다. 허용 범위가 확인되지 않은 플랫폼은 강사가 직접 제출하는 흐름으로 평가한다. 최종 선택은 R05의 조사와 R01의 범위 결정에 따른다.

공식 로그인·도움말·약관과 기존 사례를 대조한 문서 조사다. 실제 계정 접속, 자동 입력·제출 시험, 운영사 회신은 없었다. R05가 비교할 세부 근거와 미확인 항목은 [조사 원본](../../../artifacts/research/R02_PLATFORM_LOGIN_20261123.json)에 기록했다.
