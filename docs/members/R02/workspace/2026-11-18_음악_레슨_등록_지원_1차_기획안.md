# AI 기반 음악 레슨 다중 플랫폼 등록 지원 서비스

> **상태: 1차 기획안**  
> 회의에서 **레슨 선생님을 위한 다중 플랫폼 등록 지원**을 우선 구체화하기로 했습니다. 기존의 지도 기반 레슨 탐색·가격 비교 아이디어는 후속 검토안으로 유지합니다. 이번 논의가 팀의 최종 프로젝트 주제 확정이나 구현 완료를 의미하지는 않습니다.

---

## 1. 프로젝트 소개

### 한 줄 소개

음악 레슨 선생님이 **레슨 정보를 한 번 정리하면**, 여러 플랫폼의 형식과 요구사항에 맞춰 내용을 준비하고, 허용되는 범위에서 실제 등록까지 지원하는 AI 서비스입니다.

### 기획 배경

음악 레슨 선생님은 레슨생을 모집하기 위해 여러 플랫폼과 커뮤니티에 수업을 알립니다.

이때 수업의 기본 내용은 비슷하지만, 플랫폼마다 입력 항목이나 글의 형식, 가격 옵션, 게시 방식이 다를 수 있습니다. 선생님은 이미 정리한 정보를 다시 입력하거나, 특정 플랫폼에 맞게 내용을 수정하고 추가로 준비해야 합니다.

이 프로젝트는 선생님이 **레슨을 알리기 위해 반복하는 정보 정리와 등록 업무**를 줄일 수 있는지 확인하고자 합니다.

---

## 2. 문제를 확인하게 된 경험

기획자는 직접 음악 레슨을 제공하면서 여러 플랫폼과 커뮤니티를 통해 레슨생을 모집했습니다.

- 네이버 카페에는 약 일주일 주기로 레슨 글을 올렸습니다.
- 뮬에서는 매일 기존 글을 **‘최신글 올리기’**로 갱신했습니다.
- 다른 플랫폼에는 모두 같은 주기로 새 글을 올린 것이 아니라, **사이트마다 관리 방식이 달랐습니다.**
- 문의를 받으면 공고에 이미 적어 둔 커리큘럼·장소·월 가격 등을 다시 설명해야 하는 불편도 있었습니다.

또한 회의에서는 한 플랫폼에 레슨을 등록할 때 **여러 가격 옵션을 구성해야 했던 경험**이 공유됐습니다. 원래 준비한 수업 정보를 그대로 옮기는 것만으로는 부족해, 플랫폼에 맞는 수업 시간과 가격을 추가로 정리해야 했던 사례입니다.

이 경험들은 문제를 발견한 출발점입니다. 다만 다른 선생님들도 같은 어려움을 얼마나 자주 겪는지, 최초 등록에 실제로 얼마나 시간이 드는지는 추가 확인이 필요합니다.

---

## 3. 페인포인트

### 핵심 불편

> 음악 레슨 선생님은 여러 플랫폼에 수업을 알리기 위해, 같은 레슨 정보를 사이트별 형식과 요구사항에 맞춰 반복해서 정리하고 입력해야 합니다.

### 실제로 겪을 수 있는 어려움

1. **같은 내용을 여러 번 입력합니다.**  
   레슨 분야, 수업 장소, 커리큘럼, 가격, 강사 이력 등을 플랫폼마다 다시 작성하거나 복사해 넣어야 합니다.

2. **플랫폼별 형식이 다릅니다.**  
   어떤 곳은 자유로운 게시글로, 어떤 곳은 정해진 입력 항목에 맞춰 수업을 설명해야 할 수 있습니다.

3. **처음에 없던 정보를 추가로 정해야 할 수 있습니다.**  
   한 가지 수업을 준비했더라도 플랫폼에서 여러 상품이나 가격 옵션을 요구하면, 각 과정의 시간·가격·수업 내용을 새로 구성해야 할 수 있습니다.

4. **등록 후 관리 방식도 다릅니다.**  
   어떤 곳은 게시글을 다시 올리고, 어떤 곳은 기존 글을 최신글로 갱신하거나 문의에 답해야 합니다.

## 4. 문제 정의

> 음악 레슨 선생님은 여러 플랫폼에서 레슨생을 모집할 때, **같은 수업 정보를 사이트별 입력 방식과 요구사항에 맞게 반복해서 준비하고 등록하는 데 시간과 노력이 듭니다.**

### 현재 업무 흐름

| 단계 | 선생님이 하는 일 | 발생할 수 있는 불편 |
|---|---|---|
| **레슨 정보 준비** | 분야·가격·장소·커리큘럼·이력 정리 | 같은 내용을 여러 곳에서 재사용해야 함 |
| **플랫폼 확인** | 각 사이트의 입력 방식과 필요한 정보 확인 | 플랫폼마다 무엇을 요구하는지 다시 살펴봐야 함 |
| **내용 수정** | 제목·소개·가격 옵션 등을 사이트에 맞게 조정 | 원래 준비하지 않은 정보나 상품 구성이 필요할 수 있음 |
| **등록** | 각 플랫폼에 내용을 입력하고 게시 | 여러 사이트에서 같은 작업을 반복해야 함 |
| **게시 후 관리** | 필요에 따라 글 갱신이나 문의 응대 | 플랫폼마다 관리 방법과 주기가 다름 |

이번 기획은 이 중 **레슨 정보 준비부터 최초 등록까지**를 우선 검토합니다. 게시글 갱신과 문의 응대는 후속 기능으로 분리합니다.

## 5. 타깃 사용자

### 주요 사용자

기타·베이스·드럼·보컬·건반·미디·작곡·믹싱 등 음악 레슨을 제공하며, **여러 플랫폼에서 레슨생을 모집하는 개인 선생님**입니다.

예를 들면 다음과 같습니다.

- 여러 사이트에 레슨을 알리고 싶은 선생님
- 플랫폼마다 커리큘럼·위치·가격을 다시 작성하거나 수정하는 선생님
- 수업 홍보에 필요한 반복 작업을 줄이고 싶은 선생님

서비스 대상은 힙합에 한정하지 않고 **음악 레슨 전체**로 생각합니다.

### 함께 고려할 사용자

레슨을 찾는 사람도 선생님이 등록한 정보를 확인하고 문의하는 이용자입니다. 다만 이번 기획에서 **먼저 해결할 문제는 선생님의 등록 업무**입니다.

---

## 6. 서비스 목표

### 사용자 관점의 목표

선생님이 레슨의 공통 정보를 한 번 정리하고, 여러 플랫폼에 맞는 내용을 준비해 **등록까지 진행하는 데 드는 수고를 줄입니다.**

### 서비스 흐름

```text
레슨 선생님이 공통 정보 입력
        ↓
등록할 플랫폼 선택
        ↓
플랫폼별 필요한 정보 확인
        ↓
부족한 정보를 선생님에게 질문
        ↓
사이트별 형식으로 내용 준비
        ↓
선생님이 결과 검토·수정
        ↓
허용되는 범위에서 등록 지원
        ↓
플랫폼별 완료·실패·확인 필요 상태 표시
```

**실제 등록까지 돕는 것**이 목표입니다. 다만 각 플랫폼에서 자동 등록이 허용되는지 아직 확인되지 않았으므로, 가능한 경로를 먼저 조사해야 합니다.

## 7. 핵심 기능

### 7-1. 공통 레슨 정보 입력

선생님이 여러 사이트에서 공통으로 사용할 정보를 한곳에 정리합니다.

| 정보 | 내용 |
|---|---|
| 레슨 분야 | 기타, 보컬, 미디, 작곡, 믹싱 등 |
| 수업 대상 | 취미 입문자, 음악 작업 경험자 등 |
| 수업 목표 | 연주·녹음·자작곡 등 수업에서 다루는 목표 |
| 커리큘럼 | 수업 내용과 진행 방식 |
| 수업 조건 | 장소, 1회 시간, 월 횟수, 가격 |
| 선생님 정보 | 강의 경험, 음악 활동 이력 |
| 포트폴리오 | 선생님이 제공한 작업물과 참고 자료 |
| 상담 정보 | 상담 가능 여부와 문의 방법 |

한 선생님이 여러 과정을 제공한다면, **과정별 수업 내용·시간·횟수·가격을 각각 구분**합니다.

### 7-2. 플랫폼별 필수 정보 확인

선생님이 등록할 플랫폼을 선택하면 해당 플랫폼에 필요한 항목을 확인합니다.

예를 들어 한 플랫폼에서 여러 가격 옵션을 요구하는데 선생님이 한 과정만 입력했다면:

> “이 플랫폼에 필요한 다른 가격 옵션이 있는지 확인해 주세요.”

처럼 안내하고, 선생님에게 추가 입력을 받습니다.

AI가 없는 상품이나 가격을 **임의로 만들어 넣지 않습니다.** 플랫폼별 실제 필수 항목과 현재 등록 방식은 조사 후 반영합니다.

### 7-3. 플랫폼별 형식으로 내용 변환

선생님이 제공한 정보를 바탕으로 각 플랫폼에서 사용할 내용을 준비합니다.

- 게시글 제목과 레슨 소개
- 수업 대상과 커리큘럼
- 위치·수업 시간·가격
- 선생님 이력과 포트폴리오 설명
- 상담 및 문의 안내

변환 과정에서 원본에 없는 경력·가격·수업 성과를 추가하지 않고, 선생님이 원본과 변환된 내용을 확인할 수 있도록 합니다.

### 7-4. 내용 검토와 오류 확인

등록 전에 빠진 정보나 서로 맞지 않는 내용을 확인합니다.

- 가격은 있지만 수업 시간이 없는 경우
- 다른 과정의 시간과 가격이 잘못 섞인 경우
- 플랫폼에서 요구하는 항목이 빠진 경우
- 선생님이 입력하지 않은 내용이 생성된 경우

판단하기 어려운 내용은 **‘확인 필요’**로 남기고 선생님에게 묻습니다.

### 7-5. 등록 지원과 결과 확인

선생님이 내용을 검토한 후, 플랫폼별 등록을 진행합니다.

- **자동 등록이 허용되는 경우:** 공식적으로 허용된 방법과 사용자 권한을 확인해 실제 등록을 지원합니다.
- **자동 등록이 불가능하거나 미확인인 경우:** 선생님이 직접 등록할 수 있도록 해당 플랫폼에 필요한 내용을 제공합니다.
- **일부 단계가 실패한 경우:** 완료·실패·확인 필요 상태를 구분해 보여줍니다.

자동 등록이 불가능할 때 제공하는 직접 등록 지원은 **대안**입니다. 기획의 목표를 글 작성만으로 축소하는 것은 아닙니다.

## 8. 실제 사용 예시

### 상황

한 선생님이 미디 레슨을 두 곳에 알리고 싶습니다.

- **A 플랫폼:** 제목, 소개, 수업 시간, 가격을 입력
- **B 플랫폼:** 수업 정보 외에 여러 가격 옵션이 필요한 상황

### 서비스 사용

1. 선생님이 미디 레슨의 커리큘럼, 위치, 시간과 가격을 한 번 입력합니다.
2. 등록할 A·B 플랫폼을 선택합니다.
3. 시스템이 A 플랫폼에 필요한 내용을 정리합니다.
4. B 플랫폼에 추가 가격 옵션이 필요하면 선생님에게 알려줍니다.
5. 선생님이 실제로 제공할 옵션을 입력하고 내용을 확인합니다.
6. 각 플랫폼에서 허용하는 방법으로 등록을 진행합니다.
7. 어느 플랫폼은 등록이 완료됐고 어느 플랫폼은 추가 확인이 필요한지 보여줍니다.

위 A·B 플랫폼은 **사용 흐름을 설명하기 위한 예시**입니다. 특정 플랫폼에서 실제 자동 등록이 가능하다는 의미는 아닙니다.

## 9. AI와 멀티에이전트 활용 방향

AI는 선생님이 입력한 레슨 정보를 바탕으로 **플랫폼별 내용을 준비하고 오류를 확인하는 작업**에 활용할 수 있습니다.

### 역할 구상

| 역할 | 수행할 일 |
|---|---|
| **정보 정리** | 선생님의 입력을 분야·가격·시간·커리큘럼 등으로 정리 |
| **플랫폼 요구사항 확인** | 해당 플랫폼에 필요한 입력 항목과 형식 확인 |
| **내용 변환** | 제공받은 정보에 맞춰 플랫폼별 글과 입력 내용 준비 |
| **검토** | 누락·가격 불일치·원본에 없는 내용 확인 |
| **등록 지원** | 허용된 방식에 따라 등록을 진행하거나 직접 등록에 필요한 내용 제공 |

이 역할들을 반드시 각각 독립된 에이전트로 구현해야 한다고 미리 정하지는 않습니다. **일반 템플릿, 단일 AI, 역할을 나눈 AI 방식**을 비교해 실제로 도움이 되는 구성을 찾습니다.

과정 가이드의 멀티에이전트·보안·자동 복구 등 요구사항과 이 서비스의 연결 방식은 멘토님과 함께 확인합니다.

## 10. 데이터·플랫폼 정책 및 구현 조건

실제 플랫폼에 등록하는 기능은 사이트마다 이용 조건과 기술 환경이 다를 수 있습니다. 다음 사항을 먼저 확인해야 합니다.

- 자동 등록을 허용하는지
- 공식 API 또는 제휴를 통한 등록 방법이 있는지
- 로그인·인증이 필요한 단계는 무엇인지
- 사용자가 어떤 정보를 직접 확인하거나 입력해야 하는지
- 플랫폼별 필수 입력 항목과 가격 상품 구성은 무엇인지
- 등록 실패 시 완료 여부를 어떻게 확인할 수 있는지

**허용 여부가 확인되지 않은 사이트의 자동 등록은 가능하다고 가정하지 않습니다.**

회의에서는 자동 수집과 관련해 `robots.txt`와 트래픽 준수를 언급했지만, 과정 가이드와 프로젝트 기준은 **무단 자동 크롤링을 금지**합니다. 공개 페이지이거나 `robots.txt`가 허용한다는 사실만으로 자동 수집 권한이 생기는 것은 아닙니다.

브라우저 자동화나 화면 분석도 이 기준을 우회하는 방법으로 전제하지 않습니다. 실제 게시 자동화 역시 **해당 플랫폼의 정책·공식 연동 범위·사용자 권한**을 별도로 확인합니다.

## 11. 1차 구현·검증 범위

### 우선 구현을 검토할 흐름

- 레슨 선생님의 공통 정보 입력
- 플랫폼별 필요한 항목 확인
- 정보 부족 시 선생님에게 추가 질문
- 사이트별 등록 내용 준비
- 선생님의 최종 검토
- **허용된 실제 등록 경로가 있다면 등록까지 연결**
- 완료·실패·확인 필요 상태 표시

### 단계별 확인

1. **플랫폼 조사:** 실제 선생님이 사용하는 플랫폼의 입력 항목과 자동 등록 허용 여부를 확인합니다.
2. **한 플랫폼 검증:** 허용된 경로가 확인되면 한 곳에서 입력부터 실제 등록까지 동작하는지 확인합니다.
3. **여러 플랫폼 비교:** 서로 다른 형식의 플랫폼을 추가할 수 있는지 확인하고, 같은 원본 정보의 재사용 효과를 평가합니다.
4. **등록이 어려운 경우:** 직접 등록 지원이 얼마나 도움이 되는지 별도로 검증하고, 자동 등록 범위를 다시 결정합니다.

한 플랫폼에서만 성공한 결과는 **한 플랫폼의 검증 결과**로 기록합니다. 여러 플랫폼의 반복 업무가 해결됐다고 단정하지 않습니다.

### 후속 기능

- 게시글 갱신과 최신글 관리
- 광고 관리
- 홍보 문구 추천
- 레슨생 문의 응대 지원
- 다른 예술·취미 분야의 레슨으로 확장

## 12. 기존 방식과 차별화 검증

선생님은 이미 다음 방법을 이용할 수 있습니다.

- 이전 글을 복사해 수정하기
- 문서에 레슨 정보를 저장해 놓고 붙여넣기
- 일반 AI에게 플랫폼별 홍보 글을 작성해 달라고 요청하기
- 각 플랫폼에 직접 입력하고 등록하기

따라서 **AI가 레슨 글을 만들어 준다는 사실만으로 추가 가치가 생기는 것은 아닙니다.**

검증할 질문은 다음과 같습니다.

> 선생님이 기존에 사용하던 방법보다, 여러 플랫폼의 요구사항을 확인하고 내용을 준비해 등록하는 과정을 **더 적은 수고로 정확하게 마칠 수 있는가?**

## 13. 사용자 검증 계획

### 13-1. 레슨 선생님의 실제 업무 확인

여러 플랫폼을 사용하는 음악 레슨 선생님에게 최근 경험을 묻습니다.

- 실제로 어떤 플랫폼에 레슨을 등록했는가?
- 각 플랫폼에서 다시 입력하거나 수정한 내용은 무엇인가?
- 플랫폼별 가격 옵션이나 필수 정보 때문에 막힌 적이 있는가?
- 최초 등록과 게시 후 관리에 각각 어느 정도 시간과 노력이 드는가?
- 이미 문서 템플릿이나 일반 AI를 사용하고 있는가?
- 자동으로 등록까지 되는 것과, 글만 준비해 주는 것 중 무엇이 더 필요한가?

기획자는 서비스가 충분히 도움이 된다면 본인도 사용하고 비용을 낼 수 있을 것 같다는 의견을 갖고 있습니다. 이는 **개인적인 초기 의견**이며, 다른 선생님들의 수요나 실제 지불 의사는 확인되지 않았습니다.

### 13-2. 같은 과제로 비교

동일한 레슨 정보와 등록 과제를 사용해 다음을 비교합니다.

1. 선생님이 평소처럼 직접 작성하거나 복사하는 방식
2. 일반 AI로 플랫폼별 내용을 준비하는 방식
3. 제안한 등록 지원 서비스

### 관찰할 항목

- 레슨 정보 준비와 플랫폼별 입력에 걸린 시간
- 선생님이 직접 수정한 횟수와 내용
- 가격·수업 시간·커리큘럼의 누락이나 오류
- 실제 등록의 완료·실패·확인 필요 상태
- 플랫폼별 추가 인증이나 수동 작업
- AI 호출량과 예상 운영 비용

시간이 줄었더라도 가격이나 수업 내용이 잘못 등록되면 좋은 결과로 보지 않습니다. **작업 부담과 정보의 정확성을 함께 확인**합니다.

## 15. 후속 아이디어: 지도 기반 레슨 탐색 서비스

기존에 논의한 **음악 레슨 지도 탐색·가격 비교 서비스**는 후속 검토안으로 유지합니다.

장기적으로 선생님들이 등록 지원 서비스를 통해 레슨 정보를 제공하고, 해당 정보의 공개와 활용에 동의한다면, 레슨을 찾는 사람에게 지도 형태로 보여주는 방안도 생각할 수 있습니다.

다만 다음을 확인하기 전에는 자동으로 연결된다고 볼 수 없습니다.

- 선생님의 정보 제공·공개 동의 범위
- 가격을 공개하지 않고 문의로 받고 싶은 선생님의 선택
- 충분한 지역별·분야별 레슨 정보 확보
- 위치와 가격의 최신성
- 사용자가 실제로 지도에서 비교하는 방식을 원하는지

지도 탐색안 역시 별도로 **기존 플랫폼을 이용한 뒤에도 어떤 불편이 남는지** 검증해야 합니다.
