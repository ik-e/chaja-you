# AppFinder AI｜최종 프로젝트 기획안 v2.1

> **사용자 취향을 기억하고 숨겨진 앱을 발굴하는 멀티 에이전트 탐색 서비스**

- **작성일:** 2026년 11월 11일
- **문서 상태:** 팀 논의를 위한 개인 기획 초안
- **작성 기준:** 「기획서 잘 쓰는 법」 및 84일차 프로젝트 회의·강사 피드백

---

## 1. 프로젝트 개요

**AppFinder AI**는 사용자가 원하는 기능과 취향을 자연어로 입력하면, 여러 AI 에이전트가 앱 정보를 조사·비교하고 적합한 후보를 추천하는 서비스다.

기존 앱 검색에서 발견하기 어려운 앱을 추가로 탐색하고, 사용자가 선택적으로 저장한 선호도와 이전 검색 기록을 활용하는 기능을 목표로 한다.

### 핵심 목표

1. 원하는 조건의 앱을 쉽게 찾도록 돕는다.
2. iOS와 Android 사용자 모두를 고려한다.
3. 기본 탐색 외에 새로운 앱을 발굴하는 기능을 제공한다.
4. 앱별 추천 이유와 확인 가능한 출처를 보여준다.
5. 사용자 선호도를 저장하고 다음 검색에 활용한다.

처음부터 모든 앱을 조사하는 서비스를 만들기보다 팀에서 선정한 카테고리를 중심으로 핵심 기능을 구현한 후 확장한다.

## 2. WHY｜문제 정의

### 2-1. 해결하려는 문제

사용자는 앱을 찾을 때 여러 검색 결과와 상세 페이지를 직접 비교해야 하는 경우가 있다.

특히 원하는 조건이 구체적이거나 인기 앱이 마음에 들지 않는 경우, 다른 앱을 찾기 위해 검색을 반복할 수 있다.

**핵심 문제 정의**

> 사용자가 원하는 조건에 적합한 앱을 찾기 위해 여러 검색 결과를 확인하고 비교해야 하는 탐색 부담을 줄이고자 한다.

### 2-2. 주요 문제 가설

- 인기 검색 결과가 항상 개인의 취향과 일치하지 않는다.
- 여러 앱의 기능과 특징을 같은 기준으로 비교하기 번거롭다.
- 검색 순위가 낮은 앱은 발견하기 어려울 수 있다.
- 과거 검색 조건과 관심사를 반복해서 입력해야 할 수 있다.
- AI가 추천한 앱의 실제 기능을 검증하기 어려울 수 있다.

위 항목은 팀의 초기 가설이며 실제 사용자 전체의 경험으로 일반화하지 않는다.

## 3. WHY｜초기 문제 조사 방식

### 3-1. 팀원 내부 의견 취합

별도 외부 인터뷰를 의무적으로 진행하지 않고, **팀원 5명의 실제 앱 탐색 경험을 취합하는 방식**으로 초기 문제를 정리한다.

각 팀원은 다음 내용을 공유한다.

1. 사용하는 스마트폰 운영체제
2. 최근 앱을 검색하거나 설치했던 경험
3. 앱을 찾고 비교할 때 불편했던 점
4. AppFinder AI에 있었으면 하는 기능

각자가 실제로 경험한 사례를 중심으로 작성하며, 경험하지 않은 불편함을 만들어내지 않는다.

### 3-2. 의견 취합 방법

팀원들의 의견을 다음 항목으로 분류한다.

- 앱 발견의 어려움
- 앱별 기능 비교의 어려움
- 검색 결과의 부족함
- 개인 취향 반영의 필요성
- 기타 불편함

공통으로 언급된 문제와 실제 사용 사례를 중심으로 우선순위를 정한다.

### 3-3. 내부 조사 결과 활용

조사 결과는 다음과 같이 연결한다.

**팀원 경험 → 공통 문제 도출 → 필요한 기능 정의 → 테스트 시나리오 작성**

예를 들어 여러 팀원이 앱 비교가 번거롭다고 답했다면 동일 조건의 앱을 비교하는 기능을 우선 개발할 수 있다.

반면 특정 기능에 대한 수요가 확인되지 않았다면 우선순위를 낮출 수 있다.

팀원 수가 5명으로 제한되어 있으므로 이 조사는 **초기 문제 탐색과 내부 기획 근거**로만 사용한다.

실제 시장 수요가 검증되었다고 표현하지 않는다.

## 4. WHO｜대상 사용자 및 지원 범위

### 4-1. 주요 대상 사용자

**자신의 목적과 취향에 맞는 스마트폰 앱을 찾으려는 사용자**

다음과 같은 사용자를 대상으로 한다.

- 새로운 앱을 찾고 싶은 사용자
- 현재 사용 중인 앱을 대체하고 싶은 사용자
- 여러 앱의 기능을 비교하고 싶은 사용자
- 덜 알려진 앱을 발견하고 싶은 사용자
- 자신의 취향을 반영한 추천을 원하는 사용자

### 4-2. 초기 지원 운영체제

**iOS와 Android를 모두 초기 지원 대상으로 설정한다.**

팀원들이 실제 사용하는 두 환경에서 서비스 흐름을 검증할 수 있도록 구성한다.

검색 시작 시 사용자가 원하는 운영체제를 선택한다.

- iOS
- Android
- 두 운영체제 모두

단, '모두'를 선택했을 때에는 실제로 각 플랫폼에서 확인된 앱만 제공하고, 양쪽에 동일 앱이 존재하는지 확인되지 않았다면 단정하지 않는다.

### 4-3. 초기 앱 카테고리

초기 카테고리는 팀원들의 의견을 취합해 결정한다.

선정 기준은 다음과 같다.

- 팀원이 실제로 검색하거나 사용하는 분야인가?
- 앱을 비교할 수 있는 명확한 기준이 있는가?
- iOS와 Android 모두에서 데이터를 확보할 수 있는가?
- 기존 검색과 차별성을 보여줄 수 있는가?
- 정해진 기간 안에 구현 가능한가?

후보로는 가계부, 생산성, 일정 관리, 게임 등을 검토할 수 있다.

**최종 카테고리는 팀원 의견 취합 및 데이터 수집 검증 후 확정한다.**

### 4-4. 범위 제한

두 운영체제를 모두 고려하되 모든 앱 카테고리와 국가를 처음부터 지원하지 않는다.

초기에는 다음과 같이 범위를 제한한다.

- 한국 사용자를 주요 대상으로 설정
- 팀에서 선정한 첫 번째 앱 카테고리
- iOS·Android 각각 확인 가능한 데이터 범위
- 한국어 질문 및 추천 결과
- 앱 검색·비교·추천과 기억 기능 중심

## 5. WHAT｜핵심 기능

### 5-1. 사용자 요구사항 분석

사용자의 자연어 질문에서 앱 검색 조건을 분석한다.

예시:

> 광고가 적고 간단하게 사용할 수 있는 무료 앱을 찾아줘.

시스템은 앱의 목적, 가격 선호, 광고 조건, 사용성 등을 분석한다.

운영체제 등 필수 조건이 부족하면 간단한 추가 질문을 제공한다.

### 5-2. 기본 앱 탐색

사용자가 입력한 조건에 맞는 앱을 검색한다.

- 검색어 분석
- 실제 앱 정보 수집
- 중복 결과 제거
- 조건별 비교
- 추천 이유와 원본 출처 표시

### 5-3. 새로운 앱 발굴

기본 검색보다 더 다양한 후보를 찾는 기능이다.

- 관련 검색어 확장
- 유사 키워드 탐색
- 기본 검색과 결과 비교
- 추가 후보 발굴
- 사용자 조건 적합성 검증

단순히 검색 결과 수를 늘리는 것이 아니라 **기본 검색에서 발견하지 못한 유효한 앱을 찾는 것**을 목표로 한다.

### 5-4. 개인화 추천

사용자가 입력하거나 선택한 취향을 추천에 반영한다.

초기에는 복잡한 개인정보 분석 대신 다음과 같은 정보를 활용한다.

- 선호 앱 카테고리
- 중요하게 생각하는 기능
- 무료·유료 선호
- 광고 허용 정도
- UI 복잡도 선호

사용자는 자신의 선호도를 수정하거나 삭제할 수 있다.

### 5-5. 검색 기록 및 기억 기능

사용자가 저장한 정보를 다음 검색에 활용한다.

예시:

> 지난번에 저장했던 앱은 제외하고 추천해 줘.

저장 대상:

- 사용자 선호도
- 검색 조건
- 저장한 앱
- 검색 결과 요약
- 확인된 정보 출처와 수집 시점

초기에는 일반 데이터베이스를 활용해 저장 및 조회 기능을 구현한다.

RAG 기반 의미 검색은 필요성과 구현 가능성을 검토해 확장한다.

### 5-6. 근거 중심 비교

최종 추천 결과에는 다음 정보를 표시한다.

- 앱 이름
- 지원 운영체제
- 주요 기능
- 조건과의 적합성
- 추천 이유
- 공식 앱스토어 링크
- 정보 수집 시각
- 검증되지 않은 항목

확인되지 않은 정보는 임의로 생성하지 않고 '확인 필요'로 표시한다.

## 6. WHAT｜기능 우선순위

### Must Have

1. iOS·Android 선택 기능
2. 자연어 요구사항 분석
3. 플랫폼별 앱 정보 검색
4. 기본·확장 탐색 모드
5. 출처가 있는 앱 비교 및 추천
6. 사용자 선호도 저장과 재사용

**우선순위 원칙:** 두 플랫폼의 실제 데이터 확보 가능성을 먼저 검증한다. 한쪽의 자동 수집이 어려우면 제한된 검증 데이터로 시연하고 그 범위를 명시한다.

### Should Have

- 과거 검색 결과 조회
- 저장한 앱 제외 기능
- 조사 단계별 진행 상태 표시
- 검색 응답 캐싱과 비용 최적화

### Could Have

- 검색 지도 자동 갱신
- 기존 AI 대화 기록 가져오기
- 고급 취향 분석
- 상세 차트 및 시각화
- 다양한 앱 카테고리 지원

### Won't Have

- 모든 국가의 앱 통합 검색
- 앱스토어 전체 목록의 완전한 수집
- 앱 자동 설치 및 결제
- 의류·중고거래·스포츠 등 다른 도메인으로 즉시 확장
- 개인정보 자동 수집

## 7. HOW｜서비스 이용 흐름

**사용자 질문 → 조건 분석 → 운영체제 확인 → 탐색 모드 선택 → 플랫폼별 앱 검색 → 후보 통합 및 검증 → 비교·추천 → 선택적 저장**

### 사용자 시나리오

1. 사용자가 원하는 앱을 자연어로 입력한다.
2. iOS, Android 또는 모두를 선택한다.
3. 필요한 조건이 부족하면 AI가 질문한다.
4. 기본 탐색 또는 숨은 앱 발굴을 선택한다.
5. 시스템이 해당 플랫폼의 앱 정보를 수집한다.
6. 에이전트가 사용자 조건에 맞게 비교한다.
7. 최대 5개 앱과 추천 이유를 제공한다.
8. 사용자가 원하는 앱과 선호도를 저장한다.
9. 다음 검색에서 저장된 정보를 활용한다.

## 8. HOW｜멀티 에이전트 아키텍처

### 기본 구조

```text
[사용자]
    |
    v
[웹 UI]
    |
    v
[FastAPI]
    |
    v
[LangGraph 오케스트레이터]
    |
    +-- 요구사항 분석 에이전트
    |
    +-- 운영체제 및 검색 모드 분기
    |        |
    |        +-- iOS 데이터 수집 모듈
    |        |
    |        +-- Android 데이터 수집 모듈
    |
    +-- 후보 정규화 · 중복 제거
    |
    +-- 비교·검증 에이전트
    |
    +-- 사용자 선호도 조회
    |
    v
[추천 결과 및 앱 비교 화면]
    |
    v
[선택적 기록 저장]
```

### 구성 요소별 책임

| 구성 요소 | 역할 |
|---|---|
| 오케스트레이터 | 전체 실행 순서 및 예외 관리 |
| 요구사항 분석 에이전트 | 사용자 의도와 검색 조건 분석 |
| 앱 탐색 에이전트 | 검색어 생성 및 앱 데이터 수집 요청 |
| 비교·검증 에이전트 | 조건 적합성 분석, 출처 검증, 추천 설명 |
| iOS 데이터 모듈 | iOS 앱 정보 수집 |
| Android 데이터 모듈 | Android 앱 정보 수집 |
| 메모리 모듈 | 사용자 선호도 및 기록 저장·조회 |

검색 도구와 데이터베이스를 모두 LLM 에이전트로 만들 필요는 없다.

결과가 명확한 작업은 일반 프로그램으로 구현하고, 판단과 분석이 필요한 작업에 LLM을 활용한다.

## 9. HOW｜플랫폼별 데이터 확보 계획

### 9-1. iOS

Apple iTunes Search API를 우선 검토한다.

검색어로 앱을 찾고 이름, 설명, 앱 고유 ID, 원본 링크 등 실제 제공되는 정보를 수집한다.

호출 제한과 데이터 이용 조건을 확인한다.

### 9-2. Android

Google Play의 공식 개발자 API는 전체 공개 앱 검색을 직접 제공하는 용도와 다르므로 별도 데이터 수집 방법이 필요하다.

다음 순서로 검토한다.

1. 이용 조건에 맞는 앱 데이터 제공 서비스 조사
2. 공개된 Google Play 앱 상세 정보 활용 가능성 검토
3. 수집 가능한 정보와 호출 제한 확인
4. 적절한 자동화 방법이 없으면 공식 링크를 확인한 소규모 앱 데이터를 수동 구성

데이터 수집 방식이 제한적인 경우 이를 사용자 화면과 결과 보고서에 명시한다.

### 9-3. 공통 데이터 형식

두 운영체제의 앱 데이터를 동일한 구조로 정리한다.

예시 필드:

- `app_id`
- `platform`
- `app_name`
- `developer`
- `category`
- `description`
- `price`
- `rating`
- `store_url`
- `collected_at`

스토어에 존재하지 않는 필드는 임의로 채우지 않는다.

두 운영체제에 모두 출시된 앱이라도 플랫폼별 고유 ID는 별도로 관리한다.

## 10. HOW WELL｜검증 방법과 성공 기준

### 10-1. 팀 내부 검증

외부 사용자 인터뷰를 필수 조건으로 두지 않는다.

팀원 각자가 실제 앱 탐색 경험을 바탕으로 하나 이상의 테스트 질문을 작성한다.

가능한 경우 서로의 테스트 질문을 교차 실행하여 자신이 제안한 기능만 평가하는 편향을 줄인다.

iOS와 Android 테스트가 모두 포함되도록 질문을 구성한다.

### 10-2. 평가 방법

다음 세 가지 방식의 검색 결과를 비교한다.

- 기존 앱스토어 검색
- 일반 AI 검색
- AppFinder AI

비교 항목:

- 원하는 조건에 적합한 앱이 나왔는가?
- 추천 내용이 실제 앱 정보와 일치하는가?
- 기존 검색에 없는 새로운 후보를 발견했는가?
- 정보를 비교하기 쉬웠는가?
- 검색에 걸린 시간은 얼마나 되는가?

### 10-3. 초기 품질 목표

| 항목 | 제안 기준 |
|---|---|
| 플랫폼 지원 | iOS·Android 각각 실제 데이터 기반 시나리오 테스트 수행 |
| 기능 정상 작동 | 핵심 시나리오 모두 완료 |
| 출처 제공 | 추천 결과의 원본 링크 100% 제공 |

| 신규 후보 발굴 | 기본 검색에 없는 적합 후보 발견 여부 측정 |
| 개인화 | 저장한 선호도가 다음 검색에 반영 |
| 사용자 만족도 | 팀원별 평가와 개선 의견 기록 |
| 성능 | 운영체제·탐색 모드별 처리 시간 측정 |
| 비용 | 검색 1회당 모델 및 API 비용 기록 |

## 14. 최종 시연 구성

### 시연 1. iOS 앱 검색

아이폰 사용자의 요구 조건을 입력하고 iOS 앱 검색 결과를 비교한다.

### 시연 2. Android 앱 검색

갤럭시 사용자의 요구 조건을 입력하고 Android 앱 검색 결과를 비교한다.

데이터 수집 범위가 제한적이면 그 사실을 안내한다.

### 시연 3. 숨은 앱 발굴

동일 플랫폼과 동일 질문으로 기본 검색과 확장 검색을 실행한다.

확장 검색에서 새롭게 발견한 유효 후보를 비교한다.

### 시연 4. 사용자 기억

사용자가 선호도와 앱을 저장한 뒤 다시 검색한다.

저장된 조건이 새로운 검색에 반영되는지 확인한다.

## 15. 최종 결론

AppFinder AI는 iOS와 Android 사용자 모두를 고려하는 **개인화된 멀티 에이전트 앱 탐색 서비스**를 목표로 한다.

기획 초기에는 외부 인터뷰를 무리하게 추진하기보다 팀원들이 실제 경험한 문제를 취합하고, 이를 근거로 기능을 정한다.

다만 내부 조사와 실제 시장 수요 검증은 구분한다.

두 운영체제는 공통 사용자 경험으로 지원하되, 데이터 수집 방식은 플랫폼별로 설계하고 확보 가능한 범위를 확인한다.

프로젝트에서는 다음 세 가지에 가장 집중한다.

1. 사용자 조건에 맞는 앱을 정확하게 조사·비교하는 기능
2. 기본 검색에서 발견하지 못한 적합한 앱을 발굴하는 기능
3. 이전 검색과 사용자 취향을 기억해 다음 검색에 활용하는 기능

**프로젝트의 목표는 가장 많은 앱을 검색하는 것이 아니라, 사용자가 자신에게 필요한 앱을 더 쉽고 신뢰할 수 있게 발견하도록 만드는 것이다.**
