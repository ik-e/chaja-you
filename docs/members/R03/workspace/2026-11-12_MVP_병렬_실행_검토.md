## 1. 목적과 현재 결론

사용자 요청에 따라 구성한 여러 작업을 서로 기다리지 않고 동시에 진행해도 되는지 판단하는 기준을 정리한다.

MVP에서는 선행 조건이 충족된 독립 작업을 찾아, 고정된 동시 실행 한도 안에서 병렬로 실행하는 방안을 제안한다. 작업별 상태와 결과를 분리해 기록하고 시간·호출 수·비용·오류·결과 품질을 평가한다.

이 문서는 사용자가 개인 폴더에 작성을 요청한 논의 메모다. TASK-005 전체 결과나 확정 설계를 대체하지 않는다. 실제 구현·시험과 성능 측정은 아직 수행하지 않았다.

## 2. 병렬 실행 가능 조건

의존 관계·실행 한도·충돌을 관리하는 원칙은 공통 구조 제안이다.  머리말의 공식 INTENT·PROJECT·TASK-005 intent에 따라 병렬 대상의 역할·작업·출처·검증 내용은 앱 도메인 첫 후보군과 사용자 요청에서 선택하며, 다른 도메인에 같은 검증 작업을 강제하지 않는다. 공식 방향과 구체 실행 제안의 구분은 [통합본 2·5절](2026-11-12_TASK-005_동적_구성_MVP_검토_통합.md)을 참고한다.

- 작업에 필요한 입력이 준비되어 있다.
- 다른 작업의 결과를 기다릴 필요가 없다.
- 같은 데이터를 동시에 수정해 충돌하지 않는다.
- 모델·검색 도구의 호출 한도와 실행 예산을 넘지 않는다.

예를 들어 지정된 A와 B 앱을 비교할 때 두 앱의 자료 조사는 독립적으로 시작할 수 있다.

```text
             ┌→ A 자료 조사 → A 조건 검증 ─┐
요청 분석 ──┤                             ├→ 비교 → 결과 종합
             └→ B 자료 조사 → B 조건 검증 ─┘
```

A 조사가 먼저 끝나면 A 검증을 시작할 수 있다. B 조사가 끝날 때까지 기다릴 필요는 없다. 비교 작업은 두 앱의 판정 결과가 준비된 뒤 실행한다. 판정에는 미확인도 포함할 수 있다.

## 3. 병렬로 실행하면 안 되는 경우

| 상황 | 이유 | 처리 제안 |
|---|---|---|
| 후보 발굴과 그 후보의 기능 검증 | 검증할 대상이 아직 없음 | 후보 확보 후 검증 시작 |
| 두 후보 판정과 조건부 대안 발굴 | 대안을 찾을 실행 조건이 확인되지 않음 | 판정 후 실행 여부 결정 |
| 근거 조사와 그 근거를 사용하는 판정 | 필요한 입력이 아직 없음 | 자료 확보 또는 실패 기록 후 판정 |
| 동일 보고서를 여러 작업이 직접 수정 | 변경을 덮어쓸 수 있음 | 작업별 결과를 분리하고 종합 단계에서 반영 |

“두 앱 모두 미충족이면 대안을 찾아줘”라는 요청에서 대안 발굴을 미리 실행하면 필요 없는 작업을 수행할 수 있다. 일부 조건이 미확인이라는 이유만으로 미충족 조건을 충족한 것으로 취급하지 않는다.

## 4. 실행 가능 여부와 실제 실행 결정의 구분

독립 작업이 많아도 모두 동시에 실행하지 않는다. 준비된 작업 중 호출 한도와 예산 안에서 실행할 작업을 결정한다.

| 제약 | 확인할 내용 |
|---|---|
| 호출 한도 | 동시에 요청할 수 있는 모델·검색 API 호출 수 |
| 실행 예산 | 남은 호출 수·토큰·비용 예산 |
| 중복 조사 | 같은 페이지를 여러 작업이 반복 조회하는지 |
| 공유 데이터 | 같은 기록을 동시에 변경하는지 |
| 취소 가능성 | 필요 없어진 작업을 중단할 수 있는지 |

초기 MVP에서는 동시 실행 수 상한을 설정하고 준비된 작업을 그 한도 안에서 실행한다. AI가 상한 자체를 임의로 변경하는 기능은 우선 포함하지 않는 안을 제안한다. 구체적인 한도와 대기 작업 우선순위는 미정이다.

## 5. 작업 크기와 병렬 실행

같은 공식 페이지에서 확인할 수 있는 무료 범위·계정 조건 등을 각각의 조회 작업으로 나누면 중복 실행이 발생할 수 있다. 자료 조회는 묶고 결과에서 조건별 판정을 나누는 방안을 검토한다.

반면 서로 다른 출처가 필요한 요금제 확인과 브라우저 호환성 확인은 입력·의존 관계를 확인한 뒤 분리해 병렬로 조사할 수 있다.

독립적인 정보를 확인하는 작업은 분리하고 동일 자료를 반복해서 읽는 작업은 묶는 방향을 제안한다. 적정 작업 크기와 실제 효율은 중복 조회·호출 수·결과 품질을 측정해 확인해야 한다.

## 6. 실패·지연·취소 처리

| 상황 | 처리 제안 |
|---|---|
| A 성공·B 실패 | B 실패 원인을 기록하고 한도 안에서 재시도·대체 출처 조회 |
| A 완료·B 진행 중 | A 결과를 보관하고 B를 기다림 |
| B 조사 상한 도달 | B를 미확인으로 정리하고 확인된 결과와 함께 종합 |
| 추가 작업이 불필요해짐 | 시작 전이면 생략. 실행 중이면 취소 가능 여부와 이미 발생한 호출 기록 |

한 작업이 실패해도 다른 작업의 유효한 결과를 버리지 않는다. 모든 작업이 성공할 때까지 무한히 대기하지 않도록 한다. 실패·취소·상한 도달을 작업별 상태와 사유로 남긴다.

## 7. 고정할 부분과 동적으로 결정할 부분

| 고정할 부분 제안 | 동적으로 결정할 부분 제안 |
|---|---|
| 선행 입력이 준비돼야 실행한다는 규칙 | 현재 실행 가능한 작업 목록 |
| 동시 실행·호출·재시도 상한 | 한도 안에서 실제 실행할 작업 |
| 작업별 결과·상태 기록 형식 | 요청별 병렬 작업의 조합 |
| 공유 결과 반영과 충돌 방지 방식 | 중간 결과에 따른 추가·생략·취소 |

## 8. 평가 계획

역할·작업 구성의 효과와 병렬 실행의 효과를 구분해 비교한다.

| 비교 | 확인할 내용 |
|---|---|
| 같은 작업 계획을 순차 실행 / 병렬 실행 | 실행 방식이 시간·오류·비용에 미치는 영향 |
| 고정 흐름 / 요청별 동적 구성에 같은 병렬 정책 적용 | 작업 구성 방식의 적절성 |

모델·검색 도구·자료 조건·호출 예산 등을 맞추고 다음 항목을 기록한다.

- 선행 조건을 어기고 시작한 작업이 있는가?
- 실행 가능한 작업을 불필요하게 대기시켰는가?
- 호출 한도 초과나 동시 수정 충돌이 발생했는가?
- 중복 조회·재시도·불필요한 실행이 늘었는가?
- 전체 완료 시간과 호출 수·비용이 어떻게 달라졌는가?
- 필수 조건 판정과 근거 품질이 유지됐는가?

APP-A의 독립적인 앱 조사, APP-B의 후보 확보 후 독립 검증, APP-C의 중간 판정 이후 조건부 작업을 시험 사례로 연결한다. APP-C 모의 분기 시험은 실제 앱 기능 확인과 구분한다.

병렬 실행은 대기 시간을 줄일 가능성이 있으나 아직 측정하지 않았다. 같은 작업을 동시에 실행하는 것만으로 총 작업량이 줄어드는 것은 아니므로 토큰·비용 절감을 미리 성과로 주장하지 않는다. 중복 실행·재시도로 비용이 늘어나는지도 확인한다.

## 9. 미확인 사항과 결정 요청

- 실제 모델·검색 도구의 동시 호출·이용 제한은 R02의 결과와 대조해야 한다.
- 상태 관리, 결과 저장, 공유 데이터 갱신과 취소 처리는 R05의 구현 구조와 맞춰야 한다.
- 동시 실행 수·시간·호출·재시도 상한과 준비된 작업의 우선순위는 미정이다.
- 적정 작업 크기, 실제 시간 변화와 결과 품질은 실험이 필요하다.
- 이 병렬 실행 범위를 TASK-005의 MVP 제안에 포함할지 팀 확인이 필요하다.
