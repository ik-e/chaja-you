## 1. 평가 질문과 현재 가설

사용자 요청과 중간 결과에 따라 역할·작업·선행 관계를 구성하는 방식이, 사전에 작성한 고정 워크플로보다 적절한가?

동적 구성이 필수 검증을 유지하면서 불필요한 실행을 줄이거나 요청 변형에 대응할 수 있다는 가설을 검토한다. 계획 생성 자체의 시간·호출·비용과 오류도 함께 측정한다. 고정 흐름과 차이가 없거나 오히려 불리할 가능성을 열어 둔다.

사용자가 개인 폴더에서 진행 중인 TASK-005 논의의 다음 단계로 작성한 계획이다. 실제 실행·앱 조사·기기 시험·성능 측정은 수행하지 않았으며, 이 문서의 표는 측정 결과가 아니다. TASK-005 완료 상태나 프로젝트 정본을 변경하지 않는다.

## 2. 비교할 두 구성 방식

### B0 — 조건 분기를 갖춘 고정 워크플로

평가 전에 사람이 정의한 작업 유형·역할 배정·연결 순서를 고정한다. 요청별 대상·조건을 채우고, 준비된 반복·분기 규칙을 적용한다.

```text
요청 구조화
  → 후보 확보: 지정 후보 사용 / 지정 후보가 없으면 발굴
  → 후보별 자료 조사
  → 조건 검증: 기능·요금 / 호환성·권한 등 관련 항목
  → 후속 조건 평가
       ├ 조건 충족 → 대안 발굴 → 새 후보 조사·검증
       ├ 근거 부족·충돌·접근 실패 → 한도 내 보완 → 재판정
       └ 조건 불성립·확인 불가·한도 도달 → 생략 이유 기록
  → 비교·결과 종합
```

검증 항목 중 무관한 것은 비적용으로 기록하고 실제 호출을 생략한다. 후보별 반복, 독립 검증의 병렬 실행, 보완 조사와 재시도도 허용한다. 보완 후 후속 조건을 다시 평가한다. 자유로운 역할 생성이나 실행 중 새로운 연결 구조 생성은 하지 않는다.

이 도식은 공정 비교를 위한 baseline 설계 제안이며 구현 결과가 아니다. 특히 무조건 후보를 발굴하게 하거나 APP-C 조건 처리를 못 하게 만들어 baseline을 불리하게 하지 않는다. 분기 평가 같은 일반 코드 단계는 LLM 호출과 구분한다.

### D0 — 요청별 동적 구성

B0와 같은 역할 후보·작업 유형·도구·판정 규칙 안에서 요청과 중간 결과에 따라 작업 목록·역할 배정·의존 관계·병렬 조합을 구성한다. 작업 추가·생략·연결 변경과 그 이유를 기록한다. 같은 요청에서 같은 계획이 나와도 실패는 아니며, 필요 없는 차이를 만들도록 요구하지 않는다.

| 구분 | B0 고정 흐름 | D0 동적 구성 |
|---|---|---|
| 작업 연결 | 미리 정의한 그래프와 분기 | 허용된 유형 안에서 실행별 구성 |
| 요청 처리 | 대상·조건을 고정 구조에 대입 | 대상·조건으로 작업과 관계 구성 |
| 후속 행동 | 미리 정의한 조건부 경로 실행 | 조건에 맞는 작업·역할·관계 추가·생략 |
| 공통 능력 | 요청 해석, 발굴, 조사, 검증, 조건부 처리, 보완, 종합 | B0와 동일 |
| 추가 부담 | 고정 흐름 적용 비용 | 계획 생성·검사·수정 비용까지 포함 |

## 3. 비교 조건과 공정성

- B0/D0 모두 동일한 **앱 도메인 첫 역할·작업 후보군, 출처 접근 범위, 검증 기준의 버전**을 사용한다. 실제 선택 출처·페이지·검증 항목은 요청별로 달라질 수 있으므로 선택 이유와 범위를 기록한다.
- 공통 관리 구조와 앱 특화 정의를 구분한다. 사용자가 전달한 팀장 의도에 따라 현재 후보군을 다른 도메인까지 영구 고정하지 않는다. [통합본 2·5절](2026-11-12_TASK-005_동적_구성_MVP_검토_통합.md)에 반영 근거를 남겼다.
- 동일한 모델·버전·지원되는 생성 설정을 사용한다.
- 동일한 사용자 요청, 공통 요청 구조화 방식, 도구 구현과 출력 스키마를 사용한다.
- 역할 지침·근거 판정 규칙·도구 접근 권한을 공통으로 둔다. 계획 구성 지침과 그래프가 실험의 차이임을 명시한다.
- 동일한 전체 호출·토큰·시간·비용 상한, 재시도·추가 조사 한도를 적용한다. 계획 생성도 D0 전체 예산에 포함한다.
- 같은 병렬 실행 상한과 캐시 초기 조건을 적용한다. 공유 캐시로 나중 실행한 쪽만 이득을 보지 않도록 한다.
- 제공 자료·모의 판정·도구 응답이 같은 통제 시험을 먼저 구성한다. 실시간 웹 시험에서는 같은 시점·도구 설정을 적용하되 검색어와 결과가 달라질 수 있으므로 조회 자료를 별도로 보존·기록한다.
- 실행 순서의 영향을 줄이도록 B0/D0의 실행 순서를 교대한다. 반복 횟수는 실행 예산을 보고 사전에 정하고 개별 결과와 변동도 보고한다.
- 결과를 본 뒤 baseline이나 기대값을 한쪽에만 유리하게 고치지 않는다. 변경 시 버전을 나누고 같은 조건으로 다시 비교한다.

## 4. 단계별 시험 범위

1. **계획·분기 통제 시험:** 동일 입력·모의 결과로 역할 선택, 선행 관계, 조건 분기와 변경 이력을 점검한다. 실제 앱 기능 증거나 실시간 조사 비용으로 해석하지 않는다.
2. **종단간 조사 시험:** 실제 허용된 출처를 사용해 요청부터 결과까지 실행하고 조건 판정·근거·시간·실제 호출·비용을 확인한다. 실제 중간 결과가 모의 분기와 다르더라도 분기를 강제로 맞추지 않는다.
3. **필요한 기기 시험:** 문서 확인으로 알 수 없는 오프라인 타이머·예약 차단 등의 실제 동작을 기기·버전·설정과 함께 별도 기록한다.

통제 시험의 벽시계 시간과 실제 모델·웹 호출 시험 시간을 혼합해 속도 개선을 주장하지 않는다.

## 6. 평가 항목과 측정 방법

| 항목 | 측정·확인 방법 |

| 토큰·비용 | 입력·출력 토큰과 제공자 usage, 실제 모델·도구 과금 기준 및 확인일 기록 |

비용 정보가 없으면 0으로 채우지 않고 미확인으로 둔다. 추정 비용은 계산식·요율·캐시 적용 여부를 남겨 실제 청구액과 구분한다. 미완료 실행도 실패·중단 시점까지의 자원을 포함한다.

## 8. 판정과 유효성 해석

- 이 비교는 앱 도메인 내부 구성의 평가이며 다중 도메인 효과를 주장하지 않는다. 여러 도메인 실제 구현은 후속 범위지만 도메인별 특화 가능성은 상위 의도로 유지한다.
- 개별 검사에는 `pass` / `fail` / `inconclusive`와 근거를 남긴다. 수행하지 않았거나 증거가 부족한 검사는 통과로 표시하지 않는다.
- 잘못된 분기, 필수 조건 누락, 근거 없는 충족 판정이 있으면 해당 검사 실패다. 빠르거나 저렴하다는 이유로 상쇄하지 않는다.
- 품질 조건을 충족한 실행끼리 시간·호출·비용 차이를 비교한다. 전체 실패 사례도 함께 공개해 성공 사례만 선택하지 않는다.
- 차이는 사례·반복별 B0와 D0의 원값과 차이로 보고한다. 개선율은 기준값이 유효할 때만 계산한다.
- 같은 결과에 D0의 계획 부담만 늘면 고정 흐름 유지나 동적 범위 축소를 검토한다.
- 요청 변형 대응이나 누락 감소가 확인되더라도 시간·비용 증가가 있으면 절충 관계를 제시한다.
- 유효성 판단에 사용할 정량 합격선·허용 비용과 확대 여부는 기준 실행 후 R01이 결정한다. 현재 개선 성과나 최종 우수 방식은 미확인이다.

## 9. 실행 전 준비와 결정 요청

1. R01: 이 baseline 정의와 MVP 최소 범위 검토. 자유 역할 생성은 이번 비교에서 제외하는 안을 제안한다.
2. R02: 실제 접근 가능한 데이터·검색 도구·호출 제한·요금과 확인 범위 제공.
3. R05: 공통 실행기·도구·작업 기록 형식, 실패·재시도·동시 실행 관리와 연결.
4. R03: 정확한 변형 요청·통제 입력·기대값과 고정 그래프/동적 계획 검사를 준비.
5. 공통: 반복 횟수·실행 예산·캐시 초기 상태를 실행 전에 기록. 첫 측정 후 정량 합격선 결정 절차 합의.

문서 정리는 완료했으나 baseline 구현·모의 실행·실제 비교 실험은 아직 하지 않았다. TASK-005 전체 완료나 검증 통과를 주장하지 않는다.
