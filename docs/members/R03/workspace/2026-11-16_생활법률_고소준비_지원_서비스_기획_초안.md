## 1. 서비스와 목표

**온라인 중고거래 피해를 의심하는 사람이 흩어진 거래 자료와 사건 경위를 정리하고, 빠진 내용을 확인해 상담·신고를 준비하도록 돕는 서비스다.**

사용자가 받는 결과는 사건 요약·보유 자료 목록·미확인 항목·상담 질문이다. 목표는 **자료 재확인과 반복 작성·수정 부담을 줄이는 것**이다.

## 2. 타겟과 문제 정의

| 구분 | 정의 |
|---|---|
| 타겟 | 온라인 중고거래에서 돈을 보냈지만 물품을 받지 못해, 처음 상담·신고를 준비하면서 거래 경위와 자료 정리에 막힌 사람 |
| 핵심 pain | 흩어진 자료를 다시 찾고 사건을 반복 정리하며, 누락·잘못된 설명을 걱정해 재확인·수정하는 부담 |
| 보조 pain | 작성 중 법률·절차 용어와 입력 항목을 이해하기 어려움 |
| 문제 정의 | 처음 상담·신고를 준비하는 중고거래 피해 의심자는 흩어진 거래 자료와 사건 경위를 정확히 설명하기 위해 재확인·수정을 반복해야 한다. |

첫 검증은 물품 미수령·최초 상담/신고 준비에 집중한다. 투자사기·피싱·수사 진행 관리는 제외한다. 위 pain은 사용자 확인 전 가설이다.

## 3. 핵심 피처와 결과

| 피처 | 입력 → 처리 → 출력 | 확인할 효과 |
|---|---|---|
| ① 사건·자료 구조화 | 자유 설명·비식별 자료 문구 → 입력 원문 문장·구간에 ID를 부여하고 일시·금액·행위 진술을 추출해 원문 ID에 연결 → 수정 가능한 사건 초안 | 순서 혼동·원문 재탐색·사실 누락 감소 |
| ② 누락 확인·결과 갱신 | 초안·추가 답변·사용자 수정 → 사례별 점검 항목(송금액·물품·연락 상태 등)의 누락·값 불일치 확인, 수정 항목 ID를 참조하는 결과만 재점검·갱신 → 요약·자료 목록·미확인·질문 | 반복 질문·재작성·수정 후 불일치 감소 |


핵심 피처는 위 2개다. 용어·항목 설명은 작성 중 요청할 때 제공하는 보조 기능이며 별도 핵심 피처로 계산하지 않는다.

점검 항목은 누락 질문을 고르는 기준이며 필수 입력·신고 접수 요건을 뜻하지 않는다. 원문 ID는 출처 추적, 항목 ID는 경위·금액 등 수정 대상 추적에 사용한다. 구체적인 필드명·발급 방식은 구현 때 정한다.

자료는 우선 비식별 텍스트와 보유 목록으로 입력한다. ‘자료가 있다’는 응답은 보유 여부에 관한 진술이며, 자료 내용 확인이나 진위 검증으로 처리하지 않는다.

## 4. 네 단계 이용 흐름

아래는 첫 검증 시제품의 화면안이다. 한 번에 읽을 양을 줄이고 원문·출처는 항목을 누르면 펼쳐본다.

| 단계 | 사용자 행동·화면 | 시스템 처리·다음 이동 |
|---|---|---|
| 1. 시작 | ‘중고거래에서 있었던 일을 함께 정리해요.’ / 내 상황 정리하기·가상 예시 보기 | 시작 버튼 옆에 ‘상담·신고 준비를 돕습니다. ECRM 온라인 접수 이후에는 원칙적으로 경찰서 방문·진술 등 후속 절차를 진행합니다’ 표시 |
| 2. 입력 | 기억나는 만큼 자유 입력. 필요하면 작성 도움 열기 | 날짜·금액 전체를 필수 입력으로 요구하지 않고 초안 생성 |
| 3. 확인 | 초안 수정, 필요한 질문에 답변·기억 안 남 선택 | 이미 말한 항목 재질문 생략. 미확인 상태로도 현재 결과 이동 허용 |
| 4. 결과 | 사건 요약 → 미확인 → 자료 목록 → 상담 질문·공식 경로 검토 | 원문 확인·수정·검토한 요약 복사. 복사에도 주장·미확인 표시 유지 |

작성 도움 문구: ‘무엇을 거래했고, 돈을 보낸 뒤 어떤 일이 있었는지 적어주세요. 정확한 날짜는 몰라도 괜찮아요.’ 입력칸 옆에는 이름·전화번호·계좌번호 등 식별정보 제외 안내를 둔다.

## 5. 가상 사례로 본 동작

### 입력과 정리 초안

> “중고거래로 10만 원을 보냈는데 물건을 받지 못했고 판매자와 연락이 안 돼요.”

| 추출할 항목 | 표시할 내용 | 입력 원문 연결 |
|---|---|---|
| 송금액 | 사용자는 10만 원을 보냈다고 설명함 | U1의 ‘10만 원을 보냈는데’ |
| 현재 상황 | 사용자는 물품 미수령·연락 두절이라고 설명함 | U1의 해당 문구 |
| 송금일·배송 약속일 | 미확인 | 연결 정보 없음 |

U1은 가상 입력 원문 ID다. 입력에 없는 상품·날짜·배송 약속 변경·정확한 사건 순서를 생성하지 않는다.

### 확인과 수정

- 질문 예시: ‘판매자가 언제 보내겠다고 했나요?’ → 날짜 입력 / 정확히 기억나지 않아요 / 약속한 날짜가 없어요.
- ‘기억나지 않음’은 미확인으로 보존한다. ‘약속한 날짜가 없었음’이라는 사용자 진술과 구분한다.
- 자료 목록은 판매 글·대화·이체 내역의 보유 여부부터 확인한다. 미보유·아직 확인 안 함도 구분한다.
- 특정 항목(예: 송금액)을 수정하면 해당 항목 ID를 참조하는 요약 문장·후속 질문·자료 연결을 부분 재점검한다. 영향받는 항목은 **‘재검토 필요’**로 표시하고 사용자 검토 후 **‘검토함’**으로 바꾼다.
- 수정 전 입력 원문과 이전 대조 기록은 보존한다. 새 답변·수정은 별도 원문 ID로 연결하고, 변경된 결과에 이전 대조 결과를 그대로 적용하지 않는다. 무관한 조사까지 재실행하지 않는다.
- 필요한 질문만 우선 제시하고, 사용자는 언제든 현재 내용 검토·결과로 이동한다.

### 결과 표현 규칙

| 내용 | 누가 말했는지 | 연결 입력·자료 | 남은 확인 |
|---|---|---|---|
| ‘배송했다’는 메시지가 있음 | 판매자 | 가상 대화 M1 | 실제 발송 여부는 미확인 |
| ‘처음부터 속이려 했다’고 생각함 | 사용자 | 가상 입력 U2 | 의도에 관한 추측으로 보존 |

각 추출 항목은 **항목 ID·내용·발언 주체·근거 원문 ID**와 아래 속성을 함께 기록한다. 상태 이름은 설계 표현이며 확정된 저장 스키마는 아니다.

| 구분 | 기록 예시·판단 의미 |
|---|---|
| 정보 성격 | ‘사용자 경험 진술’·‘상대방 주장’·‘사용자 추측’. 자료에 판매자 주장이 있으면 발언자는 판매자, 출처는 해당 자료 원문으로 기록 |
| 확인 상태 | ‘미확인’ 또는 확인한 범위를 명시. ‘원문 기재 확인’은 배송·사건 사실의 진위 확인과 다름 |
| 충돌 여부 | 서로 다른 값은 ‘충돌 있음’과 양쪽 원문 ID·값을 함께 보존. 사용자 정정과 해결되지 않은 입력 충돌을 구분 |
| 사용자 검토 | ‘미검토’·‘검토함’·‘재검토 필요’. 내용 확인 상태와 별개로 관리 |

예를 들어 판매자의 배송 주장은 원문 기재를 확인했더라도 실제 배송은 ‘미확인’일 수 있다. 추측·충돌·미확인은 동시에 존재할 수 있어 하나의 배타적인 상태값으로 합치지 않는다. 자료 보유도 ‘보유’·‘미보유’·‘아직 확인 안 함’으로 별도 기록한다.

결과에는 **사용자 검토 여부와 남은 미확인**을 표시한다. 검토는 증거 충분성·진위·법률 검토 완료를 뜻하지 않는다. 복사한 결과도 제출처 항목에 맞춘 추가 작성이 필요할 수 있다.

### 피처별 행동과 평가

| 피처 | 줄일 pain·행동 전후 | 지표·기준선 |
|---|---|---|
| 사건·자료 구조화 | 자료를 훑으며 경위를 다시 작성 → 입력 원문 연결 초안 검토 | 기준 사실 누락·왜곡·추정 생성 건수, 원문 ID 연결. ECRM 안내만·체크리스트·충분한 지시의 LLM 대비 |
| 누락 확인·수정 반영 | 금액·날짜를 여러 곳에 재입력 → 연결된 요약·질문 갱신 | 정정 후 남은 불일치·재작성 횟수·검토 시간. 동일 정정 입력·동일 자료로 비교 |

자료 찾기부터 최종 설명까지의 총시간은 공통 지표다. 보기 좋은 결과와 전체 수고 감소는 별도로 판단한다.

[주장별 근거 검토](2026-11-16_중고거래_기획_근거_검토.md): 준비 과제의 존재와 실제 사용자 pain의 입증을 구분하고, 아래 폴봇의 기능 중복을 반대 근거로 기록했다.

| 대안 | 확인 범위·역할 | 비교할 남는 부담 |

| [더치트 API](https://apidocs.thecheat.co.kr/docs/api-usage/api-search-plain/) | 특정 API의 연락처·계좌 등록 피해사례 조회 | 조회 이후 사건 정리는 어떻게 하는가 |
| 플랫폼 자체 신고·안전결제 | 플랫폼별 상세 지원 범위는 조사 대상 | 이미 송금한 사용자에게 적용되는 대응과 추가 준비는 무엇인가 |
| [생활법령정보](https://www.easylaw.go.kr/CSP/CSP/OnhunqueansInfoRetrieve.laf?curPage=1&onhunqnaAstSeq=86&onhunqueSeq=1083&pageType=20&sch=)·[법률구조 안내](https://immigration.go.kr/moj/177/subview.do) | 고소 방법 설명·무료 상담 경로 | 안내·상담 전 사건 설명 준비가 어려운가 |
| 범용 LLM | 요약·질문·설명 기능을 비교할 대상 | 충분한 지시를 줘도 재확인·수정 부담이 남는가 |

공식 출처는 2026-11-16 공개 안내 확인 기준이다. 더치트 API 설명을 서비스 전체 기능으로 확대하지 않는다. 실제 서비스 전체 이용·접수 시험은 하지 않았다.

**반대 근거:** 경찰청의 2022-11-30 발표는 폴봇의 질문·답변 기반 진술서 자동 작성을 설명한다. 작성 지원 기능이 없다는 전제를 사용하지 않는다. 현재 제공 범위·효과와 원문 연결·부분 수정 기능은 추가 확인 대상이다. [공식 발표](https://m.korea.kr/news/policyNewsView.do?newsId=148908906) (확인일: 2026-11-16)

**왜 기존 방식인가:** ECRM은 방문 전 서류 작성으로 방문 시간을 단축하는 목적을 설명한다. 하지만 자동 구조화의 전체 제공 여부와 설계 이유는 미확인이다. 원진술 보존·책임·플랫폼 간 접근 제약은 조사 가설이며, 공식 근거 없이 이유로 확정하지 않는다. 우리에게도 같은 제약이 적용되는지 확인한다.

**차별화 가설:** 각 사건 문장을 입력 원문·자료에 연결하고, 주장·추측·미확인·충돌을 보존하며 사용자 수정 사항을 연결된 결과에 반영해 반복 작업을 줄인다. 범용 LLM도 충분히 수행할 수 있으므로 같은 자료와 충분한 지시로 비교한다.

## 7. 첫 검증 시제품의 범위

### ECRM으로 이동하기 전 준비 안내

사용자가 제공한 화면에서 확인한 접수 단계는 **범죄유형 선택 → 증거자료 첨부 → 인적사항 입력 → 내용입력 → 완료**다. 화면은 ‘증거자료 첨부’ 단계가 강조된 진행 표시이며, 실제 입력·첨부·수정·완료를 모두 시험한 근거는 아니다.

공식 경로를 보여줄 때 **본인 신분증·이체/결제 내역·대화 내역·판매 글 등 거래 관련 자료를 준비**하도록 안내한다. 공식 ECRM 안내는 신분증·이체내역서·메신저 대화내역 등 첨부를 설명한다. 신분증은 공식 신고와 경찰서 방문을 위한 준비물이며 우리 서비스에는 업로드·제출을 요구하지 않는다. [ECRM 공식 안내](https://ecrm.police.go.kr/minwon/main) (확인일: 2026-11-16)

사용자 안내 문구는 다음과 같이 통일한다.

> **상담·신고 준비를 돕는 서비스입니다. ECRM 온라인 접수 이후에는 원칙적으로 경찰서에 방문해 진술 등 후속 절차를 진행합니다.**
>
> 일부 사건은 출석 없이 진행될 수 있으므로 ECRM과 담당 수사관의 안내를 확인하세요.

결과 화면에는 본인 신분증·증빙자료와 임시 접수번호를 준비하고 ECRM의 방문 안내를 확인하도록 연결한다. 결과 버튼은 **‘검토한 요약 복사하기’·‘ECRM 안내 보기’**로 두고 ‘신고 완료’로 표시하지 않는다. 우리 서비스의 역할은 온라인 작성과 방문 시 설명에 활용할 내용을 정리하는 것이며, 방문 면제나 신고·수사를 대신 처리하는 기능을 포함하지 않는다.

온라인 작성의 ‘완료’를 공식 절차 전체 종료로 표시하지 않는다. 기본 절차는 온라인 접수 → 경찰서 방문·진술 → 조사이며, 일부 다수 피해 사이버사기 사건은 조건에 따라 출석 없이 진행될 수 있다. 임시 접수번호와 방문 안내는 ECRM의 실제 안내를 따른다. 첨부 파일 형식·용량, 필수 입력값, 저장·수정 방법은 미확인이다. [ECRM 절차 안내](https://ecrm.police.go.kr/minwon/main) (확인일: 2026-11-16)

### 제공 범위

| 포함 | 제외·후속 |
|---|---|
| 비식별 텍스트·자료 목록 입력, 원문 연결, 누락·충돌 확인 | 플랫폼 자동 수집·실제 파일 자동 판독 |

자료를 찾고 옮기는 부담은 남는다. 입력·검토가 ‘두 번 작성하는 일’이 되는지도 측정한다. 구현 기술·역할별 호출 수는 아직 선정하지 않았다.

### 운영 주체·사용 시점 — 제안

팀이 비용을 부담하는 **무료 웹 시제품**을 운영 후보로 둔다. 사용자는 ECRM 작성 또는 경찰 상담을 준비할 때 비식별 자료를 정리하고 결과를 직접 검토한다. 기관 연계·플랫폼 탑재·유료 법률 서비스는 초기 계획에 넣지 않는다. 이는 운영안 제안이며 배포·외부 제공·예산 승인이나 법률 적합성 검토 완료를 뜻하지 않는다.

## 8. 현재 작업과 사용자 가치 점검

### 이번 반증 점검 결과

가상 사례 1건·2턴의 CLI 기반 LLM은 원문 연결·금액 충돌·사용자 정정과 배송 미확인을 처리했다. 이 사례에서는 LLM 대비 추가 가치가 확인되지 않았다. 폴봇의 공개 진입 표시는 확인했으나 브라우저 연결 불가로 실제 대화·수정은 미시험이다. [원응답·조건·판정 기록](2026-11-16_기존대안_반증점검_결과.md)


**현재 순서:** 가상·비식별 사건 자료 및 기준 답안 준비 → 동일 조건 비교 → 오류·수고 기록 → 시제품 우선순위 조정. 시제품이 없으면 수동 모의 점검으로 표시한다.

| 점검 | 같은 출발점 | 기록·해석 |
|---|---|---|
| 실험 A: 구조화 품질 | 동일하게 준비된 텍스트·자료 | 기준 답안의 중요 사실 누락 건수, 입력 원문과 다른 값·의미의 왜곡 건수, 원문에 없는 추가 내용 건수, 문장별 원문 ID 연결 일치 여부, 필요한 누락 질문 도출 여부, 초안 수정 횟수·시간. 자료 수집 부담 감소로 확대하지 않음 |
| 실험 B: 가상 환경 전체 준비 부담 | 흩어 배치한 같은 가상 판매 글·대화·입금 자료 | 찾기·옮기기·입력·답변·검토·수정·설명까지의 총시간, 왕복·재입력·수정 횟수 |

비AI 비교는 A. ECRM 공개 안내로 직접 작성 / B. A+종이 체크리스트 / C. 제안 방식으로 구분한다. 별도로 충분한 지시를 준 범용 LLM 결과와 C를 대조한다. ECRM이 자동 요약한다고 가정하지 않는다. 범용 LLM에도 원문 연결·미확인/충돌 보존·누락 확인·수정 반영을 요청한다.

**공통 완료 과제:** 요약·자료 목록·미확인·상담 질문을 검토하고, 자신의 상황과 남은 확인 사항을 설명한다. 완료 선언과 과제 종료 시점을 따로 기록하고, 정확성은 별도 평가한다. 중단·포기·도움 요청도 남긴다.

**임시 성공 방향:** 중요한 사실 누락과 반복 작성 부담을 줄이고, 없는 사실·의도를 추가하지 않는다. 비교 결과는 아래 세 항목으로 나눠 보고하며 정량 합격선은 초기 결과 후 정한다.

| 비교 | 판단할 내용 |
|---|---|
| ECRM 안내를 참고한 직접 작성 대비 | 누락·왜곡·작성 수고가 줄었는가 |
| 충분한 지시를 준 범용 LLM 대비 | 원문 추적·수정 반영·사용자 수정 부담에서 추가 가치가 있는가 |
| 고정 멀티에이전트 대비 | 품질을 유지하면서 불필요한 작업·호출·비용을 줄였는가 |

각 비교에서 정확성 개선과 부담 감소를 별도로 판정하며 왜곡 증가를 시간 단축으로 상쇄하지 않는다. 기준 답안의 중요 사실·필요한 질문·연결 정답은 사례별로 실행 전에 정한다. 누락은 기준 사실 중 빠진 항목, 왜곡은 원문과 달라진 값·의미, 추가 생성은 원문에 없는 내용으로 세며 한 오류의 중복 집계 여부도 기록한다.

진행자 도움·자료·목표·평가 기준을 맞추고, 반복 수행은 순서·학습 효과를 기록한다. 가상 자료 결과는 실제 문제 빈도·수요·현실 앱 이용 부담을 입증하지 않는다.

## 9. 기술 비교 계획

멀티에이전트는 사용자 가치를 구현할 후보로 둔다. 단일 에이전트·고정 흐름·동적 멀티에이전트를 비교해 사실 보존·수정 반영의 정확성과 실행 효율을 확인한 뒤 구현 방식을 선택한다. 역할을 나누는 것 자체를 제품 가치나 채택 이유로 삼지 않는다.

| 구성 | 실행 방식 | 확인할 효과 |
|---|---|---|
| 단일 에이전트 | 같은 도구로 정리·안내 확인·자체 대조 | 한 에이전트로 충분한가 |
| 고정 멀티에이전트 | 모든 사례에 사전 정의한 역할·의존 관계 적용. 독립 작업은 사전 정의대로 병렬 실행 | 역할 분담이 사실 보존·근거 연결을 개선하는가 |
| 동적 멀티에이전트 | 같은 역할 후보에서 요청·중간 결과로 작업 선택·변경 | 품질을 유지하며 불필요한 작업을 줄이는가 |

- 같은 모델·버전·생성 설정·사건 자료·도구 접근·출력 항목을 사용한다. 역할 지시 차이는 보존하고 고정 계획은 실행 전에 정한다.
- 전체 토큰·호출·시간·비용 상한과 재시도·수정 한도를 맞춘다. 계획·조정·대조·수정 비용도 합산하며 같은 예산을 반드시 소진하지 않는다.
- 10절의 네 대표 사례(① 경위 정리만 요청 ② 경위 정리+상담 준비 ③ 금액·날짜 충돌과 사용자 정정 ④ 공식 자료 확인 실패)를 점검한다. 사례별 기준 사실·기대 분기·실행 순서·반복 횟수·재시도 상한을 실행 전에 정하며 같은 기준일의 이용 허용 자료·실패 조건을 사용한다.
- 고정·동적 구성 모두 동일한 독립 작업 병렬 허용 기준을 쓴다. 직렬 대비 병렬 자체의 속도 효과와 동적 작업 선택·생략 효과를 섞지 않는다.
- 사실 누락·왜곡·추정 추가, 근거 연결, 분기 정확성, 불필요한 작업, 시스템 시간·답변 대기, 모델/도구 호출·토큰·실행 당시 단가와 비용·예산 소진을 기록한다.
- 단일 대 고정은 역할 분담 효과, 고정 대 동적은 구성 변경 효과를 본다. 모의 기록 점검과 실제 LLM·웹 실행 성능, 사용자 수요 검증을 구분한다.

## 10. 멀티에이전트 책임과 실행 분기

| 역할 | 입력 | 맡을 일·다음 역할에 전달할 출력 |
|---|---|---|
| 계획·조정 | 사용자 요청 유형·입력 원문·이전 결과 상태·남은 실행 예산 | 실행 역할·하위 작업 지정, 순차/병렬 의존 관계·실행 조건·변경 이유·상태 기록, 최종 결과 조립 |
| 사건 정리 | 원문 ID가 있는 설명·자료 문구·자료 보유 목록·추가 답변 | 항목 ID·원문 ID가 연결된 경위 초안, 미확인·충돌 목록, 추가 확인 질문. 필요 안내 결과를 받아 상담 질문 작성 |
| 공식 안내 조사 | 사용자 막힘 항목·조회 질문/키워드·허용 출처 | 출처명·URL·확인일·적용 범위를 갖춘 설명 또는 ‘미확인’과 조회 실패 사유 |
| 결과 대조 | 조립된 초안·연결된 입력 원문·안내 결과·이전 대조 기록 | 원문/출처 미연결 문장·왜곡/임의 추정·미확인 누락 점검, 점검 범위·문제 항목·수정 요청 또는 ‘점검 범위 내 문제 미발견’ |

자동 대조의 문제 미발견은 법률 전문가 승인이나 진위 확인을 뜻하지 않는다. 입력 원문이 없는 공식 설명은 공식 출처에 연결한다.

| 대표 사례 | 실행 흐름 | 계획 변경·종료 |
|---|---|---|
| 경위 정리만 요청 | 계획 → 사건 정리 → 결과 조립 → 대조 | 공식 안내 조사 생략 |
| 경위 정리+상담 준비 | 사건 정리 ∥ 일반 공식 안내 → 상담 질문 작성 → 조립·대조 | 독립적인 일반 안내만 병렬. 사건 세부 조건이 필요한 안내는 정리 후 실행 |
| 금액·날짜 충돌과 사용자 정정 | 충돌 확인 → 답변 대기 → 관련 부분 수정 → 재대조. 별도 정정 단계: 초기 결과 → 사용자 금액 정정 → 연결 요약·질문 갱신 → 기존 대조 결과의 적용 범위 재확인 | 미해결 충돌은 보존. 정정 후 이전 값 잔존·원문 연결·재검토 상태·무관한 조사 재실행 건수를 비교 기록 |
| 공식 자료 확인 실패 | 원인 기록 → 예산 내 대체 출처 검토 → 부분 결과 조립·대조 | 안내 미확인 표시, 확인한 경위는 보존 |

계획·작업·시도별 목적·입출력 참조·선행 관계·실행 조건·상태·추가/생략/보류 이유를 남긴다. 수정은 관련 작업만 다시 실행하고 이전 실패·계획을 덮어쓰지 않는다. 답변 대기·미실행·실패·부분 결과를 구분한다. 수정·조회 한도 후에는 남은 문제를 명시해 부분 결과로 종료한다.

요청·작업·근거·상태 연결은 공통 구조이고, 거래 자료 항목·용어·공식 출처·사실 보존 기준은 도메인 특화다. 역할 분리가 효과적이라는 결론은 9절 비교 후 판단한다.

## 11. 전제·위험과 변경 배경

- 개인 제안이며 팀 앱 MVP·요구사항·WBS 변경이나 TASK 완료·제출을 의미하지 않는다. 실제 수요·서비스 차별점·현실 준비 부담 감소·멀티에이전트 성능은 미검증이다. 가상 사례 1건의 LLM 실행 결과와 구분한다.
- 사용자 검토·자동 결과 대조는 자료 진위·법률 정확성·증거 충분성 판단이 아니다. 법률·절차 출력과 제공 범위의 전문 검토 담당은 미정이다.
- 피해자뿐 아니라 판매자·송금 상대방의 이름·계좌·전화번호·대화에도 제3자 개인정보가 포함된다. 가상·비식별 자료만 공개 기록하고 실제 식별정보·사건번호·원문은 저장소에 넣지 않는다. 실제 자료 취급 전 저장 여부·보관 기간·삭제·접근 통제·외부 모델 전송 조건을 정한다.
- 공식 API·승인 데이터·필요한 최소 개별 문서를 이용한다. 공개 열람과 자동 수집·저장·재사용 권한을 구분한다.

### 법적 경계·전문 검토

사건 경위와 자료를 정리하는 기능도 제공 방식에 따라 법률상담·법률관계 문서 작성과의 경계 검토가 필요하다. 구현·서비스 제공 전 무료/유료 여부, 수익·소개 대가, 문서 작성 범위와 실제 출력을 바탕으로 전문적인 법적 검토를 받는다. ‘정리 지원’이라는 명칭이나 면책 문구만으로 적법성을 판단하지 않는다.

변호사법 제109조는 비변호사의 이익 수수·약속과 법률상담·법률관계 문서 작성 등 법률사무 취급을 규정한다. 모든 법률 정보 제공이 곧 위법이라고 단정하거나 이 초안으로 적법성을 판단하지 않는다. [국가법령정보센터 변호사법 제109조](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900175916) (확인일: 2026-11-16; 조문 표시 시행일: 2026-10-02)

법률·절차 출력의 정확성을 검토할 담당자와 범위, 서비스 제공의 법적 경계 검토자는 미정이다. 검토자를 확보하고 검토를 수행하기 전 정확성·적법성 검토 완료로 표시하지 않는다.

### 주제 변경 배경

부동산은 실제 상태의 현장 확인이 중요해 온라인 정리로 해결할 범위가 불확실하다고 두나가 판단했다. 보유 자료 정리에 집중하는 중고거래 상담·신고 준비로 변경했으며, 멘토가 주제 전환을 직접 지시한 것으로 기록하지 않는다. 새 안의 효과는 가상 사례 점검과 후속 사용자 검증으로 확인한다.
