## 1. 목적과 현재 결론

사용자 요청에 따른 동적 구성을 평가하기 위해, 요청이 달라져도 유지할 구성 규칙과 실행 경계를 정리한다.

MVP에서는 역할 후보·책임, 작업 유형, 입출력·기록 형식, 판정·분기 규칙, 실행 상한과 오류 처리 원칙을 고정하는 안을 제안한다. 그 안에서 요청과 중간 결과에 따라 역할과 작업의 선택·조합·순서·추가·생략을 바꾼다.

이 문서는 사용자가 개인 폴더에 작성을 요청한 논의 메모다. TASK-005 전체 결과나 확정 설계를 대체하지 않는다. 아래 내용은 구현·실험 전 제안이며, 효과를 확인한 결과가 아니다.

## 2. 역할 후보와 책임

| 역할 후보 | 고정할 책임 제안 |
|---|---|
| 후보 발굴 | 조사할 대상을 찾기 |
| 자료 조사 | 정보를 수집하고 출처 기록하기 |
| 조건 검증 | 근거를 바탕으로 조건 충족 여부 판단하기 |
| 비교·분석 | 대상별 차이와 적합성 정리하기 |
| 결과 종합 | 요청에 답하는 결과와 미확인 사항 전달하기 |

요청마다 역할을 새로 발명하는 기능은 우선 제외하고, 선택할 역할과 배정 작업을 바꾼다. 계획·조정 기능이 선택과 배정을 관리하는 안을 검토한다. 위 목록은 논리 역할이며 실제 에이전트 수를 5개로 확정하는 의미가 아니다. 역할 분리·병합과 실제 배치는 후속 검증 및 팀 결정 사항이다.

## 3. 허용할 작업 유형

- 요청 조건 추출·확인
- 후보 발굴
- 자료 조회·추출
- 조건 판정
- 대상 비교
- 결과 작성
- 근거 부족·충돌·조회 실패에 대한 보완 조사

“조건 판정”이라는 유형은 고정하지만, 판정 내용은 오프라인 지원·무료 예약·사이트 수 한도 등 요청에 따라 달라진다. 새 유형이나 도구를 실행 중 임의로 추가하는 기능은 우선 범위 밖으로 두는 안을 제안한다.

## 4. 입출력과 기록 형식

| 기록 대상 | 공통으로 남길 최소 항목 제안 |
|---|---|
| 사용자 요청 | 목적, 대상, 필수 조건, 선호, 후속 작업 조건 |
| 작업 계획 | 작업 ID, 유형, 목표, 담당 역할, 입력, 선행 작업, 실행 조건, 완료 기준 |
| 실행 기록 | 상태, 시작·종료 시각, 결과, 오류, 추가·생략 이유 |
| 근거 | 출처, 확인 시점, 확인한 내용, 관련 조건 |
| 최종 결과 | 조건별 판정, 비교·추천 이유, 근거, 미확인 사항 |

같은 종류의 정보를 일관된 형식으로 남긴다는 원칙을 제안한다. 구체적인 필드 이름·자료형·상태 코드는 R05의 구현 구조 및 기존 구조화 원본과 맞춰야 한다. 이 표를 확정 스키마로 간주하지 않는다.

## 5. 판정 기준과 분기 규칙

### 판정의 의미

| 판정 | 의미 |
|---|---|
| 충족 | 해당 조건을 만족한다는 근거가 있음 |
| 미충족 | 해당 조건을 만족하지 않는다는 근거가 있음 |
| 미확인 | 근거가 부족하거나 충돌해 판단할 수 없음 |

자료 조회 실패를 미충족으로 바꾸지 않는다. 사용자 선호를 필수 조건으로 바꾸지 않는다. 출처가 뒷받침하는 범위에서만 판정한다.

### 고정 규칙과 요청별 조건의 구분

- **고정할 규칙:** 명시된 실행 조건이 충족된 경우에만 후속 작업을 시작한다.
- **요청별로 달라질 내용:** “두 후보 모두 미충족이면”, “확인할 수 없으면”, “다른 후보도 함께” 등 요청에서 추출한 조건과 행동.

분기 규칙을 고정한다는 것은 APP-A·B 두 경로만 고정한다는 뜻이 아니다. 요청에서 얻은 조건을 공통 규칙에 적용하고 중간 판정에 따라 행동을 결정한다.

## 6. 실행·오류 처리의 경계

- 선행 입력이 준비된 작업만 실행한다.
- 서로가 서로를 기다리는 순환 의존 관계를 허용하지 않는다.
- 같은 목적의 작업이 중복 생성되는지 확인한다.
- 사용자의 필수 조건을 임의로 완화하지 않는다.
- 동시 실행·호출·재시도·추가 조사에 상한을 적용한다.
- 상한에 도달하면 확인된 결과와 미확인 사항을 전달한다.
- 실행 실패와 조건 미충족을 구분하고 실행·생략·보류·취소 사유를 기록한다.

상한을 적용한다는 원칙을 고정하고 구체적인 값은 기준 실행 후 정할 수 있다. 비교 실험 중에는 양쪽에 동일한 상한을 적용하고, 실행 중 AI가 임의로 바꾸지 않는 안을 제안한다.

## 7. 평가에서 고정할 조건

동적 구성의 효과를 확인하기 위해 고정 워크플로와 요청별 구성에 다음 조건을 맞춘다.

- 동일한 모델과 검색 도구
- 동일한 사용자 요청과 제공 자료
- 동일한 호출·비용 예산과 병렬 실행 정책
- 동일한 조건 판정 기준과 평가 항목

고정 워크플로에도 같은 검증 도구와 조건부 처리 능력을 제공한다. 단순히 baseline에 필요한 기능을 빼서 동적 구성이 우수하게 보이게 하지 않는다. 계획을 구성하는 방식의 차이를 비교한다.

고정 흐름 대비 필수 작업 누락, 불필요한 실행, 선행 관계·분기 오류, 사용자 조건 충족 판정, 근거 품질, 시간·호출 수·비용을 평가한다. 품질이 떨어졌는데 더 빠르거나 저렴하다는 이유만으로 적절한 구성으로 판단하지 않는다. 실제 비교 결과와 정량 합격선은 아직 미확인이다.

## 8. 고정 범위와 동적 범위 요약

| 고정할 것 제안 | 동적으로 바꿀 것 제안 |
|---|---|
| 역할 후보와 기본 책임 | 필요한 역할 선택과 작업 배정 |
| 허용된 작업 유형 | 작업 대상·내용·개수 |
| 공통 입력·출력·기록 형식 | 요청별 조건과 작업 결과 |
| 선행 관계·조건 평가 규칙 | 실행 순서·의존 관계·병렬 조합 |
| 오류 처리와 상한 적용 원칙 | 중간 결과에 따른 추가·생략·보류·취소 |
| 비교 실험 조건과 평가 방식 | 실제 측정 결과와 사례별 판정 |

## 9. 고정의 적용 범위와 재검토

고정은 영구히 변경하지 않는다는 뜻이 아니다. 한 버전과 비교 실험 안에서 일관되게 적용하고 시험 결과에 따라 수정 이력을 남겨 바꾸는 기준이다.

역할 책임 중복, 작업 유형 부족, 스키마 누락, 실행 상한의 부적절함이 발견되면 근거와 영향을 기록한다. 실험 조건이 바뀌었다면 이전 결과와 변경 후 결과를 같은 조건인 것처럼 비교하지 않는다. 제품 범위·주요 기준 변경은 권한 있는 담당자의 결정과 구분해 반영한다.

## 10. 미확인 사항과 결정 요청

- 역할 후보의 적정 분리 수준과 작업 유형의 충분성은 요청 변형 시험이 필요하다.
- 입출력 필드·상태 코드·실행 구조는 R05와 정합성을 확인해야 한다.
- 호출 제한·비용·접근 조건은 R02 결과를 반영해야 한다.
- 실제 상한 수치와 품질·시간·비용의 정량 합격선은 기준 실행 후 결정한다.
- 이 고정 범위를 TASK-005의 MVP 제안으로 채택할지 팀 확인이 필요하다.
