- 담당: R03 (두나)
- 상태: 초안 — 구현·시험 및 팀 확정 전 제안

## 1. 목적과 확인 범위

사용자 요청에 따라 역할과 작업을 구성하는 기능을 첫 평가 사례 APP-A·B·C에 적용해 예상 동작과 실패 기준을 정리한다. 사용자 요청에 대응하는 구성 기능이 구현 대상이며, 세 사례는 첫 검증 범위다.

사례의 요청과 기대 분기는 집중 앱 명세를 기준으로 한다. 세부 작업 배정과 순서는 시험 전 제안이다. 실제 조사 실행, 앱 기능 판정, 기기 시험, 성능 측정은 수행하지 않았다. 사용자가 개인 폴더에 작성을 요청한 논의 메모이며 TASK-005 전체 결과나 확정 설계를 대체하지 않는다.

## 2. APP-A — 지정 앱 비교

### 요청과 조건

> 안드로이드에서 인터넷 없이 공부하려고 해. PomoToki와 Focus To-Do 중 오프라인에서 뽀모도로 타이머를 쓸 수 있는 앱을 비교해줘. 가능하면 계정 없이 쓰고 싶어.

- 지정 대상: PomoToki, Focus To-Do
- 플랫폼: Android
- 필수 조건: 오프라인 뽀모도로 타이머
- 선호: 계정 없는 사용
- 신규 후보 발굴: 요청하지 않음

### 역할·작업·선행 관계 제안

| 작업 | 담당 역할 | 선행 작업 |
|---|---|---|
| 두 앱의 오프라인·계정 관련 자료 조사 | 자료 조사 | 요청 구조화 |
| 앱별 필수 조건과 선호 판정 | 조건 검증 | 해당 앱 자료 조사 |
| 두 앱의 조건별 차이 비교 | 비교·분석 | 두 앱 판정 |
| 근거와 미확인 사항을 포함한 결과 작성 | 결과 종합 | 비교 결과 |

두 앱의 자료 조사는 독립적으로 병렬 실행할 수 있다. 한 앱의 조사가 끝나면 해당 앱의 검증을 시작할 수 있다. 후보 발굴 역할은 선택하지 않는다.

### 예상 결과와 실패 기준

- 예상 결과: 앱별 오프라인 지원 판정, 계정 조건, 비교 이유, 근거·출처·확인 시점과 미확인 사항.
- 실패: 다른 앱을 불필요하게 발굴함, 계정 없는 사용을 필수 조건으로 바꿈, 근거 없는 기능을 충족으로 판정함.

## 3. APP-B — 신규 후보 발굴

### 요청과 조건

> 공부 중에 안드로이드 폰으로 웹사이트를 자꾸 열게 돼. 내가 지정한 사이트 2개를 평일 저녁에 무료로 차단할 수 있는 앱을 찾아줘.

- 지정 앱: 없음
- 플랫폼: Android
- 필수 조건: 사이트 2개 차단, 평일 저녁 예약, 해당 기능의 무료 사용
- 확인할 실행 조건: 대상 브라우저와 필요한 권한
- 누락된 구체값: 사이트 주소와 정확한 예약 시간

사이트 주소와 정확한 시간은 기능 지원 가능성 조사와 실제 기기 설정·시험에서 필요한 수준을 구분한다. 값이 없는 상태에서 실제 차단 동작까지 확인했다고 기록하지 않는다. 판정에 필요한 정보가 부족하면 확인 질문이나 미확인으로 남긴다.

### 역할·작업·선행 관계 제안

| 작업 | 담당 역할 | 선행 작업 |
|---|---|---|
| 조건에 맞을 가능성이 있는 후보 발굴 | 후보 발굴 | 요청 구조화 |
| 후보별 기능·요금제·호환성 자료 수집 | 자료 조사 | 후보 확보 |
| 무료 예약·사이트 수 한도 검증 | 조건 검증 | 관련 자료 확보 |
| 브라우저·권한 확인 | 조건 검증 | 후보 및 관련 자료 확보 |
| 적합 후보 비교와 결과 작성 | 비교·분석, 결과 종합 | 후보별 판정 |

후보 확보 전에 후보별 검증을 시작하지 않는다. 요금제 검증과 브라우저·권한 검증은 필요한 입력이 준비되면 독립적으로 진행할 수 있다. 무료 설치와 무료 예약 차단을 구분한다.

### 예상 결과와 실패 기준

- 예상 결과: 조건에 맞는 후보와 무료 기능 범위, 호환성·권한, 근거·출처·확인 시점 및 미확인 사항.
- 실패: 무료 설치를 무료 예약 차단으로 오해함, 후보 확보 전에 후보별 검증을 실행함, 사이트 수·예약 조건을 누락함, 호환성 미확인을 실제 동작 보장으로 표현함.

## 4. APP-C — 중간 판정에 따른 대안 발굴

### 요청과 조건

> PomoToki와 Focus To-Do의 안드로이드 오프라인 타이머를 비교해줘. 두 앱 모두 오프라인에서 타이머를 쓸 수 없다고 확인되면 대안도 찾아줘.

처음에는 지정 앱의 조사·검증을 구성한다. 대안 발굴은 “두 후보 모두 미충족으로 확인”이라는 실행 조건을 가진 후속 작업으로 둔다. APP-A의 계정 선호를 이 요청에 임의로 추가하지 않는다.

### 분기별 예상 동작

| 사례 | 중간 결과 | 후속 작업 | 예상 결과 |
|---|---|---|---|
| APP-C1 | 두 앱 모두 미충족 | 두 앱 판정 완료 후 대안 발굴 → 새 후보 조사·검증 → 종합 | 기존 후보 탈락 근거와 대안의 조건별 판정 |
| APP-C2 | 한 앱 이상 충족 | 대안 발굴 생략 | 충족 후보와 근거, 나머지 후보의 판정 |
| APP-C3 | 충족 후보 없이 일부 미확인 | 대안 발굴을 실행하지 않음. 필요하면 한도 내 보완 조사 | 미확인 조건과 확인에 필요한 정보 |

APP-C2에서 대안 발굴이 불필요해졌더라도 나머지 지정 앱의 비교 요청 자체를 임의로 취소하지 않는다. APP-C3에서 보완 조사 후 판정이 바뀌면 실행 조건을 다시 평가한다. 끝내 확인할 수 없으면 발굴을 실행하지 않은 사유를 남기고 미확인으로 안내한다.

### 실패 기준과 시험 경계

- 두 후보의 판정 전에 대안 발굴 실행
- 미확인·조회 실패를 미충족으로 취급
- 새 후보의 필수 조건을 검증하지 않고 추천
- 추가·생략 이유와 새 결과의 반영 이력 누락

분기 시험에는 모의 판정값을 사용한다. 이는 실제 앱이 조건을 충족하거나 충족하지 않는다는 증거가 아니다. 실제 앱 기능은 공개 출처와 기기 시험으로 별도 확인한다.

## 5. 사례 간 구성 차이

| 구성 요소 | APP-A | APP-B | APP-C |
|---|---|---|---|
| 후보 발굴 역할 | 생략 | 처음부터 선택 | 실행 조건 충족 시 배정 |
| 작업 대상 | 지정된 두 앱 | 발굴한 후보 | 지정 앱, 필요 시 대안 |
| 주요 검증 | 오프라인·계정 조건 | 무료 예약·사이트 수·호환성 | 오프라인 판정과 후속 실행 조건 |
| 순서 | 조사 → 검증 → 비교 | 발굴 → 조사·검증 → 추천 | 조사·검증 → 분기 → 필요 시 발굴 |
| 중간 조정 | 근거 부족 등에 대한 보완 | 후보와 조사 결과에 따른 보완 | 판정에 따른 발굴 추가·생략 |

## 6. 요구사항과 완료 조건 연결

| 요구사항 | 입력 | 완료 조건 | 평가 사례 |
|---|---|---|---|
| FR-01 요청 구조화 | 사용자 요청 | 플랫폼·대상·필수·선호·발굴 조건을 구분하고 판단에 필요한 누락은 질문 또는 미확인으로 남김 | A의 필수·선호, B의 복합 조건, C의 조건부 발굴 및 요청 변형 |
| FR-02 계획 구성 | 구조화한 요청 | 각 작업의 목표·역할·선행 관계·실행 조건을 기록하고 필수 작업 포함 | A의 발굴 생략, B의 발굴 선행, C의 조건부 작업 |
| FR-03 실행 조정 | 계획과 선행 결과 | 계획과 실제 역할·순서·상태를 연결하고 추가·생략 사유 기록 | C1·C2·C3, A·B 순서·병렬 관계 |
| FR-04 근거 연결 | 조사 자료와 조건 판정 | 조건별 충족·미충족·미확인에 근거·출처·확인 시점을 연결 | 전체 사례 |

이 표는 평가 기준 제안이다. 실제 통과 결과는 아직 없다.

## 7. 요청 변형 시험 제안

| 변형 | 예상 변화 |
|---|---|
| APP-A에서 지정 앱을 제거하고 조건에 맞는 앱 탐색 요청 | 후보 발굴 작업과 역할 추가 |
| APP-B에 비교할 앱을 지정하고 추가 후보는 요청하지 않음 | 불필요한 후보 발굴 생략, 지정 후보 검증 구성 |
| APP-C를 “확인할 수 없어도 대안을 찾아줘”로 변경 | 미확인 상태도 요청에 명시된 발굴 조건으로 평가 |
| 앱 이름을 다른 지정 후보로 변경 | 이름과 무관하게 같은 원칙으로 계획 구성 |
| “가능하면 계정 없이”를 “반드시 계정 없이”로 변경 | 선호에서 필수 조건으로 바꾸어 조건 판정과 비교 반영 |

실행 전 변형 요청의 정확한 문장과 기대 작업을 고정해 두고, 결과를 본 뒤 기대값을 임의로 바꾸지 않는다. 사용자의 요청을 구성하는 기능이 예시 두 경로에만 묶이지 않는지 확인한다.

## 8. 남은 평가 계획과 결정 요청

- 고정 워크플로 baseline의 구체적인 계획과 비교 평가표 작성이 다음 작업이다.
- 동일 모델·검색 도구·자료 조건·호출 상한·병렬 정책을 맞추고, baseline에도 같은 검증·조건부 처리 능력을 제공한다.
- 필수 작업 누락, 불필요한 실행, 순서·분기 오류, 조건·근거 정확도, 시간·호출 수·비용을 비교한다.
- 실제 앱 기능 확인과 모의 분기 시험, 문서 확인과 기기 동작 시험을 분리해 기록한다.
- 후보 수·조사 상한·모델·프레임워크·정량 합격선은 아직 확정하지 않는다.
- R02의 데이터 접근 결과와 R05의 실행·기록 구조를 반영하고, R01이 제출본 MVP 범위를 결정할 때 이 안을 참고하도록 제안한다.
