# 멘토 설명문 — 중고거래 상담·신고 준비 자료 정리

## 1. 누가 언제 사용하는가

제가 제안한 서비스는 중고거래 피해를 의심하는 사람이 처음 상담이나 신고를 준비할 때, 증빙과 사건 경위를 정리하도록 돕는 서비스입니다. 우선은 돈을 보냈지만 물건을 받지 못한 상황에 집중했습니다.

신고 준비에는 이체 내역, 판매 글, 대화 같은 자료와 사건 설명이 필요합니다. 제가 다루려는 문제는 접수 항목을 인증 후 화면에서 확인하며 준비하다가 로그인 시간이 끝나면 재인증·재진입해야 하는 번거로움입니다. 이는 제가 전달한 이용상 불편이며, AI가 실제 시간 만료 동작까지 시험한 결과는 아닙니다. 공개 메인에서도 준비자료 예시를 볼 수 있으므로 모든 확인에 로그인이 필요하다는 주장은 하지 않습니다. 법률 용어 설명은 작성 중 막힐 때 돕는 보조 기능으로 두었습니다.

## 2. 어떤 실제 근거를 찾았는가

공개 블로그에서 직접 티켓 거래 피해를 겪었다고 밝힌 분의 경험담을 찾았습니다. 작성자는 첫 경찰 신고라 긴장했고, 여러 증빙을 첨부하고 상세한 항목을 작성했다고 설명합니다. 그래서 증빙 준비와 상세 경위 작성이 실제 이용 과정에 있다는 첫 사례로 사용했습니다.

동시에 작성자는 온라인에 구체적으로 작성한 뒤 경찰서에서는 오래 걸리지 않았다고 설명합니다. 이 내용은 기존 ECRM도 도움이 된다는 근거로 함께 기록했습니다. 이 한 글이 반복 재작성이나 모든 피해자의 어려움을 입증한다고 해석하지는 않았습니다.

## 3. 기존 대안과 무엇이 다른가

기존 대안으로 ECRM과 폴봇, 체크리스트, 충분한 지시를 준 LLM을 보고 있습니다. 폴봇은 과거 공식 발표에 질문 기반 자동 작성 기능이 있어, 작성 지원 기능이 없다는 전제는 사용하지 않았습니다. 현재 폴봇의 실제 대화와 수정 기능은 아직 시험하지 못했습니다.

LLM에는 가상 사건 한 건을 두 차례 입력했습니다. 원문 연결과 금액 충돌 표시, 사용자 정정 반영, 배송 여부 미확인을 수행했습니다. 그래서 이 기능들이 우리만 가능하다고 설명하지 않겠습니다.

확인하고 싶은 차이는 같은 일을 더 정확하고 적은 수고로 끝낼 수 있는지입니다. 기존 공개 안내와 체크리스트만으로 충분히 준비할 수 있는지, 제안 방식이 인증 후 화면을 다시 확인하는 수고를 더 줄이는지가 현재 핵심 질문입니다. 반복 수정은 핵심 pain에서 제외하고 정정 반영은 정확성 기능으로 유지합니다.

## 4. 사용자는 무엇을 하는가

먼저 공식 공개 안내를 바탕으로 준비 목록을 보고, 각 자료를 보유했는지 모르는지 정리합니다. 그런 다음 기억나는 내용을 자유롭게 적습니다. 시스템은 사용자가 제공한 문구를 원문과 연결해 사건 초안과 자료 목록으로 정리합니다. 필요한 내용이 빠졌으면 질문하지만 모르는 항목 때문에 진행을 막지는 않습니다.

예를 들어 처음에는 10만 원을 보냈다고 적었는데 사용자가 이체 자료에 12만 원이라고 적혀 있다고 설명하면, 어느 쪽을 임의로 선택하지 않고 차이를 보여줍니다. 사용자가 12만 원이 맞다고 정정하면 현재 요약과 관련 질문을 갱신하고 과거 진술은 이력으로 남깁니다. 판매자가 배송했다고 말한 사실과 실제 발송 여부도 구분합니다. 사용자가 자료를 설명한 것과 실제 파일을 시스템이 읽은 것도 구분하며, 첫 시제품은 파일 판독 없이 텍스트와 자료 목록만 받습니다.

마지막에는 사용자가 요약·자료 목록·미확인 항목을 검토하고 복사합니다. 자료를 자동으로 찾아 모으거나 신분증을 받거나 ECRM 인증·세션을 관리하거나 신고를 대신 입력·접수하는 기능은 포함하지 않습니다. 흐름은 준비 목록 확인, 자유 입력, 초안·누락 확인, 검토 후 복사, ECRM 직접 접수입니다.

## 5. 어떻게 판단할 것인가

같은 가상 자료와 정정 문구로 ECRM 안내만 보는 방법, 체크리스트를 추가한 방법, 충분한 지시의 LLM을 비교할 계획입니다. 제안 방식은 시제품이 준비된 뒤 같은 과제로 비교합니다. 지금은 비교 계획이며 새 실험 결과는 없습니다.

사실 누락이나 왜곡, 정정 후 불일치를 확인하고 준비·입력·검토·수정에 걸린 시간과 횟수도 함께 기록하겠습니다. 결과가 빨라도 사실을 왜곡하면 성공으로 보지 않겠습니다. 대안만으로 충분하다면 개발을 당연히 진행하지 않고 축소하거나 보류하겠습니다.

오늘 조언받고 싶은 것은 기능을 더 늘리는 방법보다, 재인증·재진입 불편을 어떤 실제 동작과 비교로 확인할지입니다.

3. 추가 가치가 확인되지 않을 때 어느 수준으로 축소하거나 보류하는 것이 적절할까요?

## 기술을 물어보시면

멀티에이전트는 미리 정한 제품 가치가 아니라 구현 후보입니다. 같은 모델·도구·예산에서 단일 구성, 고정 역할 구성, 요청별 동적 구성을 비교해 품질과 불필요한 실행 차이가 있을 때 채택하려고 합니다. 이번 개인 제안이 팀의 앱 MVP를 대체하기로 결정된 것은 아닙니다.
