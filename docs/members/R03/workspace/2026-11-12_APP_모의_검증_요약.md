## 1. 수행한 일과 결과

수동으로 구조화한 요청과 모의 판정값을 규칙 기반 계획·실행 원형에 입력했다. 작업 생성, 역할 배정, 선행 작업 완료 순서, 조건부 발굴 추가·생략, 비교로의 결과 전달을 검사했다.

| 구분 | 결과 |
|---|---|
| APP-A, B, C1, C2, C3 | 5건 통과 |
| V1~V4 요청 변형 | 4건 통과 |
| APP-C 판정 조합 전체 | 9건 통과 |
| 합계 | 18건 통과, 0건 실패 |
| 의도적으로 잘못 만든 실행 기록 | 4건 모두 오류 탐지 |

APP-C의 9건은 충족·미충족·미확인의 두 후보 조합 전체다. 기본 C1~3과 일부 조합이 겹치며, 18개의 서로 독립적인 사용자 요청을 시험했다는 뜻은 아니다. 반복 실험이나 통계적인 성능 증거도 아니다.

## 2. 사례별 관찰

| 사례 | 원형에서 관찰한 동작 |
|---|---|
| APP-A | 지정 후보 두 개의 조사·검증·비교·종합 구성. 신규 발굴 없음. 오프라인 필수와 계정 선호 보존 |
| APP-B | 후보 발굴 후 모의 후보 조사·검증. 무료 예약·사이트 2개·평일·저녁 조건, 브라우저·권한 항목 보존 |
| APP-C1 | 두 후보 미충족 판정 작업이 끝난 뒤 발굴 작업을 계획에 추가. 모의 대안 조사·검증 후 비교에 연결 |
| APP-C2 | 한 후보 이상 충족이면 발굴 생략. 두 지정 후보의 검증 결과를 비교에 연결 |

앱 출처는 `mock-developer-help`, `mock-pricing`, `mock-browser-help`라는 가상 유형 표식이다. 실제 자료를 읽거나 기능을 입증한 것이 아니다. 판정값도 모의 입력이며, PomoToki나 Focus To-Do의 실제 지원 여부를 뜻하지 않는다. 모의 대안은 미확인으로 유지하며 추천 적합성이 입증됐다고 하지 않는다.

## 3. 검사 방법과 오류 탐지

사례별 기대 발굴 횟수와 실행 계획·이벤트 순서를 대조했다. 필요한 조건 보존, 실제 선행 완료 순서, 지정 후보 조사 누락, 모든 후보 판정의 비교 입력 연결, 앱 출처 유형과 역할 후보 준수 등을 확인했다.

평가기 민감도를 점검하기 위해 정상 실행을 복제해 다음 오류를 넣었다.

1. 필수 검증 조건 제거
2. 비교 작업에서 후보 판정 의존 관계 제거
3. APP-C3의 미확인 상태에서 불법 발굴 작업 삽입
4. APP-C1의 조건부 발굴 추가 시점을 선행 판정 이전으로 이동

네 오류 모두 한 개 이상의 검사에서 탐지됐다. 이 결과는 해당 오류에 대한 검사기의 반응이며 모든 계획 오류를 탐지한다는 보장은 아니다. 사건 순서는 실제 벽시계 시간이 아닌 모의 실행 이벤트 순서다.

| FR-03 | 규칙 기반 원형의 선행 완료 순서와 조건부 추가·생략 확인 | 실제 에이전트·도구 실행, 실패 복구·취소·재시도·병렬 실행은 미검증 |

역할·작업·관계·이벤트는 공통 관리 구조의 원형이고, 조건명·앱 후보·출처 유형은 앱 도메인 설정이다. 이 구분은 기록했지만 다른 도메인의 실행 시험은 하지 않았다.

### 4.1 공통 관리 구조와 앱 특화의 구분

아래 표는 검증 코드와 결과 JSON을 대조한 기록이다. ‘공통’은 A·B·C에서 공유하며 다른 도메인에도 재사용할 후보라는 뜻이다. 실제로 도메인 교체가 가능한 범용 엔진을 완성했다는 의미가 아니다.

| 구분 | 공통 구조 후보 | 앱 도메인 특화 내용 | 이번 확인 범위 |
|---|---|---|---|
| 요청 표현 | 대상 목록, 필수 조건, 선호, 후속 조건을 담는 구조 | Android, PomoToki·Focus To-Do, 오프라인 타이머·계정·무료 예약 등 값 | 수동 입력의 전달·보존. 자연어 추출은 미검증 |
| 역할·작업 기록 | 작업 ID·유형·담당 역할·대상·선행 작업·상태를 연결하는 형식 | 앱 발굴·앱 자료 조사·기능/요금 판정·앱 비교 책임 | 역할 후보 준수와 작업 배정 검사. 역할 종류를 도메인과 무관한 영구 목록으로 확정하지 않음 |
| 순서·실행 이력 | 선행 완료 후 실행, 작업 추가와 완료 이벤트·계획 버전 기록 | 앱 후보를 찾은 후 해당 후보 조사·검증, 앱 판정을 비교에 연결 | 모의 이벤트 순서와 의존 작업 대조. 실제 동시 실행은 아님 |
| 조건부 후속 행동 | 판정 집합과 요청의 조건을 평가해 추가·생략하고 이유 기록 | 두 지정 앱의 오프라인 미충족 시 대안 앱 발굴 | C 판정 조합과 요청 변형의 규칙 실행 확인 |
| 판정 표현 | 충족·미충족·미확인의 구분과 전달 | 오프라인 사용·무료 예약 등이 충족됐음을 입증할 앱별 근거 | 상태값은 입력 주입. 기능별 근거 판정은 미검증 |
| 출처 연결 | 작업에 출처 유형·근거 참조를 연결하는 방식 | 개발사 도움말·요금제·브라우저 도움말의 가상 유형 | 출처 유형 배정만 검사. 실제 URL·문서·직접 지지 근거 연결은 미검증 |
| 결과 종합 | 모든 대상 판정이 비교와 최종 결과 단계에 연결됨 | 앱 후보별 적합성·추천 이유·미확인 정보 | 작업 관계만 검사. 실제 자연어 보고서 생성은 미검증 |

작업 순서가 다르다는 사실과 앱의 검증 내용이 다르다는 사실을 구분한다. 앱 도메인에서 어떤 사실이 ‘충족’을 입증하는지는 실제 출처·기기 확인으로 별도 정의·검증해야 한다.

### 4.2 A·B·C에서 실제로 달라진 앱 특화 설정과 구성

| 사례 | 앱 특화 입력·선택 | 공통 규칙에 따른 모의 실행 | 결과 JSON에서 확인할 위치 |
|---|---|---|---|
| APP-A | `timer`, 두 지정 앱, `offline_pomodoro` 필수, `accountless` 선호, `mock-developer-help` | 두 후보별 조사·검증 → 비교 → 종합. 발굴 생략 | 해당 run의 `structured_input`, T1~T6, `decisions` |
| APP-B | `blocker`, 지정 후보 없음, `two_sites`·`weekday_schedule`·`evening_schedule`·`free_scheduled_blocking`, `browser`·`permissions`, 요금/브라우저 가상 출처 | T1 발굴 → T2 조사 → T3 검증 → T4 비교 → T5 종합 | 해당 run의 `structured_input`, `tasks[].source_profiles`, `conditions`, `context_checks` |
| APP-C1 | `timer`, 두 지정 앱, 오프라인 필수, 계정 선호 없음. `all_fail`과 두 미충족값 | T2·T4 판정 후 T5 발굴 추가 → T6·T7 대안 조사·검증 → T8 비교 → T9 종합 | `mock_outcomes`, `events`, `decisions`, T5의 `depends_on`과 T8의 입력 |
| APP-C2 | C와 같은 앱 정의, 충족·미충족 입력 | 대안 발굴 생략. 지정 두 후보의 판정으로 비교·종합 | `decisions.reason`: `qualifying candidate exists` |
| APP-C3 | C와 같은 앱 정의, 미충족·미확인 입력 | 발굴 조건 미확립으로 생략. 미확인값 유지 | `decisions.reason`: `condition not established (unknown)` |

APP-C1·C2·C3는 서로 다른 도메인 정의가 아니라, **같은 앱 특화 정의와 요청에 다른 중간 판정값을 넣은 시험**이다. APP-A와 C도 같은 타이머 출처 유형을 쓰지만 선호·후속 조건이 다르다. APP-B에서 브라우저·권한은 한 검증 작업의 항목으로 보존했으며 이를 독립 병렬 작업으로 실제 실행하지 않았다.

### 4.3 현재 코드에서 아직 분리되지 않은 부분

- `domain` 객체에는 앱 역할 후보와 가상 출처 유형이 있고, `a`·`b`·`c`에는 앱 조건과 수동 구조화 값이 있다.
- `execute()`의 작업 생성·이벤트 기록·의존 검사에는 공통화할 요소가 있으나, 조사 → 검증 → 비교 → 종합 패턴과 역할 매핑도 코드에 직접 들어 있다. 완전히 분리된 공통 엔진·도메인 모듈은 아니다.
- `all_fail`·`no_pass` 조건 평가는 규칙으로 구현했지만 임의의 사용자 조건을 해석·조합하는 기능은 없다.
- 플랫폼 값은 수동 입력에 기록되어 있을 뿐, Android 자료만 검색·검증하도록 실제 도구를 제한하는 동작은 없다.
- 새로운 도메인 정의로 교체하는 시험은 하지 않았다. 이번 기록은 도메인별 특화 가능성을 상위 의도로 유지하면서 현재 코드의 경계를 밝히는 것이며, 다중 도메인 구현을 새로 완료 과제로 추가하지 않는다.

현재 확인한 것은 **앱 정의의 일부 값이 다른 요청과 중간 결과에 따라 작업·조건·관계에 반영되는 규칙**이다. 실제 앱 특화 검증의 정확성, 자유로운 동적 계획, 다중 도메인 효과는 아직 확인하지 않았다.

## 5. 결과의 한계

- 실행기는 규칙 기반 조건부 프로토타입이다. 실제 D0 동적 계획기나 프로젝트 구현을 완료한 것이 아니다.
- 자연어 원문을 보관했으나 구조화 입력은 수동 작성했다. ‘사용자 요청 자동 이해 통과’로 표현하지 않는다.
- B0/D0를 각각 구현·실행해 비교하지 않았다. 고정 흐름보다 동적 구성이 유효하다는 결론은 아직 없다.
- 준비된 작업의 병렬 가능 그룹은 기록하지만 실제 실행은 순차 모의 방식이다.
- 실제 모델·웹 호출·요금·토큰·기기 시험을 사용하지 않았다. 속도·비용 개선을 측정한 것으로 해석하지 않는다.
- 보완 조사·출처 충돌·조회 실패·예산 상한의 동작은 이번 원형에 구현하지 않았다.
- TASK-005 전체 통과·완료가 아니라 계획·분기 규칙의 일부를 실행해 확인한 단계다.

## 6. 재실행

저장소 루트의 PowerShell에서 실행한다. 기존 Node.js를 사용하며 외부 의존성·API 키·네트워크 요청은 필요 없다.

```powershell
node docs/members/R03/workspace/2026-11-12_APP_모의_검증.cjs
```

스크립트는 앱 명세를 읽기만 하고 결과 JSON은 같은 R03/workspace에 저장한다. JSON은 재실행 시 최신 결과로 덮어쓰므로 비교 실행을 보존할 때는 별도 실행 ID·파일명으로 관리해야 한다. 이번 결과에는 입력 명세 SHA-256과 실행 시각을 기록했다.
