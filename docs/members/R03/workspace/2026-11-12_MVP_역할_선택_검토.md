## 1. 목적과 기록 범위

“사용자의 요청에 따라 역할과 작업을 구성하는 기능을 MVP에서 어느 수준까지 구현하고, 그 구성이 고정 워크플로보다 적절한지 어떻게 평가할 것인가?”라는 질문 중 **역할 선택**을 검토한다.

사용자의 요청을 해결하는 데 어떤 책임이 필요한지 판단하고, 미리 정의한 역할 후보에서 필요한 역할을 선택하는 방안을 제안한다. 앱 이름이나 문장 표현만으로 선택하지 않고 사용자가 원하는 결과와 확인할 조건을 기준으로 한다.

이 문서는 사용자가 R03/workspace에 작성을 요청한 논의 메모다. TASK-005 전체 결과나 확정 설계, 실제 실행·평가 결과를 대체하지 않는다. 아래 역할 구분과 선택 규칙은 검증 전 제안이다.

## 2. 역할 후보와 선택 기준

이 목록은 **앱 리서치 도메인의 첫 역할 후보군**이다. 사용자가 2026-11-12 전달한 팀장 추가 의도에 따라, 도메인마다 역할·작업·출처·검증 기준을 특화하고 그 안에서 요청별로 선택한다. 전체 시스템의 영구 공통 목록이 아니다. 공통 구조와 앱 역할의 구체적인 책임·입출력은 [통합본 5·6절](2026-11-12_TASK-005_동적_구성_MVP_검토_통합.md)에 정리했다.

| 역할 | 책임 | 선택하는 상황 | 기대 출력 |
|---|---|---|---|
| 후보 발굴 | 플랫폼·목적에 맞는 앱 후보를 찾는다. | 지정 후보가 없거나, 다른 후보도 함께 요청했거나, 조건부 대안 탐색 조건이 충족된 경우 | 앱 후보·플랫폼·스토어 식별 정보·발견 출처 |
| 자료 조사 | 대상 정보를 수집하고 출처를 기록한다. | 대상에 관해 확인할 정보가 있는 경우 | 수집 내용, 출처, 확인 시점과 접근 상태 |
| 조건 검증 | 근거를 대조해 사용자 조건의 충족 여부를 판단한다. | 기능·가격·지원 환경 등을 판정해야 하는 경우 | 조건별 충족·미충족·미확인과 근거 |
| 비교·분석 | 대상 간 차이와 사용자에게 중요한 장단점을 정리한다. | 여러 대상을 비교하거나 우선순위를 정해야 하는 경우 | 조건별 차이, 장단점과 판단 이유 |
| 결과 종합 | 확인된 결과와 미확인 사항을 사용자에게 전달한다. | 최종 결과를 작성하는 경우 | 요청에 답하는 결과와 출처·미확인 사항 |

계획·조정 기능은 요청 분석 결과를 바탕으로 위 역할을 선택하고 작업과 선행 관계를 배정하며, 중간 결과에 따른 구성을 관리한다. 계획·조정 기능을 별도 에이전트로 구현할지는 아직 결정하지 않는다.

역할 후보 수는 실제 LLM 에이전트 수와 다르다. 한 에이전트가 여러 논리 역할을 수행할 수 있으며, 역할마다 별도 모델 호출을 할 필요가 있는지도 구현·평가에서 확인한다.

## 3. 역할과 작업의 차이

- **역할:** 어떤 책임을 맡는가? 예: 자료 조사
- **작업:** 이번 요청에서 구체적으로 무엇을 하는가? 예: A 앱의 무료 제공 범위 확인, B 앱의 오프라인 기능 확인

같은 자료 조사 역할에 대상별·조건별로 여러 작업을 배정할 수 있다. 작업 수가 증가한다고 역할 종류나 에이전트 수를 반드시 늘리지는 않는다.

## 4. 사용자 요청에 따른 선택 예시

예시 요청: “A와 B 중 무료로 오프라인에서 사용할 수 있는 앱을 비교해줘.”

| 역할 | 선택 여부 | 이유와 작업 |
|---|---|---|
| 후보 발굴 | 생략 | 비교할 대상이 이미 지정되어 있고 대안 탐색 요청이 없음 |
| 자료 조사 | 선택 | 두 앱의 무료 제공 범위와 오프라인 기능에 관한 자료 확보 |
| 조건 검증 | 선택 | 무료·오프라인 조건의 충족 여부 판정 |
| 비교·분석 | 선택 | 두 앱의 조건별 차이를 비교 |
| 결과 종합 | 선택 | 비교 결과와 근거·미확인 사항 전달 |

이 예시에서 무료·오프라인은 필수 조건으로 해석한다. “가능하면 무료”처럼 요청 표현이 달라지면 선호로 구분해야 하며, 이 문장의 판정을 모든 요청에 그대로 적용하지 않는다.

## 5. 조사 중간 결과에 따른 역할 배정

예시 조건: “두 앱 모두 조건에 맞지 않으면 대안을 찾아줘.”

후보 발굴 역할은 조건부 배정 대상으로 두고 처음부터 실행하지 않는다.

| 중간 결과 | 후보 발굴 처리 |
|---|---|
| 두 앱 모두 필수 조건 미충족으로 확인 | 발굴 작업을 추가하고 담당 역할 배정 |
| 한 앱 이상 필수 조건 충족 | 발굴 생략 |
| 충족 후보가 없고 일부 조건이 미확인 | 발굴 보류·생략 사유 기록, 미확인 항목과 필요한 확인 정보 제시 |

미확인은 미충족이 아니다. 조건부 후속 작업은 사용자 요청에 명시된 실행 조건이 확인됐을 때 시작한다. 새로 찾은 후보도 동일한 필수 조건 검증을 거쳐야 한다.

## 6. 역할 선택 기록 항목

| 항목 | 기록 예시 |
|---|---|
| 선택 역할 | 조건 검증 |
| 선택 이유 | 사용자가 무료·오프라인 사용을 필수 조건으로 요청 |
| 배정 작업 | 앱별 무료 제공 범위와 오프라인 지원 판정 |
| 필요한 입력·선행 작업 | 사용자 조건, 자료 조사 결과와 출처 |
| 기대 출력 | 조건별 판정과 근거 |
| 실행 조건 | 해당 대상의 조사 자료 확보. 근거 부족 시 미확인 판정 |
| 추가·생략 이유 | 두 후보 모두 미충족 확인으로 대안 발굴 추가 등 |

## 7. 평가 계획

앱 도메인에 정의한 책임과 출처·검증 기준을 사용했는지, 요청에 필요한 앱 검증 항목을 선택했는지도 기록한다. 이 결과는 앱 도메인 내부 평가이며 다중 도메인 유효성의 증거가 아니다.

역할 이름의 개수보다 선택한 역할의 필요성과 책임을 설명할 수 있는지 평가한다.

- 요청 해결에 필요한 책임이 빠지지 않았는가?
- 요청과 무관한 역할을 실행하지 않았는가?
- 서로 다른 역할이 같은 작업을 불필요하게 중복 수행하지 않았는가?
- 역할에 필요한 입력과 선행 작업이 연결됐는가?
- 중간 결과에 따른 조건부 역할 배정이 올바른가?
- 선택·추가·생략 이유를 사용자 조건과 조사 결과까지 추적할 수 있는가?

APP-A·B·C와 후보 지정 여부·필수 조건을 바꾼 요청으로 위 항목을 시험한다. 동일한 모델·검색 도구·호출 조건의 고정 워크플로와 비교하며, 역할 선택의 적절성뿐 아니라 조건 누락·근거 품질·시간·호출 수·비용을 함께 본다. 실제 시험은 아직 수행하지 않았다.

## 8. 미확인 사항과 팀 결정 요청

- 후보 발굴과 자료 조사, 조건 검증과 비교·분석을 어느 수준으로 분리해야 효과적인지 미검증이다.
- 논리 역할을 실제 에이전트에 배치하는 방식과 동시 실행 수는 미정이다.
- 역할 후보 목록과 실행 상한은 팀 확인이 필요하다.
- 이 역할 선택안을 TASK-005의 MVP 제안에 포함할지 결정이 필요하다.

## 9. 현재 결론

MVP에서는 역할의 기본 책임을 정의하고, 사용자의 목적·필수 조건·선호에 따라 필요한 역할을 선택한다. 각 역할에 요청별 작업을 배정하고, 중간 결과가 명시된 조건을 충족하면 후속 역할에 작업을 추가한다. 역할 선택과 변경 이유를 기록해 적절성을 평가한다. 새로운 역할을 임의로 생성하는 기능은 우선 후속 범위로 제안한다.
