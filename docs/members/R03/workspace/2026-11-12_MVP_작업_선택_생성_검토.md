## 1. 목적과 현재 결론

“사용자의 요청에 따라 역할과 작업을 구성하는 기능을 MVP에서 어느 수준까지 구현하고, 그 구성이 고정 워크플로보다 적절한지 어떻게 평가할 것인가?”라는 질문 중 **작업 선택·생성**을 정리한다.

MVP에서는 미리 정의한 작업 유형을 선택하고, 사용자 요청의 대상·조건에 맞는 구체적인 작업을 생성하는 방안을 제안한다. 각 작업에 담당 역할, 필요한 입력, 선행 관계와 완료 기준을 명시한다. 중간 결과에 따라 작업을 추가·생략할 때도 이유를 기록한다.

사용자가 개인 작업 폴더에 작성을 요청한 논의 메모이며, TASK-005 전체 결과나 확정 설계를 대체하지 않는다. 실제 구현·시험은 수행하지 않았다.

## 2. 역할, 작업 선택, 작업 생성의 구분

여기서 준비하는 유형은 **앱 리서치 도메인의 첫 작업 후보군**이다. 머리말의 공식 INTENT·PROJECT·TASK-005 intent에 따라 다른 도메인까지 같은 작업·출처·검증을 강제하지 않는다. 앱에서는 플랫폼·버전·무료 기능·브라우저 호환성 검증 등을 구체화하고 요청마다 필요한 출처·검증 항목을 선택한다. 상위 방향과 구체적인 작업 설계 제안을 구분하며, 공통/앱 특화 내용은 [통합본 5·6절](2026-11-12_TASK-005_동적_구성_MVP_검토_통합.md)을 따른다.

| 구분 | 의미 | 예시 |
|---|---|---|
| 역할 | 어떤 책임을 맡는가 | 자료 조사, 조건 검증 |
| 작업 선택 | 준비한 작업 유형 중 무엇이 필요한가 | 공식 자료 조회, 후보 발굴, 조건 판정, 비교, 결과 작성 |
| 작업 생성 | 이번 요청의 대상·조건·완료 기준을 넣어 실행할 일을 구체화 | A 앱의 Android 무료판에서 오프라인 타이머를 사용할 수 있는지 근거와 함께 판정 |

동일한 역할에 여러 작업을 배정할 수 있다. 작업 수가 늘어난다고 역할이나 LLM 에이전트 수를 반드시 늘리지는 않는다.

## 3. 요청에서 작업 구성에 필요한 정보 추출

| 요청 정보 | 작업 구성에 미치는 영향 |
|---|---|
| 목적 | 비교·추천·사실 확인 등 결과에 필요한 작업 선택 |
| 대상 | 지정 대상을 조사할지 후보부터 발굴할지 결정 |
| 필수 조건 | 반드시 검증해야 하는 항목과 완료 기준 생성 |
| 선호 | 비교와 우선순위에 반영할 항목 생성 |
| 추가 탐색 조건 | 조건부 후속 작업 구성 |
| 정보 부족 | 필요한 확인 질문 또는 미확인 항목 구성 |

“가능하면 계정 없이” 같은 선호를 필수 조건으로 바꾸어 후보를 탈락시키지 않는다. 작업 입력에도 필수 조건과 선호를 구분해 전달한다.

## 4. 작업 생성 예시

예시 요청: “A와 B 중 무료로 오프라인 타이머를 쓸 수 있는 앱을 비교해줘. 가능하면 계정 없이 쓰고 싶어.”

이 예시에서는 무료·오프라인 타이머를 필수 조건, 계정 없는 사용을 선호로 해석한다. 요청의 표현이 달라지면 다시 구분한다.

| 작업 ID | 작업 내용 | 담당 역할 | 선행 작업 |
|---|---|---|---|
| T1 | A의 무료 범위·오프라인 타이머·계정 관련 자료 수집 | 자료 조사 | 없음 |
| T2 | B의 동일 항목 자료 수집 | 자료 조사 | 없음 |
| T3 | A의 필수 조건과 선호 판정 | 조건 검증 | T1 |
| T4 | B의 필수 조건과 선호 판정 | 조건 검증 | T2 |
| T5 | 조건별 차이와 적합성 비교 | 비교·분석 | T3, T4 |
| T6 | 근거·출처·미확인 사항을 포함한 결과 작성 | 결과 종합 | T5 |

- 지정 후보가 있고 추가 후보 요청이 없으므로 후보 발굴 작업은 생략한다.
- T1과 T2는 독립적으로 병렬 실행할 수 있다.
- T3는 T1이 끝나면 실행할 수 있으며 T2까지 기다릴 필요는 없다. T4도 동일하다.
- T1~T6은 계획 예시이며 실제 실행 기록이나 고정된 작업 개수가 아니다.

## 5. 작업을 나누는 크기

조건 하나마다 반드시 별도 작업을 만들지는 않는다. 같은 자료에서 확인할 수 있는 항목은 함께 조사하되, 결과에서는 조건별 판단을 분리한다.

예를 들어 같은 공식 도움말에서 오프라인 지원과 계정 필요 여부를 확인할 수 있다면 자료 조회는 하나로 묶을 수 있다. 판정은 각각의 근거를 연결해 남긴다.

독립적인 입력·출력이나 완료 기준이 필요할 때 작업을 분리한다. 지나치게 잘게 나누어 동일 페이지 조회와 모델 호출을 반복하지 않는지 평가한다. 적정 작업 크기는 아직 미검증이다.

## 6. 중간 결과에 따른 작업 추가·생략

| 발생 상황 | 후속 처리 제안 |
|---|---|
| 필수 조건의 근거 부족 | 해당 조건의 대체 공식 자료 조사 |
| 자료 간 충돌 | 버전·플랫폼·확인 시점 등을 대조하는 검증 |
| 사용자가 명시한 대안 탐색 조건 충족 | 새 후보 발굴과 후보별 검증 추가 |
| 페이지 접근 실패 | 허용된 대체 출처 조회 |
| 근거가 충분함 | 같은 목적의 추가 조사 생략 |
| 요청과 무관한 정보 발견 | 요청 해결에 필요한 이유가 없으면 작업을 추가하지 않음 |

미확인은 미충족이 아니다. “두 후보 모두 미충족이면 대안을 찾는다”는 조건에서 일부 미확인만으로 대안 발굴을 시작하지 않는다.

추가 조사·재시도에는 상한을 적용하고, 범위 안에서 확인할 수 없으면 미확인과 확인에 필요한 정보를 결과에 남긴다. 상한의 구체적인 수치는 팀 결정 및 기준 실행 후 정한다.

## 7. 작업별 최소 기록 항목

| 항목 | 내용 |
|---|---|
| 작업 ID | 계획과 실제 실행을 연결할 식별자 |
| 목표 | 알아내거나 만들어야 하는 결과 |
| 대상·조건 | 조사 대상과 필수 조건·선호 |
| 담당 역할 | 해당 작업을 책임지는 역할 |
| 입력·선행 작업 | 시작 전에 필요한 정보와 작업 |
| 실행 조건 | 실행하거나 생략할 조건 |
| 완료 기준·출력 | 작업이 끝났다고 판단할 기준과 결과 형식 |
| 생성·변경 이유 | 연결된 사용자 조건이나 중간 결과 |
| 실제 상태 | 실행·실패·생략 등 상태와 사유 |

“앱 조사하기”처럼 모호한 이름만 남기지 않는다. “A 앱의 Android 무료판에서 오프라인 타이머 지원 여부를 확인하고, 근거와 함께 판정하기”처럼 실행과 완료 판단이 가능하게 작성한다. 조회 실패·근거 부족 등도 기록하되 기능 충족으로 처리하지 않는다.

## 8. 고정할 부분과 동적으로 바꿀 부분

| 고정할 부분 제안 | 동적으로 바꿀 부분 제안 |
|---|---|
| 허용된 작업 유형과 입력·출력 형식 | 요청에 필요한 작업 유형 선택 |
| 작업·판정·출처 기록 스키마 | 대상·조건에 맞는 작업 내용과 개수 |
| 선행 조건 준수와 실행 상태 기록 규칙 | 작업 간 선행 관계와 병렬 실행 구성 |
| 조건부 실행·추가 조사 상한을 적용하는 규칙 | 중간 결과에 따른 작업 추가·생략 |

## 9. 평가 계획

APP-A·B·C 및 후보 지정 여부·필수 조건·선호·발굴 조건을 바꾼 요청으로 다음을 확인한다.

- 사용자 필수 조건에 대응하는 작업이 빠졌는가?
- 불필요하거나 중복된 작업이 생성·실행됐는가?
- 각 작업에 충분한 입력과 판단 가능한 완료 기준이 있는가?
- 선행 작업 완료 전에 의존 작업이 실행되지 않았는가?
- 중간 결과에 따른 작업 추가·생략이 조건에 맞는가?
- 생성·변경 이유를 사용자 요청과 조사 결과까지 추적할 수 있는가?
- 핵심 판단에 근거·출처·확인 시점이 연결됐는가?

동일한 모델·검색 도구·자료 조건·호출 상한의 고정 워크플로를 baseline으로 비교한다. 고정 흐름에도 같은 검증 작업과 조건부 처리 능력을 제공하고, 필수 조건 누락·판정 및 근거 품질·전체 시간·모델 및 검색 호출 수·토큰과 API 비용을 기록한다. 작업 수가 적다는 이유만으로 우수하다고 판정하지 않는다.

위 항목은 평가 계획이며 실행 결과가 아니다. 실제 차이와 정량 합격선은 아직 확인하지 않았다.

## 10. 미확인 사항과 결정 요청

- 작업을 나누는 적정 크기와 중복 조회 방지 방식은 실험이 필요하다.
- 근거 부족·접근 실패 시 추가 조사와 재시도의 구체적인 상한은 미정이다.
- 작업 형식과 실행 상태는 R05의 구현 구조와 맞춰야 한다.
- 데이터 접근 가능성과 이용 조건은 R02의 결과를 반영해야 한다.
- 이 작업 선택·생성 범위를 TASK-005의 MVP 제안에 포함할지 팀 확인이 필요하다.
