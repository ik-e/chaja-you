## 1. 목적과 현재 결론

사용자 요청에 맞춰 생성한 작업을 실행할 때, 각 작업에 어떤 입력과 선행 결과가 필요한지 정리한다.

MVP에서는 요청과 필요한 입력을 기준으로 선행 관계를 구성하고, 중간 판정에 따라 후속 관계를 변경하며, 실제 실행이 이를 따랐는지 기록하는 방안을 제안한다. 앞에 나열된 작업이라는 이유로 기다리는 것이 아니라, 그 결과가 필요한 경우에만 기다린다.

이 문서는 사용자가 개인 폴더에 작성을 요청한 논의 메모다. TASK-005 전체 결과나 확정 설계를 대체하지 않으며, 아래 동작은 구현·시험 전 제안이다.

## 2. 목록 순서와 의존 관계의 차이

단순히 “조사 → 검증 → 비교 → 보고서”로 나열하는 것 외에, 어떤 조사 결과를 어떤 검증 작업이 기다리는지 명시한다.

```text
A 자료 조사 → A 조건 검증 ─┐
                          ├→ 비교·분석 → 결과 종합
B 자료 조사 → B 조건 검증 ─┘
```

- A와 B의 자료 조사는 서로 기다리지 않고 시작할 수 있다.
- A 조건 검증은 A 자료 조사가 끝나면 시작할 수 있으며 B 조사를 기다릴 필요는 없다.
- 비교·분석은 두 앱의 판정 결과가 준비된 뒤 시작한다. 판정 결과에는 미확인도 포함할 수 있다.

## 3. 선행 관계를 정하는 기준

| 기준 | 예시 | 필요한 관계 |
|---|---|---|
| 조사 대상이 먼저 정해져야 함 | 후보 이름을 알아야 해당 앱을 조사 가능 | 후보 발굴 → 후보별 조사 |
| 판정할 근거가 필요함 | 무료 기능 여부를 판단하려면 요금제 자료 필요 | 자료 조사 → 조건 검증 |
| 여러 결과를 함께 봐야 함 | 두 앱의 적합성 비교 | 각 앱의 조건 검증 → 비교 |
| 특정 결과에서만 실행함 | 두 앱 모두 미충족이면 대안 탐색 | 두 앱 판정 → 조건 확인 → 대안 발굴 |
| 최종 설명에 사용할 결과가 필요함 | 추천 이유와 미확인 사항 작성 | 검증·비교 → 결과 종합 |

## 4. 선행 작업의 종료와 성공 구분

자료 조사 작업이 끝났다고 충분한 근거를 확보한 것은 아니다. 후속 작업은 종료 여부와 함께 실제 출력과 입력의 충분성을 확인한다.

| 선행 작업 결과 | 다음 처리 제안 |
|---|---|
| 필요한 자료 확보 | 근거를 사용해 검증 |
| 자료는 있으나 조건 설명 부족 | 추가 확인 필요 여부를 판단하거나 미확인으로 판정 |
| 조회 실패 | 허용된 대체 출처를 조사하거나 실패·미확인 기록 |
| 자료 간 충돌 | 버전·플랫폼·확인 시점을 대조하는 작업 추가 검토 |

조회 실패를 기능 미지원으로 해석하지 않는다. 일부 작업이 실패해도 확인된 결과와 미확인 사항을 구분해 최종 안내할 수 있도록 한다. 재시도·추가 조사 상한의 구체적인 수치는 미정이다.

## 5. 조건부 의존 관계

예시 요청: “A와 B를 비교하고, 둘 다 오프라인 타이머를 지원하지 않는다고 확인되면 대안도 찾아줘.”

```text
A 조건 검증 ─┐
             ├→ 두 후보의 판정 확인
B 조건 검증 ─┘           │
                        ├─ 모두 미충족 → 대안 발굴 → 대안 조사·검증
                        ├─ 하나 이상 충족 → 대안 발굴 생략
                        └─ 충족 없이 일부 미확인 → 미확인 안내
```

| 항목 | 후보 발굴 작업의 예시 |
|---|---|
| 선행 작업 | A 조건 검증, B 조건 검증 |
| 실행 조건 | 두 후보 모두 필수 조건 미충족으로 확인 |
| 생략 조건 | 하나 이상 충족 |
| 보류·미실행 사유 | 일부 미확인으로 발굴 조건을 확인할 수 없음 |

**선행 관계는 무엇을 기다리는지, 실행 조건은 그 결과가 어떨 때 실행하는지를 뜻한다.** 미확인은 미충족이 아니므로 임의로 대안 발굴 조건을 충족한 것으로 처리하지 않는다.

## 6. 요청에 따라 달라지는 관계

| 사용자 요청 | 필요한 관계 제안 |
|---|---|
| “A와 B를 비교해줘.” | 지정 앱 조사 → 검증 → 비교 |
| “내 조건에 맞는 앱을 찾아줘.” | 후보 발굴 → 후보별 조사·검증 → 추천 |
| “A가 조건에 안 맞으면 다른 앱을 찾아줘.” | A 검증 → 미충족 확인 시 후보 발굴 |
| “A도 비교하고 다른 후보도 함께 찾아줘.” | A 조사와 후보 발굴을 독립적으로 시작 가능 |

“안 맞으면”은 조건부 실행이고, “함께”는 처음부터 필요한 작업이다. 두 요청을 같은 실행 순서로 처리하지 않는다.

## 7. 작업별 기록과 계획 변경

| 기록 항목 | 예시 |
|---|---|
| 작업 ID | T3 |
| 목표 | A의 오프라인 타이머 지원 판정 |
| 선행 작업 | T1: A 공식 자료 조사 |
| 필요한 입력 | 조사 근거, 사용자 필수 조건 |
| 시작 조건 | 조사 결과 또는 조회 실패 기록이 준비됨 |
| 기대 출력 | 충족·미충족·미확인과 근거 |
| 실행 상태·사유 | 완료 / 근거 부족으로 미확인 등 |

추가 작업을 생성하면 선행 관계와 생성 이유를 기록한다. 기존 결과 중 갱신이 필요한 부분도 확인한다. 예를 들어 대안을 추가한 경우 새 후보 조사·검증 결과를 반영해 비교와 최종 결과를 갱신한다. 기존 작업 전체를 무조건 재실행할 필요는 없으며 재실행 범위는 입력 변경의 영향을 기준으로 정하는 안을 검토한다.

## 8. 고정할 부분과 동적으로 바꿀 부분

| 고정할 부분 제안 | 동적으로 바꿀 부분 제안 |
|---|---|
| 선행 입력을 확인한 뒤 시작하는 규칙 | 요청별 작업의 연결 관계 |
| 실행 조건과 상태·사유를 기록하는 형식 | 어떤 작업을 병렬로 실행할 수 있는지 |
| 순환 관계를 허용하지 않는 검사 | 중간 결과에 따른 후속 작업·관계 추가와 생략 |
| 실패·미확인 처리와 상한 적용 규칙 | 새 결과로 인해 갱신이 필요한 후속 결과의 범위 |

## 9. 평가 계획

- 필요한 입력이 준비되기 전에 작업을 시작하지 않았는가?
- 독립 작업을 불필요하게 기다리게 하지 않았는가?
- 조건부 작업을 판정 전에 실행하지 않았는가?
- 실패·미확인으로 전체 흐름이 끝없이 대기하지 않는가?
- 서로가 서로를 기다리는 순환 관계가 없는가?
- 계획한 선행 관계와 실제 실행 순서가 일치하는가?
- 추가 작업의 결과가 비교·최종 결과에 반영됐는가?

APP-A의 지정 조사, APP-B의 후보 발굴 선행, APP-C의 중간 판정별 분기와 요청 변형으로 점검한다. APP-C 분기 시험의 모의 판정값은 실제 앱 기능 확인과 구분한다. 동일 조건의 고정 워크플로와 비교해 순서 위반·불필요한 대기·결과 품질·시간·호출 수·비용을 기록하는 계획이다. 실제 실행 결과와 성능 개선은 아직 확인하지 않았다.

## 10. 미확인 사항과 결정 요청

- 작업 상태·오류·재시도·완료 처리 형식은 R05의 구현 구조와 맞춰야 한다.
- 자료 일부만 확보했을 때 후속 검증을 시작할 기준과 입력 변경 시 재실행 범위는 검증이 필요하다.
- 실제 병렬 실행 수와 시간·호출 상한은 미정이다.
- 이 선행 관계 구성 범위를 TASK-005의 MVP 제안에 포함할지 팀 확인이 필요하다.
