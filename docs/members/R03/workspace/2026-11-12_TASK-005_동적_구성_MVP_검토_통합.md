## 1. 질문과 통합 범위

**사용자의 요청에 따라 역할과 작업을 구성하는 기능을 MVP에서 어느 수준까지 구현하고, 그 구성이 고정 워크플로보다 적절한지 어떻게 평가할 것인가?**

R03 개인 폴더에서 작성한 동적 범위, 고정 범위, 시험 사례, baseline 평가 계획을 검토해 중복과 표현 차이를 정리했다. 사용자가 요청한 개인 통합 문서이며, 기존 문서는 세부 논의와 작성 경위를 확인할 자료로 유지한다.

이번 통합은 논의·제안·평가 계획에 한정한다. 사용자 요청에 따라 기획서 반영안과 WBS 작업 분해·담당·일정은 작성하지 않는다. 프로젝트 정본, 사람 입력, TASK 상태와 result, 공용 명세는 변경하지 않는다.

## 2. 현재 결론 — 제안

**MVP에서는 앱 리서치 도메인의 첫 역할·작업 후보군과 출처·검증 기준을 준비하고, 그 안에서 사용자 요청의 목적·대상·필수 조건·선호·후속 조건에 맞는 역할·작업·출처·검증 항목을 선택한다. 작업의 내용·개수·선행 관계·병렬 조합을 구성하고, 중간 결과에 따라 추가·생략하며 변경 이유를 기록한다.**

### 팀장 추가 의도 반영 — 대화에서 전달된 내용

2026-11-12 사용자가 전달한 팀장 답장의 핵심은 도메인에 맞게 역할·작업·출처·검증 기준을 특화하고, 해당 도메인 안에서 요청과 중간 결과에 따라 구성을 선택한다는 것이다. 출처는 현재 대화이며 PROJECT나 기존 R01 작업 의도 파일에 이미 반영됐다고 주장하지 않는다. 전달받은 상위 의도와 R03의 구체적인 구현 제안을 구분한다.

현재 역할·작업 목록은 모든 도메인에 영구 적용할 목록이 아니다. **도메인별 특화 가능성은 상위 의도이고, 여러 도메인을 실제 구현하는 것은 후속 범위**다. 이를 자유 역할 생성·장기 기억과 같은 선택적 고급 기능의 보류로 해석하지 않는다. 이번에는 앱 내부 구성을 APP-A·B·C로 검증하며, 다중 도메인 플랫폼이나 도메인 자동 선택기를 새로 구현할 필요는 없다.

새로운 역할·도구의 자유 생성이나 범용 워크플로 엔진 전체 구현은 우선 후속 범위로 제안한다. APP-A·B·C는 사용자 요청 대응 기능을 확인하는 첫 평가 사례이며, 제품 목표를 세 요청으로 제한하지 않는다.

동적 구성의 유효성은 조건 분기를 갖춘 고정 흐름과 동일 조건에서 비교한다. 필수 조건·근거 품질을 유지하면서 작업 누락·불필요한 실행·변형 대응·시간·호출·비용에서 어떤 차이가 나는지 확인한다. 차이가 없거나 계획 생성 부담이 더 크면 고정 흐름 유지 또는 동적 범위 축소도 검토한다. 아직 어느 방식이 우수한지 확인하지 않았다.

고정은 앱 도메인의 한 버전과 비교 실험에서 일관되게 적용한다는 뜻이다. 다른 도메인의 역할·작업·출처·검증 방식까지 같게 고정하지 않는다. 변경 시 근거와 버전을 남기고 같은 조건으로 다시 비교한다. 모델·프레임워크·실제 에이전트 수·정량 상한은 확정하지 않는다.

## 6. 역할·작업·실행의 최소 구성

### 역할과 작업 유형

역할 후보는 후보 발굴, 자료 조사, 조건 검증, 비교·분석, 결과 종합이다. 계획·조정 기능이 요청 구조화 결과를 받아 작업과 관계를 배정하는 안을 제안한다. 별도 조정 에이전트가 필요한지와 역할 분리·병합은 미정이다.

같은 역할 이름을 다른 도메인에서도 쓸 수 있으나 책임까지 같다고 보지 않는다. 앱에서는 아래처럼 특화하는 안을 제안한다.

| 역할 | 앱 도메인 책임 | 주요 입력·출력 |
|---|---|---|
| 후보 발굴 | 플랫폼·목적에 맞는 앱과 스토어 식별 정보 찾기 | 요청·허용 출처 → 후보·플랫폼·발견 근거 |
| 자료 조사 | 앱 설명·도움말·요금제·지원 환경 자료 확보 | 앱 식별·조건 → 출처·확인 시점·기능/요금 자료 |
| 조건 검증 | 플랫폼·버전·요금제별 조건을 근거 범위에서 판정 | 조건·자료 → 항목별 판정·근거·기기 확인 필요 여부 |
| 비교·분석 | 같은 사용자 조건으로 앱별 차이와 선호 적합성 비교 | 후보별 판정 → 차이·제약·추천 이유 |
| 결과 종합 | 앱 후보·조건 판정·출처·미확인과 확인 범위 안내 | 비교·근거 → 문서 확인과 기기 시험을 구분한 결과 |

작업 유형은 요청 조건 추출·확인, 발굴, 조회·추출, 판정, 비교, 결과 작성, 보완 조사다. 역할은 책임이며 작업은 이번 요청에서 수행할 구체적인 일이다. 역할·작업·모델 호출을 같은 개수로 취급하지 않는다.

### 작업별 기록

작업 ID, 목표, 유형, 대상, 사용자 조건 ID, 담당 역할, 입력, 선행 작업, 실행 조건, 완료 기준과 출력을 남긴다. 실제 실행에는 상태·시각·출처·근거·오류·사용 자원·변경 이유를 연결한다. 세부 필드와 자료형은 R05 구조와 맞출 검토 사항이다.

### 실행 원칙

- 후보를 확보한 뒤 그 후보를 검증하고, 해당 자료가 준비되면 다른 후보를 불필요하게 기다리지 않는다.
- 선행 작업 종료만으로 근거가 충분하다고 판단하지 않는다. 조회 실패는 기능 미지원의 근거가 아니다.
- 입력이 준비되고 공유 수정 충돌이 없는 독립 작업을 한도 안에서 병렬 실행한다.
- 같은 페이지를 반복 읽는 불필요한 작업 분할을 피하고 조건별 판정은 구분한다.
- 요청 완수에 필요한 보완과 명시된 후속 행동만 추가한다. 무관한 기능 조사나 사용자 필수 조건의 임의 완화는 하지 않는다.
- 기존 결과를 재사용할 때 대상·플랫폼·버전·시점의 적용 범위를 확인한다. 이는 현재 실행 내 중복 방지이며 장기 기억 기능을 확정한 것이 아니다.

## 7. 중간 결과에 따른 후속 작업과 상태

| 중간 결과 | 처리 제안 |
|---|---|
| 근거 충분 | 같은 목적의 추가 조사 생략 |
| 근거 부족·충돌 | 중복 여부·가능성·예산을 확인한 뒤 보완 조사 또는 미확인 |
| 조회 실패 | 허용된 대체 출처 또는 실패·미확인 기록 |
| 요청의 후속 조건 충족 | 필요한 작업과 역할 배정·관계 추가 |
| 입력·판정 진행 중 | 보류 |
| 후속 조건 불성립 | 해당 작업 생략 |
| 조건 확인 불가·상한 도달 | 미실행 사유와 미확인 정보로 종결 |

생략은 불필요하거나 조건이 성립하지 않은 미실행, 보류는 입력을 기다리는 일시 상태, 실패는 실행 오류, 취소는 불필요해진 예정·실행 작업 중단을 뜻한다. 상태 코드는 확정하지 않는다. 새 근거가 생기면 해당 판정과 영향을 받는 비교·결과만 갱신하는 안을 검토한다.

APP-A에는 무료 필수 조건을 임의로 추가하지 않는다. APP-C에는 APP-A의 계정 선호를 전이하지 않는다. APP-B의 구체적인 사이트·예약 시각·브라우저는 기능 조사와 기기 시험의 필요 수준을 구분해 확보한다.

APP-C 모의 판정은 실제 앱 기능에 대한 주장이 아니다. 보완 후 판정이 바뀌면 조건을 다시 평가한다. 한 후보가 충족해서 대안이 불필요해져도 원래 지정 앱 비교 요청은 유지한다.

변형 시험은 지정 후보 제거·추가, 다른 후보 이름, 선호의 필수 조건 전환, ‘미확인이어도 대안 발굴’ 조건 변경을 포함한다. 실제 문장·입력·기대값은 실행 전에 정한다. 필요한 책임과 관계가 같으면 여러 계획을 허용하며 작업 ID의 일치로만 평가하지 않는다.

## 10. 고정 워크플로 대비 평가 방법

### 비교 대상

**B0 고정 흐름:** 사전 작성한 요청 구조화 → 지정 후보 사용 또는 발굴 → 후보별 조사·검증 → 조건부 보완·대안 발굴 → 비교·종합 구조를 사용한다. 관련 없는 검증은 생략할 수 있고 반복·병렬·조건부 처리 능력을 제공한다.

**D0 동적 구성:** 같은 역할·작업·도구·판정 규칙 안에서 요청과 중간 결과를 따라 작업 목록·배정·연결을 실행별로 구성한다. 계획 생성·검사·수정 부담도 전체 시간과 예산에 포함한다.

B0에도 APP-C 처리 능력을 제공한다. 둘이 같은 계획·결과를 내는 것은 가능하며, 의도적인 차이를 만들지 않는다. D0가 실질적으로 B0 분기를 다시 표현할 뿐이면 이 한계도 결과로 남긴다. 구체적인 baseline 구현은 아직 없다.

### 공통 조건

동일 모델·버전·지원 설정, 요청 구조화 방식, 도구 구현, 역할 지침, 출력 형식, 판정 기준, 전체 예산·재시도·병렬 정책을 맞춘다. 캐시 초기 조건과 실행 순서를 관리하고 반복 횟수는 예산을 고려해 사전 결정한다.

B0/D0 모두 같은 앱 도메인 역할·작업 후보군, 출처 접근 범위, 검증 기준의 버전을 사용한다. 실제 선택 출처는 계획에 따라 달라질 수 있으나 접근 가능한 범위를 한쪽에만 유리하게 제공하지 않는다.

통제 시험은 동일한 자료·도구 응답·모의 판정을 사용한다. 실시간 시험은 같은 시점·도구 설정을 적용하되 검색어·조회 결과가 다를 수 있음을 기록하고 이용 조건에 맞게 필요한 근거를 보존한다. 한쪽에만 유리하게 baseline·기대값을 사후 변경하지 않는다.

### 평가 항목

| 항목 | 기록할 증거 |
|---|---|
| 필요한 작업 누락·불필요 실행 | 사전 조건·책임 목록, 계획·실행, 중복 및 생략 사유 |
| 선행 관계·분기 | 시작·종료 시각, 선행 출력, 조건 판정과 후속 실행 |
| 사용자 조건 보존 | 조건별 누락·오판·선호 혼동·임의 완화 여부 |
| 앱 특화 선택 | 적용한 앱 역할·작업 정의, 선택 출처·검증 항목과 이유. 무관한 앱 검증까지 모두 실행하지 않았는지 확인 |
| 근거 품질 | 핵심 판단을 직접 지지하는 내용·출처·확인 시점과 충돌 표시 |
| 추적 가능성 | 계획 버전, 변경 이유, 실행 상태와 결과 갱신 연결 |
| 시간 | 전체 시간과 계획·대기·조사·재시도 시간 |
| 호출·토큰·비용 | 모델·검색·본문 조회·재시도별 사용량, 요율·확인일·계산식 |

일반 코드 단계나 생략 작업을 모델 호출로 세지 않는다. 비용을 모르면 0으로 채우지 않고 미확인으로 둔다. 실패·중단 실행의 사용 자원도 기록하고 추정액과 실제 과금을 구분한다.

### 시험 단계와 판정

1. 계획·분기 통제 시험: 역할·작업 선택, 관계와 조건 변경을 모의 입력으로 확인.
2. 실제 조사 시험: 허용된 자료를 사용해 결과·근거·실제 시간과 호출·비용 확인.
3. 필요한 기기 시험: 오프라인·예약 차단 실제 동작을 기기·버전·설정과 함께 별도 확인.

각 검사는 pass / fail / inconclusive와 근거를 남긴다. 아직 실행하지 않은 것은 미실행으로 두고 성공으로 표시하지 않는다. 품질 실패를 속도·비용 이점으로 상쇄하지 않는다. 품질을 충족한 실행끼리 자원을 비교하되 전체 실패 사례도 함께 보고한다. 통제 시험 시간을 실제 서비스 속도 개선으로 해석하지 않는다.

병렬 실행 자체의 효과를 따로 볼 때는 동일 계획의 순차/병렬 실행을 비교한다. 구성 방식 평가에서는 B0/D0에 동일 병렬 정책을 적용해 두 효과를 섞지 않는다. 정량 합격선과 허용 비용은 기준 실행 후 결정한다.

| R01 결정 요청 | 제품의 필수 범위·확대 여부를 선택 | R03 제안이며 채택 결정은 미확인 |

### 12.2 R03이 먼저 구체화할 항목

| ID | 항목 | 다음 행동 | 확인 기준 | 현재 상태 |
|---|---|---|---|---|
| U01 | 역할 분리·병합과 실제 배치 초안 | 발굴/조사, 검증/비교의 분리안과 병합안에서 책임·입출력·중복을 대조. 논리 역할과 모델 호출을 별도 표시 | 사례마다 필요한 책임이 빠지지 않고 역할 간 전달 내용을 설명 가능 | 역할 후보는 작성, 대안 대조는 미작성 |
| U02 | 작업 크기·중복 방지 | 대상·조건·출처가 겹치는 조회를 언제 묶고 나눌지 규칙과 예시 작성 | 같은 조회의 불필요한 중복 없이 조건별 근거를 추적 가능 | 원칙은 작성, 구체 규칙은 보완 필요 |
| U03 | 보완 조사·재실행 판단 | 근거 부족·충돌·실패별 후속 작업과 종료 조건, 새 입력으로 갱신할 결과를 표로 작성 | 부족/충돌/실패를 판정과 혼동하지 않고 반복 종료 이유를 설명 가능 | 처리 방향은 작성, 시험 입력·기대값은 보완 필요 |
| U04 | 요청 변형과 기대값 | 8절의 변형을 정확한 문장으로 작성하고 필요한 책임·관계·금지 실행을 사전 지정 | 같은 입력으로 B0/D0를 대조할 수 있는 시험 세트 존재 | 변형 유형은 작성, 정확한 문장 세트는 미완성 |
| U05 | 비교 실행 조건 | baseline 상세 경로, 통제 자료, 기록 형식과 시험용 상한·반복 조건을 작성 | 구성 방식 외 차이를 식별하고 전체 계획 비용까지 기록 가능 | 평가 설계는 작성, 실행 설정은 미완성 |

위 초안 작성은 팀장의 최종 범위 결정을 기다리지 않고 진행할 수 있다. 다만 실제 서비스 효과와 적정성을 입증했다는 의미는 아니다. 비용이 발생하는 실험은 사용 가능한 도구·계정·예산과 사용자 승인 범위가 확인된 뒤 수행한다.

### 12.3 담당자 자료와 맞출 항목

| ID | 연결 대상 | 확인할 자료·내용 | R03이 반영할 것 | 반영 완료 기준 |
|---|---|---|---|---|
| U06 | R02 / TASK-004 | 허용된 출처, 실제 확보 필드, 이용·저장 조건, 호출·동시 이용 제한과 요금 | 조회 가능 작업·대체 출처·미확인 처리·실험 상한 | 실제 문서 경로·확인 범위·반영 위치를 기록. 미확인은 그대로 표시 |
| U07 | R05 / TASK-006 | 요청·작업·근거 입출력, 상태 전이, 실패·재시도·취소, 공유 결과 갱신 | 논리 역할·작업 계획과 실행 기록의 대응 관계 | 필드·상태의 일치점/차이와 수정안을 기록. 설계 초안과 구현 확인을 구분 |

단순한 ‘확인 필요’ 대신 **자료 확인 전 / 자료 확인·차이 정리 / 반영 완료 / 근거 부족**으로 구분해 후속 갱신한다. 현재는 자료 확인 전이며, 상대 담당자의 진행 상태를 추정하지 않는다.

### 12.4 실험으로 확인할 항목

| ID | 질문 | 확인 방법 | 현재 판정 |
|---|---|---|---|
| U08 | 역할·작업을 나누는 수준이 적절한가 | 같은 요청에서 책임 누락·중복 조회·전달 오류·호출 수 비교 | 미실행 |
| U09 | 의존 관계·분기와 변경이 올바른가 | APP-C1~3, 근거 충돌·조회 실패·요청 변형을 통제 입력으로 대조 | 일부 수행: APP-A/B/C·변형·C 판정 조합 규칙 원형 검사. 실제 계획기·충돌·조회 실패는 미검증 |
| U10 | 병렬 실행이 도움이 되는가 | 동일 계획의 순차/병렬 실행에서 시간·오류·근거 품질·자원 비교 | 미실행 |
| U11 | 동적 구성이 B0보다 적절한가 | 같은 조건의 B0/D0로 작업 누락·불필요 실행·조건·근거·시간·호출·비용 비교 | 미실행 |

실험 결과가 없으므로 우수 방식·최적 작업 크기·속도나 비용 개선은 미확인이다. 품질 실패를 자원 절감으로 상쇄하지 않으며, 동적 구성의 이점이 없다는 결과도 허용한다.

### 12.5 시험용 상한과 제품 합격 기준의 구분

| 구분 | 정할 시점과 용도 | 유의 사항 |
|---|---|---|
| 제공자·도구 제한 | U06에서 확인. 실제 실행 전 적용 | 확인하지 않은 제한값을 사실로 가정하지 않음 |
| 시험용 설정 | 실행 전에 후보 수·동시 실행·시간·호출·재시도·반복 횟수의 임시값 기록 | 검증 목적의 변경 가능한 기본값. B0/D0에 동일 적용. 실제 사용 가능 예산 안에서 설정 |
| 제품 목표·정량 합격선 | 기준 실행의 품질·자원 자료로 제안하고 R01 결정 | 임시 상한을 제품 성능 목표로 표현하거나 결과를 본 뒤 성공하도록 기준을 바꾸지 않음 |

기존의 ‘상한은 기준 실행 후 결정’은 최종 권고값을 뜻한다. **첫 시험에도 종료 상한은 필요**하므로 임시 설정을 먼저 기록하고, 시험 후 수정하면 별도 버전으로 다시 비교한다. 현재 수치가 정해졌다는 뜻은 아니다.

### 12.6 R01에게 요청할 결정

| ID | 결정 질문 | R03 현재 제안 | 전달할 근거 | 시점 |
|---|---|---|---|---|
| D01 | MVP 필수 동적 수준을 어디까지 둘 것인가 | 정의된 역할·작업 안에서 선택·조합·관계 구성·조건부 추가·생략까지 검토 | 5~9절의 범위·요구사항·사례, U06/U07의 제약 | 검토 가능. 아직 확정안 아님 |
| D02 | 앱 후보군 밖의 자유 역할 생성을 포함할 것인가 | 이번 최소 비교에서는 보류하는 안 | 후보군 한계가 드러난 사례와 자유 생성 비용·위험 | 필요성 확인 후 |

| D06 | 장기 기억·RAG 등 재사용 기능을 현재 실행에 포함할 것인가 | 실제 재사용 과제와 근거로 별도 판단 | 필요한 데이터·품질·비용·개인정보 영향 | 별도 과제가 구체화되면 |

| D04 | 제품 목표와 허용 비용·합격선을 어떻게 둘 것인가 | 기준 실행 후 제안 | 조건별 판정·근거 품질과 시간·호출·비용의 실제 분포 | 기준 실행 후 |

위 항목은 제품 범위·주요 수용 기준에 대한 결정 요청이며, 역할 이름이나 모든 작은 설정마다 승인을 요청한다는 뜻은 아니다. 이번 문서 수정으로 어떤 결정도 승인된 것으로 처리하지 않는다.

### 12.7 다음 확인 순서

1. U01~U05의 상세 초안과 시험 세트를 작성한다. 이미 작성된 개념 논의와 아직 없는 실행 자료를 구분한다.
2. 병행해 U06·U07 자료를 읽고 차이를 표시한다. 확인 전에는 R02·R05 결과를 적용 완료로 표시하지 않는다.
3. D01의 제안과 근거·미해결 영향을 R01 검토용으로 정리한다. 아직 하지 않은 실험을 근거로 사용하지 않는다.
4. 실행 조건이 갖춰지면 U08~U11을 수행하고, D03·D04를 판단할 결과를 남긴다.

기존 원문들의 ‘팀 확인 필요’는 이 절의 처리 분류로 해석한다. 개별 문서에 적힌 모든 항목을 작업 중단 조건이나 승인 대기로 취급하지 않는다.

현재 통합 범위는 개인 제안과 평가 계획이다. 기획서·WBS 반영은 팀장의 정확한 정리와 후속 요청이 있을 때 별도로 진행한다.
