## 1. 결론과 이번 작업의 범위

**의도·설계 원칙은 대체로 일치하지만 현재 R03 출력은 TASK-006의 최소 연결 의미를 전부 제공하지 못한다.** 특히 요청/작업 식별 범위, 작업별 명시적 실행 조건, 대상 × 조건별 판정과 evidence 연결, APP-C 확인 한도 후 부분 결과 종료가 남아 있다.

이번에는 정본 초안과 로컬의 기존 결과를 읽고 차이·영향·제안을 기록했다. 계약 필드·상태를 최종 합의하지 않았고, 코드·기존 실행 JSON·공용 TASK·R05 파일은 수정하지 않았다. 18건·오류 주입 4건의 기존 검사 범위를 확대 해석하지 않는다. 새로운 테스트도 추가·실행하지 않았다.

TASK-006은 진행 중이며 인터페이스 자체가 팀 간 필드명·전송 방식 미합의인 R05 제안이다. 아래 내용은 실제 R05 구현이나 공동 합의가 아니라 그 초안과의 대조다. 필드명 차이와 의미 누락을 구분한다.

## 2. 같은 의미로 이해한 부분

- 사용자 요청에서 지정 후보·필수 조건·선호·발굴 조건을 구분한다.
- 앱 역할·조건·출처·검증은 도메인 특화로 두고 요청·작업·근거·판정·상태의 연결을 공통 의미로 다룬다.
- APP-A는 지정 비교의 첫 연결, APP-C는 중간 판정에 따른 추가·생략·보류의 핵심 확인이다.
- 미확인은 미충족이 아니며 조회 실패를 기능 미지원으로 바꾸지 않는다.
- 작업이 끝나도 근거가 부족하면 조건은 미확인일 수 있다.
- 확인된 내용은 보존하고 미확인·실패를 결과에 드러낸다. 자동 재시도·복잡한 복구를 우선 확정할 필요는 없다.
- APP-B는 조사·모의 사례로 유지할 수 있으나 최종 필수 시연 여부는 R01 미결정 사항이다. 기존 R03의 평가 사례 존재와 필수 구현 결정은 구분한다.

### 기존 결과에서 직접 확인할 위치

- APP-A: 검증 task T2·T4에 `conditions=['offline_pomodoro']`, `preferences=['accountless']`, 후보당 `mock_verdict` 하나가 있다.
- APP-C1: T5 발굴은 T2·T4를 선행 작업으로 가지며 두 모의 판정 뒤 추가된다. 그러나 T5 자체의 실행 조건 필드는 없다.
- APP-C3: `decisions.action=skip_discovery`, 이유는 `condition not established (unknown)`이다. 확인 한도·대기 종료·부분 보고서 객체는 없다.
- APP-B: 브라우저·권한은 검증 task의 문맥 항목이다. 별도 작업·조건별 근거·실제 브라우저 확인은 아니다.

## 4. 최소 연결안 — R05 확인 전 제안

```text
request 식별
  ├ 대상 식별 + 조건 식별(필수/선호, 앱 문맥)
  ├ task 식별 + 역할 + 선행 task + 명시적 실행 조건
  │    └ 출처 조회 기록(source) → 확인 내용(evidence)
  └ 대상 × 조건별 판정 → 직접 지지 evidence 참조
        ├ 조건부 계획 결정 → 추가/생략/보류 사유
        └ 결과(report) → 판정·주장·근거·미확인·실패
```

화살표는 논리 참조이며 저장 테이블·통신 프로토콜·최종 필드명을 확정하지 않는다. 모든 참조는 같은 요청 문맥으로 추적 가능해야 한다. 앱 이름은 표시값, 대상 ID는 식별값으로 구분한다. 예를 들어 R03의 `offline_pomodoro`와 R05 예시의 `offline_timer`가 정확히 같은 범위인지 확인한 뒤 매핑한다. 단순 문자열 변경으로 동일 의미를 가정하지 않는다.

근거 없는 후보당 집계 판정에서 개별 조건 판정을 만들어내지 않는다. 현재 모의 결과는 새 계약으로 자동 변환해 실제 근거처럼 취급할 수 없으며, 기존 JSON은 그대로 둔다.

### R05와 확인할 최소 의미

1. 요청과 실행 시도를 식별하는 주체·범위, 작업 ID의 고유 범위와 후속 작업·재시도 연결 방식.
2. `run_if`가 참조할 조건·판정과 ‘미확인’의 처리, 분기 평가 주체 및 기록 소유자.
3. 생성하지 않은 조건부 작업의 생략/보류를 계획 결정으로 기록할지, 미리 만든 작업 상태로 기록할지.
4. 대상 × 조건별 판정과 근거 없는 미확인, 한 조건을 지지하는 여러 evidence의 표현.
5. 부분 결과의 필수 내용, 생성 실패와 부분 결과 구분, 한도 종료 사유 전달.

## 5. APP-C 보류와 부분 결과 종료 대조

| 단계 | 함께 유지할 의미 | 현재 R03 상태 | 제안 |
|---|---|---|---|
| 확인 진행 중 | 충족 없음·일부 미확인은 대안 발굴 조건 미확립 | 즉시 skip 이유만 기록 | 확인 중 보류와 확인 종결 후 미실행을 분리 |
| 한도 내 보완 | 가능하면 부족한 조건만 보완하고 다시 판정 | 보완 실행 미구현 | 재시도 자동화를 새 필수로 두지 않음. 확인 진행 여부와 종료 이벤트를 먼저 표현 |
| 한도 도달·여전히 미확인 | 모두 미충족으로 간주하지 않고 발굴하지 않음 | 한도·종료 필드 없음 | 한도 종료 사유와 최종 발굴 미실행 이유를 기록 |
| 결과 제출 | 확인된 내용과 남은 미확인·실패를 보존한 부분 결과 | 보고서 객체 없음 | 작업 실패 / 조건 미확인 / 부분 결과 상태를 구분해 전달 |

R03 문서의 ‘생략’과 R05 초안의 ‘보류’는 실행하지 않는다는 관찰만으로 합의됐다고 볼 수 없다. 조사 진행 중인지, 더 확인할 수 없는 최종 상태인지에 따라 화면과 후속 실행이 달라진다. **보류 → 한도 종료 → 발굴 최종 미실행 + 미확인 부분 결과**라는 제안 흐름을 공동 확인할 필요가 있다.

한도 종류·값, 한도를 판단하는 구성요소, 부분 결과 제출의 세부 수용 기준은 아직 미합의다. R03이 임의의 수치를 정하거나 ‘재시도 성공’으로 표시하지 않는다. 비교 대상이 모두 미확인인 경우 등 확인된 주장이 없는 결과를 어떻게 표시할지도 R01·R04·R05 확인 항목으로 남긴다.

| 종류 | 항목 | 처리 제안 |

| 아직 결정 필요 | 한도·부분 결과 기준·상태 전이의 소유권 | R05와 차이 기록 후 필요한 범위만 R01 검토 |
