- 상태: 개인 참고 기록. 사용자 전달 피드백을 정리한 것이며 실제 사용자 수요·기술 성능·팀 제품 채택의 근거와 구분한다.

## 1. 주요 피드백과 반영 상태

| 피드백 | 현재 반영·판단 | 확인 위치 |
|---|---|---|
| 타겟·핵심 pain을 좁히기 | 물품 미수령·최초 상담/신고 준비, 재확인·반복 정리·수정 부담 중심. 용어 설명은 보조 | 기획안 2~3절 |
| 설명보다 구체적인 이용 흐름 | 시작·자유 입력·초안 보완·결과 활용. 미확인 진행·수정·복사 동작 | 4~5절 |
| 입력 수고와 정리 품질 분리 | A는 구조화 품질, B는 가상 환경에서 찾기부터 수정까지의 수고. 실제 수요로 확대하지 않음 | 8절 |
| 범용 LLM과 공정하게 비교 | 동일 자료와 충분한 지시 제공. 직접 작성/범용 LLM/고정 멀티에이전트 대비를 별도 보고 | 8~9절 |
| 수정 반영을 시험 항목으로 만들기 | 금액 정정 후 연결 결과 갱신·이전 대조 재점검·무관한 조사 재실행 여부 기록 | 9~10절 |
| 병렬 처리와 동적 선택 효과 구분 | 고정·동적 모두 같은 독립 작업 병렬 허용 기준 적용 | 9절 |
| 입출력·정보 상태 명확화 | 원문 ID·항목 ID 연결. 정보 성격/확인/충돌/사용자 검토를 구분. 자동 대조는 전문가 승인과 구분 | 3·5·10절 |
| 기존 대안과 설계 이유 확인 | ECRM·더치트·플랫폼·상담·LLM 비교. 미제공 기능·설계 이유는 단정하지 않음 | 6절 |
| 인터뷰와 실제 pain 근거 | 사용자 결정에 따라 인터뷰 계획 제외. 실제 문제·수요·현실 부담 감소는 미검증으로 유지. 공개 실제 사례·상담 사례에서 pain 근거를 찾는 작업은 미수행 | 8·11절 및 아래 미확인 |
| 부동산에서 변경한 이유 | 현장 확인이 중요해 온라인 정리의 해결 범위가 불확실하다는 두나의 판단 보존 | 11절 |
| 법적 경계·민감정보 취급 | 사건 정리와 법률 자문/문서 작성 경계의 전문 검토 필요, 비식별 자료 사용 | 11절 |
| TASK-018 연결·Git 정리 요청 | TASK-018 result에 기획안·요약·본 기록과 미확인을 연결하고 상태는 진행 중으로 반영. 실제 pain·성능 검증과 완료 판정은 구분. 커밋·푸시는 별도 | 후속 확인 필요 |
| 사용자 가치와 기술의 위계 | 사용자 목표는 반복 정리 부담 감소로 제시. 멀티에이전트는 단일·고정 구성과 비교할 구현 후보이며 우위 미검증 | 1·9~10절 |

‘문서 반영’은 해당 동작이 구현되거나 시험에 통과했다는 의미가 아니다. 받은 제안을 모두 확정 스키마로 복사하지 않고, 추측·충돌·미확인이 겹칠 수 있다는 기존 의미를 유지했다.

## 2. ECRM 접수 흐름 — 사용자 화면에서 확인

**범죄유형 선택 → 증거자료 첨부 → 인적사항 입력 → 내용입력 → 완료**

사용자 제공 이미지에는 위 다섯 단계와 ‘증거자료 첨부(현재단계)’가 보인다. 단계 표시를 관찰한 근거이며 각 화면의 입력 항목·버튼·필수값·첨부·수정 동작을 실제로 시험한 결과는 아니다. 원본 이미지는 공개 저장소에 복사하지 않고 관찰 내용을 요약한다.

## 3. 접수 전 준비와 우리 서비스 안내

| 준비할 것 | 사용자에게 안내할 내용 |
|---|---|
| 본인인증 수단 | 공식 로그인 화면상 본인 명의 휴대전화 또는 아이핀. 개인정보 동의 절차 확인 |
| 본인 신분증 | 공식 신고·경찰서 방문을 위해 준비. 우리 서비스에 신분증 제출을 요구하지 않음 |
| 이체·결제 자료 | 보낸 금액·일시 등 거래 내역 준비 |
| 대화·판매 글 등 | 약속·연락 경위를 보여주는 보유 자료 준비. 없는 정보를 임의 생성하지 않음 |
| 피해 경위 | 상대방 정보·일시·플랫폼/장소·피해 내역·과정·신고 이유를 아는 범위에서 정리 |

신분증·이체내역서·메신저 대화내역 등 첨부와 피해 내용의 육하원칙·작성 예시는 공식 공개 안내에서 확인했다. 판매 글 등은 거래 맥락에 따른 준비 안내이며 모든 자료를 갖춰야 접수 가능하다고 확인한 것은 아니다. [ECRM 공식 안내](https://ecrm.police.go.kr/minwon/main) (확인일: 2026-11-16)

본인인증 방법과 동의 화면은 공개 로그인 진입 화면에서 확인했다. 실제 인증이나 신고 제출은 수행하지 않았다. [ECRM 로그인·동의 안내](https://ecrm.police.go.kr/sci/pcc_V3_send) (확인일: 2026-11-16)

온라인 작성 후 기본적으로 경찰서 방문·진술이 필요하며 일부 다수 피해 사건의 예외가 있다. 따라서 화면의 ‘완료’는 절차 전체 종료로 안내하지 않는다. [ECRM 접수·방문 안내](https://ecrm.police.go.kr/minwon/main) (확인일: 2026-11-16)

## 4. 남은 확인 사항

- 첨부 파일 형식·용량·개수, 신분증 제출의 실제 방식과 적용 화면, 저장·수정·보완 흐름 및 로그인 후 필수 입력 항목.
- 기존 서비스가 사건 자동 구조화를 제공하는 전체 범위와 현재 설계 이유. 공개 화면에 보이지 않는다는 이유로 미제공을 단정하지 않음.
- 실제 자료 재탐색·반복 작성·수정 부담이 나타나는 공개 실제 사례 또는 상담 사례. 어려움이 적었던 반대 사례도 필요.
- 서비스 C·폴봇·단일/고정/동적 구성의 실제 비교 결과는 없음. 가상 사례 1건·LLM 2턴 실행은 별도 반증 점검 기록에 있으며, 서비스 추가 가치는 미확인이다.
- 전문 검토 담당·범위와 TASK-018 작업 계약에 맞춘 산출물 연결 여부.

## 5. 이번 순서별 작업 결과

요약 형식 정리 → 폴봇 공개 범위와 가상 LLM 점검 → 조건부 8주·중단 계획을 반영했다. [반증 점검 결과](2026-11-16_기존대안_반증점검_결과.md)에서 실제 실행·접근 불가·미구현과 다음 판단을 구분했다. LLM은 이 사례의 정정·미확인 요구를 수행했고, 폴봇 실제 대화는 브라우저 연결 불가로 미시험이다.
