## 2. APP-A 한 건의 연결

출력 위치는 `runs[0]`이다. 요청 ID는 `MOCK-REQ-R03-APP-A-001`이며 아래 표의 접미사 앞에는 이 요청 ID가 붙는다.

| 연결 대상 | 합성 출력 예시 | 의미 |
|---|---|---|
| 요청 | `input.request_id` | 평가 사례 APP-A와 실제 요청 식별 의미를 구분 |
| 대상 | `C1`, `C2` | 표시 이름과 별도의 후보 ID |
| 작업 | `R1` → `V1`, `R2` → `V2` | 자료 확인 작업과 조건 판정 작업. 목표·역할·depends_on·run_if·상태·사유 포함 |
| 판정 | `J1-1` | C1 × `offline_pomodoro`, 생성 작업 V1 참조 |
| 근거 | `J1-1.evidence_ids` → `E1-1` | 그 대상·조건을 지지하는 합성 내용 |
| 출처 | `E1-1.source_id` → `S1` | 자료 확인 작업 R1에 연결된 합성 출처 |
| 주장·보고서 | `CLAIM1` → J1-1/E1-1, `REPORT1` → claim/verdict/source IDs | 확인·미확인 판정을 모두 보존하고 근거 있는 합성 주장만 생성 |

APP-A는 오프라인 뽀모도로를 필수, 계정 없는 사용을 선호로 유지한다. **후보 2개 × 조건 2개로 판정 4개**를 만든다. 후보당 단일 판정을 여러 조건에 복사하지 않는다.

합성 입력은 C1 오프라인 충족·계정 미확인, C2 오프라인 미확인·계정 조건 충족이다. 이는 실제 PomoToki·Focus To-Do의 기능 판정이 아니다. 미확인 두 건에도 각각 verdict ID와 생성 task ID가 있고, evidence는 빈 배열과 사유로 남는다. 후보 발굴 작업은 만들지 않으며 보고서는 부분 결과다.

## 3. APP-C3의 보류와 최종 미실행

출력 위치는 `runs[1]`이다. 요청 ID는 `MOCK-REQ-R03-APP-C3-001`이다. APP-C에는 계정 선호를 임의로 추가하지 않는다. 두 후보의 `offline_timer` 판정을 각각 기록한다.

| 단계 | 출력 위치·상태 | 의미 |
|---|---|---|
| 계획 | `snapshots[0]`, D1 대기 | 발굴은 조건부 노드로 미리 표시. 아직 실행하지 않음 |
| 확인 중 | `snapshots[1]`, D1 보류 | 두 판정은 미충족·미확인. `run_if` 결과는 미확인이므로 DEC1에 `condition_unknown` 기록 |
| 한도 종료 | `steps`의 `confirmation_limit_reached`, `snapshots[2]` | 시험용 모의 tick 2에 종료 이벤트 주입. 실제 시간 경과·도구 호출 한도 검증은 아님 |
| 최종 미실행 | D1 생략, DEC2 `action=최종 미실행` | `status_reason=limit_reached_condition_unknown`. 발굴 시작 이벤트 없음 |

한도 값 2는 **재현용 fixture 설정**이다. 제품의 초·호출 수·재시도 횟수로 확정한 값이 아니다. 이 원형은 보완 조사나 자동 재시도를 실제로 수행하지 않는다. 한도 이벤트를 주입한 후에도 판정이 미확인일 때 종료하는 상태 표현을 확인한다.

두 번째 후보의 자료 확인 R2는 합성 접근 실패다. 해당 출처에서 evidence를 만들지 않는다. V2는 실패 기록을 입력으로 받아 판정을 미확인으로 남기고 작업 자체는 완료한다. 선행 실패를 성공으로 바꾸지 않는다. 판정 작업은 `depends_on`과 명시적 `all_tasks_terminal` 입력 조건으로 실패 기록을 받을 수 있게 한 **R03 예시 정책**이며, 실패 시 모든 후속 작업을 허용하는 일반 규칙이 아니다.

## 4. R04가 확인할 출력

각 run의 `screen_payload`에 저장 보고서를 펼친 예시 응답을 넣었다. 실제 화면이나 API 응답 규격은 아니다.

- `task_statuses`: 작업 상태, 상태 사유, 실패 사유.
- `verdicts`: 대상·조건별 판정, verdict/task ID와 evidence 참조.
- `claims`, `evidence`, `sources`: 합성 주장과 근거·출처 연결.
- `report_status`, `uncertainties`, `failures`: 부분 결과와 조건 미확인·작업 실패를 각각 표시.
- `discovery_decisions`: 확인 중 보류와 최종 미실행의 별도 ID·사유·조건 판정 참조.

APP-C3에서는 **R2 작업 실패 / J2-1 조건 미확인 / REPORT1 부분 결과 / D1 최종 미실행 이유**를 서로 바꾸지 않고 전달한다. 중간 화면은 `snapshots`와 `steps`로 검토할 수 있으며 실시간 이벤트 전송은 구현하지 않았다.

모든 run과 근거에는 합성임을 표시했다. 출처 URL은 `mock://`이고 실제 조회 시각 `retrieved_at`은 `null`이다. `access_status=원문 확인`은 합성 원문의 시험 상태이며 실제 원문을 조회했다는 기록이 아니다. 모의 tick을 실제 조회 시각으로 채우지 않는다.

## 6. 아직 공동 확인할 항목

1. ID는 이 원형에서 요청 접두사를 붙여 유일하게 만들었다. 발급 주체·재시도/실행 시도 구분·고유 범위는 R05와 확인해야 한다.
2. 조건부 D1 노드를 먼저 만들고 대기·보류·생략을 기록하는 방식을 택했다. 기존 원형처럼 미생성 작업에 결정만 기록하는 방식과의 선택은 팀 합의 전이다.
3. `run_if` 객체의 op·참조 방식, `보류/생략` 상태명과 reason 코드, 실패 결과를 받는 판정 작업의 준비 조건은 예시다.
4. APP-A의 `offline_pomodoro`와 APP-C의 `offline_timer`는 요청의 문구에 따라 구분했다. R05의 조건 ID·`no_account` 등과 자동 동일시하지 않는다.
5. 확인 한도의 종류·수치·판단 주체, `retrieved_at=null`인 합성 자료 전달 방법, 필드 자료형·전송 방식은 미합의다.
6. 모든 후보에 확인된 내용이 전혀 없는 결과의 종료 정책은 이번 두 fixture에서 제외했다. R05의 단일 실패 예시와 함께 확인해야 한다.
7. C1·C2는 기존 모의 분기 근거만 유지했다. 새 ID 계약의 C1·C2 종단간 검사나 실제 API·화면 통합을 통과했다고 하지 않는다.

이번 변경은 R03 안의 코드·출력·설명·기록에 한정한다. TASK-005 공용 result는 이전 문서 대조 시점의 기록으로 유지하며, 이 새 원형을 검토·수용한 것으로 자동 갱신하지 않는다. 기획서·WBS·R05 원본도 변경하지 않았다.
