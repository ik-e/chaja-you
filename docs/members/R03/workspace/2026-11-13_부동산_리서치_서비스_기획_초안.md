## 1. 서비스 구상

사용자가 원하는 부동산의 예산·위치·형태·필수 조건·선호를 입력하면, 이용이 허용된 자료에서 후보 정보를 정리하고 같은 기준으로 비교하도록 돕는다. 관심 후보를 선택한 뒤에는 계약 전에 무엇을 추가 확인해야 하는지 공식 안내에 근거해 정리한다.

사용자 흐름은 **조건 정리 → 후보 탐색·비교 → 추가 정보 확인 → 계약 전 확인 안내**로 구성한다. AI는 확인된 사실·출처·미확인을 구분하고, 모르는 내용을 임의로 채우지 않는다.

## 2. 타겟 유저

두나가 제안한 대상은 다음 세 집단이다.

| 타겟 후보 | 상황·목적 | 확인할 문제 가설 |
|---|---|---|
| 전월세 주택을 찾는 사람 | 아파트·빌라·오피스텔 등에서 예산과 생활 조건에 맞는 거주지를 선택 | 여러 후보를 비교하고 계약 전 확인할 내용을 파악하기 어려움 |
| 창업을 위해 상가를 찾는 사람 | 위치·예산·면적·업종 조건에 맞는 사업 공간을 선택 | 매물 정보와 사업 목적에 필요한 조건을 따로 확인해야 함 |
| 주택을 매매하려는 사람 | 목적·예산·주거 조건에 맞는 주택을 구매 | 여러 정보의 확인 범위와 부족한 내용을 구분하기 어려움 |

이번 상세 피처 논의는 **전월세 계약 경험이 부족한 임차인**을 첫 검증 대상 후보로 삼았다. 이는 대화에서 구체화한 초안이며, 나머지 대상을 삭제하거나 최종 타겟으로 확정한 결정은 아니다. 상가·매매는 필요한 정보와 계약 맥락이 달라 동일한 점검 목록을 그대로 적용하지 않는다.

## 3. 페인 포인트 — 조사할 가설

| ID | 문제 가설 | 확인할 근거 |

| P1 | 여러 출처에서 조건을 반복 입력하고 후보를 찾아야 해 탐색에 시간·수고가 듦 | 실제 사용자의 최근 탐색 과정, 방문 경로, 반복 검색 행동 |
| P2 | 후보마다 정보의 표현·누락 항목이 달라 같은 기준으로 비교하기 어려움 | 후보별 비교 과정, 직접 계산·재확인한 항목, 누락으로 생긴 질문 |
| P3 | 계약 경험이 부족하면 어떤 정보·서류를 왜 확인해야 하는지, 충분히 확인했는지 알기 어려움 | 실제 사용자의 질문·누락 사례, 공식 안내와 기존 서비스 활용 과정 |

사용자가 떠올린 탐색 경로에는 네이버부동산·피터팬·직방·다방·당근부동산·네이버카페 등이 있다. 이는 출발점으로 제시한 예시이며 각 서비스의 최신 범위·연동 가능성·수집 권한을 조사한 목록은 아니다.

‘대부분 외출을 싫어한다’, ‘귀찮아서 사기를 당한다’, ‘여러 플랫폼 때문에 사기가 발생한다’는 빈도·인과 주장은 현재 근거가 없으므로 사실로 사용하지 않는다. 실제 사용자 행동·발생 빈도·불편의 정도와 기존 대안으로 충분히 해결되는지부터 확인한다.

## 4. 문제 정의

> 부동산 계약 경험이 부족한 임차인은 자신의 조건에 맞는 매물을 찾고 비교하는 과정에서 여러 출처를 반복 확인해야 하며, 계약 전 필요한 정보와 서류를 알기 어려워 충분히 확인했는지 판단하기 어렵다.

AI·멀티에이전트나 플랫폼 통합 자체를 문제 정의의 전제로 삼지 않는다. 이 문제의 빈도와 심각성, 해결할 사용자 가치도 아직 검증 가설이다.

## 5. 핵심 피처 1 — 사용자 조건 기반 후보 정리

### 입력과 조건 구조화

사용자는 자연어로 원하는 조건을 입력한다. 아래는 가상의 요청 예시다.

> 보증금 1,000만 원 이하, 관리비 포함 월 70만 원 이하이고 반려동물을 키울 수 있는 집을 찾고 싶어. 가능하면 역과 가까웠으면 좋겠어.

| 구분 | 정리한 조건 |
|---|---|
| 필수 | 보증금 1,000만 원 이하 |
| 필수 | 관리비 포함 월 지출 70만 원 이하 |
| 필수 | 반려동물 가능 |
| 선호 | 역과 가까운 곳 |
| 추가 확인 | 지역·입주 시기, 관리비에 포함할 비용의 범위 |

정리한 조건은 사용자가 확인·수정할 수 있게 한다. 후보 탐색·선택에 꼭 필요한 정보가 빠졌을 때만 질문한다. ‘선호’를 필수로 바꾸거나 필요한 후보가 부족하다는 이유로 예산 등 필수 조건을 임의 완화하지 않는다.

### 처리와 출력

- 사용자 제공 후보·자료 또는 사용이 허용된 API·데이터에서 확보한 후보를 조건에 맞춰 정리한다.
- 후보별 조건 충족 여부와 부족한 정보를 전달한다. 조건에 맞는 후보가 없거나 자료가 부족하면 그 이유를 알린다.
- 사용자가 직접 제공한 URL도 자동 조회·저장 권한까지 보장한다고 가정하지 않는다.
- 이름만 있는 후보 목록이 아니라 어떤 사용자 조건과 연결됐는지 남긴다.

대응 페인 포인트는 P1이다. 조건 해석 정확도·사용자 수정 횟수·반복 검색 행동과 탐색 부담의 변화를 확인한다. 감소 효과를 현재 달성한 것으로 표현하지 않는다.

## 6. 핵심 피처 2 — 현재 매물 비교와 과거 거래 참고·근거·미확인 표시

후보들을 같은 조건으로 비교하고, 어떤 정보가 확인됐으며 무엇이 아직 빠졌는지 보여준다.

| 비교 항목 | 가상 후보 A | 가상 후보 B |
|---|---|---|
| 월세＋관리비 | 68만 원으로 기재 | 관리비 금액 미기재 |
| 반려동물 | 가능하다고 기재 | 확인 필요 |
| 역과의 거리 | 도보 시간 확인 필요 | 도보 시간 확인 필요 |
| 현재 판단 | 비용 조건은 게시 정보상 충족 | 비용 조건 판정 보류 |

이 표는 출력 설계 예시로 실제 매물·가격·조건을 조사한 결과가 아니다.

실제 출력에서는 각 설명 끝에 출처·확인 시점을 연결하고 적용 범위를 표시한다. 광고 기재와 별도 확인, 조건 미충족과 정보 부족, 현재성 확인과 재확인 필요를 구분한다. 단순 추천 순위만으로 판단 근거를 대신하지 않는다.

예를 들어 ‘후보 B는 관리비가 없어 월 지출 조건을 판단할 수 없습니다. 관리비와 포함 항목을 확인하면 비교를 이어갈 수 있습니다’처럼 다음 확인 행동을 안내한다. 요청한 비용 항목 일부만 확인하고 총 주거비를 확인했다고 표시하지 않는다.

### 현재 매물과 과거 거래 이력의 구분

현재 선택할 수 있는 매물을 우선 보여주고, 과거 거래 이력은 가격과 거래 방식을 이해하는 별도 참고 정보로 제공한다. 과거 거래 기록을 현재 계약 가능한 매물로 표시하거나, 그 기록만으로 현재 사용자 조건을 충족했다고 판정하지 않는다.

| 상황 | 안내 방식 |
|---|---|
| 현재 매물과 관련 과거 거래가 모두 있음 | 현재 매물의 게시 가격·조건과 과거 거래 유형·계약 시점·가격을 구분해 비교 |
| 확인한 자료에서 조건에 맞는 현재 매물을 찾지 못함 | 검색한 자료·지역·조건·확인 시점을 밝히고, 관련 과거 거래가 있으면 참고 정보로 제공 |
| 같은 단지·비슷한 면적의 거래만 확인됨 | 동일 매물 이력이 아닌 ‘유사 거래’로 표시 |
| 과거 거래 자료도 부족함 | 참고할 거래를 확인하지 못했다고 안내하고 가격을 임의 추정하지 않음 |

‘매물이 없다’고 시장 전체에 대해 단정하지 않고, ‘확인한 자료에서는 조건에 맞는 현재 매물을 찾지 못했다’고 안내한다. 자료 접근 실패로 확인할 수 없는 경우에는 검색 결과 없음과 구분해 미확인 사유를 표시한다.

‘이 매물은 전에 이 가격으로 거래됐다’는 표현은 동일 호실임을 확인할 수 있을 때만 사용한다. 아파트 전월세 실거래가 API는 동·호 정보를 제공하지 않으므로, 같은 단지·면적이라는 이유만으로 동일 매물 이력으로 연결하지 않는다. [국토교통부 아파트 전월세 실거래가 공식 안내](https://www.data.go.kr/data/15126474/openapi.do) (확인일: 2026-11-13; 공식 문서 확인이며 실제 API 호출·동일 매물 식별 검증은 미실시)

아래는 실제 조사 결과가 아닌 가상 출력 예시다.

> **현재 매물 검색 결과**  
> 확인한 자료에서는 조건에 맞는 현재 매물을 찾지 못했어요. 검색 범위와 확인 시점을 함께 표시합니다.
>
> **참고할 과거 거래 — 유사 거래**  
> 같은 단지의 전용면적 59㎡ 주택이 2025년 10월에 보증금 1,000만 원·월세 60만 원으로 거래된 기록이 있다고 가정한 예시입니다. 동일 호실의 거래 이력으로 확인된 정보는 아니에요.
>
> 과거 거래는 현재 계약 가능한 매물이나 현재 가격을 의미하지 않아요. 실제 화면에서는 이 설명 끝에 해당 거래의 출처 링크·계약 시점·조회일을 연결합니다.

현재 매물과 과거 거래는 화면 영역과 표의 구분 항목으로 명확하게 나눈다. 과거 기록의 거래 유형(매매·전세·월세), 가격, 계약 시점, 비교 대상과의 일치·차이, 출처·조회일을 제공하고, 현재 매물의 관리비·반려동물 허용·입주 가능일 같은 조건을 과거 기록에서 추정해 채우지 않는다.

대응 페인 포인트는 P2다. 사용자가 후보 차이·누락 정보를 찾는 정확도와 시간, 추가로 해야 할 질문을 파악하는지를 확인한다. 현재 매물과 과거 거래, 동일 매물 이력과 유사 거래, 검색 결과 없음과 자료 접근 실패를 구분할 수 있는지도 검증한다. 이 기능의 실제 구현·사용성 효과는 아직 검증 전이다.

## 7. 핵심 피처 3 — 계약 전 확인 안내

관심 후보를 선택하면 거래 유형과 계약 단계에 맞는 공식 안내를 바탕으로 확인할 항목과 경로를 정리한다. 사용자에게 필요한 정보는 다음과 같다.

| 표시할 정보 | 목적 |
|---|---|
| 확인할 것 | 어떤 정보·서류를 확인해야 하는지 안내 |
| 확인 이유 | 그 항목이 선택·계약 판단에 왜 필요한지 설명 |
| 확인 경로 | 공식 기관·서비스 또는 관계자·전문가에게 확인할 방법 연결 |
| 현재 상태 | 확인 전 / 자료 확보 / 추가 확인 필요 등 진행 상태 구분 |
| 다음 행동 | 사용자에게 남은 질문·확인·상담 행동 안내 |

위 목록은 기능에 담을 정보 구조이며, 개별 계약의 법적 필수 서류나 충분한 안전 점검 기준을 확정한 목록이 아니다. 실제 항목은 거래 유형·단계에 맞는 공식 안내의 출처와 확인 시점을 붙여 작성해야 한다.

사용자의 ‘확인했어요’ 체크는 진행 상태이지 자료의 진위·최신성·계약 안전을 보장하는 판정이 아니다. 서비스는 사기를 자동 확정하거나 안전한 계약을 보증하지 않고, 확인된 내용과 남은 확인 사항을 구분해 필요한 공식·전문가 확인 경로를 안내한다.

초기에는 확인 목록·확인 목적·질문·공식 경로를 제공하는 범위를 검토한다. 계약 문서 자동 판독·사기 확률 산정·법률 판단을 필수 기능으로 추가하지 않는다.

대응 페인 포인트는 P3다. 사용자가 필요한 확인 항목과 다음 행동을 이해하는지, 모르는 정보를 확인 완료로 오해하지 않는지 확인한다.

## 8. 기존 대안과 반대 근거

- 부동산 플랫폼·일반 검색·범용 AI가 후보 탐색·조건 비교를 이미 충분히 해결할 수 있는지 조사한다. 서비스별 기능 차이를 현재 확인한 사실처럼 단정하지 않는다.
- HUG는 공식 서비스에서 안심조회·임대인 정보조회·셀프 체크리스트 등을 안내한다. 따라서 ‘계약 체크리스트 제공’만으로 차별화가 생긴다고 가정하지 않는다. [HUG 공식 서비스](https://onestop.khug.or.kr/) (확인일: 2026-11-13; 공식 웹 안내 확인이며 개별 조회 서비스 실행 시험은 아님)
- 사용자에게 여러 단계가 묶인 서비스가 오히려 복잡할 수 있다. 사용자가 이미 선택한 플랫폼·전문가의 도움만으로 충분한 경우도 반대 가설로 확인한다.
- 허용된 매물 데이터가 충분하지 않거나 최신성·정확성을 확보하지 못하면 후보 탐색 기능의 가치가 제한될 수 있다.
- 전월세·상가·주택 매매를 동시에 다루면 조건과 확인 절차가 넓어진다. 첫 타겟을 좁히는 것이 사용자 가치와 자료 확보에 도움이 되는지 검토한다.

## 9. 검증할 가치와 다음 조사

핵심 가설은 다음과 같다.

> 사용자 조건에 따른 후보 비교와 계약 전 확인 사항을 한 흐름으로 연결하면, 사용자가 반복 확인하는 수고와 확인 항목의 누락을 줄일 수 있다.

1. 실제 사용자에게 최근 매물을 찾은 과정을 구체적으로 확인한다. 사용한 경로·비교 항목·확인하지 못한 정보·다시 질문한 내용을 조사한다.
2. 기존 대안만 사용한 과정과 제안 기능을 이용한 과정을 대조한다. 같은 자료·사용자 과제에서 확인 시간·누락·조건 이해·다음 행동 파악을 비교한다.
3. 사용할 매물·주변 정보·공식 안내의 접근 가능성, API와 수집·저장·재사용 권한을 확인한다.
4. 각 피처가 실제 문제를 해결하는지, 불필요한 기능이 있는지 검토한다. 시간·피해 감소 등의 효과를 근거 없이 수치화하지 않는다.
5. 사실·관찰·추정·미확인·반대 근거와 다음 검증을 구분해 TASK-013 제출 결과로 구조화한다.

사용자 인터뷰·문제 빈도 조사·기존 대안 비교 실험은 아직 수행하지 않았다. 따라서 수요·효과·차별점은 가설로 유지한다.

## 10. 데이터·범위 경계와 현재 상태

- 무단 크롤링, 플랫폼 전체 매물 수집·통합, 권한이 없는 원문·이미지·개인정보 저장을 전제로 하지 않는다.
- 검색 결과·게시 정보·실제 확인·전문가 판단을 구분한다. 자료가 부족하면 추가 확인 필요로 남긴다.
- 공식 안내를 찾았다는 사실과 개별 계약에 적용되는 법률 판단·안전 보증은 구분한다.
- 다른 팀원의 독립 최종 제안을 읽거나 사전 합의한 내용이 아니다. 이번 문서는 두나의 구상과 해당 대화 내용을 정리한 것이다.
- TASK-013 result 작성·완료 판정은 아직 하지 않았다. 현재 프로젝트의 앱 MVP·기획서·WBS·다른 TASK를 변경하지 않는다.
