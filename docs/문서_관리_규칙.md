# 문서 관리 규칙

이 문서는 `docs/` 안의 문서 작성·연결·갱신 기준입니다. 디렉터리별 `README.md`는 이 규칙에 따라 해당 위치의 문서로 연결하는 라우터 역할을 합니다.

## 1. 기준 문서와 중복 방지

- 문서 주제마다 기준 문서(canonical document)를 하나만 둡니다. 최신 팀 운영 규칙은 `charter/팀_헌장.md`, 회의 기록은 `meetings/`의 날짜별 파일, 현재 설계는 해당 `design/` 문서가 기준입니다.
- 다른 문서에서 같은 내용을 다시 길게 복사하지 말고 상대 경로 링크로 참조합니다. 필요한 경우 한두 문장 요약과 링크를 둡니다.
- 기준 문서를 바꾸면 그 문서를 직접 수정합니다. 참조 문서에는 중복된 본문 대신 링크를 유지해 동기화 부담을 줄입니다.
- 문서를 이동·이름 변경·보관할 때는 `rg`로 이전 경로와 제목을 찾아 모든 내부 링크와 README 라우트를 함께 갱신합니다.

## 2. 디렉터리와 README 라우팅

- 새 디렉터리 이름은 영어로 짓고, 문서 제목과 본문은 한국어로 씁니다. 새 이름은 소문자와 `_`를 권장합니다. 팀원 폴더는 `R01`~`R05`를 사용합니다. 원본 파일과 출처 폴더의 원래 이름은 보존이 필요하면 유지합니다.
- `docs/` 아래의 모든 디렉터리에는 `README.md`를 둡니다. 새 디렉터리를 만들 때도 같은 변경에서 README를 추가합니다.
- 각 README에는 **이 폴더의 용도**, **이곳의 기준 문서·원본**, **관련 문서로 가는 상대 경로 링크**, **갱신 담당 또는 규칙**을 적습니다.
- 상위 README는 다음 단계의 하위 디렉터리와 주요 문서를 연결합니다. 문서 본문은 필요한 상위 맥락과 관련 기준 문서로 다시 연결합니다.
- 경로는 저장소 안에서 열리는 상대 경로 Markdown 링크를 사용합니다. 제목이 바뀌어도 찾기 쉽도록 문서 첫머리에 주제·담당·상태를 표시합니다.

## 3. 파일 형식과 이름

- 작성 문서의 기본 형식은 Markdown (`.md`)입니다. 원본이 PDF, HTML, TXT, XLSX 등 다른 형식이면 원본 형식을 유지합니다.
- 일반 문서는 주제를 나타내는 한국어 이름을 씁니다. 날짜별 기록은 `YYYY-MM-DD_주제.md`로 작성하고 같은 날 같은 종류 기록이 여러 개면 `_02`, `_03`을 붙입니다.
- 일일 상태는 `members/Rxx/daily/YYYY-MM-DD.md`, 개인 초안은 `members/Rxx/workspace/`에 둡니다.
- 설계 결정은 `design/decisions/ADR-001_주제.md`처럼 순번을 부여합니다.
- 한 문서에는 한 주제를 담습니다. 여러 주제를 다루면 문서를 나누고 README와 본문에서 서로 링크합니다.

## 4. 문서 머리말과 상태

새 문서와 주요 내용을 크게 갱신하는 문서의 본문 맨 위에 다음 메타데이터를 둡니다. 기존 문서에 메타데이터가 없으면 다음 주요 갱신 때 추가합니다. 짧은 체크인처럼 문맥상 불필요한 문서에는 담당자와 상태를 생략할 수 있습니다.

```markdown
# 문서 제목

- 담당: Rxx 또는 역할
- 상태: 초안 | 확인 요청 | 확정 | 보관
- 작성일: YYYY-MM-DD
- 갱신일: YYYY-MM-DD
- 출처: 내부 논의 또는 원문 링크
```

- **초안**은 작성·논의 중인 내용, **확인 요청**은 사실이나 합의 확인이 남은 내용, **확정**은 담당자가 정리하고 필요한 의사결정권자가 결정한 내용, **보관**은 현재 기준으로 사용하지 않는 기록입니다.
- 회의록에 작성된 결정과 제안은 구분합니다. 출처에서 확인하지 못한 정보는 추측해 채우지 말고 `미확인`으로 표시합니다.
- 초안·확정 상태는 동료 간 검토 의무를 뜻하지 않습니다. 헌장에 따라 각 담당자가 자기 결과를 확인하며, 팀 전체 범위·우선순위·일정 결정은 팀장이 최종 정리합니다.

## 5. 소스별 기록 위치

| 자료 종류 | 저장 위치 | 작성·갱신 방법 |
|---|---|---|
| 팀 운영 원칙 | `charter/` | 기준 헌장 하나를 갱신하고 제안 원본·종합본을 연결 |
| 교육·프로젝트 가이드 | `guidelines/` | 원문은 그대로 보존, 해석·적용 사항은 별도 한국어 문서로 작성 |
| 회의·결정 기록 | `meetings/` | 회의마다 파일을 만들고 안건·결정·담당·기한·출처 링크 기록 |
| 조사 자료 | `research/sources/`, `research/topics/` | 원본은 불변 보존, 분석은 출처·조사일과 함께 별도 작성 |
| 현재 설계 | `design/architecture/`, `api/`, `data/` | 현재 유효한 설명을 갱신하고 중요한 선택은 ADR로 연결 |
| 코드 협업 방식 | `development/` | 브랜치·푸시·최소 확인·통합·릴리스 기준을 단일 문서에 유지 |
| 개인 체크인·초안 | `members/Rxx/daily/`, `workspace/` | 개인 상태와 작업 메모 기록, 팀 결정은 기준 문서로 이관 |
| 제출받은 원본 | `members/originals/` | 수정하지 않고 제출자·수신일·원본 파일명을 README에 색인 |
| 지난 버전·폐기 문서 | `archive/` | 삭제 대신 보관하고 현재 대체 문서로 연결 |

## 6. Discord·회의 기록 절차

1. Discord는 빠른 소통과 알림에 사용합니다. 합의·결정·담당자·기한이 정해지면 `docs/`의 관련 기준 문서에 옮깁니다.
2. 옮긴 내용에는 메시지 또는 첨부 원문 링크와 작성일을 남깁니다. 팀원의 제안은 결정으로 확정되기 전까지 제안이라고 표시합니다.
3. 회의는 정기적으로 열지 않습니다. 팀장이 필요할 때 소집하고, 소집자나 지정 기록자가 회의록을 작성합니다.
4. 회의록에는 확인된 참석자, 일시, 안건, 결정, 담당자, 기한, 미해결 사항을 기록합니다. 확인되지 않은 항목은 `미확인`으로 씁니다.
5. 회의록 첨부 원본과 팀원이 제출한 원본은 바이트·내용을 수정하지 않습니다. 요약은 별도 Markdown 파일을 만들고 원본으로 연결합니다.
6. 일일 상태는 팀원별 문서의 아침·점심·저녁 항목을 갱신합니다. 팀장은 이를 확인해 일일 업무와 막힘을 관리하고, 조정 사항은 필요한 공용 문서에 기록합니다.

## 7. 조사와 설계의 출처·상태

- 조사 문서에는 질문, 결론, 근거, 출처 URL 또는 원본 파일, 조사자, 조사일, 미확인 사항을 적습니다.
- 회의에서 언급된 아이디어·조사 계획은 조사 결과와 구분합니다. 출처를 확인하지 못한 정보는 사실로 단정하지 않습니다.
- 설계 문서에는 현재 동작 기준과 관련 API·데이터 모델·ADR 링크를 둡니다. 변경 시 영향 받는 문서의 링크와 설명을 함께 갱신합니다.
- 개인정보, 비밀번호, API 키, 봇 토큰, `.env` 값은 문서·커밋·Discord 요약에 기록하지 않습니다.

## 8. 갱신·보관 절차

- 문서 담당자는 내용이 바뀐 날 갱신일과 관련 링크를 업데이트합니다. 팀 전체에 영향을 주는 결정은 팀장이 최종 내용과 후속 작업을 확인해 기준 문서에 반영합니다.
- 문서가 Git으로 관리되는 경우 변경 이력을 버전 기록으로 사용하고 수동 버전 번호를 반복하지 않습니다. Git이 없는 작업공간에서는 이 규칙이 적용되는 것처럼 가정하지 않습니다. 중요한 결정은 ADR, 회의록 또는 변경 근거를 링크합니다.
- 대체된 문서는 상태를 `보관`으로 바꾸고 `archive/`로 옮긴 뒤 상단에 대체 문서 링크를 남깁니다. 원본 보존 대상은 보관본으로 옮기거나 덮어쓰지 않습니다.
- 각 디렉터리 README의 링크를 통해 문서를 찾을 수 있는지 변경 후 확인합니다.
