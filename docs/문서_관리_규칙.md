## 사람과 AI의 폐루프

사람이 쓰는 권위 입력은 [사람 작업 공간](human/README.md)에 둔다. 장기 목표·운영 원칙은 `human/INTENT.md`, 현재 단계의 추진/보류와 재검토 조건은 `human/phase-intents/`, 특정 검토 항목에 대한 승인·수정·보류·거절은 `human/responses/`에 기록한다. 생성된 `PROJECT.md`, `CURRENT.md`, `EVAL.md`, `review/`, `submissions/`는 사람이 읽는 프로젝션이며 직접 편집하지 않는다.

AI는 사람 입력을 읽고 관련 ADR·state·spec·task 원본에 반영한 뒤 프로젝션을 다시 생성한다. 사람 응답은 결정의 출처로 보존하며, AI가 적용했다는 이유로 원문을 삭제하거나 재작성하지 않는다. 서로 충돌하는 사람 입력은 최신 파일을 임의로 우선하지 않고 충돌 상태로 사람에게 돌려준다.

```text
AI 원본 → 사람용 프로젝션 → 사람 의도/응답 → ADR·state·spec·task → 다음 AI 작업
```

## AI 산출물

새 AI 산출물은 JSON으로 작성한다. 각 산출물은 `schema_version`, 안정적인 `id`, `kind`, `status`를 갖고 해당 작업의 입력·출력·근거·검증을 [TASK](../TASK.md)의 계약에 맞춰 저장한다. 요구사항·사례·작업·주장·근거·검증을 각각 접근 가능한 필드로 둔다. 긴 설명은 구조화된 항목의 보충 텍스트로 쓴다.

기존 조사·제안은 `kind: document`로 이관해 담당·원래 상태·출처·섹션별 내용을 보존했다. `provenance.original_path`와 원본 해시로 이관 전 자료를 식별한다. 후속 작업에서 필요한 주장·근거는 현재 TASK 결과에 구조화하고 원문을 참조한다. 이전 제안의 수치나 기술 후보는 현재 결정으로 승격하지 않는다.

CSV·이미지·도구 로그 등 원래 형식이 필요한 실행 자료는 JSON에서 경로로 연결한다. 제출받은 원본과 외부 원문은 원래 내용과 파일 형식을 보존하고 조사 결과에는 출처와 확인 시점을 붙인다.

## 후보와 현재 기준의 분리

가치가 있을 수 있지만 아직 채택되지 않은 아이디어·가설·대안·미래 기능은 `artifacts/candidates/`에 보존할 수 있다. Candidate는 사람의 Intent와 병행해 존재할 수 있지만 현재 설계·범위·일정·요구사항을 바꾸지 않는다.

후보는 일반 AI 작업의 기본 입력이 아니다. 현재 TASK가 후보를 명시적으로 참조하거나 아이데이션·대안 비교·재검토 자체가 작업 목적일 때만 필요한 후보를 읽는다. 후보에는 잠재 가치뿐 아니라 현재 도입하지 않는 이유, 위험, 필요한 근거, 다시 볼 조건을 함께 남긴다.

팀원이나 AI의 가공 전 제안은 `docs/ideas/`에 먼저 남길 수 있다. Candidate로 정리할 때는 원제안의 `proposed_by`와 Idea 경로를 provenance로 보존하고, 유사 제안은 하나의 Candidate로 병합할 수 있다. 원제안을 Candidate로 정리한 행위 자체는 승인·채택을 뜻하지 않는다.

후보의 기본 승격 경로는 `Candidate → Research/Task/Run/Evaluation → Human decision → Design/Spec/ADR/Task/State`다. 근거와 권한 있는 사람의 결정 없이 후보를 현재 정본으로 자동 승격하지 않는다. 반대로 후보를 채택하지 않는다고 즉시 삭제할 필요는 없으며, 과거 판단을 이해할 가치가 있으면 보존한다.

## 작업과 결정

작업은 [TASK 템플릿](artifacts/tasks/template.json)에 질문·목적·입력·범위·산출물·완료 조건·검증을 기록한다. 활성 TASK는 `phase_intent_ref`를 CURRENT의 `active_phase_intent_ref`와 일치시키고, 구현/제출 가능 범위를 단계 의도에 따라 해석한다. 이전 제품안·WBS의 구현 보류를 신규 TASK가 자동 해제하지 않는다.

새 TASK는 필요한 경우 `traceability`로 상위 Intent·Design Hypothesis·Requirement·Evaluation의 ID를 연결한다. 이 참조는 문서 계층을 늘리기 위한 것이 아니라 **작업이 왜 존재하고 어떤 가설·요구사항을 실제로 검증했는지 역추적하기 위한 관계**다. 기존 TASK 전체를 일괄 변환하지 않고 이후 수정이나 재검증이 필요한 작업부터 연결한다.

구현 성격의 TASK는 가능한 범위에서 `validation_plan`을 구현 범위와 함께 작성한다. 검증 질문, 관측값, 성공·실패·미확인 경계, 필요한 경우 baseline과 동일 조건을 기록하고 실제 실행 결과는 run/evaluation에서 판정한다. 단순 작업은 `validation_plan: null`을 허용한다.

작업은 [TASK 템플릿](artifacts/tasks/template.json)에 질문·목적·입력·범위·산출물·완료 조건·검증을 기록한다. 실제 결과는 `result`에 결론, 주장과 근거, 검증, 남은 불확실성, 결정 요청을 담는다. 예정된 작업은 실제 실행이나 검증 결과로 표시하지 않는다.

목적·제약에서 정해지는 선택은 적용하고, 작고 되돌리기 쉬운 선택은 기본값으로 진행한다. 영향이 크고 불확실한 선택에는 결정을 바꿀 최소 근거를 확보한다. 중요한 결정은 [ADR](adr/README.md)에 맥락·선택지·근거·결정·이유·재검토 조건을 남긴다. 구현 편의 때문에 PROJECT의 목표를 바꾸면 그 변경도 명시한다.

원본의 상태는 제안·확정·관찰 결과를 구분한다. TASK는 팀 헌장의 작업 상태를 쓰고 평가 판정은 `pass`, `fail`, `inconclusive`를 쓴다. AI의 추천만으로 팀 결정이나 제출 상태를 확정하지 않는다.

## 협의·정본 수정·커밋 규칙

팀 협의는 모든 미확정 사항을 합의하기 위한 절차가 아니다. **다른 TASK가 그 의미·인터페이스·상태·완료 조건을 전제로 작업하거나 판단해야 하는 항목만 합의 대상으로 둔다.** 담당자 내부의 구현 방식, 문서 표현, 쉽게 되돌릴 수 있는 기본값은 해당 담당자가 결정한다. 합의가 되지 않은 항목은 억지로 확정하지 않고 미합의·미확인으로 남긴다. 그 차이가 제품 범위·필수 요구사항·완료 기준·프로젝트 방향을 바꾸는 경우에만 R01 결정 대상으로 올린다.

canonical TASK 원본은 **한 시점에 한 명의 책임자만 직접 수정한다.** 기본 책임자는 해당 TASK의 `owner`이며, 다른 팀원은 자기 workspace·daily·회의 기록 등에서 근거·차이·수정 제안을 남기고 TASK owner가 이를 정본에 반영한다. 소유권을 넘기거나 R01이 범위·결정 때문에 직접 수정해야 하면 그 사실을 명시하고 동시에 같은 TASK 원본을 편집하지 않는다. 이 규칙은 파일 잠금 제도를 도입하려는 것이 아니라, 같은 정본을 서로 다른 의미로 동시에 수정하는 일을 막기 위한 최소 운영 규칙이다.

## 브랜치·PR·main 운영

`main`은 병렬 작업을 직접 수행하는 공간보다 **통합된 현재 상태**로 사용한다. 의미 있는 기능·계약 변경은 기본적으로 TASK 단위 작업 브랜치와 PR을 거쳐 통합한다. 단순 오탈자나 생성 프로젝션 갱신처럼 의미가 바뀌지 않는 작은 변경에는 무거운 절차를 강제하지 않는다.

검토 책임은 변경 범위에 따라 나눈다.

- TASK 내부·저위험 변경: owner가 구현과 검증을 확인하고 통합할 수 있다.
- 다른 TASK가 의존하는 공유 인터페이스·상태·계약 변경: 관련 owner끼리 확인한다.
- 제품 범위·Must/Done·공통 구조·해결되지 않는 cross-task 충돌: R01 결정 후 통합한다.

모든 PR에 R01 승인을 강제하지 않는다. R01은 모든 결과를 다시 검증하는 사람이 아니라 제품 경계·우선순위, cross-task 통합 기준, 핵심 E2E·릴리스 판단에 집중한다.

작업 브랜치는 통합 후 유지하지 않는 것을 기본으로 한다. 취소·미채택·보류된 작업은 사유 및 필요한 근거를 보존한 뒤 정리하며, 후속 작업에 실제로 필요한 브랜치만 유지한다. 최신 HEAD·정본 반영·의존 PR/TASK·보존 상태 확인과 담당자 책임은 [GitHub 코드 관리 협업 규칙의 브랜치 수명 주기](development/GitHub_코드_관리_협업_규칙.md#브랜치-수명-주기와-종료)를 따른다.

GitHub에는 다음 작업에서도 다시 참조할 **지속 상태, 결정, 계약, 검증 결과**를 남긴다. 실행 중 worker 상태, retry 횟수, queue, 임시 context처럼 일시적인 runtime 상태는 제품 실행 계층에서 관리하고 GitHub 프로젝트 상태와 혼합하지 않는다.

일반 커밋 메시지는 **`<종류>(<대상>): <실제 변경 요약>`** 형식을 권장한다. 종류는 `docs`, `feat`, `fix`, `test`, `refactor`, `chore`, `merge` 정도로 제한하고, 대상은 `TASK-005`, `R03`, `ops`처럼 변경 범위를 짧게 적는다. 예: `docs(TASK-004): record app source constraints`, `fix(TASK-006): preserve unknown state in APP-C3`. 가장 중요한 기준은 **메시지가 실제 diff의 주된 변경과 일치하는 것**이며, 설명을 위해 긴 메시지나 별도 티켓 번호를 강제하지 않는다.

- 기존 Notion 멘토 공간은 의견·질문·참고 자료 수신용으로 유지한다. 의견을 확인할 때 날짜, 출처 식별, 공개 가능한 원문 인용/요약, 검토 상태 및 관련 GitHub 경로를 보존한다. 의견 자체와 R01의 채택·보류·반려 및 실제 적용 결과를 구분한다.
- [회의 기록](meetings/README.md)이나 관련 `artifacts/planning/` 기록에 기존 의견을 참조하고, 동일 의견의 중복 산출물을 만들지 않는다. [11/27 의견 보존 예시](artifacts/planning/lesson-registration-20261126/mentor-feedback-20261127.json).
- [공개 저장소 보안](public/공개_저장소_운영_안내.md)을 우선한다. 비공개 Notion URL·페이지 ID, 개인 연락처·멘션, 권리 미확인 외부 자료 전체는 Git에 올리지 않는다. 필요한 원문은 승인된 비공개 경로에 유지하고 GitHub에는 공개 가능한 근거를 남긴다.
- 기존 멘토 의견과 팀원 자료는 임의 삭제하지 않는다. Notion 수정·삭제·블록 확보 여부는 별도 확인한다. 자동 피드백 수집/자동 TASK 배정은 기본으로 하지 않는다.

## 프로젝션 생성

담당자가 원본을 갱신한 뒤 `uv run --no-project python tools/project_docs.py`로 PROJECT·CURRENT·EVAL·검토 화면·제출물·ADR을 생성한다. `--check`는 데이터 검증과 생성 문서의 최신 여부를 검사한다. 생성 도구는 문서 동기화를 확인하며 제품의 조사 품질은 EVAL에 따른 실제 실행으로 판정한다.

생성 문서의 첫머리에는 원본과 갱신 명령을 표시한다. 사람이 요약에서 결론·검증·불확실성·결정 요청을 확인하고 상세 원본으로 이동할 수 있게 한다. 프로젝션에서 바꾸고 싶은 내용이 있으면 사람이 `human/INTENT.md` 또는 `human/responses/`에 의도와 판단을 남긴다. AI가 이를 원본에 반영한 뒤 재생성한다.

## 과거 TASK 종료 정산과 당시 증거 보존

- Phase Intent가 변경되어 이전 TASK를 더 이상 실행하지 않을 때에는 canonical TASK의 `status`·`result`를 일괄 완료/삭제하지 않는다. 해당 시점의 원본 상태는 유지하고, 새 `closeout` 원장에 분류·사유·근거·인계 TASK와 실제 남은 의무를 기록한다.
- 원본 근거는 **기준 commit SHA + Git blob SHA + 당시 파일 경로 + 독립 스냅샷 경로**로 함께 고정한다. 가능하면 원래 blob을 그대로 복제하며, 보존한 파일의 digest를 자동 검증한다.
- 개인 브랜치와 main의 동일 파일에 서로 다른 결과가 있으면 각 branch/commit을 독립적으로 보존한다. 자료 보존은 사실성 검증·제품 채택·공식 제출 확인을 의미하지 않는다.
- 외부 원본의 재배포 권한이 없으면 무단 복제하지 않고 당시 확인 시점·링크·한계만 남긴다. 추후 판단이 바뀌면 과거 사본을 덮어쓰지 않고 새 결정/정산을 추가한다.
- 현재 적용 사례는 [ADR-003](adr/ADR-003_이전_TASK_정산과_근거_보존.md) 및 [2026-11-18 스냅샷](archive/2026-11-18-task-closeout/README.md)에서 확인한다.

## 경로와 보존

새 디렉터리는 소문자 영어 이름으로 만들고 README에 용도·기준 원본·관련 링크·갱신 담당을 둔다. AI 원본은 `artifacts/`, 사람이 보는 검토 화면은 `review/`, 제출 상태 인덱스는 `submissions/`, 교육 과정의 실제 필수 제출물은 `stepN/`에 둔다. PROJECT·CURRENT·EVAL·TASK는 루트 진입점이다.

문서를 이동하거나 형식을 바꾸면 링크를 함께 갱신한다. 원래 상태와 출처는 이관된 데이터에 남긴다. 대체된 기준본은 `archive/`에서 대체 경로와 함께 보관한다. 제출받은 원본은 내용과 바이트를 유지한다. 개인 일일 상태와 회의 기록은 기존 경로에서 사실·담당·날짜·후속 작업을 기록한다.

공개 범위는 [공개 저장소 운영 안내](public/공개_저장소_운영_안내.md)를 따른다. 비밀값·개인 연락처·비공개 URL을 JSON·실행 로그·프로젝션에도 포함하지 않는다.
