## 기준과 현재 상태

[PROJECT](../PROJECT.md)는 최종 목표와 성공 상태를 담는다. 요청별 동적 워크플로·에이전트 팀 구성이 최종 목표이고, 집중 앱은 현재 검증 범위다. 현재 범위·우선순위·열린 결정은 `artifacts/state/current.json`, 요구사항·사례는 `artifacts/specs/focus_apps.json`에서 관리한다. 팀 역할과 공식 일정은 [팀 헌장](charter/팀_헌장.md)을 따른다.

## 사람과 AI의 폐루프

사람이 쓰는 권위 입력은 [사람 작업 공간](human/README.md)에 둔다. 장기 목표·운영 원칙은 `human/INTENT.md`, 특정 검토 항목에 대한 승인·수정·보류·거절은 `human/responses/`에 기록한다. 생성된 `PROJECT.md`, `CURRENT.md`, `EVAL.md`, `review/`, `submissions/`는 사람이 읽는 프로젝션이며 직접 편집하지 않는다.

AI는 사람 입력을 읽고 관련 ADR·state·spec·task 원본에 반영한 뒤 프로젝션을 다시 생성한다. 사람 응답은 결정의 출처로 보존하며, AI가 적용했다는 이유로 원문을 삭제하거나 재작성하지 않는다. 서로 충돌하는 사람 입력은 최신 파일을 임의로 우선하지 않고 충돌 상태로 사람에게 돌려준다.

```text
AI 원본 → 사람용 프로젝션 → 사람 의도/응답 → ADR·state·spec·task → 다음 AI 작업
```

## AI 산출물

새 AI 산출물은 JSON으로 작성한다. 각 산출물은 `schema_version`, 안정적인 `id`, `kind`, `status`를 갖고 해당 작업의 입력·출력·근거·검증을 [TASK](../TASK.md)의 계약에 맞춰 저장한다. 요구사항·사례·작업·주장·근거·검증을 각각 접근 가능한 필드로 둔다. 긴 설명은 구조화된 항목의 보충 텍스트로 쓴다.

기존 조사·제안은 `kind: document`로 이관해 담당·원래 상태·출처·섹션별 내용을 보존했다. `provenance.original_path`와 원본 해시로 이관 전 자료를 식별한다. 후속 작업에서 필요한 주장·근거는 현재 TASK 결과에 구조화하고 원문을 참조한다. 이전 제안의 수치나 기술 후보는 현재 결정으로 승격하지 않는다.

CSV·이미지·도구 로그 등 원래 형식이 필요한 실행 자료는 JSON에서 경로로 연결한다. 제출받은 원본과 외부 원문은 원래 내용과 파일 형식을 보존하고 조사 결과에는 출처와 확인 시점을 붙인다.

## 작업과 결정

작업은 [TASK 템플릿](artifacts/tasks/template.json)에 질문·목적·입력·범위·산출물·완료 조건·검증을 기록한다. 실제 결과는 `result`에 결론, 주장과 근거, 검증, 남은 불확실성, 결정 요청을 담는다. 예정된 작업은 실제 실행이나 검증 결과로 표시하지 않는다.

목적·제약에서 정해지는 선택은 적용하고, 작고 되돌리기 쉬운 선택은 기본값으로 진행한다. 영향이 크고 불확실한 선택에는 결정을 바꿀 최소 근거를 확보한다. 중요한 결정은 [ADR](adr/README.md)에 맥락·선택지·근거·결정·이유·재검토 조건을 남긴다. 구현 편의 때문에 PROJECT의 목표를 바꾸면 그 변경도 명시한다.

원본의 상태는 제안·확정·관찰 결과를 구분한다. TASK는 팀 헌장의 작업 상태를 쓰고 평가 판정은 `pass`, `fail`, `inconclusive`를 쓴다. AI의 추천만으로 팀 결정이나 제출 상태를 확정하지 않는다.

## 협의·정본 수정·커밋 규칙

팀 협의는 모든 미확정 사항을 합의하기 위한 절차가 아니다. **다른 TASK가 그 의미·인터페이스·상태·완료 조건을 전제로 작업하거나 판단해야 하는 항목만 합의 대상으로 둔다.** 담당자 내부의 구현 방식, 문서 표현, 쉽게 되돌릴 수 있는 기본값은 해당 담당자가 결정한다. 합의가 되지 않은 항목은 억지로 확정하지 않고 미합의·미확인으로 남긴다. 그 차이가 제품 범위·필수 요구사항·완료 기준·프로젝트 방향을 바꾸는 경우에만 R01 결정 대상으로 올린다.

canonical TASK 원본은 **한 시점에 한 명의 책임자만 직접 수정한다.** 기본 책임자는 해당 TASK의 `owner`이며, 다른 팀원은 자기 workspace·daily·회의 기록 등에서 근거·차이·수정 제안을 남기고 TASK owner가 이를 정본에 반영한다. 소유권을 넘기거나 R01이 범위·결정 때문에 직접 수정해야 하면 그 사실을 명시하고 동시에 같은 TASK 원본을 편집하지 않는다. 이 규칙은 파일 잠금 제도를 도입하려는 것이 아니라, 같은 정본을 서로 다른 의미로 동시에 수정하는 일을 막기 위한 최소 운영 규칙이다.

일반 커밋 메시지는 **`<종류>(<대상>): <실제 변경 요약>`** 형식을 권장한다. 종류는 `docs`, `feat`, `fix`, `test`, `refactor`, `chore`, `merge` 정도로 제한하고, 대상은 `TASK-005`, `R03`, `ops`처럼 변경 범위를 짧게 적는다. 예: `docs(TASK-004): record app source constraints`, `fix(TASK-006): preserve unknown state in APP-C3`. 가장 중요한 기준은 **메시지가 실제 diff의 주된 변경과 일치하는 것**이며, 설명을 위해 긴 메시지나 별도 티켓 번호를 강제하지 않는다.

## 프로젝션 생성

담당자가 원본을 갱신한 뒤 `uv run --no-project python tools/project_docs.py`로 PROJECT·CURRENT·EVAL·검토 화면·제출물·ADR을 생성한다. `--check`는 데이터 검증과 생성 문서의 최신 여부를 검사한다. 생성 도구는 문서 동기화를 확인하며 제품의 조사 품질은 EVAL에 따른 실제 실행으로 판정한다.

생성 문서의 첫머리에는 원본과 갱신 명령을 표시한다. 사람이 요약에서 결론·검증·불확실성·결정 요청을 확인하고 상세 원본으로 이동할 수 있게 한다. 프로젝션에서 바꾸고 싶은 내용이 있으면 사람이 `human/INTENT.md` 또는 `human/responses/`에 의도와 판단을 남긴다. AI가 이를 원본에 반영한 뒤 재생성한다.

## 경로와 보존

새 디렉터리는 소문자 영어 이름으로 만들고 README에 용도·기준 원본·관련 링크·갱신 담당을 둔다. AI 원본은 `artifacts/`, 사람이 보는 검토 화면은 `review/`, 제출 상태 인덱스는 `submissions/`, 교육 과정의 실제 필수 제출물은 `stepN/`에 둔다. PROJECT·CURRENT·EVAL·TASK는 루트 진입점이다.

문서를 이동하거나 형식을 바꾸면 링크를 함께 갱신한다. 원래 상태와 출처는 이관된 데이터에 남긴다. 대체된 기준본은 `archive/`에서 대체 경로와 함께 보관한다. 제출받은 원본은 내용과 바이트를 유지한다. 개인 일일 상태와 회의 기록은 기존 경로에서 사실·담당·날짜·후속 작업을 기록한다.

공개 범위는 [공개 저장소 운영 안내](public/공개_저장소_운영_안내.md)를 따른다. 비밀값·개인 연락처·비공개 URL을 JSON·실행 로그·프로젝션에도 포함하지 않는다.
