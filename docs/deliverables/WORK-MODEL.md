# 작업 정보 모델 · 중복 최소화 설계

## 설계 선택

**16개 제출물의 목차를 정본으로 만들지 않습니다.** 실제 작업에서 만들어지는 정보를 정보 종류별 정본에 넣고, 문서는 필요할 때 필요한 조각을 합칩니다. ISO/IEC/IEEE 15289의 정보 항목 목적별 구분과 arc42의 유지 가능한 아키텍처 기록 접근을 참고했습니다. 이는 **팀 내부 설계 판단**이며 ISO 인증 또는 교육기관 공식 구조 지정은 아닙니다.

### 권장 정보 영역 (13개, 별도 파일 13개를 강제하지 않음)

| 영역 | 어떤 질문에 답하는가 | 기본 정본/참조 | 최소 기록 |
| --- | --- | --- | --- |
| `problem` | 누가·언제·무엇 때문에 불편한가 | 후보/팀원 제안, TASK | 사용자·상황·기존 대안·잔여 Pain·관측 근거 |
| `requirements` | 해결해야 할 조건과 완료 기준은 무엇인가 | spec/요구사항 | 안정 ID, 중요도, 테스트 가능한 수용 기준 |
| `task` | 누가 어떤 결정을/결과를 위해 일하는가 | TASK, CURRENT | owner, 상태, 대상 결과, 검증·미확인 |
| `interface` | 시스템 경계의 입출력·실패 계약은 무엇인가 | API/tool 계약 | 식별자, input/output, validation, auth, errors |
| `data` | 데이터를 어떻게 구조·관계·접근 제어하는가 | 스키마/ERD | 엔터티, 키, 관계, 저장/삭제/접근 전제 |
| `workflow` | 상태·전이·재시도·종료가 어떻게 작동하는가 | 상태 전이/Run | state schema, edge, guard, failure |
| `architecture` | 구성요소와 결정의 영향은 무엇인가 | 아키텍처/ADR | 구성·경계·의존·대안·제약 |
| `risk` | 무엇이 실패하거나 침해될 수 있는가 | 위협/리스크 기록 | 위험원, 영향, 통제, 잔여 위험, 테스트 |
| `test` | 무엇을 어떤 동일 조건에서 검증할 것인가 | Eval/테스트케이스 | 입력, 기대/기준선, 합격선, 결과 연결 |
| `run` | 실제 어떤 결과를 관측했는가 | Run/로그·Evaluation | 실행 ID, 환경/커밋, 입력·관측·실패·증거 |
| `deployment` | 어떤 버전이 어디에서 동작하는가 | 배포 기록/릴리스 | URL/환경, 커밋, 접근권한, 검증 |
| `decision` | 왜 이 선택을 했고 언제 다시 볼 것인가 | HRESP/ADR | 권한, 대안, 근거, 결정, 재검토 조건 |
| `submission` | 공식 제출·접수 여부는 무엇인가 | current.json + 비공개 대시보드 | 산출물, 파일/링크, 권한, 제출·접수 증빙 |

`submission`은 다른 영역의 기술·내용 진실성을 보증하지 않으며, `test`는 `run`의 대체물이 아닙니다.

## 최소 공통 레코드

`id`, `kind`, `title`, `status`, `owner`, `phase_intent_ref`, `source_refs`, `assumptions`, `uncertainties`, `updated_at`. **필요한 경우에만** `requirement_refs`, `decision_refs`, `run_refs`, `output_refs`를 추가합니다.

**Evidence/claim 구조:** 주장마다 주장·검증 수준·근거 위치(고정 커밋/원본 해시 또는 합법적으로 참조 가능한 URL)·확인 날짜·한계가 연결돼야 합니다. 복잡한 모든 문서를 JSON으로 재작성할 필요는 없습니다. Mermaid, OpenAPI, SQL, 테스트코드, 실행 로그 등 **원래 의미가 살아 있는 형식은 그대로 소유**하고 JSON 정본에는 참조만 둡니다.

## 증거 수준

| 수준 | 표기 | 의미 | 금지 해석 |
| --- | --- | --- | --- |
| 직접 관측 | `observed` | 지정 환경·시점에서 실제 관측 | 일반 사용자 전체에서도 동일 |
| 공식/외부 근거 | `sourced` | 출처가 명시된 문서·공식 안내 | 실기기·실사용에서 확인된 결과 |
| 합성/모의 | `synthetic` | 모의 입력/가상 데이터 시험 | 제품 실측 성능 |
| 가설·추정 | `hypothesis` | 미검증 설명·예상 수치 | 확인된 사실 |
| 미확인 | `unknown` | 자료 부족·조사 불가능 | 조건 불충족 |
| 반증 | `contradicted` | 근거에 의해 주장과 충돌 | 모든 조건에서 영구 거짓 |

개별 주장마다 **유효 범위**, **확인 날짜**, **검증 가능한 원문 참조**가 필요합니다. 링크 하나를 부착했다고 실제 사용자 문제나 AI 품질이 증명된 것은 아닙니다.

## 권한과 변경 전파

- R01은 공통 기준·제출·교차 충돌을 관리하고 각 영역의 owner는 자기 TASK와 실제 근거를 기록합니다. 작은 기술 선택은 담당자에게 위임할 수 있으나 **주제·Must/Done·제품 범위 결정은 R01/팀 결정으로 남깁니다.**
- 기존 TASK/ADR/Phase의 권위 입력은 변경하지 않습니다. 새 작업 정보는 `source_refs`로 원본을 참조합니다.
- 제출본이 참조한 `source_commit`/데이터 버전을 고정합니다. 정본 변경 시 **영향받는 제출물 목록만 재생성**하고, 제출 후 변경은 새 버전으로 생성합니다.
- 근거가 외부에 있어 변경 가능하면 당시 확인 날짜와 가능한 고정 URL/해시를 기록합니다. 권한이 없는 외부 원본은 복사하지 않습니다.

## 하지 않을 것

- 새 데이터베이스/온톨로지/복잡한 이벤트 버스를 필수 조건으로 만들지 않음
- 모든 기록의 양식 일괄 변경·과거 TASK 재작성 없음
- 모든 문서에 같은 목차·엔터티·다이어그램 강제 없음
- 아직 선택하지 않은 제품의 기능·API·DB·모델을 ‘채택’으로 격상하지 않음
