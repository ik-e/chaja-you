# 산출물 품질 및 제출 게이트

> 이 기준은 **팀 내부 검수 계약의 제안**입니다. 강사의 공식 합격 점수/평가표로 표기하지 않습니다.

## 두 개의 독립적 완료 상태

- **내용·근거 수준:** `not_started → draft → structurally_checked → evidence_reviewed → reviewed`
- **제출 상태:** `not_ready → ready → link_checked → submitted → receipt_verified`

작성 완료(`reviewed`)와 대시보드 제출(`submitted`), 강사/매니저 접수 확인(`receipt_verified`)은 서로 다릅니다. 둘 중 하나만 진행돼도 다른 상태를 자동 올리지 않습니다.

## 공통 품질 게이트

| 게이트 | 필요한 증거 | 자동 검사(가능) | 사람 확인(필수) |
| --- | --- | --- | --- |
| G0 근거·목차 | 공식 원본 경로/버전, 제공 양식 대조표 | 원본 ID·참조 존재 | 최신 강사 기준과 별도 제출 예외 확인 |
| G1 구조 | 필수 항목, 문서 ID, 버전, 적용 Phase | 필드·목차 누락, 참조 검증 | 문서 목적에 필요한 정보만 있는지 |
| G2 내용 | 요구/주장/가정/모의/미확인/반증 구분 | 근거 링크·관련 ID·스키마 | 사실과 추정, 강한 대안 이후 잔여 문제 |
| G3 교차 정합성 | 요구↔설계↔테스트, API↔DB, WBS↔상태 | 참조 ID, 중복 ID, 형식·계약 검사 | 설계 결정의 타당성 및 불필요 복잡도 |
| G4 제출 파일 | 생성 버전, 렌더/가독성, 열람 권한 | 파일 존재, 생성 시각·커밋 | 강사 접근, 문서 레이아웃, 링크 열림 |
| G5 제출·접수 | 대시보드 링크 등록, 상태 전환, 접수 관측 | 내부 상태 상충 감지 | 대시보드의 실제 제출·접수 확인 |

**경량 운영:** 5인·8주 프로젝트에는 6개 게이트를 위한 별도 회의 6회가 필요하지 않습니다. PR/제출 전 체크리스트 하나로 묶되, 확인 실패를 `unknown`/ `blocked`로 보존합니다.

## 산출물 유형별 추가 게이트

| 유형 | 추가로 반드시 확인할 것 |
| --- | --- |
| 기획/요구 | 실제 사용자·대안·잔여 문제·수용 기준의 연결 |
| 작업/WBS | 담당·기한·선행관계·이전 일정 보류와 실제 실적 분리 |
| 설계/아키텍처 | 경계·계약·오류·상태·권한·미확정 가정 |
| 테스트 계획 | 케이스·입력·기준선·합격선·환경 |
| 테스트/구현 결과 | 실제 수행 ID·버전·측정·실패·로그·재현 |
| 실행물/배포 | URL/저장소 커밋, 접근/실행 재현, 화면과 동작 일치 |
| 발표/영상 | 증거로 설명하는 흐름, 현재 버전과 수치 일치, 재생/열람 |

## AI 사용 원칙

**허용:** 공식 목차 차이 검사, 누락·문서 간 불일치 탐지, 초안 생성, 링크/ID/스키마·표 검증, 결과 로그 요약, 피드백 대응표 생성.

**허용 안 됨:** 실제로 안 한 인터뷰/시연/테스트 수치 생성, 가상의 통과율을 실적에 편입, 모델의 자체 점수만으로 제품 가치 승인, 강사의 미확인 규칙을 확정. AI 출력은 검토 대상이며 근거의 대체물이 아닙니다.

### 출력 품질 판정

- `pass`: 해당 게이트 증빙 확인
- `fail`: 필수 조건 위반·모순
- `inconclusive`: 필요한 확인 또는 실행 미완료
- `not_applicable`: 실제 제품·기술 범위에 해당 없음(사유 필수)

G0 또는 G4/G5가 미확인이면 **‘공식 제출 완료’** 또는 ‘전 양식 합격’을 선언하지 않습니다.

## 현재 잠정 제출 트랙에 적용

11/20 전에는 기존 찾아you 기획을 사용하여 Step 1~2를 작성하되 **잠정/보류** 상태를 표기합니다. 기술·기능은 실제 채택과 별도로 `proposed`로 기록하며, 토요일 이후 제품 방향이 달라지면 G2/G3를 재검토합니다. 결과 보고서는 실제 Run 데이터가 생기기 전까지 G2 결과 판정을 할 수 없습니다.
