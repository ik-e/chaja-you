## 1. 서비스 정의

### 서비스 정의 (원본 DOCX 샘플 구조)

| 항목 | 내용 |
| --- | --- |
| 서비스명 | 찾아you — **현재 제품으로 미선정**, Step1·2 제출 대응에 재사용하는 과거안 |
| 타깃(가설) | Android 집중 앱 두 후보를 조건별로 비교하는 개인. 실제 사용자의 발언·인터뷰 없음 |

| 핵심 가치(가설) | 후보×조건별 verdict·evidence·source와 확인 시각, 실패·미확인 이유를 함께 전달 |

| 결정 상태 | 11/21 팀 주제 채택/보류 목표. **강사·매니저에게 방향 공유**, 구체 승인/마감 연기 확정 아님 |

### 사용자의 문제를 한 문장으로

**검증 전 가설:** 두 앱의 오프라인 타이머 같은 필수 기능을 비교하는 사용자는 일반 검색·앱 공식 설명·범용 AI를 써도 조건별 출처/시점과 미확인 사유를 재검토할 수 있다.

**단정하지 않는 것:** 기존 서비스가 이를 해결하지 못한다는 주장, 사용자가 실제로 시간을 절약한다는 주장. 경쟁 우위와 수요는 아직 관측하지 않았습니다.

### 페르소나 및 Before / After — 가상 시나리오

가상의 사용자는 두 개의 집중 앱(PomoToki, Focus To-Do)을 선택했고, **오프라인 타이머 필수 / 무계정 선호**로 비교하려 합니다. 구체적 인구통계·선호 빈도는 확인하지 않았습니다.

| 단계 | Before: 검색·공식 안내·범용 AI | After: 찾아you 설계안 | 검증 지표 |
| --- | --- | --- | --- |
| 요청 | 대상·조건을 다시 나열하고 대조 | 한 번에 targets/criteria를 구조화 | 조건 누락, 재입력 수 |
| 조사 | 자료 출처의 접근 성공/실패를 수작업으로 확인 | 허용 자료만 조회하고 접근 상태 기록 | 출처 확인 가능 비율 |
| 판정 | 결론과 근거가 어디서 나왔는지 재확인 | verdict→evidence→source를 조건별 연결 | 잘못된 확정 판정 수 |
| 불확실성 | 앱 버전·기기 차이 등 사후 확인 | unknown/partial/failed로 구분 | 미확인 사유 재인식률 |

### 기존 대안과 잔여 검증 질문

| 이미 존재하는 대안 | 해결하는 부분 | 아직 조사해야 할 문제 |
| --- | --- | --- |
| 공식 앱 안내 | 제공자가 명시한 기능·제약 | 기기·버전별 동작과 공식 설명의 차이 |
| 검색 | 다양한 공개 설명·사용 경험 | 같은 조건의 출처 시각·상충 여부 정리 부담 |
| 범용 LLM | 비교·요약을 빠르게 생성 | 출처 연결·미확인·잘못된 확정 비율이 실제로 다른가 |
| 직접 기기 시험 | 가장 직접적인 관찰 | 기기/버전이 없을 때의 확인 비용과 한계 |

현재는 **측정 가능한 잔여 Pain 가설**만 있습니다. 각 대안을 실제로 비교한 결과는 없습니다.

### 성공 기준·측정 방법

| 기준 | 분모·계산 또는 관측법 | 현 수준 |
| --- | --- | --- |
| 조건 판정 정확성 | 독립 정답이 있는 후보×조건 중 일치 판정 수 / 판정 가능 수 | 실측·기준선 없음 |
| 미확인 처리 | 증거 부족 케이스의 unknown 처리율·잘못된 확정 건수 | 합성 사례만 있음 |
| 추적성 | 확정 판정에서 source+locator+retrieved_at까지 도달한 비율 | 구조 검토 |
| 사용 부담 | 같은 자료·조건에서 가장 강한 대안과 작업 완료 시간/재확인 수 비교 | 사용자 테스트 없음 |
| 동적 작업 이점 | 동일 모델·도구·예산의 B0 vs D0 호출 수/판정 품질 비교 | 비교 실행 전 |

**평가 계획:** 합성 케이스 → 허용된 실제 자료와 필요한 기기 확인 → 강한 대안과 동일 과제 비교. 수치 목표/기준선은 시험 설계·정답 자료 확보 후 사전 확정합니다. 수치나 실제 성과를 만들어 넣지 않습니다.

### 일정·역할·리스크

현재 R02~R05 후보 조사(TASK-022~025), R01 운영·제출(TASK-026~027)는 기존 할당이며 **이 기획서로 새로운 구현 TASK를 발행하지 않습니다.** Step2 마감은 11/20, 주제 선택/보류 목표는 11/21, 최종 제출은 2027/1/4입니다. 위험은 기존 서비스로 충분히 해결될 가능성, 공개 자료 이용 제약, 제품 미선정·일정 충돌, 실기기/통합 검증 부재입니다.

R01이 강사·매니저에게 **프로젝트 진행 방향을 공유**했다고 알려준 사실을 반영합니다. 특정 기획안·기술·마감 변경을 승인받았다고 해석하지 않습니다.

## 2. 기능 요구사항

**기존 찾아you 잠정 사례의 요구 가설**입니다. 샘플의 ID·기능·우선순위·수용 기준 구조를 따릅니다.

| ID | 기능/우선순위 | 입력·조건 | 사전 검증 가능한 수용 기준 | 증거 |
| --- | --- | --- | --- | --- |
| FR-01 | 요청 구조화 / Must | 지정 대상 2개, 필수·선호 조건 | 유효하면 202와 request_id, 중복/빈 조건이면 422; 응답과 DB의 criteria/targets 일치 | 설계 |
| FR-02 | 작업 선택 / Must | APP-A의 지정 후보 | 불필요한 후보 발굴을 제외하고 task/depends_on/run_if를 조회 가능 | 합성 구조 검토 |
| FR-03 | 작업·부분 결과 상태 / Must | 작업 성공·실패·근거 부족 | task_id 유지, 재시도마다 attempt_id 새로 부여, partial/failed/unknown 구분 | 합성 구조 검토 |
| FR-04 | 근거 연결 비교 / Must | 후보×조건별 결과 | 확정 판정은 request_id·task_id·verdict_id에서 evidence_id/source_id 추적, 없으면 unknown | 설계·실측 전 |

APP-C의 추가/생략/보류는 이전 합성 검증만 있으며, 실제 앱 자료의 분기 성립이 **미확인**입니다. APP-B는 지금 Must가 아닙니다. 요구사항과 API 연결: FR-01/02→API-01/04, FR-03→API-02/04, FR-04→API-03. **Step2 [공통 계약](contract.json)을 단일 필드 의미 기준**으로 사용합니다.
