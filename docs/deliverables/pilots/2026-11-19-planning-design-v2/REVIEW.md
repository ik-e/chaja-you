## 5. 한계 및 채택 조건

- [Python 검증기](../../../../tools/validate_planning_design_model.py)는 작성해 두었지만 **이 세션에서는 실제 Python 실행을 하지 않았습니다.** 저장소 체크아웃 환경에서 실행해야 하며 CI 성공으로 오인하면 안 됩니다.
- 자동 검증은 ID·필드형·관계의 구조적 검증이며 실제 사용자 Pain·대안 우수성·정책 적합성·설계 타당성을 보증하지 않습니다.
- CAND-016의 후속 설계는 모형을 검증하는 가상 예시로서 실제 구현이나 승인되지 않았습니다.
- 공식 16개 산출물의 목차 전체를 검증하지 않았습니다. 문서 투영 6개는 예시 연결뿐입니다.
- 실제 제품 선정 이후 승인된 시나리오 하나를 실제 FR/NFR→데이터/상태/계약→테스트→문서로 추적해 설계 누락과 중복을 검토해야 합니다.
- 새 워크플로 엔진·복잡한 의존성 DB·전면 스키마 이관은 기본 요구가 아닙니다.

- 중요한 결정을 상위부터 세분화하는 L0~L7 순서와 유보 항목이 5인·8주 프로젝트에 충분히 가벼운가?
- L3에서 업무 용어/핵심 규칙을 먼저 합의하는 것이 L4 컴포넌트 책임 충돌을 줄일 것인가?
- 컴포넌트와 물리 배포를 구별했을 때 현재 요구를 만족하는 더 단순한 구현 방식은 무엇인가?
- 실제 승인된 유스케이스 1개에서 화면·데이터·API·상태·검증·문서 관계를 추적할 때 빠진 개념이 있는가?

**반영 정책:** 이 기록은 Draft PR의 설계 제안·검증 기록일 뿐이며 Human Intent/Phase·실제 제품 범위·TASK·WBS·제출 상태를 변경하지 않는다.

## 9. 설계 전용 V4 — 수준별 검증·시험 설계 통합 (2026-11-19)

### 설계 범위 재정렬

본 대화에서 R01이 정의한 목적은 AI 작업 운영 절차가 아니라 **사용자 문제 → 제품 요구 → 도메인/경계 → 상위 해결 전략 → 논리 실행 단위/컴포넌트 → 상태/데이터/API·UI/보안·배포 → 정합성 확인**이라는 설계 정보의 의존관계입니다. 이전 AI 운영 플레이북은 기록으로만 보존하고, [README](../../README.md)의 기본 진입점을 [설계 전용 모델](../../PLANNING-DESIGN-INFO-MODEL.md)로 교체했습니다.

### 검증·테스트는 설계 단계에서 무엇을 의미하나

- L1 사용자 문제·기존 대안 → 실제 Pain·잔여 손실의 관찰/반증 계획
- L2 시나리오·FR/NFR → 사용자 확인 방법·수용 조건·테스트 데이터의 종류
- L3 도메인·시스템 경계 → 업무 불변식 반례·신뢰 경계/권한 검토
- L4 해결 전략·실행 단위·컴포넌트 → 품질 대안 평가·요구→책임 및 단위/통합 시험 대상
- L5 상세 설계 → 상태 전이·무결성·API/UI·오류·성능/보안/복구 시험 설계
- L6 정합성 → 요구/컴포넌트/상태/데이터/API/UI/시험 계획의 추적·누락·모순 검토
- L7은 실제 구현·시험 실행·문서 제출로 **전달하는 경계**로서 설계의 추가 수준이 아님.

각 [모델 JSON](../../planning-design-info-model.json)의 17개 세부 단계와 L0~L7에 `verification_design`을 추가했고 `IT-20`의 속성에 검증 종류·설계 수준·검증 대상·테스트 데이터/환경 계획·실행 구분을 확장했습니다. 자료는 별도 문서나 테스트 결과를 자동 생성하지 않습니다.

### 검증 상태

- GitHub 최신 설계 변경의 [AI 구조 검증 워크플로](https://github.com/ik-e/chaja-you/actions/runs/44453429945): **completed/success**.
- 같은 커밋의 [기존 문서 검사 워크플로](https://github.com/ik-e/chaja-you/actions/runs/44453429946): **completed/success**.
- 첫 검사는 모든 판단 단계의 검증 질문·방법·계획 ID 및 `not_run` 구분, 설계 수준별 검증 계획, 기존 구성요소/업무 상태 계약을 검사합니다.
- 이 결과는 **모델 구조의 기계 검증**이며 사용자 Pain의 실재, 선택한 아키텍처의 우수성, 실제 단위/통합 테스트 실행, 제품 효과를 증명하지 않습니다.

### 남은 의미적 평가

R01 검토에서 실제 제품의 대표 시나리오를 사용해 각 단계에서 필요한 설계 항목과 검증 질문이 누락·중복되지 않는지 확인해야 합니다. 요구사항 하나에서 하위 구성요소/계약/검증 계획까지 추적한 결과에 따라 실제 모델을 조정합니다. 현재 CAND-016은 **비채택 가상 사례**이며 실제 테스트 결과는 여전히 `not_run`입니다.

### 탄력성 수용 조건

1. 앞선 업무 정의·요구가 부족해도 **가설/미확인**으로 설계 초안을 작성할 수 있어야 한다.
2. 치명적 제약이나 공통 계약 충돌이 아니면 **영향 대상만 재검토**해야 한다.
3. 상세 상태·데이터·API·UI 초안은 병렬로 작성하고 **설계 기준선 합류 시** 공통 계약을 대조한다.
4. 검증 계획이 상세하지 않다고 L0/L1의 문제 탐색을 차단하지 않으며, 실제 시험 수행 기록을 꾸며내지 않는다.
5. 제품 채택·기술·현장 권한의 공식 결정을 사람 승인 없이 확정하지 않는다.
