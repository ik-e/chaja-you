## 3. 오류주입 검증

GitHub 파일을 다시 읽어 **별도 JavaScript 구조 검사**로 정상 데이터 오류 0건을 확인했습니다. 이후 다음 9개 오류를 각각 주입해 탐지되는지 검사했습니다.

| 변형 | 탐지된 오류 |
|---|---|
| 잘못된 요구 우선순위 | enum 위반 |
| 미채택 후보를 adopted로 변경 | 후보 채택 금지 |
| FR→검증 관계 제거 | 검증 연결 누락 |
| FR→상태 변경 영향 제거 | 영향 대상 누락 |
| 단계 PD-00↔PD-11 순환 추가 | 결정 순환 |
| API input_schema 자료형 변경 | 필드형 불일치 |
| 잠정 레코드 필수 job 삭제 | 필수 필드 누락 |
| 유효하지 않은 DLV 문서 ID | 문서 매핑 오류 |
| 사용자→As-Is 핵심 연결 삭제 | 연속 추적 경로 단절 |

**9개 모두 탐지했습니다.** 이 결과는 Python 스크립트 실행 결과가 아니라 같은 GitHub 데이터에 적용한 별도 구조 검사의 결과입니다.

## 4. V1 대비 수정

1. 상위 해결 전략 PD-07A·IT-25를 상세 아키텍처 전에 배치.
2. 상세 설계 4개 분야를 병렬 초안으로 분리하되 PD-10 합류에서 계약 정합성 요구.
3. 실제 유형 관계 49개, 사례 관계 36개, 문서 투영 관계 6개를 구분.
4. 175개 필드에 자료형과 확정 시 필수 조건 부여.
5. FR/NFR→검증 관계가 빠지면 오류 처리.
6. 사용자 외에 도입자·운영자·보호 대상의 관심사를 IT-24로 모델링.
7. 주요 결정의 adopted 상태와 사람의 권한 참조를 분리.

## 5. 한계 및 채택 조건

- [Python 검증기](../../../../tools/validate_planning_design_model.py)는 작성해 두었지만 **이 세션에서는 실제 Python 실행을 하지 않았습니다.** 저장소 체크아웃 환경에서 실행해야 하며 CI 성공으로 오인하면 안 됩니다.
- 자동 검증은 ID·필드형·관계의 구조적 검증이며 실제 사용자 Pain·대안 우수성·정책 적합성·설계 타당성을 보증하지 않습니다.
- CAND-016의 후속 설계는 모형을 검증하는 가상 예시로서 실제 구현이나 승인되지 않았습니다.
- 공식 16개 산출물의 목차 전체를 검증하지 않았습니다. 문서 투영 6개는 예시 연결뿐입니다.
- 실제 제품 선정 이후 승인된 시나리오 하나를 실제 FR/NFR→데이터/상태/계약→테스트→문서로 추적해 설계 누락과 중복을 검토해야 합니다.
- 새 워크플로 엔진·복잡한 의존성 DB·전면 스키마 이관은 기본 요구가 아닙니다.
