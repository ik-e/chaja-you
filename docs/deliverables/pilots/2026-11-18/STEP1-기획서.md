### 사용자 문제와 대안 이후 잔여 Pain

**타깃은 검증 전 가설**입니다. 조건이 많은 Android 앱을 비교해야 하는 사용자가 PomoToki/Focus To-Do를 대상으로 오프라인 타이머 필수·무계정 사용 선호를 확인하는 상황을 대표 사례로 둡니다.

기존 대안인 일반 검색, 공식 앱 문서, 범용 LLM 조사, 실기기 확인으로도 많은 조건을 확인할 수 있습니다. 다만 출처별 시점과 앱 동작이 달라질 때 **대상×조건별 충족/미충족/미확인 판단을 근거와 함께 재검토해야 한다**는 잔여 부담이 있을 수 있습니다. **이 가설은 직접 사용자 관찰로 입증되지 않았습니다.**

### 핵심 기능과 MVP 경계

| 사례 | 해야 할 일 | 현재 상태 |
| --- | --- | --- |
| APP-A(이전 Must) | 지정 후보 두 개에 대해 조건별 판정과 출처·근거 링크 제공, 신규 후보 발굴 생략 | 문서·합성 연결 점검. 실제 통합 미실행 |
| APP-C(이전 Must) | 중간 판정에 따라 발굴 추가/생략/보류 | 합성 분기 검사. 실제 자료에서 둘 다 미충족하는 조건은 미확인 |
| APP-B(후순위) | 지정 후보 없는 요청에서 탐색 | 선택 여부 미정 |

요청→작업→시도→출처→근거→판정→결과의 공통 의미는 재사용 후보지만, 앱의 조건·출처·분기 규칙은 새 주제로 자동 복사하지 않습니다.

### 기대 효과·검증 질문

고정 흐름(B0)과 작업 선택 흐름(D0)을 **동일 입력·도구·모델·예산**에서 비교하는 것을 제안합니다. 조건 누락·근거 연결 정확도·미확인 처리·불필요한 호출·완료 시간·비용을 측정합니다. 현재 실측 개선 수치와 사용자 효용은 없습니다.

R03 ECRM, R05 메뉴 선택 등은 과거 멘토 검토 후보였을 뿐 채택 제품이 아닙니다. 11/21 결정 전에는 후보 간 대안·반증 수준을 별도로 관리합니다.

## 2. 기능 요구사항

이전 APP-A/C 제출용 사례에 한정한 기능 요구 **가설**입니다. 다음 주제의 확정 기능은 아닙니다.

| ID | 기능 | 우선순위(이전 안) | 테스트 가능한 수용 기준 | 실제 확인 |
| --- | --- | --- | --- | --- |
| FR-01 | 요청 구조화 | Must | 플랫폼·대상·필수 조건·선호·발굴 조건을 분리하고 정보 부족 시 미확인 처리 | 명세 |
| FR-02 | 요청별 작업 선택 | Must | 지정 후보 APP-A에서는 후보 발굴을 계획하지 않고 선행 관계가 있는 작업 생성 | 합성 구조 검토 |
| FR-03 | 상태/조건부 분기 | Must | APP-C의 후속 조사 추가·생략·보류 이유와 실패를 구분 기록 | 합성 사례 |
| FR-04 | 근거 연결 결과 | Must | verdict→evidence→source 및 확인 시점 연결, 근거 없으면 미확인 | 설계·합성, 실제 UI 미검증 |

**교차 연결:** FR-01~02는 잠정 API의 요청·작업 계약에, FR-03은 task/attempt 이력에, FR-04는 source/evidence/verdict 관계에 대응시켜 Step2와 정합성을 확인합니다. 이는 구현 승인이나 통합 시험 통과를 뜻하지 않습니다.

**재검토 조건:** 11/21 다른 제품 방향이 채택되면 사용자 요구·선별된 Must 기능을 **새로 정의**하고, 기존 FR은 역사적 참조로만 유지합니다.
