# 실제 사용 예 · 2트랙과 AI 활용

## 예시 A · 11/20까지 잠정 API·DB 제출

1. 기존 찾아you 원본(기획서 JSON·WBS·기존 REQUEST/TASK/Source/Evidence 설계)에서 **검증된 기록만** 참조합니다.
2. 현재 미선정/구현보류 [Phase](../human/phase-intents/PHASE-20261118-01.md)를 입력으로 사용합니다.
3. AI가 [DLV-03](registry.json) API 계약 초안과 [DLV-04](registry.json) DB 관계를 같은 사용자 흐름/ID로 생성합니다. **가설 기술은 `proposed`**, 실제 없는 API/테이블은 `not_implemented`입니다.
4. G0: 공식 목차의 추가 필수 항목 대조, G1/G3: API/DB 상호 참조·오류·권한 검사, G4: 제출용 파일의 가독성·열람 검사.
5. R01은 서식/제출 링크·상태/접수의 사실 여부를 관리합니다. R05는 필요시 기술 계약의 불일치만 짧게 검토하며 기존 제품 구현을 재개하지 않습니다.

**결과:** 제출할 수 있는 완성도 있는 *형식*을 재사용하되, 내부 실제 제품 선정은 이 작업으로 확정하지 않습니다.

## 예시 B · 토요일 이후 신규 제품 선정

1. 새 결정/Phase가 기록되면 `problem`·`requirements`부터 교체하고 이전 찾아you 문서/근거는 당시 스냅샷으로 보존합니다.
2. 후속 `interface`/`data`/`workflow`의 가정과 실제 후보를 업데이트합니다.
3. API-DB, 요구사항-테스트 등의 연결을 확인하여 **관련된 제출물만 다시 생성**합니다. 기존 제출본과 변경된 버전을 구분합니다.
4. 새 제품에서 멀티에이전트가 필요하지 않으면 역할 수를 억지로 늘리지 않고, **교육 과정의 요구 산출물**과 실제 제품 범위 사이의 차이를 강사에게 확인합니다.

## 예시 C · AI가 결과서를 쓰는 경우

- AI가 입력 가능한 자료: 실행 ID, 테스트케이스, 실제 요청/응답·오류 로그, 커밋, 환경, 관측값.
- AI가 할 수 있는 일: 테스트표 구조화, 누락 검출, 합격선 비교, 요약·시각화.
- AI가 하면 안 되는 일: 없는 실행 로그 생성, 가상 성능 수치를 실제 결과로 표기, 자체 검증만으로 제품 완료 선언.
- 실행이 없다면 `not_run`, 일부만 있다면 `inconclusive` 및 **추가 시험 요구**를 기록합니다.

## 비용 제어

- 모든 영역에 같은 수의 문서를 만들지 않습니다. 기존 TASK·JSON·ADR·Run/Evaluation과 상호 참조가 충분하면 별도 문서 생성을 생략합니다.
- 16개 제출물 중 **공식 목차가 확인되지 않은 항목**은 무거운 내용을 만들지 않고 조사·목차 매핑 상태만 보존합니다.
- R01의 승인 병목을 피하기 위해 **문서 형식·검사 로직은 자동화**, 콘텐츠 정확성·제품 방향·제출 상태만 사람이 최종 확인합니다.
