# 작업 정보 → 공식 제출물 프로젝션 계약

## 기본 원리

**정본 Work Record → 공식 목차 매핑 → 문서 생성 → 기계 검사 → 사람 검토 → 공식 제출**. 16개 산출물은 각각 고유한 목적·검증 근거가 있고, 동일한 기술 용어가 나타난다고 동일 내용을 여러 곳에서 직접 수정하지 않습니다.

### 출력 계약

각 제출물 생성 작업에는 다음 입력/출력이 필요합니다.

| 입력 | 내용 |
| --- | --- |
| 산출물 ID | [registry.json](registry.json)의 `DLV-01~16` |
| 양식 출처 | 공식 원본 URL/확인 시점/고정 버전; 교육 예시인지 필수 양식인지 구분 |
| 원본 매핑 | `work_domains`에서 실제 정본 자료를 선택, 원본 경로/commit/ID 기록 |
| 적용 Phase | 현재 프로젝트 주제 미선정/잠정 제출/채택 여부 |
| 주장 근거 | 관측·문서 출처·합성·가설·미확인을 분리 |
| 제외/보류 | 정보가 없거나 아직 해당 기술을 사용하지 않을 경우 `N/A` 또는 `미확인` 사유 |

각 생성 출력에는 **제목/산출물 ID/기준 커밋/작성 상태/원본 참조/기준일/검증 결과/제출 파일 위치**를 메타정보로 연결하되, 강사 제출 양식의 표지 형식을 방해하지 않습니다.

## 예시 매핑

| 작업 정본의 사실 | 제출물에 투영되는 위치 | 하나의 원본 유지 |
| --- | --- | --- |
| 사용자 상황·고통·기존 서비스 비교 | 기획서·중간 발표·최종 발표 | `problem` |
| FR/NFR·acceptance | 기획서·API·테스트·발표 | `requirements` |
| API의 Request/Response/error schema | API 설계·상태 흐름·통합 테스트 | `interface` |
| 엔터티·키·민감정보·관계 | DB 설계·API·보안·배포 | `data` |
| 에이전트 상태/전이/회복 가드 | 상태 전이·협업·Auto-Healing 결과 | `workflow` |
| 도구 권한·프롬프트 주입 위험 | 가드레일·통합 테스트·아키텍처 | `risk` |
| 실제 run 로그·eval verdict | 자기 성찰 결과서·통합 시험·발표 | `run` + `test` |
| 릴리스 버전/접속 URL | 웹 앱·배포 설계·소스코드·시연영상 | `deployment` |

**예시**: 후보 R03의 실사용 Pain이 검증되지 않았으면 기획서·발표 모두 `가설/미확인` 상태를 전달해야 하며, 어느 문서에서도 `검증됨`으로 자동 격상시키지 않습니다.

## 공식 목차 대조 규칙

1. 원본에서 제공된 산출물별 제목/필수 목차/표/파일 형식/제출 방법을 확보합니다. **교육용 예시는 참고**이므로 강사 제공 공식 양식인지 구별합니다.
2. [official-outline-template.json](official-outline-template.json)에 필수 항목을 기록하고, 어떤 `work_domain` 또는 `source_ref`가 이를 충족하는지 연결합니다.
3. 누락된 항목은 `missing`으로 표시합니다. 강사의 필수 항목을 임의로 삭제하거나 일반 목차로 바꾸지 않습니다.
4. 검증 후 제출용 파일을 생성합니다. 현재 `project_docs.py`는 Step1 등 일부 프로젝션만 지원하므로 **16개 전체 자동 생성은 아직 구현되지 않았습니다.**
5. 제출 전에 [QUALITY-GATES](QUALITY-GATES.md) G0~G5를 적용하고 실제 대시보드 접수 상태를 별도 확인합니다.

## 최소 도입 순서

- **G0:** 16개 산출물의 명칭/기한과 01~12 교육 예시의 목차를 확인; 공식 추가 목차는 확인 전 `unverified`.
- **Step 1~2:** 현행 JSON 정본 + 기존 기술 가정으로 필요한 입력만 만들고, 잠정 문서를 조합해 정합성 검사.
- **Step 3~5:** 테스트·Run·릴리스 정보가 실제로 생길 때 관련 정보를 붙여 문서 생성.
- **발표/영상:** 기존 정보 중 실제 증거가 있는 부분만 스토리텔링/시연에 재활용.

## 상태 변경 전파

`source_version`이 바뀌면 같은 정보를 사용하는 산출물의 `mapping`만 최신화하거나 'stale'을 표시합니다. 이미 제출된 출력 파일을 몰래 덮어쓰지 않고, 수정본 버전과 수정일을 기록하여 강사 피드백과 연결합니다.

## 비목표

- 각 산출물마다 별도 도메인 DB·온톨로지·워크플로 엔진을 만드는 것
- 자동 생성된 Markdown 자체를 진실의 정본으로 삼는 것
- 결과/보안/사용성 평가를 AI 텍스트 생성으로 대체하는 것
