## 이미 받은 개별 피드백

### R01

이미 유사한 서비스와 기능들이 존재하므로 더 많은 조사와 기존 서비스에서 남은 페인 포인트를 찾는 방향으로 문제 정의를 구체화한다.

- 기능이 존재하지 않는다는 전제로 차별화를 만들지 않는다.
- 기존 서비스가 이미 해결하는 부분을 먼저 확인한다.
- 기존 서비스를 사용해도 남는 실제 사용자 고통이 무엇인지 추가 조사한다.
- 남은 문제의 강도와 반복성은 실제 사용자/비교 검증 전까지 가설로 둔다.

### R02

타겟 유저와 페인포인트를 더 구체적으로 좁힌다.

- '20대 후반~30대 초반'보다 **결혼 적령기**처럼 문제 상황이 드러나는 표현으로 명확히 한다.
- 사용자가 가지지 못한 역량이나 일반적인 현상 자체를 페인포인트로 두지 않는다.
- 사용자가 실제로 겪는 구체적인 고통을 정의한다.
- 서비스가 그 고통을 직접 줄이는 **진통제(painkiller)** 역할을 하도록 기능을 구체화한다.

### R03

범용 타겟과 실제 인터페이스/사용 상황의 차이를 다시 본다.

- 처음 가정과 달리 실제 인터페이스 방식 때문에 타겟이 더 좁아질 수 있으므로 실제 사용 흐름에 맞춰 타겟을 재정의한다.
- 기존 서비스가 특정 방식을 변경하지 않은 데에도 이유가 있을 수 있으므로 기능 부재만으로 문제를 정의하지 않는다.
- 부동산 주제는 데이터 접근·품질과 여러 부수 제약 때문에 검증·구현 난도가 높을 수 있으므로 문제 가치와 별도로 현실적인 제약을 확인한다.

## R04·R05 적용 기준

R04와 R05는 아직 위와 같은 개별 피드백을 받지 않았으므로, R01~R03에서 공통으로 드러난 기준을 적용해 자기 기획안을 구체화한다.

R05의 기존 가전안은 자료 불일치라는 **현상**과 실제 구매자가 겪는 **고통**을 분리하고, 가격비교·제조사 안내·상담·범용 AI 이후에도 남는 페인포인트를 확인한다.

## 공통 완료 기준

각 기획안은 다음을 3~5분 안에 설명할 수 있어야 한다.

1. **Target User** — 실제 문제를 겪는 상황·목적·현재 행동까지 드러나는 사용자
2. **Pain Point** — 역량 부족이나 현상이 아니라 시간·비용·불안·반복 행동·실패 등 실제 고통
3. **Current Alternative** — 현재 어떤 서비스·도구·사람·수작업으로 해결하는지
4. **Remaining Pain** — 기존 대안이 해결하는 부분을 인정한 뒤에도 남는 문제와 그 대안이 현재 방식을 유지하는 이유
5. **Problem Statement** — 누가, 어떤 상황에서, 무엇을 하려는데, 무엇 때문에, 어떤 고통을 겪는지 한 문장
6. **Painkiller Features** — 위 고통을 직접 줄이는 핵심 피처 2~3개
7. **Evidence / Unknown** — 확인한 사실·관찰·반대 근거와 아직 검증하지 않은 가설 분리

## 독립성과 범위 경계

- 공통으로 공유하는 것은 **평가 기준**이며 각 팀원의 답을 통일하지 않는다.
- R01의 상위 비전이나 현재 APP-A·C에 맞추기 위해 문제를 억지로 선택하지 않는다.
- 현재 제출용 기획서·WBS와 기존 MVP는 이번 구체화만으로 자동 변경하지 않는다.
- 5개→2개 압축 후 멘토 피드백과 사람 권위 결정을 거쳐 실제 제품 범위·MVP·작업 계획 변경 여부를 결정한다.
- R04는 이전 TASK-015 작성 당시 휴가 상태였으나 이번 라운드에서는 복귀해 동일 기준의 문제 정의 작업에 참여한다.
