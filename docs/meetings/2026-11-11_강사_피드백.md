## 피드백 요약

강사님 피드백은 단순히 앱을 더 많이 찾는 것보다 **사용자의 목적과 선호를 파악해 검색 순위가 낮더라도 적합한 앱을 찾아주는 경험**을 차별화 방향으로 검토하자는 내용이다. 앱 탐색부터 구현하고, 개인화·기억을 이어 붙인 뒤 다른 도메인으로 확장하는 단계적 접근도 공유했다.

이 기록은 피드백과 검토 아이디어를 정리한 것으로, 구현 기능이나 기술 결정이 확정됐다는 뜻은 아니다.

## 제안된 방향

### 검색 순위 밖의 앱도 사용 조건에 맞춰 발굴

인기순이나 검색 상위 결과만 반복해서 보여주기보다, 사용자가 말한 조건에 부합하면 덜 알려진 앱도 찾아 후보에 포함하자는 의견이다. 목표는 결과 수를 늘리는 것 자체가 아니라 개인 요구에 맞는 앱을 발견하는 것이다.

### 사용자 조건을 파악하는 방법

두 가지 접근이 논의됐다.

- **선택형 질문:** 앱에서 중요한 기능, 광고 허용 정도, 기기, 단순함과 기능성 선호 등을 묻는다. 원문에 약 8개 또는 16개 문항 아이디어가 나오지만 질문 수와 질문지는 확정되지 않았다. 모든 질문을 필수로 하지 않고 건너뛰게 하는 방안도 검토됐다.
- **대화형 확인:** 사용자의 요청을 받은 뒤 꼭 필요한 조건만 대화로 하나씩 물어본다. 긴 설문을 처음부터 작성시키지 않는 방식이다.

두 방식을 어떤 조건에서 사용할지, 질문을 언제 멈출지는 후속 기획에서 정해야 한다.

### 기존 AI 대화 기록 또는 사용자 프로필 활용

사용자가 직접 내보낸 기존 AI 대화 기록에서 관심사와 선호를 정리하는 아이디어가 나왔다. 대안으로 AI가 만든 프로필 초안을 사용자가 확인·수정한 뒤 입력하거나, 사용자가 직접 프로필을 작성하는 방법도 제안됐다. 기록 전체 연동은 부담이나 구현 복잡성이 있을 수 있고, 자동 요약이 틀릴 수 있으므로 사용자 확인·수정·삭제 가능성이 필요하다는 의견이다.

### 개인화 정보의 로컬 저장 검토

초기에는 사용자 기기/로컬 환경 저장을 고려하고 이후 플랫폼 확장을 검토하자는 의견이 나왔다. 로컬 저장과 서버 저장은 동기화·확장성·보안 관리에서 장단점이 다르며, 구체 저장 기술은 정해지지 않았다. 로컬 저장만으로 개인정보 보호 의무가 사라지는 것은 아니며 외부 API 전송과 접근·이용 목적도 함께 검토해야 한다.

### 단계적 개발과 상호운용성

원문은 앱 탐색과 비교의 흐름을 먼저 구현하고, 이후 개인화·기억 기능을 결합한 다음 다른 도메인으로 확장하는 예시를 제시한다. 다른 AI 모델/서비스와 연동 가능한 구조도 언급됐으나 구체 인터페이스나 지원 모델은 미정이다. 단계와 순서는 구현 계획으로 확정된 것이 아니다.

## 기획서와 PoC에 반영할 질문

1. 앱을 찾는 실제 사용자는 어떤 선택 문제를 해결하려는가?
2. 개인화의 핵심 입력을 대화형 질문과 선택형 질문 중 어디서 받을 것인가?
3. “검색 순위 밖의 적합한 앱 발굴”을 어떤 대표 과제와 기준으로 평가할 것인가?
4. 기존 대화 기록을 받을지, 사용자가 확인한 프로필만 입력받을지?
5. 사용자가 저장된 선호를 확인·수정·삭제할 수 있는 최소 범위는 무엇인가?
6. 로컬 저장과 외부 검색/모델 API 이용 사이에서 어떤 개인정보가 밖으로 전송되는가?
7. 다른 도메인 및 모델 연동은 이번 MVP에 필요할까, 장기 구조로만 고려할까?
