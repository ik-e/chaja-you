# 테이블 음성 도우미 — 기획안 초안 v1

> 바쁜 홀 직원 대신, 손님이 테이블에서 묻는 반복 질문에 바로 답하는 음성 도우미
> 작성: R05 · 2026-11-19 · 상태: 초안 (팀 검토 전)

## 2. 타깃

- **매장:** 피크 시간(점심·저녁)에 홀을 1~2명이 맡는 소규모 식당
- **사용하는 사람:** 테이블에 앉은 손님
- **혜택을 받는 사람:** 홀 알바생, 점주

**왜 이 매장인가**
- 음식점업은 인력 부족률이 전 산업 평균보다 높다 (2026년 상반기 음식점업 3.9%, 전 산업 2.4%).
- 인력 채용이 어려워지면서 1~2인으로 운영하는 소형 매장이 대안으로 늘고 있다.
- 홀 인원이 적을수록 반복 질문 하나하나가 일을 끊는 부담이 된다.

---

## 3. 페인포인트

**알바생·점주 쪽**
- 서빙·계산 중에 "화장실 어디예요?", "음식 언제 나와요?" 같은 같은 질문을 계속 받아 일이 끊긴다.
- 바쁠 때 여러 테이블이 동시에 부르면 주문·요청을 놓치기 쉽다. 테이블오더 업체도 "테이블 3곳에서 동시에 부르는" 상황이 매장에서 흔하다고 소개한다.

**손님 쪽**
- 안내문이 있어도 찾아 읽기보다 직원에게 묻는 게 편하다.
- 그런데 바쁜 시간에는 직원을 부르기 어렵고, 불러도 기다려야 한다.
- 직원이 자신을 알아채지 못하면, 매장이 바쁜 상황이어도 무시당한다고 느낄 수 있다.

---

## 4. 문제 정의

> **테이블에서 바로 해결할 수 있는 질문인데도 직원이 직접 와서 답해야 한다.**

기존 테이블오더의 **직원 호출 버튼**은 물·수저·냅킨 같은 **물건 요청**을 받는 기능이다.
"화장실 어디예요?" 같은 **정보 질문**은 호출을 눌러도 결국 직원이 테이블까지 와서 말로 답해야 한다.
이 기획안은 그 **왕복을 없애는 것**이 목표다.

---

## 5. 해결 방안과 핵심 피처

손님이 테이블에서 말로 물으면 바로 답하고, **직원이 필요한 일만 직원 화면으로 넘긴다.**

| 묶음 | 질문 예시 | 답의 출처 | 직원에게 넘기는 경우 |
|---|---|---|---|
| **① 매장 정보** | 화장실 어디예요? / 와이파이 비번? / 주차 돼요? / 남은 거 포장 돼요? | 점주가 처음에 한 번 입력 | 포장 요청(용기 필요), 주차 등록 연동이 안 된 매장 |
| **② 대기 시간** | 음식 언제 나와요? | 주문 시각 + 메뉴별 평균 조리 시간 | 안내한 시간을 넘긴 경우 |
| **③ 메뉴 추천** | 뭐 먹지? / 추천해 주세요 | 메뉴 정보 + 추천 태그 + AI | 알레르기 질문 |
| **④ 차량 번호 등록** | 주차 등록해 주세요 | 손님이 터치로 입력 | 주차 시스템과 연결이 안 된 매장 |
| **⑤ 직원 전달** | — | 위 항목에서 넘어온 요청 | — |

### ① 매장 정보 안내
- 점주가 처음에 한 번 입력한 정보로만 답한다. **입력되지 않은 질문은 지어내지 않고 직원에게 넘긴다.**
- 포장은 "가능해요, 용기는 ○○원이에요"라고 답한 뒤 **"직원을 불러 드릴까요?"**로 이어 간다.

### ② 음식 대기 시간 안내
- **범위로 안내:** 평균 조리 시간 ~ 평균 + 5분
  > "보통 **15~20분** 걸려요. 지금 12분 지났어요."
- **5분은 시작값**이다. 사전 점검에서 실제로 얼마나 늦게 나오는지 보고 조정한다.
- **범위를 넘긴 경우:** 손님에게 사과하고 직원에게 알렸다고 말한다. 동시에 직원에게 알림을 보낸다.
  > 손님 화면: "늦어져서 죄송해요. **직원에게 바로 알렸어요.**"
  > 직원 화면: "3번 테이블이 22분째 기다리고 있어요."

### ③ 메뉴 추천 (기존 R05 키오스크 기획안 v5 그대로)
- 손님이 **"뭐 먹지?", "추천해 주세요"**라고 말했을 때만 시작한다. 기계가 먼저 묻지 않는다.
  > 기계: "지금 끌리는 음식 있으세요? 국물, 매콤한 거, 담백한 거처럼 말씀해 주셔도 돼요."
- 자주 찾는 느낌은 **추천 태그**(#속편한국물, #기름기없는담백함, #매콤한것)로 AI 없이 고른다.
- 태그로 안 되는 말에만 AI를 쓰고, **그 매장 메뉴 안에서만** 고른다.
- **알레르기는 AI가 판단하지 않는다.** 알레르기를 말하면 추천을 멈추고 직원에게 넘긴다.
- **점주가 확인한 메뉴 정보만** 사용한다.

### ④ 차량 번호 등록
- **입력은 터치 키패드로 한다.** 숫자와 글자가 섞인 번호는 소음 속 음성 인식으로 틀리기 쉽다. 입력 후 화면에서 한 번 더 확인한다.
- **주차 시스템과 연결된 매장:** 바로 등록한다.
- **연결이 안 된 매장:** 직원 화면에 "3번 테이블 12가3456 등록 요청"으로 전달한다.
- **삭제 시점**

| 매장 | 삭제 시점 |
|---|---|
| 주차 시스템 연결 매장 | 출차와 동시에 삭제 |
| 연결 안 된 매장 | 계산 완료 시 삭제 (늦어도 당일 영업 종료 시) |

### ⑤ 직원 전달
- 대기 시간 초과, 포장 요청, 알레르기 질문, 답이 입력되지 않은 질문, 연결 안 된 매장의 주차 등록 요청을 직원 화면으로 넘긴다.

### 음성 입력 원칙 (기존 v5 그대로)
- **버튼을 누를 때만 듣는다** (push-to-talk).
- **인식한 말을 글자로 보여 줘서** 손님이 바로 확인하고 고칠 수 있게 한다.
- 말하기가 부담스럽거나 인식이 안 되면 **터치로 입력**하거나 태그·버튼을 누르면 된다.
- 녹음은 저장하지 않는다.

## 6. 기존 서비스와의 차이

| 구분 | 기존 테이블오더 (예: 토스 테이블오더) | 기존 AI (예: 티오더AI) | 이 기획안 |
|---|---|---|---|
| 누구를 돕나 | 손님 → 직원 요청 | 점주의 매장 운영 (메뉴 수정, 배너 등록) | 손님의 질문 → 바로 답변 |
| 처리하는 것 | 물·냅킨·수저 요청, 직원 호출 | 운영 업무 자동화 | 정보 질문, 대기 시간, 메뉴 추천 |
| 직원이 와야 하나 | 요청 물건을 가져다줘야 하므로 와야 함 | 해당 없음 | **답만 필요하면 오지 않아도 됨** |

※ 손님 질문에 음성으로 답하는 기능이 이미 있는 제품은 이번 조사 범위에서 찾지 못했다. "아무도 안 한다"고 단정하지 않는다.

## 7. 실현 가능성 판단

### 7-1. 결론

| 기준 | 판단 | 이유 |
|---|---|---|
| **팀 프로젝트 (데모)** | **높음** | 외부 연동 부분을 자체 화면으로 대신하면 모든 기능을 보여 줄 수 있다 |
| **실제 서비스** | **중간 이하** | 주문 정보와 주차 시스템이 다른 회사 시스템에 있어서, 혼자서는 연결하기 어렵다 |

### 7-2. 기능별 판단

| 기능 | 데모 | 실서비스 | 걸림돌 |
|---|---|---|---|
| ① 매장 정보 안내 | 높음 | 높음 | 거의 없음. 입력된 정보로만 답하면 틀릴 위험이 낮다 |
| ② 대기 시간 안내 | 높음 | **낮음~중간** | 주문 시각이 테이블오더 회사 시스템에 있다. 테이블오더와 POS 연동도 대리점·설치 기사가 API 키를 넣어 주는 제휴 방식이라, 외부 서비스가 바로 가져오기 어렵다 |
| ③ 메뉴 추천 | 높음 | 중간 | 기존 v5 설계를 재사용할 수 있다. 오답·알레르기 안전장치가 필요하다 |
| ④ 차량 번호 등록 | 중간 | **낮음** | 주차 할인 등록은 주차장 운영사마다 시스템이 다르다. 공개된 연동 방법을 이번 조사에서 확인하지 못했다 |
| ⑤ 직원 전달 | 높음 | 높음 | 기존 직원 호출과 같은 구조다 |
| 음성 인식 (공통) | 중간 | 중간 | 여러 사람 말소리와 생활 소음이 있으면 인식 정확도가 떨어진다. push-to-talk, 글자 확인, 터치 대체로 보완한다 |

### 7-3. 가장 큰 위험 3가지

1. **연동 문제 (실서비스):** 대기 시간과 주차 등록은 다른 회사 시스템의 데이터가 있어야 한다. 독립 서비스보다 **기존 테이블오더에 들어가는 기능** 형태가 현실적이다.
2. **경쟁사가 쉽게 따라 할 수 있음:** 테이블오더 1위 업체(티오더)가 이미 AI에 투자하고 있다. 기능 자체보다 **"질문과 요청을 나눠서 직원 왕복을 줄인다"는 설계와 검증 결과**가 차별점이 되어야 한다.
3. **질문 빈도 근거 없음:** 매장에서 어떤 질문을 얼마나 자주 받는지에 대한 공개 데이터를 찾지 못했다. 이 기획안에서 가장 먼저 확인해야 할 근거다.

### 7-4. 프로젝트 범위 제안

기능이 5개라서 우선순위를 나눈다.

| 우선순위 | 기능 | 데모 구현 방식 |
|---|---|---|
| **1순위** | ① 매장 정보 안내 · ② 대기 시간 안내 · ⑤ 직원 전달 | 간단한 테이블 화면 + 직원 화면을 직접 만들고, 주문 시각은 자체 데이터로 대신한다 |
| **2순위** | ③ 메뉴 추천 | 기존 v5 설계(메뉴 25개, 추천 태그 3개)를 재사용한다 |
| **3순위** | ④ 차량 번호 등록 | 직원 화면 전달까지만 구현하고, 주차 시스템 연결은 확장 계획으로 둔다 |

## 8. 아직 확인할 것

| 확인할 것 | 방법 |
|---|---|
| 홀 직원이 가장 많이 받는 질문과 횟수 | 홀 알바 경험자 인터뷰 ("가장 많이 받은 질문 3개"), 피크 시간 관찰 |
| 손님이 직원 대신 기계에게 물어볼지 | 사전 점검에서 직원 호출과 음성 도우미 중 무엇을 고르는지 관찰 |
| 대기 시간 안내의 범위(+5분)가 적절한지 | 사전 점검에서 실제 조리 시간과 비교 |
| 소음 속 음성 인식이 쓸 만한지 | 식당 소음 수준에서 짧은 질문 인식 확인 |

## 9. 예상 반문과 답변

**Q. 화장실 위치는 안내문 붙이면 되지 않나요?**
안내문이 있어도 손님들은 찾아보기보다 직원에게 묻는 경우가 많습니다. 찾는 것보다 묻는 게 편하기 때문입니다. 음성 도우미는 손님이 하던 행동, 즉 **말로 묻는 것**은 그대로 두고 답하는 쪽만 직원에서 기계로 바꿉니다. 실제로 얼마나 자주 묻는지는 직접 확인하겠습니다.

**Q. 옆에 직원이 있는데 굳이 기계한테 물어볼까요?**
한가할 때는 직원에게 물으시면 됩니다. 하지만 홀을 1~2명이 맡는 매장이 늘고 있어서, 바쁜 시간에는 직원을 부르기도 어렵고 기다려야 합니다. 기존 호출 버튼은 물건 요청용이라 화장실 위치를 물어도 직원이 와야 합니다. 이 도우미는 **직원이 오지 않아도 바로 답하고**, 직원이 필요한 경우에만 알립니다.

**Q. 대기 시간 안내가 틀리면 손님이 더 화나지 않나요?**
그래서 딱 떨어지는 숫자가 아니라 **범위(평균~평균+5분)**로 안내합니다. 범위를 넘기면 기계가 사과하고 **직원에게 바로 알려서**, 오래 기다린 손님은 사람이 직접 챙깁니다.

**Q. 왜 하필 5분이에요?**
5분은 시작값입니다. 사전 점검에서 실제로 얼마나 늦게 나오는지 보고 조정하겠습니다.

**Q. 차량 번호는 개인정보 아닌가요?**
맞습니다. 그래서 출차와 동시에 삭제하고, 주차 시스템과 연결이 안 된 매장은 계산 완료 시 삭제합니다.
