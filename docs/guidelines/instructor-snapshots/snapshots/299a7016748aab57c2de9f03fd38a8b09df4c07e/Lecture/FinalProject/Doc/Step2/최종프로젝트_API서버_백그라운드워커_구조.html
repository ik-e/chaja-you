이 자료를 다 보고 나면 할 수 있어야 하는 것

멀티에이전트 + LLM + 외부 API가 섞인 서비스를 "요청 받는 곳"과 "일하는 곳"으로 나눠 설계한다.

① 왜 나누는지 설명한다

LLM 호출을 HTTP 요청 안에서 기다리면 무엇이 깨지는지 말할 수 있다.

② 전체 그림을 그린다

프런트 → API → 큐 → 워커 → LLM/외부 API, 그리고 결과가 돌아오는 길을 그릴 수 있다.

③ 폴더를 나눈다

backend/, agents/, shared/, docker/가 각각 무엇을 담고 어떤 이미지가 되는지 안다.

④ 오토힐링 위치를 안다

재시도·폴백·자동 재시작을 어느 계층에 넣어야 하는지 구분한다.

02
문제 상황

LLM을 API 요청 안에서 그냥 호출하면?

멀티에이전트 한 번 = LLM 호출 여러 번 + 외부 API 여러 번 → 수십 초 ~ 수 분.

# ❌ 이렇게 만들면 안 됩니다
@router.post("/analyze")
async def analyze(body: Req):
    result = await graph.ainvoke(body.dict())
    #  ↑ Supervisor → 진단 → 복구 → 검증
    #    LLM 6번 + 외부 API 4번 … 90초
    return result

사용자는 90초 동안 로딩 스피너만 봅니다. 그 사이에 무슨 일이 생길까요?

  • 타임아웃 — 로드밸런서·프록시(보통 30~60초)가 먼저 연결을 끊음 → 504
  • 새로고침 = 작업 증발 — 브라우저를 닫으면 결과를 받을 길이 없음
  • 서버 재시작 = 작업 유실 — 배포하는 순간 진행 중이던 작업이 사라짐
  • 재시도 불가 — 외부 API가 잠깐 죽었을 때 "나중에 다시"가 안 됨
  • 서버가 막힘 — 무거운 작업이 API 서버 자원을 잡아먹어 로그인·조회까지 느려짐

06
흐름

요청 한 건의 일생 (9단계)

핵심: API는 ②에서 즉시 응답하고 빠진다. 무거운 일은 ④~⑧, 워커가 한다.

FE① 사용자가 "분석 요청" 클릭 → POST /api/v1/jobs

API② 검증 후 DB에 Job 저장 status=queued

API③ Celery로 send_task("agents.run_agent_job", [job_id]) → 202 + job_id 응답

FE④ GET /jobs/{id}/events (SSE) 구독 시작

Worker⑤ Celery 워커가 태스크 수신 → status=running

Worker⑥ LangGraph 실행. 노드가 끝날 때마다 {"type":"step","node":"diagnosis"} 발행

Ext⑦ 외부 API 실패 → 재시도 / 폴백 (오토힐링)

Worker⑧ 결과 DB 저장 status=succeeded + done 이벤트

FE⑨ done 수신 → GET /jobs/{id}로 최종 결과 표시

새로고침해도 괜찮습니다. job_id만 있으면 GET /jobs/{id}로 언제든 현재 상태·결과를 다시 볼 수 있어요.

08
실시간 표시

워커의 진행 상황을 화면에 보여주는 3가지 방법

방식동작장점단점
폴링프런트가 2초마다 GET /jobs/{id}가장 쉬움. 일단 이것부터지연·불필요한 요청
SSE ⭐ 권장서버 → 브라우저 한 방향 스트림. 이벤트가 생길 때마다 pushHTTP 그대로, 구현 간단, 자동 재연결단방향 (요청은 별도 POST)
WebSocket양방향 연결 유지채팅처럼 주고받기가 잦을 때연결 관리·인증·배포 설정이 더 복잡
추천 순서: ① 폴링으로 흐름을 먼저 완성 → ② SSE로 교체해 "에이전트 사고 과정 가시화" 구현
LLM 토큰 스트리밍도 같은 길로 흘려보내면 됩니다: 워커가 {"type":"token","text":"..."} 이벤트를 발행 → SSE로 전달.
09
선택 기준

무엇을 워커로 보내고, 왜 Celery인가

워커로 보낼 작업

  • 멀티에이전트 실행 (LLM 여러 번)
  • 외부 API 여러 개를 엮는 작업
  • 재시도·승인 대기가 필요한 작업
  • 주기 작업 (모니터링·이상 감지) → Celery Beat

API에서 바로 해도 되는 것

  • DB 조회·저장, 로그인
  • 수 초 안에 끝나는 단일 LLM 응답 스트리밍
Celery 용어뜻 (식당 비유)
Broker태스크 메시지가 대기하는 곳 = 주문 레일. 우리는 Redis
Task워커가 실행할 함수 = 레시피. @app.task로 등록
Worker태스크를 꺼내 실행하는 프로세스 = 주방. 컨테이너 여러 개로 확장
Queue태스크를 나누는 줄. 예: agents, monitor
Beat정해진 시각에 태스크를 넣는 스케줄러 = 알람
Flower워커·태스크 상태를 보는 웹 대시보드 (시연·모니터링용)

왜 Celery? 파이썬 백그라운드 작업의 사실상 표준 → 자료·예제가 가장 많고, 재시도·시간 제한·스케줄·모니터링이 모두 갖춰져 있음. (가벼운 대안: arq, Taskiq / 데모 전용: FastAPI BackgroundTasks)

be와 agents를 왜 나누나?

be는 가볍고 빨라야 하고(요청 응답), agents는 무겁고 오래 걸립니다(LangGraph·LLM SDK). 이미지를 나누면 따로 빌드·배포·확장할 수 있고, 에이전트를 고쳐도 API 서버는 그대로 둘 수 있습니다.

shared/에는 무엇을?

양쪽이 똑같이 알아야 하는 것만: 설정(Settings), DB 연결, jobs 테이블 모델과 상태 상수. 빌드할 때 두 이미지에 모두 복사됩니다.

.env는 커밋 금지. LLM·외부 API 키는 be·agents 환경변수로만. 프런트 코드에 키가 들어가면 누구나 볼 수 있습니다.

가장 중요한 규칙

be는 agents 코드를 import하지 않는다

✅ 이름으로 보내기

be는 send_task("agents.run_agent_job", ...)처럼 문자열 이름으로 보냅니다. 그래서 be 이미지에는 LangGraph·LLM 라이브러리가 없어도 됩니다.

✅ 인자에는 ID만

큰 입력(문서·대화 내용)은 DB에 저장하고 태스크 인자로는 job_id만. 재시도·감사 추적이 쉬워지고 브로커가 가벼워집니다.

❌ agents → backend

에이전트 노드에서 FastAPI·Request를 import하면 안 됩니다. 에이전트는 HTTP를 몰라야 단독으로 테스트할 수 있습니다.

예시 코드 ① · API 서버 (be)

Job 만들고 Celery로 보낸 뒤 바로 202

backend/app/api/v1/jobs.py
from fastapi import APIRouter, Depends, status
from app.core.celery_client import celery_client
from app.core.security import current_user
from app.schemas.job import JobCreate, JobAccepted, JobRead
from app.services import job_service
from shared.db import get_db

router = APIRouter(prefix="/jobs", tags=["jobs"])

@router.post("", status_code=status.HTTP_202_ACCEPTED,
             response_model=JobAccepted)
async def create_job(body: JobCreate, db=Depends(get_db),
                     user=Depends(current_user)):
    job = await job_service.create(db, user.id, body)  # ① DB: queued
    celery_client.send_task("agents.run_agent_job",      # ② 이름으로 전송
                            args=[job.id], queue="agents")
    return JobAccepted(job_id=job.id, status="queued")  # ③ 즉시 응답

@router.get("/{job_id}", response_model=JobRead)
async def get_job(job_id: str, db=Depends(get_db)):
    return await job_service.get(db, job_id)  # 상태·결과 조회
backend/app/core/celery_client.py
from celery import Celery
from shared.config import settings

# 보내기 전용 클라이언트
# (태스크 함수는 여기 없음!)
celery_client = Celery(
    "be", broker=settings.redis_url)

포인트

· send_task는 브로커에 메시지만 넣고 즉시 돌아옵니다 (수 ms).
· 태스크 이름 "agents.run_agent_job"은 워커 쪽 @app.task(name=...)와 정확히 같아야 합니다.
· 결과는 Celery가 아니라 DB의 jobs 테이블에서 조회합니다.

예시 코드 ② · Celery 워커 (agents)

워커: 태스크를 받아 LangGraph를 돌리고 진행 상황을 알린다

agents/worker/tasks.py
from agents.worker.celery_app import app
from agents.worker import job_store as js
from agents.worker.events import publish
from agents.graph.build import build_graph
from agents.integrations.base import TransientError
graph = build_graph()                     # 워커 시작 시 한 번만 조립
@app.task(name="agents.run_agent_job", bind=True, max_retries=3)
def run_agent_job(self, job_id: str):
    if not js.claim(job_id):              # queued→running 선점 실패면
        return                            # 이미 처리 중 → 중복 실행 방지
    try:
        state = {}
        for upd in graph.stream(js.get_input(job_id), stream_mode="updates"):
            node, data = next(iter(upd.items()))
            publish(job_id, {"type": "step", "node": node})
            state.update(data or {})
        js.succeed(job_id, state)
        publish(job_id, {"type": "done"})
    except TransientError as e:            # 잠깐의 장애 → 다시
        if self.request.retries < self.max_retries:
            js.mark_retrying(job_id)
            raise self.retry(exc=e, countdown=10 * (self.request.retries + 1))
        js.fail(job_id, e); raise       # 재시도 소진
    except Exception as e:                 # 복구 불가 → 실패 기록
        js.fail(job_id, e); raise       # status=failed + failed 이벤트
agents/worker/celery_app.py
from celery import Celery
from shared.config import settings

app = Celery("agents", broker=settings.redis_url,
             include=["agents.worker.tasks"])
app.conf.update(
    task_default_queue="agents",
    task_acks_late=True,      # 끝난 뒤 완료 처리
    task_reject_on_worker_lost=True, # 워커가
                     # 죽으면 다른 워커가 다시 받음
    worker_prefetch_multiplier=1, # 하나씩
    task_soft_time_limit=540,  # 9분: 예외로 경고
    task_time_limit=600,       # 10분: 강제 종료
    task_ignore_result=True,   # 결과는 DB에
)
agents/worker/events.py
import json, redis
r = redis.Redis.from_url(settings.redis_url)

def publish(job_id, ev):
    r.publish(f"job:{job_id}",
              json.dumps(ev, ensure_ascii=False))

from sqlalchemy import update
from shared.db import SessionLocal
from shared.models import Job

def claim(job_id: str) -> bool:
    """queued/retrying 인 Job만 running으로.
    UPDATE 한 번이라 두 워커가 동시에 와도
    한 명만 성공(rowcount == 1)."""
    with SessionLocal() as s, s.begin():
        res = s.execute(
            update(Job)
            .where(Job.id == job_id,
                   Job.status.in_(["queued", "retrying"]))
            .values(status="running"))
    return res.rowcount == 1

acks_late를 켜면 같은 태스크가 두 번 올 수 있습니다 → 이 선점 로직이 "복구가 두 번 실행"을 막아 줍니다.

Celery 태스크는 동기 함수

워커 쪽 코드(graph.stream, httpx.Client, 동기 DB 세션)는 동기로 작성하는 것이 가장 단순합니다. async 코드를 꼭 써야 하면 태스크 안에서 asyncio.run(...)으로 감쌉니다.

SSE: 워커 이벤트를 브라우저까지

import json
from fastapi.responses import StreamingResponse

@router.get("/{job_id}/events")
async def job_events(job_id: str, request: Request):
    async def stream():
        ps = request.app.state.redis.pubsub()
        await ps.subscribe(f"job:{job_id}")
        try:
            async for msg in ps.listen():
                if msg["type"] != "message":
                    continue
                yield f"data: {msg['data']}\n\n"  # SSE 형식
                if json.loads(msg["data"])["type"] in ("done", "failed"):
                    break
        finally:
            await ps.unsubscribe()
            await ps.aclose()
    return StreamingResponse(stream(),
                             media_type="text/event-stream")

외부 API 래퍼: 타임아웃 → 재시도 → 폴백

agents/integrations/base.py · public_api.py
import httpx
from tenacity import (retry, stop_after_attempt,
    wait_exponential, retry_if_exception_type)

class TransientError(Exception): ...  # "잠깐 기다리면 될 오류"

@retry(stop=stop_after_attempt(3),
       wait=wait_exponential(min=1, max=8),       # 1→2→4초
       retry=retry_if_exception_type(TransientError), reraise=True)
def get_json(client, url, params):
    try:
        r = client.get(url, params=params, timeout=5.0)
    except (httpx.TimeoutException, httpx.NetworkError) as e:
        raise TransientError(str(e)) from e
    if r.status_code == 429 or r.status_code >= 500:
        raise TransientError(f"HTTP {r.status_code}")
    r.raise_for_status()           # 4xx = 내 잘못 → 재시도 X
    return r.json()

def get_crowd(area: str) -> dict:
    with httpx.Client() as c:
        try:
            return get_json(c, PRIMARY_URL, {"area": area})
        except TransientError:
            if cached := cache.get(area):             # 폴백 ① 캐시
                return {**cached, "stale": True}
            return get_json(c, BACKUP_URL, {"area": area})  # ② 백업

오류를 두 종류로 나누기

일시적 (타임아웃·5xx·429) → 재시도할 가치 있음
영구적 (400·401·404) → 재시도해도 똑같음, 즉시 실패

재시도는 두 겹

① 여기(tenacity): 몇 초 안의 짧은 재시도
② 그래도 실패 → TransientError가 태스크까지 올라가 Celery self.retry()로 수십 초 뒤 전체 재실행

폴백 결과는 표시하기

"stale": true처럼 남겨 에이전트·화면이 "최신 아님"을 알게 합니다. LLM도 integrations/llm.py(LiteLLM 등)에 모아 모델 폴백을 한 곳에서.

build.sh와 Dockerfile

docker/build.sh
#!/usr/bin/env bash
# 사용법: ./docker/build.sh            (전체)
#        ./docker/build.sh bike-agents (일부만)
set -euo pipefail
cd "$(dirname "$0")/.."            # 프로젝트 루트로 이동

VERSION=$(date +%y%m%d-%H%M)       # 예: 261119-1650
TARGETS=("$@")
if [ ${#TARGETS[@]} -eq 0 ]; then
  TARGETS=($(ls docker/images))    # 인자 없으면 전부
fi

for name in "${TARGETS[@]}"; do
  dir="docker/images/$name"
  echo "▶ $name:$VERSION"
  docker build -f "$dir/Dockerfile" \
    -t "$name:$VERSION" -t "$name:latest" .   # 컨텍스트=루트
  echo "$VERSION" > "$dir/VERSION"  # 성공했을 때만 기록
done

구현 순서

처음부터 LLM 붙이지 말고, 뼈대부터

1가짜 워커

Celery 태스크 안에서 time.sleep(3) 세 번 + 이벤트 발행만. POST → 202 → 폴링 → done이 돌면 성공.

2상태·DB

jobs 테이블과 상태 머신(queued/running/succeeded/failed) 완성. 새로고침해도 결과가 보여야 함.

3SSE 화면

폴링을 SSE로 교체. 노드 이름이 화면에 하나씩 찍히는 "사고 과정 타임라인".

4에이전트 연결

sleep 자리에 graph.stream(). 에이전트는 노트북/단위 테스트로 먼저 검증한 뒤 붙이기.

5외부 API·힐링

agents/integrations/ 래퍼에 재시도·폴백. 장애 주입 스위치(환경변수)를 만들어 둔다.

6측정·배포

docker/build.sh → start.sh로 배포. 장애 주입 → 감지·복구 시간 로그 → Auto-Healing 결과서.

1~3단계는 LLM 비용 0원으로 끝납니다. 구조가 먼저 돌아가야 에이전트 문제와 인프라 문제를 구분해서 디버깅할 수 있어요.

흔한 실수 체크리스트

☐ API 엔드포인트 안에서 graph.ainvoke()를 기다리고 있다

☐ BackgroundTasks로 멀티에이전트를 돌린다 (재시작 시 유실)

☐ Celery 태스크 인자로 대화 전문·파일 내용을 통째로 넘긴다 → ID만

☐ Job 상태를 DB에 안 남겨서 새로고침하면 결과가 사라진다

☐ docker compose down -v로 DB 볼륨까지 지운다

☐ 모든 오류를 무조건 재시도한다 (400·401도)

☐ 재시도 횟수·타임아웃 상한이 없다 → 무한 루프·비용 폭탄

☐ LLM·외부 API 키가 프런트 코드나 GitHub에 있다

☐ API 서버의 async def 안에서 requests·time.sleep 같은 동기 호출을 한다

☐ 같은 요청이 두 번 들어와 복구가 두 번 실행된다 → 멱등 키

☐ 이미지를 latest로만 관리해 이전 버전으로 되돌릴 수 없다

한 줄 요약: API는 주문만 받고(202), 워커가 요리하고(LangGraph), 진동벨로 알리고(SSE), 납품이 늦으면 다른 길로 간다(오토힐링).
