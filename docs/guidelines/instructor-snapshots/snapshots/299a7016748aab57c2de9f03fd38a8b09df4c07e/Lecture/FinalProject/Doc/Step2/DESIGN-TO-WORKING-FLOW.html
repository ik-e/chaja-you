01 · 연결표

문서마다 같은 사용자 작업을 가리킨다

예시: 사용자가 고른 시간으로 상담 신청하기. 아래 이름·경로·상태는 교육용 예시입니다.

연결할 것예시개발 전에 합의할 질문
요구사항·화면FR-07 / 상담 시간 선택 화면누가 어떤 결과를 원하나요?
APIPOST /api/v1/bookings보낼 값과 받을 값은 무엇인가요?
에이전트·도구book_consultation(slot_id)조회만 하나요, 신청까지 하나요?
DBbookings · slot_id · status저장 성공과 중복을 어떻게 확인하나요?
시험정상 예약 / 다른 사용자 / 중복 클릭무엇이 보이면 완료라고 할까요?
팀 적용: 지금 작성한 문서에서 요구사항 ID·화면·API·도구·테이블·시험을 한 줄로 연결해 보세요.
참고: API 작성법 30쪽 · DB 작성법 20쪽
02 · 공통 계약

이름만 같아서는 연결되지 않는다

입력·출력의 의미와 실패 처리까지 정한 것이 계약입니다.

입력과 결과

  • 입력: 이름·타입·필수 여부·허용값
  • 결과: 결과 ID·상태·업무상 의미
  • 필드가 다르면 API ↔ DB 대응표 작성

ID는 용도로 구분

  • request_id: 요청 추적용인지 명시
  • job_id: 오래 걸리는 작업 조회
  • 멱등성 키: 중복 실행 방지용

실패와 상태

  • 형식 오류·권한 오류·충돌 구분
  • 재시도 가능 여부와 최대 횟수
  • 화면에 보여 줄 안내 문구

담당과 변경

  • 계약 작성·검토·사용 담당 지정
  • 변경 버전과 인계 날짜 기록
  • 변경하면 예시·모의 응답·시험도 갱신
ID 이름은 예시예요. 이미 팀이 정한 이름을 써도 되지만 서로 다른 용도를 한 값으로 혼동하지 않게 해 주세요.
참고: API 작성법 16~22쪽
03 · 모의 연결

실제 LLM보다 먼저, 정해진 응답으로 연결한다

모의 API는 화면·상태·오류를 맞추는 도구입니다. 실제 예약이나 저장 성공의 증명은 아닙니다.

먼저 만들 응답 3개

  • 정상: 결과 ID와 완료 상태
  • 진행 중: 아직 결과가 없는 상태
  • 실패: 오류 코드와 다음 행동

화면 담당이 확인할 것

  • 로딩·성공·실패 화면이 각각 보이는가
  • 중복 클릭·새로고침 시 표시가 맞는가
  • 아직 연결하지 않은 기능이 구분되는가
1. 계약 고정예시 JSON·상태
2. 모의 응답정상·지연·실패
3. 화면 연결표시와 사용자 행동
4. 실제 연동하나씩 교체
이번 단계의 완료: 모의임을 표시한 화면에서 세 상태를 재현하고, 사용한 계약 버전을 기록합니다.
참고: API 서버·워커 구조 25쪽
04 · 응답 방식

작업 시간과 사용자 경험에 맞춰 고른다

모든 기능에 큐·워커·스트리밍을 한꺼번에 넣을 필요는 없습니다.

방식서버와 화면의 약속시험할 것
바로 응답요청 안에서 결과 반환타임아웃·오류·결과 표시
202 접수 + 상태 조회job_id 반환 → 상태·결과·실패 조회작업 소유권·완료·만료·새로고침
스트리밍이벤트를 순서대로 전달종료·오류·연결 끊김 뒤 복구

오래 걸리는 일

LLM 여러 번, 외부 API 조합, 승인 대기 등은 HTTP 대기 시간과 분리할지 검토합니다.

팀이 실제 선택한 구조

기존 구현에 맞춰 결정합니다. Celery·Redis·SSE는 가능한 예시이며 이 실습의 필수 선택은 아닙니다.

참고: API 작성법 28~29쪽 · 워커 구조 10쪽
05 · 상태 읽기

HTTP 성공과 사용자 작업 성공을 구분한다

202는 접수, 조회의 200은 조회 성공입니다. 업무 성공은 작업 상태와 결과로 판단합니다.

응답 예시의미화면에서 할 일
202 · job_id=j-001처리 요청을 접수함접수 표시 후 진행 확인
200 · status=running작업 조회 성공, 처리 중결과를 성공처럼 보여 주지 않기
200 · status=succeeded작업 완료, result 있음결과와 완료 시각 표시
200 · status=failed작업 조회 성공, 업무 실패error와 가능한 다음 행동 표시
404 · not_found없거나 조회가 허용되지 않는 작업팀의 보안 계약에 맞게 안내
재시도도 구분해요. 같은 작업을 다시 조회하는 것인지, 실패한 일을 새로 실행하는 것인지 계약으로 정합니다.
상태 이름은 예시입니다. 참고: API 작성법 29쪽
06 · 실행 경계

모델이 고른 도구도 서버가 확인한 뒤 실행한다

LLM이 인자를 만들었다는 이유만으로 저장·예약·알림을 실행하지 않습니다.

① 입력·허용 도구

필수값·타입·범위를 검사하고, 이 역할이 호출할 수 있는 도구인지 확인합니다.

② 사용자·소유권

사용자의 권한과 대상 데이터가 속한 사용자·기관을 서버가 확인합니다.

③ 필요한 승인

위험하거나 승인이 필요한 업무는 실제 승인 상태를 확인합니다. 모델이 넘긴 승인 ID만 믿지 않습니다.

④ 중복과 저장 결과

이미 처리됐는지 확인하고 저장 성공을 검증합니다. 동시 수정·슬롯 충돌도 DB와 함께 막습니다.

쓰기 요청의 응답이 끊겼다면 이미 저장됐을 수 있어요. 무조건 다시 호출하기 전에 처리 결과와 중복 방지 규칙을 확인하세요.
참고: API 작성법 26쪽 · Auto-Healing 가이드 19쪽
07 · 실제 연동

한 번에 전부 붙이지 않고 확인 범위를 넓힌다

어느 부품까지 실제인지 표시해야 실패한 위치를 찾고 결과를 설명할 수 있습니다.

단계이번에 실제로 연결할 것확인할 결과
A · 화면 계약모의 응답 ↔ 화면입출력·로딩·오류 표시
B · 저장API ↔ 시험 DB행 생성·상태·제약·다른 사용자 차단
C · 외부 연동어댑터 ↔ 실제 허용된 API필드 매핑·출처·시간·제한
D · 모델LLM ↔ 도구 실행 ↔ 결과도구 선택 뒤 실제 업무 완료
공급원 접근이 미확인이라면 모의 연동 성공 / 실제 연동 대기로 적습니다. 실제 키·개인정보는 화면과 로그에 노출하지 않습니다.
참고: DB 작성법 22쪽 · API 작성법 30쪽
08 · 작업 인계

담당자를 나누되 계약과 검수는 함께 본다

폴더 이름보다 어떤 입력을 받아 어떤 결과를 넘기는지가 먼저입니다.

작업넘길 것받는 사람이 확인할 것
화면 ↔ API화면별 입력·상태·예시 응답모의 API로 정상·실패 표시
API ↔ 에이전트입력 스키마·실행 ID·권한 문맥도구 결과와 종료·실패 출력
외부 연동 ↔ DB정규화 필드·적재 기준·출처중복·갱신·만료·오류 처리
개발 ↔ 검토커밋·변경 계약·시험 명령동작 재현·기존 기능 영향

개인별 작업

담당·검토자·인계일·완료 기준을 정하고 대기하는 작업을 일지에 남깁니다.

공통 파일

라우터·설정·스키마·마이그레이션의 취합·리뷰 담당을 정합니다.

09 · 팀 적용 15분

아래는 학습용 연습 결과입니다. 새로운 공식 산출물이나 고정 마감을 추가하는 것은 아닙니다.

기록 칸팀이 채울 내용

재현과 증빙기준 커밋·환경·실행 명령·로그·화면 링크
