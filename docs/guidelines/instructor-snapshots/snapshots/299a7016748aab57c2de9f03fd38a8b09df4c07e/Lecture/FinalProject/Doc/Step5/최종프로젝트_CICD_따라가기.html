용어

CI와 CD, 한 문장씩

CIContinuous Integration · 지속적 통합

코드를 올릴 때마다 자동으로 검사한다. "이 코드, 합쳐도 안전한가?" (린트·테스트·빌드)

CDContinuous Deployment · 지속적 배포

검사를 통과한 코드를 자동으로 서버에 올린다. "사용자에게 보내자."

용어뜻공장에 비유하면
Workflow.github/workflows/*.yml 파일 하나 = 자동화 하나작업 지시서
Trigger (on:)언제 실행할지 (push, PR, 수동 버튼…)"주문이 들어오면"
Job / StepJob = 한 대의 기계에서 하는 일 묶음, Step = 그 안의 명령 한 줄공정 / 공정 안의 동작
RunnerJob을 실제로 실행하는 컴퓨터 (GitHub이 빌려주는 일회용 VM)임시로 빌린 작업대
Registry빌드한 Docker 이미지를 보관하는 창고 (GHCR, ECR, Docker Hub)완제품 창고
Secret키·비밀번호를 암호화해 보관, 로그에 ***로 가려짐금고

핵심 개념

컴퓨터가 3대다: 무엇이 어디서 실행되나

CI/CD가 헷갈리는 이유 1순위. 같은 명령이라도 어느 컴퓨터에서 도는지를 항상 구분하세요.

① 내 PC② GitHub Actions 러너③ AWS EC2
정체내 노트북GitHub이 Job마다 새로 빌려주는 Ubuntu VM. 끝나면 삭제우리가 빌린 서버. 계속 켜져 있음
여기서 하는 일코딩, 로컬 테스트, commit · pushcheckout, 린트, pytest, docker build, 이미지 push, SSH 접속git pull 또는 이미지 pull, docker compose up, 서비스 실행
키·설정로컬 .envGitHub Secrets (Settings → Secrets and variables → Actions)서버의 docker/compose/.env
로그 보는 곳터미널저장소의 Actions 탭docker compose logs
남는 것내 작업물아무것도 안 남음 (이미지는 Registry로)컨테이너·DB 볼륨·이미지
러너는 매번 빈 컴퓨터입니다. 그래서 워크플로우는 항상 "코드 내려받기 → 파이썬 설치 → 패키지 설치"부터 시작합니다. 내 PC에 깔려 있던 것은 러너에 없습니다.
05
언제 실행되나

브랜치 흐름과 트리거

on:
  pull_request:              # PR 열기·커밋 추가 시
  push:
    branches: [main]            # main에 들어왔을 때
  workflow_dispatch:          # Actions 탭의 "Run workflow" 버튼
  • PR = CI: 합치기 전에 테스트로 검문
  • main = CD: 검문을 통과한 코드만 서버로
  • main 브랜치 보호 규칙(Branch protection)으로 "CI 통과해야 merge 가능"을 걸어 두면 고장 난 코드가 배포되지 않습니다
06
워크플로우 해부 ① · CI

ci.yml 한 줄씩 읽기

.github/workflows/ci.yml
name: CI                         # Actions 탭에 보이는 이름
on:                               # ① 언제?
  pull_request:
  push:
    branches: [main]
jobs:
  test:                           # ② Job 이름
    runs-on: ubuntu-latest        # ③ 어디서? 새 Ubuntu VM
    steps:                        # ④ 무엇을? 위→아래 순서
      - uses: actions/checkout@v6        # 코드 내려받기
      - uses: actions/setup-python@v5    # 파이썬 설치
        with: { python-version: "3.12" }
      - run: pip install -r backend/requirements.txt \
               -r agents/requirements.txt ruff pytest
      - run: ruff check .              # 린트 (실수·스타일)
      - run: pytest -q                 # 테스트

uses vs run

uses: 남이 만든 액션(부품)을 가져다 씀
run: 셸 명령을 그대로 실행 — 내 PC 터미널에서 치는 것과 같음

하나라도 실패하면

명령의 종료 코드가 0이 아니면 그 Step이 ❌ → 뒤 Step은 실행 안 됨 → PR에 빨간 X

직접 확인: 이 Step들을 내 PC에서 그대로 쳐 보세요. 로컬에서 실패하면 CI에서도 실패합니다.

자주 겪는 일

"내 PC에선 되는데 CI에서만 실패해요"

러너는 빈 컴퓨터 + 저장소에 커밋된 파일만 가진 상태라는 걸 떠올리면 대부분 풀립니다.

증상원인해결
ModuleNotFoundError: langgraph내 PC엔 설치돼 있지만 requirements.txt에 없음requirements에 추가 후 커밋
FileNotFoundError: data/sample.csv.gitignore 때문에 커밋 안 된 파일테스트용 작은 파일을 커밋하거나 fixture로

테스트가 Redis·DB 연결 실패러너에 Redis·DB가 없음단위 테스트는 외부 의존 없이. 통합 테스트는 services:로 컨테이너 띄우기
CI 테스트에서 진짜 LLM을 부르지 마세요. 느리고, 돈이 들고, 결과가 매번 달라 테스트가 들쭉날쭉합니다. 에이전트 노드는 LLM 응답을 고정값으로 바꿔 테스트합니다.

CD 방식 고르기

배포 방식 3가지: 우리 팀은 어느 쪽?

코딩 에이전트가 만든 워크플로우를 열어 보면 대개 A 또는 B입니다. 먼저 우리 팀이 어느 방식인지 확인하세요.

A. 서버에서 빌드B. Actions에서 빌드 → RegistryC. Self-hosted 러너
흐름Actions가 SSH 접속 → EC2에서 git pull → docker/build.sh → start.shActions가 이미지 빌드 → GHCR에 push → SSH 접속 → EC2는 pull + up만EC2에 러너 프로그램 설치 → Job이 EC2 위에서 직접 실행
장점가장 단순, 지난 시간 스크립트 그대로 사용서버 부담 적음, 같은 이미지를 그대로 배포·롤백SSH 포트를 열 필요 없음
단점작은 EC2는 빌드 중 메모리 부족으로 멈춤, 서버에 소스·빌드 도구 필요Registry 로그인·권한 설정이 추가러너 설치·관리, 보안 설정 필요
추천처음 시작 · 중간 발표까지⭐ 최종 배포심화
워크플로우에 docker/build-push-action이 있으면 B, script: 안에 git pull과 build가 있으면 A입니다.
09
워크플로우 해부 ② · 방식 A

SSH로 들어가서 서버에서 빌드

.github/workflows/deploy.yml
name: Deploy
on:
  push: { branches: [main] }
  workflow_dispatch:
concurrency: deploy               # 배포는 한 번에 하나씩
jobs:
  deploy:
    runs-on: ubuntu-latest           # ← 러너에서 시작해서
    steps:
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.EC2_HOST }}       # 금고에서 꺼냄
          username: ${{ secrets.EC2_USER }}
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |                  # ↓ 여기부터는 EC2 위에서 실행!
            set -e                   # 한 줄이라도 실패하면 중단
            cd ~/team-project
            git pull origin main
            ./docker/build.sh
            ./docker/start.sh
            sleep 15
            curl -fsS http://localhost:8000/health

가장 중요한 한 줄

script: | 아래 명령은 러너가 아니라 EC2에서 실행됩니다. 즉, 내가 EC2에 SSH로 들어가 직접 치는 것과 똑같습니다.

손으로 똑같이 해보기

ssh -i key.pem ubuntu@<EC2 IP>
cd ~/team-project && git pull
./docker/build.sh && ./docker/start.sh
curl -f는 /health가 200이 아니면 실패 코드를 돌려줍니다 → 배포 Job이 ❌로 끝나 문제를 바로 알 수 있습니다.
10
워크플로우 해부 ③ · 방식 B

Actions에서 빌드 → GHCR → 서버는 받아서 실행만

.github/workflows/deploy.yml (요약)
env:
  REG: ghcr.io/my-team                       # 소문자만!
jobs:
  test: { ... ci.yml과 같은 내용 ... }
  build:
    needs: test                              # 테스트 통과해야 시작
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    strategy: { matrix: { image: [bike-fe, bike-be, bike-agents] } }
    steps:
      - uses: actions/checkout@v6
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }},
                password: ${{ secrets.GITHUB_TOKEN }} }
      - uses: docker/build-push-action@v6
        with:
          context: .
          file: docker/images/${{ matrix.image }}/Dockerfile
          push: true
          tags: ${{ env.REG }}/${{ matrix.image }}:${{ github.sha }}
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: appleboy/ssh-action@v1
        with:                                # host·username·key는 A와 동일
          script: |
            cd ~/team-project/docker/compose
            export BE_VERSION=${{ github.sha }} AGENTS_VERSION=${{ github.sha }}
            docker compose pull && docker compose up -d

needs = 순서

test → build → deploy. 앞 Job이 실패하면 뒤 Job은 건너뜁니다.

태그 = 커밋 SHA

github.sha로 태그를 달면 "서버에 지금 어떤 커밋이 돌고 있나"를 정확히 알 수 있고, 롤백도 SHA만 바꾸면 됩니다.

compose.yml 쪽

image: ghcr.io/my-team/bike-be:${BE_VERSION}
지난 자료의 compose에 Registry 주소만 붙입니다.

비공개 이미지라면 EC2에서 한 번 docker login ghcr.io (read:packages 권한 토큰) 필요.

서버 쪽

EC2에는 무엇이 준비돼 있어야 하나

처음 한 번만 (손으로)

  • Docker + Compose 설치, 사용자를 docker 그룹에 추가
  • 탄력적 IP 연결 — 없으면 EC2를 껐다 켤 때마다 IP가 바뀌어 배포 실패
  • 보안그룹: 22(SSH), 80/443(웹)만. 8000·5555·5432·6379는 외부에 열지 않기
  • 배포용 공개키를 ~/.ssh/authorized_keys에 추가
  • (방식 A) 저장소 clone — 읽기 전용 Deploy key 사용
  • docker/compose/.env 작성
EC2 서버의 모습 (방식 A 기준)
/home/ubuntu/
├── .ssh/authorized_keys   # 배포용 공개키
└── team-project/          # git clone 한 저장소
    ├── backend/ agents/ frontend/ shared/
    └── docker/
        ├── build.sh start.sh stop.sh restart.sh
        ├── compose/
        │   ├── compose.yml
        │   └── .env           # ★ 서버에만 있는 키
        └── images/*/VERSION   # 마지막 빌드 시각
지금 상태 확인 명령 3개
docker compose ps            # 무엇이 떠 있나 (docker/compose에서)
docker compose logs -f be    # 로그 따라가기
df -h ; free -h              # 디스크 · 메모리 여유

한 번의 배포

main에 merge한 순간부터 서비스 반영까지

순서어디서무슨 일실패하면 보이는 곳
1GitHubPR merge → main에 push 이벤트 → 워크플로우 대기열에 등록Actions 탭 (노란 점 = 실행 중)
2러너새 VM 받음 → checkout → 설치 → ruff · pytesttest Job의 해당 Step 로그
3러너(B) docker build → GHCR에 :SHA 태그로 pushbuild Job 로그 / 저장소 Packages
4러너 → EC2Secrets로 SSH 접속deploy Job: Permission denied, timeout
5EC2(A) git pull + build.sh / (B) compose pull → compose up -ddeploy 로그의 script 출력
6EC2새 컨테이너 시작, 바뀐 서비스만 교체EC2: docker compose ps, logs
7EC2curl -f /health 확인 → 성공이면 Job ✅Job ❌ → 롤백 판단
Actions 탭에서 실행 하나를 클릭 → 왼쪽 Job → 각 Step을 펼치면 터미널 출력 그대로 보입니다. 실패한 Step의 마지막 20줄이 거의 항상 답입니다.

되돌리기

고장 났다! 5분 안에 이전 버전으로

방식 A (서버 빌드, VERSION = 빌드 시각)

# EC2에서: 직전에 빌드돼 있던 이미지 태그 확인
docker images | grep bike-agents
# 그 태그로 다시 띄우기
cd ~/team-project/docker/compose
AGENTS_VERSION=261119-1650 docker compose up -d

지난 자료의 VERSION 태그(YYMMDD-hhmm)가 여기서 쓰입니다. 이미지가 남아 있어야 하므로 오래된 이미지를 너무 빨리 지우지 마세요.

방식 B (Registry, 태그 = 커밋 SHA)

① 가장 쉬움: Actions 탭 → 정상이던 이전 배포 실행 열기 → Re-run jobs → 그 커밋으로 다시 배포

② 서버에서 직접:

export BE_VERSION=<이전 SHA> AGENTS_VERSION=<이전 SHA>
docker compose pull && docker compose up -d

③ 근본 수정: git revert → PR → merge (기록이 남는 정석)

DB는 롤백되지 않습니다. 테이블 구조를 바꾸는 배포(컬럼 삭제 등)는 되돌리기 어려우니, 컬럼은 "추가 먼저, 삭제는 나중에" 원칙으로.

실습 (60분)

손으로 한 번, 망가뜨려서 한 번

1손 배포

EC2에 SSH로 접속해 워크플로우 script:에 적힌 명령을 한 줄씩 직접 실행. 각 명령의 출력이 무슨 뜻인지 팀원에게 설명.

2로그 읽기

Actions 탭에서 마지막 성공 실행을 열어 Step별 출력을 1번의 터미널 출력과 비교. "같은 명령"임을 확인.

3CI 깨뜨리기

일부러 실패하는 테스트를 넣은 PR 생성 → 빨간 X 확인 → 로그에서 실패 줄 찾기 → 고쳐서 초록색.

4배포 깨뜨리기

(연습용 브랜치/저장소에서) EC2_USER Secret을 틀리게 → 어떤 메시지가 나오는지 기록 → 원복.

5롤백 연습

/health가 500을 내는 버전을 배포 → 헬스체크 Step ❌ 확인 → 15장의 방법으로 5분 안에 되돌리기.

6정리

17장의 표를 팀 문서로 작성. "배포 아키텍처 설계도" 산출물에 그대로 활용.

원칙: 손으로 한 번 해본 것만 자동화한다. 자동화는 "내가 아는 절차를 기계가 대신 치는 것"이지 "모르는 절차를 맡기는 것"이 아닙니다.

주의

보안 · 비용 체크리스트

☐ .env, *.pem이 .gitignore에 있다 (git log에도 없다)

☐ 워크플로우에서 echo ${{ secrets.… }}로 키를 출력하지 않는다

☐ AWS 액세스 키를 Secrets에 넣었다면 권한이 최소한이다 (가능하면 키 대신 OIDC 역할)

☐ 보안그룹에 8000·5432·6379·5555가 0.0.0.0/0으로 열려 있지 않다

☐ 서버 SSH는 비밀번호 로그인 비활성, 키로만

☐ main 브랜치 보호: CI 통과 + 리뷰 1명 이상이어야 merge

☐ 팀원이 실수로 올린 키는 지우는 것이 아니라 폐기·재발급

☐ 사용하지 않는 시간엔 EC2 중지 (탄력적 IP는 연결된 상태로 유지)

☐ 오래된 이미지·로그 정리 주기 (디스크 가득 참 → 서비스 중단)

☐ LLM API 사용량 한도(Usage limit) 설정

코딩 에이전트는 "일단 되게" 만들기 위해 포트를 넓게 열거나 키를 코드에 넣는 경우가 있습니다. 배포 관련 변경은 사람이 diff를 반드시 확인하세요.

한 장 요약

오늘 기억할 다섯 문장

1. 컴퓨터는 3대다

내 PC(코딩) · GitHub 러너(검사·빌드, 매번 새 VM) · EC2(실행). 명령마다 어디서 도는지 말할 수 있어야 한다.

2. CI는 검문, CD는 배송

PR에선 테스트만, main에 들어온 것만 배포. needs로 순서를 강제한다.

3. 키는 두 금고에

들어가는 키는 GitHub Secrets, 동작하는 키는 EC2의 .env. 저장소엔 절대 없다.

4. 배포의 끝은 헬스체크, 그 다음은 롤백 계획

버전 태그(VERSION 시각 또는 커밋 SHA)가 있어야 되돌릴 수 있다.

5. 손으로 해본 것만 자동화한다

에이전트가 만든 yml을 한 줄씩 읽고, 같은 명령을 직접 쳐 본 팀만 발표에서 답할 수 있다.
