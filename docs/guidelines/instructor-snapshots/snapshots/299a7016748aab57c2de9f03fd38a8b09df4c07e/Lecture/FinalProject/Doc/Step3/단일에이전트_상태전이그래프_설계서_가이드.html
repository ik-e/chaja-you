02 · 왜 그래프부터 그리나

노선도 없이 열차를 출발시키지 않는다

LLM 에이전트는 같은 입력에도 다른 길로 갈 수 있습니다. 그래서 “갈 수 있는 길”을 사람이 먼저 정해 두는 게 설계서의 역할입니다.

그래프 없이 바로 코딩하면

  • 무한 루프 — “다시 생각해” 가 끝없이 반복되고 토큰만 소모
  • 멈춤 — 도구가 실패했을 때 갈 곳이 없어 예외로 종료
  • 이름 혼란 — 팀원마다 노드 이름 · State 필드가 다름
  • 시험 불가 — 무엇이 정상 종료인지 기준이 없음

그래프를 먼저 합의하면

  • 모든 길에 출구 — 반복마다 상한, 실패마다 갈 곳
  • 구현이 기계적 — 표의 한 행이 코드의 간선 하나
  • 시험이 표에서 나옴 — 전이 하나마다 시험 하나
  • 리뷰가 쉬움 — 코드 대신 표를 보고 빠진 길을 찾음

03 · 용어 다섯 개

식당 주문 처리로 용어부터 맞춘다

설계서의 모든 칸은 이 다섯 단어로 쓰입니다. 팀 안에서 같은 단어를 같은 뜻으로 쓰는 것부터 시작하세요.

용어한 줄 정의식당 비유이번 예시(DiagnosisAgent)
상태 · 노드에이전트가 지금 하는 일 한 단계주문 받기 → 조리 → 검수 → 서빙diagnose, validate
전이다음 단계로 가는 화살표와 그 조건“재료가 없으면 → 손님께 안내”근거 부족 → diagnose
State모든 노드가 함께 읽고 쓰는 공용 메모지주문서 (테이블 · 메뉴 · 요청)incident_id, retry_count
상한(가드)반복을 멈추게 하는 숫자“다시 조리는 최대 2번까지”retry_count < 2
종료 조건언제 끝났다고 보는지, 무엇을 돌려주는지서빙 완료 / 주문 취소 안내 / 매니저 호출finalize / finalize_error / 사람 이관
구분상태(노드)는 “지금 어디에 있나”, State는 “무엇을 들고 다니나”입니다. 이름이 비슷해 가장 많이 헷갈립니다.
주의DB의 작업 상태 컬럼(queued · running · done)은 노드 이름과 다른 것입니다. 섞어 쓰지 않습니다.

06 · 1칸 목적과 범위

에이전트 하나가 하는 일과 하지 않는 일을 먼저 적는다

예시: DiagnosisAgent는 인프라 로그와 상태 지표로 원인 후보를 추정하고, 복구 실행 권한은 없이 RecoveryAgent에 구조화된 권고만 전달합니다.

✓ 한다

  • 장애 입력을 받아 근거를 모은다
  • 원인 후보 · 근거 · 신뢰도를 만든다
  • 권고 action을 구조화해 넘긴다

✕ 하지 않는다

  • 복구를 직접 실행하지 않는다
  • 근거 없이 단정하지 않는다
  • 승인 없이 위험 작업을 하지 않는다

⇢ 입력 · 출력

  • 입력: 장애 ID, 관측 로그, 지표 요약
  • 출력: 원인 후보, 근거 ID, 권고, 신뢰도
  • 넘기는 곳: RecoveryAgent

“하지 않는다”가 왜 중요할까?

그래프
하지 않는 일은 노드가 없다는 뜻입니다. 복구 노드가 없으니 복구 간선도 없습니다.
보안
하지 않는 일은 Tool 권한이 없다는 뜻입니다. recovery.execute는 이 에이전트에 주지 않습니다.
시험
“복구해 줘” 입력이 오면 거절 · 이관되는지가 시험 케이스가 됩니다.
팀 적용우리 에이전트의 이름 · 하는 일 · 하지 않는 일 · 입력과 출력 네 칸을 먼저 채웁니다. 하는 일이 둘 이상으로 갈리면 단일 에이전트 범위를 다시 점검하세요.
참고: Auto-Healing 가이드 7~8쪽(역할 카드와 하지 않는 일) · 에이전트를 나누는 이유는 STEP4(같은 가이드 6쪽)에서 다룹니다.

07 · 2칸 상태 · 노드 · 전이

단계마다 들어오는 조건과 나가는 길을 적는다

상태 / 노드진입 조건다음 전이
collect_context신규 장애근거 확보 → reason · 실패 → handoff
reason로그 수집 완료Tool 필요 → tool_call · 충분 → verify
tool_call조회 권한 충족성공 → observe · 실패(재시도 1회 후) → handoff
observeTool 결과 수신증거 충분 → verify · 부족 → reason
verify근거 · 스키마 검증통과 → END · 미달 → reason (최대 2회)
그림은 표와 같은 내용을 그린 예시입니다. 그림의 선 개수 = 표의 전이 개수인지 세어 보세요. 팀은 노드 5~8개로 시작합니다.

08 · 한 건 따라가 보기

장애 inc-001 하나가 그래프를 지나가는 모습

그래프를 읽는 가장 쉬운 방법은 실제 입력 하나를 손으로 따라가는 것입니다. 한 줄 = 노드 한 번 실행, 오른쪽은 그때 바뀐 State입니다.

시각노드일어난 일 (요약 기록)나간 전이바뀐 State
10:01:00collect_context장애 inc-001 접수, 최근 로그 120줄 수집근거 확보 → reasonincident_id="inc-001"
10:01:01reason“API 타임아웃 의심, 지연 지표가 필요” (가설 요약)Tool 필요 → tool_call—
10:01:02tool_callget_service_metrics(svc-api-01) 호출성공 → observetool_result={p95: 9.8s}
10:01:03observep95 지연 9.8초 확인 → 지표 근거 1건 확보충분 → verifydiagnosis={cause:"API timeout"}
10:01:04verify검증 실패: 근거 로그 ID가 비어 있음미달 → reasonretry_count=1
10:01:05reason“오류 로그로 타임아웃을 확인해야 함”Tool 필요 → tool_call—
10:01:06tool_callget_recent_logs(svc-api-01) 호출성공 → observetool_result={logs:[…]}
10:01:07observe타임아웃 오류 로그 log-01 확인 → 근거 확보충분 → verifyevidence=["log-01"]
10:01:08verify근거 · JSON 스키마 통과, 신뢰도 0.91통과 → ENDdiagnosis.confidence=0.91
읽는 법주황 줄이 자기 성찰 루프입니다. verify가 되돌려 보냈고 retry_count가 1 올랐습니다.
만약세 번째 verify도 실패했다면? retry_count=2 → 한도 초과 → handoff.
연결이 표가 다음 주 결과서의 실행 추적 샘플 모양 그대로입니다.
모든 시각 · ID · 수치는 교육용 가상 샘플입니다.

09 · 3칸 LLM 및 프롬프트 정책

모델에게 주는 것, 받는 것, 실패했을 때를 정한다

LLM 노드는 “입력 → 출력” 계약이 있는 함수처럼 다룹니다. 출력 형식을 고정해야 다음 노드(검증)가 판정할 수 있습니다.

항목정책(예시)
입력장애 ID, 관측 로그, 지표 요약, 허용 Tool 목록

10 · 4칸 CoT · ReAct 매핑

생각은 요약만, 행동과 관찰은 그대로 남긴다

CoT는 문제를 단계로 나눠 추론하는 방식, ReAct는 생각(Thought) → 행동(Action) → 관찰(Observation)을 반복하는 방식입니다. 설계서는 이 반복이 그래프의 어느 노드인지 적습니다.

ReAct 한 바퀴 = 노드 세 개

Thought→ reason 노드 (가설 요약)
Action→ tool_call 노드 (조회 Tool)
Observation→ observe 노드 (로그 · 지표)
Check→ verify 노드 (검증 결과)
그래프에서 reason → tool_call → observe → reason 으로 돌아오는 고리가 바로 ReAct 루프입니다.
기록 예시 (한 단계 = 한 줄, JSON Lines)
{"step":1,"node":"reason","thought_summary":"지연 지표 필요"}
{"step":2,"node":"tool_call","action":"get_service_metrics","ok":true}
{"step":3,"node":"observe","observation":"p95=9.8s"}
{"step":4,"node":"verify","result":"missing_evidence","retry":1}

저장 · 노출한다

  • 단계 · 노드 이름 · 가설 요약
  • 호출한 Tool과 성공 여부
  • 관찰 결과 요약 · 검증 결과

저장 · 노출하지 않는다

  • 모델 내부 추론 원문
  • 비밀정보가 담긴 로그 원문
  • 사용자에게 사고 과정 전체
참고: Auto-Healing 가이드 11~12쪽(자기 성찰 루프 규칙) · 다음 주 결과서의 추적 증빙(trace_id · node · retry_count)과 같은 필드를 쓰면 편합니다.

재시도와 재추론은 다른 것

재시도 (retry)
같은 호출을 한 번 더. 네트워크 · 타임아웃 같은 일시 오류용.
재추론 (re-reason)
LLM이 다시 생각. 근거 부족 · 형식 오류 같은 판단 오류용.
→ 카운터도 따로 둡니다. 하나로 합치면 “몇 번 실패했는지” 해석이 꼬입니다.
팁재시도 횟수와 타임아웃 숫자는 API 설계 문서의 규칙과 같은 값으로 적으세요. 숫자가 다르면 시험 결과를 비교할 수 없습니다.
보안Tool 목록은 1칸 “하지 않는다”와 맞아야 합니다. 진단 에이전트 목록에 restart_service가 있으면 범위 위반입니다.

from typing import TypedDict

class AgentState(TypedDict):
    incident_id: str
    diagnosis: dict | None
    tool_result: dict | None
    retry_count: int      # 재추론 상한용
    approved: bool
    error: str | None
    fetch_count: int      # 조회 반복 상한용
    verdict: str          # "pass"|"retry"|"give_up"
팁State 필드 이름은 DB 설계서와 같게 적습니다. 체크포인트를 저장하는 곳(표 · 키)도 DB 문서에 있어야 합니다.

전이표 한 행 = LangGraph 간선 하나

조건은 라우터 함수의 반환값, 다음 노드는 매핑 dict의 값이 됩니다. 아래 코드는 18장 표를 그대로 옮긴 구조 예시입니다.

def route_diagnose(s) -> Literal["need_logs", "done"]:
    if s["diagnosis"]["need_logs"] and s["fetch_count"] < 3:
        return "need_logs"
    return "done"
def route_validate(s): return s["verdict"]  # pass|retry|give_up

g = StateGraph(AgentState)
for fn in [load_incident, diagnose, fetch_logs, validate, finalize, finalize_error]:
    g.add_node(fn.__name__, fn)
g.add_edge(START, "load_incident")
g.add_conditional_edges("load_incident", route_load,
    {"ok": "diagnose", "fail": "finalize_error"})
g.add_conditional_edges("diagnose", route_diagnose,
    {"need_logs": "fetch_logs", "done": "validate"})
g.add_edge("fetch_logs", "diagnose")
g.add_conditional_edges("validate", route_validate,
    {"pass": "finalize", "retry": "diagnose", "give_up": "finalize_error"})
g.add_edge("finalize", END); g.add_edge("finalize_error", END)

app = g.compile(checkpointer=MemorySaver())   # 6칸 체크포인트
app.invoke(init, {"configurable": {"thread_id": "inc-001"}})
