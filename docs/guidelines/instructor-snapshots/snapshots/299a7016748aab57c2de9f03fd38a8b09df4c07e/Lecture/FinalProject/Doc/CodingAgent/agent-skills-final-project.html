addyosmani/agent-skills — 시니어 엔지니어의 작업 순서를 AI 코딩 에이전트에 입히는 방법

2026년 11월 · 출처: github.com/addyosmani/agent-skills

오늘은 바이브 코딩을 ‘제대로’ 하기 위한 도구 하나를 소개합니다. Google의 Addy Osmani가 공개한 agent-skills입니다. 핵심은 새로운 기술이 아니라, AI 에이전트가 스펙·테스트·리뷰를 건너뛰지 못하게 하는 작업 절차입니다. 최종 프로젝트 5단계 산출물과 어떻게 연결되는지에 집중해서 보겠습니다.

왜 필요한가

AI 코딩 에이전트는 가장 짧은 길로 ‘완료’합니다

빠뜨리는 것 ①

스펙 없이 바로 코딩

요구사항 명세(FR/NFR)와 실제 구현이 따로 놀고, 발표 Q&A에서 “왜 이렇게 만들었나”에 답하지 못합니다.

빠뜨리는 것 ②

테스트는 “나중에”

Auto-Healing 시연과 통합 테스트 결과서를 쓸 때가 되어서야 깨진 곳이 한꺼번에 드러납니다.

빠뜨리는 것 ③

리뷰·보안 점검 생략

API 키가 커밋되고, 승인 없이 위험한 도구가 실행되는 경로가 그대로 남습니다.

agent-skills는 이 빠진 단계를 에이전트가 반드시 밟도록 강제하는 워크플로우 모음입니다.

Addy Osmani가 저장소와 블로그에서 밝힌 문제의식입니다. 에이전트는 기능은 만들지만 시니어가 당연히 하는 스펙, 테스트, 리뷰, 범위 관리를 건너뜁니다. 우리 평가 기준이 ‘문서 존재’가 아니라 ‘설계·구현·검증의 연결’이라는 점과 정확히 맞닿아 있습니다.

스킬이란

스킬 = 읽는 문서가 아니라 실행하는 절차

skills/

spec-driven-development/

SKILL.md는 frontmatter(이름·언제 쓰는지) + 단계별 절차 + 체크포인트 + 종료 조건으로 된 마크다운 파일입니다.

Process, not prose

절차형

설명문이 아니라 체크포인트와 종료 조건이 있는 단계별 워크플로우

Anti-rationalization

핑계 차단표

에이전트가 단계를 건너뛸 때 대는 핑계와 반박을 미리 적어 둠

Verification

증거로 끝남

통과한 테스트, 빌드 출력, 런타임 데이터 없이는 ‘완료’가 아님

Progressive disclosure

필요한 것만 로드

메타 스킬이 지금 단계에 맞는 스킬만 불러와 컨텍스트를 아낌

Osmani는 에세이형 가이드는 읽히고 무시되지만 단계형 워크플로우는 실행된다고 말합니다. 네 가지 원칙 중 수업에서 특히 강조할 것은 ‘증거로 끝남’입니다. 에이전트가 “다 됐습니다”라고 말하는 것만으로는 완료가 아닙니다.

Codex와 Antigravity에는 Claude Code의 짧은 커맨드가 없거나 일부 버전에서 보이지 않습니다. 그래서 커맨드가 내부적으로 부르는 스킬 이름을 직접 쓰는 표입니다. /ship은 Claude Code에서 여러 페르소나를 함께 돌리지만, 다른 도구에서는 shipping-and-launch를 부른 뒤 페르소나를 따로 호출하세요.

우리 프로젝트에 적용

최종 프로젝트 5단계에 그대로 얹기

단계필수 산출물쓰는 커맨드 · 스킬
STEP 1 기획·설계기획서(요구사항 명세), WBS/spec · interview-me · /plan
STEP 2 API·FCAPI 설계 문서, DB 스키마 설계서api-and-interface-design · /build · /test
STEP 3 단일 에이전트상태 전이 그래프 설계서, 자기 성찰 테스트 결과서context-engineering · source-driven · TDD
STEP 4 협업·Healing협업 아키텍처, AI 보안 가드레일, Auto-Healing 결과서debugging · security-and-hardening · doubt-driven
STEP 5 최적화·배포대화형 AI 웹 앱, 통합 테스트 결과서, 배포 아키텍처ci-cd · observability · /ship

평가는 문서의 존재가 아니라 설계 · 구현 · 검증의 연결을 봅니다. 스킬을 쓰면 그 연결이 저장소 안에 spec.md → tasks/todo.md → 테스트 → 리뷰 기록으로 남습니다.

매니저 가이드의 STEP 1~5 산출물 표에 스킬을 붙인 것입니다. 스킬이 산출물 문서를 대신 써 주는 건 아닙니다. 대신 문서에 들어갈 근거, 즉 승인된 스펙, 작업 목록, 테스트 결과, 리뷰 기록이 자연스럽게 쌓입니다.

STEP 1 · 기획·설계

/spec — 코드 전에 PRD부터

프롬프트 예시 (주요산출물 문서의 교육용 예시 서비스)

/spec

InfraCare AI: IT 운영자가 장애 접수→진단→

승인→복구→검증을 한 화면에서 처리하는

멀티 에이전트 서비스.

스택: FastAPI · LangGraph · Supabase · AWS

MVP: 장애 목록, AI 진단, 복구 승인, 이력

요구사항은 FR-xx / NFR-xx ID로 정리해줘.

스펙의 6개 핵심 영역

목표 · 명령어 · 프로젝트 구조 · 코드 스타일 · 테스트 전략 · 경계(Boundaries)

경계는 3단계로

Always 커밋 전 pytest 실행
Ask First DB 스키마 변경, 의존성 추가
Never .env·API 키 커밋, 승인 없는 복구 실행

PRD (Product Requirements Document, 제품 요구사항 문서) — 무엇을, 누구를 위해, 왜 만드는지와 ‘완료’의 기준을 코드보다 먼저 정리한 문서입니다. 우리 과정의 기획서(요구사항 명세 포함)에 해당합니다.

/spec은 코드를 한 줄도 쓰기 전에 짧은 PRD를 씁니다. 공식 가이드는 이것을 가장 효과가 큰 습관이라고 부릅니다. 경계 3단계는 그대로 STEP 4 보안 가드레일 문서의 출발점이 됩니다. 범위가 모호하면 interview-me 스킬로 한 번에 한 질문씩 요구사항을 끌어내게 하세요.

STEP 1 · 승인 게이트

스펙은 ‘쓰고 바로 코딩’이 아니라 ‘승인 후 다음 단계’

STEP 2~3 · 구현과 검증

/build + /test — 얇은 수직 조각, 테스트 먼저

1 · RED

실패하는 테스트를 쓰고 실제로 실패하는 것을 확인

2 · GREEN

통과할 만큼만 최소한의 코드를 작성

3 · REFACTOR

정리한 뒤 다시 통과 확인 → 작업 단위로 커밋

def test_recover_requires_approval(client, token):

res = client.post(

"/api/incidents/INC-104/recover",

json={"strategy": "restart"},

headers={"Authorization": f"Bearer {token}"},

)

assert res.status_code == 403

assert res.json()["error"]["code"] \

== "APPROVAL_REQUIRED"

한 조각 = 라우터 + 서비스 + 테스트 + 커밋. 테스트 비율은 단위 80 / 통합 15 / E2E 5를 기준으로 삼습니다.

incremental-implementation과 test-driven-development 스킬의 핵심입니다. 큰 기능을 한 번에 만들지 말고, 끝에서 끝까지 동작하는 얇은 조각을 하나씩 완성하고 커밋합니다. 예시는 주요산출물 문서의 복구 API 명세(승인 없으면 403)를 그대로 테스트로 옮긴 것입니다.

context-engineering 규칙 파일(CLAUDE.md·AGENTS.md)·컨텍스트 묶기·MCP 연동으로 “필요한 정보를 필요한 때” 주는 법 — 에이전트 프롬프트 설계에도 그대로 적용됩니다.

여기가 우리 과정의 차별점입니다. 디버깅 스킬의 다섯 단계는 Auto-Healing을 설계하는 틀로도 쓸 수 있습니다. 감지는 재현, 원인 분석은 위치 특정과 축소, 복구는 수정, 재발 방지는 가드에 해당합니다. LangGraph는 버전마다 API가 달라서 source-driven-development로 공식 문서 근거를 강제하는 것이 특히 효과적입니다.

RED 지표는 Rate, Errors, Duration, 즉 요청 수, 오류율, 응답 시간입니다. 최종 시연 직전에 /ship을 돌려 no-go가 나오면 그 이유가 곧 우리가 고쳐야 할 목록입니다. ADR은 발표 때 “왜 이 구조를 택했나” 질문에 답하는 가장 좋은 준비물입니다.

핑계 차단표 (Anti-rationalization)

에이전트도, 우리도 쓰는 핑계와 그 반박

핑계스킬에 적힌 반박
“너무 간단해서 스펙은 필요 없어요”수용 기준은 여전히 필요합니다. 다섯 줄이면 충분하지만 0줄은 안 됩니다.
“테스트는 나중에 쓸게요”‘나중’은 없습니다. 실패하는 테스트부터 씁니다.
“테스트 통과했으니 배포하죠”통과는 증거이지 증명이 아닙니다. 실제 동작, 사용자 화면, 사람이 diff를 읽었는지 확인합니다.
“요구사항은 어차피 바뀌어요”살아있는 스펙이 변경을 감당합니다. 낡은 스펙도 없는 것보다 낫습니다.

실제 사용 사례 ① · ScrapingBee 기술 블로그 (2026-08)

같은 패턴으로 ‘우리 팀 전용 스킬’을 만들었다

만든 것

가장 저렴한 스크래핑 방법부터 시작하고, 근거가 있을 때만 단계를 올리는 스킬 — SKILL.md + scripts/fetch.py, extract.py

결과

정적 페이지: 표준 라이브러리 스크래퍼로 해결, 크레딧 0
JS 페이지: 정적 확인이 실패한 근거로 렌더링 단계로 승급
같은 스킬이 상황에 따라 다른 결정을 내림

그들이 얻은 교훈

  • SDK 버전부터 고정한다
  • 마켓플레이스 SSH 오류 → HTTPS
  • 200 응답이어도 차단 페이지일 수 있다 → 필드 검증
  • 스킬은 가이드일 뿐 보장이 아니다 → 테스트·린트와 함께
  • 컬렉션 전체보다 1~5개만 설치
  • 남이 만든 스킬은 설치 전 스크립트·훅까지 검토

우리 적용: 팀 도메인의 외부 API 연동 규칙(공공 API 페일오버, 재시도 제한 등)을 팀 전용 SKILL.md로 만들어 두면 누가 에이전트를 돌려도 같은 방식으로 구현됩니다.

ScrapingBee는 agent-skills를 계기로 자기 제품용 스킬을 직접 만들어 Codex로 실행해 봤습니다. 핵심 교훈은 스킬이 보장이 아니라 가이드라는 점, 그래서 테스트와 린트로 받쳐야 한다는 점입니다. 우리 팀도 공통 스킬 위에 팀 전용 스킬 하나를 얹는 것을 목표로 해 보세요.

주의사항

우리 과정에 맞게 쓰는 5가지 원칙

1

다 깔지 말고 핵심부터

/spec · /plan · /build · /test · /review로 시작. 공식 가이드도 24개를 한꺼번에 로드하지 말라고 권합니다.

2

웹 프론트엔드 편향 걸러 내기

Core Web Vitals·브라우저 테스트 스킬은 UI 담당만. 백엔드·에이전트는 Python(pytest·ruff) 기준으로 읽습니다.

3

스킬은 권고, 강제는 CI

모델은 규칙을 빠뜨릴 수 있습니다. 테스트·린트를 GitHub Actions 품질 게이트로 막아 두세요.

4

커맨드가 안 보이면 이름으로 부르기

설치 후 /help로 확인하고, 안 되면 “follow spec-driven-development”처럼 스킬 이름으로 지시합니다.

5

내가 설명할 수 있는 코드만 머지

최종 발표는 예외 대응, 한계, 개인 기여 설명까지 평가합니다.

agent-skills는 웹 성능 전문가가 만든 만큼 일부 스킬이 프론트엔드 쪽으로 기울어 있습니다. 우리 백엔드와 에이전트 코드는 Python이므로 원칙만 가져오고 도구는 pytest, ruff로 바꿔 읽으면 됩니다. 마지막 원칙이 가장 중요합니다.
