왜 지금 생성형 UI인가

지금까지의 두 가지 방식, 두 가지 한계

방식 1 · 하드코딩 UI

개발자가 미리 정한 화면만 보여 준다

  • 질문 유형마다 화면 · 메뉴 · 버튼을 미리 만들어야 한다
  • 예상 못 한 요구 = 새 화면 개발 = 새 배포
  • 사용자는 메뉴를 여러 번 눌러 원하는 정보에 도달
방식 2 · 텍스트 채팅 에이전트

무엇이든 답하지만 글로만 답한다

  • 비교 · 선택 · 승인을 글로 하면 “몇 번이요?” 왕복이 반복
  • 표 · 지도 · 차트가 필요한 정보도 문단으로
  • 사용자가 다시 타이핑해야 행동이 일어난다

세 번째 길

에이전트가 질문을 이해하고, 우리가 미리 만든 부품으로 그 순간에 맞는 화면을 조립한다 — 이것이 생성형 UI, 그 표준 중 하나가 A2UI다.

A2UI란

A2UI: 에이전트가 “무엇을 보여줄지” 말하는 표준

한 줄 정의

에이전트는 어떤 화면을 보여 줄지를 JSON으로 설명하고, 각 앱은 그것을 자기 네이티브 컴포넌트로 그린다.

현재 상태

  • Google 주도 오픈 프로토콜, 2026년 11월 11일 1.0 정식
  • 렌더러: React · Angular · Lit(웹), Flutter, SwiftUI, Jetpack Compose
  • 에이전트 SDK: Python · TypeScript · Dart

HTML을 만드는 게 아니다

에이전트는 코드를 생성하지 않는다. 우리가 등록한 부품의 이름 · 배치 · 속성만 고른다 → 안전하고 디자인이 깨지지 않는다.

한 번 설명, 어디서나

같은 A2UI 응답을 웹 · 안드로이드 · iOS가 각자 네이티브로 렌더링한다.

주의

아직 생태계가 빠르게 변하는 중 — 실습 전 공식 문서(a2ui.org)의 최신 버전을 확인할 것

핵심 개념 3가지

카탈로그 · 데이터 바인딩 · 점진 렌더링

① 컴포넌트 카탈로그

앱이 미리 승인한 부품 목록. 에이전트는 이 목록 밖의 것을 요청할 수 없다 = 우리의 디자인 시스템

② 데이터 바인딩

부품은 데이터 “경로”만 가리키고 실제 값은 서버가 채운다 → 개인정보 등 민감한 값이 모델을 거치지 않는다

③ 점진 렌더링

ID로 연결된 평평한 부품 목록이라 LLM이 조금씩 생성하고, 화면은 도착하는 대로 그려진다

개념 예시 — 실제 필드 이름은 A2UI 스펙 버전에 따라 다르다

// 에이전트가 보내는 것: 부품 + 배치 + 데이터 경로 { "components": [ { "id": "root", "type": "Column", "children": ["map", "exits", "go"] }, { "id": "map", "type": "CrowdMap", "data": "/festival/exits" }, { "id": "exits", "type": "RadioGroup", "data": "/festival/exits" }, { "id": "go", "type": "Button", "label": "길안내 시작", "action": "start_route" } ]}

CrowdMap · RadioGroup · Button은 우리가 카탈로그에 등록한 부품이다.

사고의 전환

“화면을 만든다”에서 “부품과 규칙을 만든다”로

하드코딩 사고

  • “어떤 화면이 몇 개 필요하지?”
  • 요구사항 → 화면 설계서 → 화면 구현
  • 사용자 질문의 범위를 화면 수가 제한
→

생성형 UI 사고

  • “사용자가 어떤 결정을 내려야 하지?”
  • 결정 → 필요한 부품 → 데이터 API → 에이전트 규칙
  • 질문의 범위는 부품 조합과 데이터가 정한다

좋은 질문 하나: “이 정보를 받은 사용자는 다음에 무엇을 누르고 싶을까?” — 그 버튼이 화면에 함께 나와야 한다.

장애 대응 콘솔: 상황마다 다른 화면이 필요하다

하드코딩이면

장애 유형(결제 · 배차 · 지도 API · 라이더 앱)마다 대응 화면을 따로 만들어야 하고, 새로운 장애 유형은 화면이 없다

A2UI라면

오토힐링 에이전트가 진단 결과에 맞춰 원인 후보 · 영향 범위 · 복구안을 그 장애에 맞는 화면으로 조립하고, 사람은 승인만 한다

고정 (하드코딩)
  • 로그인 · 홈 · 내비게이션 같은 앱 뼈대
  • 매일 반복하는 핵심 화면 (운영 대시보드 메인)

  • 질문마다 달라지는 조회 · 비교 결과
  • 예외 상황 대응 (장애 · 혼잡 · 경보)
  • 조건을 확인하는 짧은 폼
  • 드물게 쓰는 다양한 요청 (롱테일)
