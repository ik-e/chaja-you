02 · 첨삭으로 이해하기

초안 → 빨간펜 → 고쳐 쓰기 → 채점

자기 성찰 루프는 글쓰기 첨삭과 같습니다. 결과서는 “첨삭을 했더니 점수가 올랐다”를 증거와 함께 보여 주는 성적표입니다.

① 초안

초기 응답

학생이 처음 쓴 글
→ 에이전트가 보정 없이 처음 낸 답
② 빨간펜

평가 · 오류 탐지

“3문단 근거가 없음”
→ missing_evidence 같은 이름 붙은 피드백
③ 고쳐 쓰기

보정

지적받은 곳만 고침
→ 로그 재조회 · 승인 단계 추가
④ 채점

최종 판정

같은 채점표로 다시 채점
→ 통과 / 상한 도달 → 사람 이관

이런 첨삭은 믿을 수 없다

  • 초안은 버리고 고친 글만 제출 → 나아졌는지 모름
  • 빨간펜이 “좋네요”만 씀 → 무엇을 잡았는지 모름
  • 점수가 안 나오면 채점 기준을 낮춤
  • 못 고친 학생은 명단에서 뺌

결과서가 보여야 하는 것

  • 같은 글의 초안과 최종본을 나란히
  • 빨간펜이 무엇을 왜 지적했는지
  • 채점 기준은 첨삭 전에 확정
  • 전체 · 통과 · 이관 수를 모두 적기

04 · 헷갈리는 세 가지

재시도 · 자기 성찰 · Auto-Healing은 고치는 대상이 다르다

세 가지 모두 “다시 한다”처럼 보이지만, 무엇이 잘못됐고 무엇을 고치는지가 다릅니다. 이 결과서는 가운데 열만 다룹니다.

06 · 1칸 목적 · 범위 및 로직

어떤 루프를 시험하는지 한 장으로 먼저 적는다

예시: DiagnosisAgent의 초기 원인 분석을 평가 노드가 검증하고, 근거 부족 · 잘못된 Tool 선택이면 최대 2회 다시 만드는 Self-Correction Loop를 시험합니다.

시험할 것 (예시)

  • 근거 부족 · 잘못된 Tool 선택을 탐지하는가
  • 보정 뒤 같은 기준으로 다시 평가하는가
  • 최대 2회에서 반드시 멈추는가
  • 통과 못 한 결과를 성공처럼 내보내지 않는가
  • 이미 맞는 답을 괜히 고치지 않는가
핵심끝까지 통과하지 못하면 실패(사람 이관)로 끝냅니다. 통과하지 못한 결과를 성공처럼 내보내지 않는다는 것이 이 시험의 핵심 기준입니다.

07 · 2칸 환경 · 조건 · 합격 기준

합격 기준은 시험을 돌리기 전에 쓴다

채점표를 먼저 정해야 점수에 의미가 생깁니다. 결과를 보고 기준을 바꾸면 그건 “탐색”이지 “시험”이 아닙니다.

항목예시

지표근거 포함률 ≥ 90% · 최종 스키마 적합률 100% · 최대 2회 반복
비용시나리오별 입력 · 출력 토큰과 총 호출 횟수 기록
데이터정상 5 · API 타임아웃 5 · 프로세스 다운 5 · 근거 누락 5 (가상)

흐린 기준 → 시험할 수 있는 기준

“답이 정확해야 한다”근거 로그 ID가 1개 이상 있다
“형식이 맞아야 한다”필수 필드 4개가 모두 있다
“위험하지 않아야 한다”restart 권고면 needs_approval=true

평가 루프 규칙 4가지

1기준: 평균 점수 하나가 아니라, 어떤 기준에서 떨어졌는지 이름이 남게
2검사: 스키마 · 근거 유무 · 금지 표현은 코드가 먼저, LLM 평가는 그다음
3피드백: 어디가 왜 틀렸는지 구체적으로 (“다시 해 봐”는 피드백이 아님)
4상한: 반복 횟수를 코드의 상수로 제한

08 · 평가를 코드로

기준 이름이 남는 평가 함수와 상한이 있는 루프

규칙 1 · 2 · 4를 그대로 옮긴 예시입니다. 평가 함수는 떨어진 기준의 이름 목록을 돌려주고, 빈 목록이면 통과입니다. (표준 라이브러리만 사용)

REQUIRED = {"cause_candidates", "evidence_ids", "recommended_action", "needs_approval"}
RISKY = {"restart_request", "rollback"}
MAX_RETRY = 2                     # 규칙 4: 상한은 코드 상수

def critique(out: dict) -> list[str]:      # 규칙 1 · 2
    fails = []
    if REQUIRED - out.keys(): fails.append("schema_missing")
    if not out.get("evidence_ids"): fails.append("missing_evidence")
    if out.get("recommended_action") in RISKY and not out.get("needs_approval"):
        fails.append("approval_required")
    return fails                         # [] = 통과

def run(case, generate, revise):
    out = generate(case)
    log = [("initial", critique(out))]      # 초기 응답도 기록
    retry = 0
    while (fails := critique(out)) and retry < MAX_RETRY:
        out = revise(out, fails)             # 규칙 3: 이름 붙은 피드백
        retry += 1
        log.append((f"revise_{retry}", critique(out)))
    status = "pass" if not critique(out) else "handoff"
    return status, retry, log
가짜 생성기로 돌려 본 결과 (실행 확인)
# SC-01 근거 누락 → 1회 보정 후 통과
('pass', 1, [('initial', ['missing_evidence']),
            ('revise_1', [])])
# SC-03 고쳐지지 않음 → 상한에서 멈춤
('handoff', 2, [... 'revise_2', ['missing_evidence']])
# SC-04 정상 입력 → 고치지 않음
('pass', 0, [('initial', [])])

시험 하나를 끝까지 돌려 같은 번호로 이어 적는다

제출 전 체크

  • ☐ 여덟 칸이 모두 있고 예시 값은 우리 값으로 바꿨다
  • ☐ 합격 기준을 시험 전에 썼다 (바꿨다면 표시했다)
  • ☐ 시나리오에 정상 · 탐지 후 보정 · 이관 사례가 있다
  • ☐ 초기 응답과 최종 응답을 같은 입력으로 비교했다
  • ☐ 종료 사유 · 전체 / 통과 / 이관 수 · 토큰 · 시간이 있다
  • ☐ 추적 로그나 화면이 첨부되고 비밀 값은 지웠다
  • ☐ TC 번호가 3 · 4 · 6 · 7칸에서 같다

팀 적용 순서 (15분)

1평가할 보정 루프 하나를 정한다
2시험 입력 3~5건과 합격 기준을 쓴다
3보정 없이 한 번, 보정을 켜고 한 번 돌린다
4TC마다 초기 · 탐지 · 보정 · 최종을 기록한다
5다른 팀원이 기록만 보고 같은 결론을 내는지 확인한다
학습용 안내입니다. 새 공식 제출물이나 마감을 추가하지 않습니다. 최종 요건은 매니저 안내와 대시보드를 따르고, 예시 값은 팀 주제에 맞게 바꿔 쓰세요.
