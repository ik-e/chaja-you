01 · 평가 목적

질문은 같아도 확인하는 대상은 다르다

도구 호출 능력, 팀 업무 판단, 실제 연동 성공을 같은 점수로 섞지 않습니다.

평가 묶음확인하는 것그 결과만으로 확정할 수 없는 것
BFCL 원본제공된 함수 정의에 맞는 도구 호출 능력우리 DB·권한·화면·내부 API의 정상 동작
팀 자체 문항팀 사용자 상황에서의 도구·업무 판단실제 예약·저장·알림의 완료
모의 도구 실행도구 결과를 받은 뒤의 다음 행동실제 공급원·DB·권한 계층의 동작
서비스 통합 시험화면·API·모델·저장·외부 연동의 연결다른 버전·미실험 상황까지의 성능
보고서에는 무엇을 시험했는지와 아직 시험하지 않은 경계를 한 줄씩 붙입니다.
공식 출처: BFCL 데이터셋 카드 · 수업 안내: BFCL-PREPARE
02 · 원본 일부 평가

BFCL은 30문항만 있는 데이터셋이 아니다

여러 범주·파일이 있고, 이 수업의 30문항은 원본에서 선택한 교육용 실행 범위입니다.

실행 전에 고정

  • 출처 URL과 원본 revision
  • 사용한 파일·범주·문항 ID 30개
  • 원본 정답과 채점기 버전
  • AST·실행·교육용 비교 등 채점 방식

결과에 남길 표현

  • BFCL 원본 일부 30문항 평가
  • 팀 자체 30문항은 별도 표·분모
  • 공식 리더보드 전체 점수와 구분
  • 준비 완료와 모델 실행 완료 구분
보고 예시 문장 틀: 고정 revision의 BFCL 원본 중 [범주·ID] 30문항을 [모델]에 실행하고 [채점 방식]으로 평가했다. 이 결과는 해당 부분집합의 결과다.
문장 틀은 실제 실행·기록 후에만 채웁니다. 출처: BFCL 데이터셋 카드 · 수업 실행·채점 안내
03 · 여러 단계 실행

첫 번째 도구 선택과 업무 완료를 따로 본다

예시: 사용 가능한 상담 시간을 찾아서, 사용자가 동의한 시간으로 신청하는 요청입니다.

① 조회 호출find_slots()
② 도구 결과모의 시간 후보 반환
③ 후속 행동확인·추가 질문 또는 신청
④ 결과 안내신청 결과와 다음 행동

첫 응답 평가

조회 도구를 올바른 인자로 골랐는지 봅니다. 이 점수만으로 신청까지 끝났다고 말하지 않습니다.

여러 단계 평가

고정된 모의 도구 결과를 돌려주고 후속 호출·종료·실패 안내까지 확인합니다. 최대 단계·시간도 정합니다.

채점 방식이 바뀌면 기존 점수를 덮어쓰지 않고 별도 결과로 남깁니다. 추가 확인이 필요한 요청은 임의로 신청하지 않는 것이 정답일 수 있어요.
참고: API 작성법 25~27쪽
04 · 실행 경계

모의 예약 성공은 실제 DB 저장 성공과 다르다

외부 호출·저장·알림마다 실제로 확인한 범위를 표시합니다.

시험에서 관찰한 것알 수 있는 것추가로 확인할 것
book 도구가 성공 JSON 반환모델이 성공 결과를 해석함진짜 DB에 예약이 저장됐는가
시험 DB에 예약 행 생성해당 환경의 저장 경로 동작중복·경합·다른 사용자 접근 거부
알림 생성 행 저장발송 대기 기록이 생성됨실제 전달·중복 발송·실패 재처리
실제 외부 API 정상 응답그 시점·조건의 연동 성공타임아웃·제한·대체 경로 검증
증빙 화면에는 mock / test DB / 실제 공급원을 표시합니다. 실제 사용자에게 예약·발송이 일어나지 않는 시험 환경을 먼저 사용하세요.
참고: API 작성법 26쪽 · DB 작성법 22쪽
05 · 비교 조건

바꾼 것과 고정한 것을 남긴다

점수 차이를 모델 때문이라고 설명하려면 다른 조건도 비교 가능해야 합니다.

고정·기록할 항목남길 내용
문항과 정답문항 버전·ID·해시·평가 유형·채점 기준
모델과 호출 환경요청 모델 ID·응답 모델 ID·공급자·실행일
프롬프트와 도구프롬프트 버전·JSON Schema·strict 등 옵션
반복·한도반복 횟수·최대 단계·시간·재시도·실패 포함 기준
비교 결과반복별 결과·평균·변동·오류·제한 사항
채점 정답을 보고 프롬프트를 맞춘 시험은 탐색용으로 표시합니다. 최종 비교에는 따로 준비한 문항도 사용해 과도한 맞춤 여부를 확인하세요.
반복 횟수·합격선은 팀이 목적에 맞게 정합니다. 반복 몇 번만으로 모든 상황의 우열을 확정하지 않습니다.
06 · 총점과 중요한 실패

점수가 비슷해도 위험한 실패는 따로 센다

아래는 평가표 구성 예시입니다. 숫자나 합격선을 새 공통 요건으로 정하는 자료는 아닙니다.

분리할 항목통과 기준을 먼저 쓰기함께 남길 결과
긴급·사람 인계정해진 상황에서 인계·안내놓친 사례 ID와 이유
권한·정보 부족금지 도구 미실행·필요한 추가 질문권한 밖 실행·값 추정 여부
저장·중복·경합업무 상태 확인·중복 효과 방지재시도 뒤 결과·오류 코드
복구·대체·실패검증된 회복·대체·이관을 구분감지·전략·검증·종료 기록
오류·타임아웃을 분모에서 조용히 빼지 않습니다. 전체 대상 수 / 실행 수 / 성공·실패 / 미실행과 각각의 처리 기준을 적습니다.
참고: Auto-Healing 가이드 20~21쪽
07 · 지연과 비용

사용자 요청 하나의 전체 실행을 잰다

LLM 첫 응답만 빠르거나 저렴해도, 도구·재시도까지 합치면 결과가 달라질 수 있습니다.

전체 시간

요청 접수 → 대기 → 모델·도구 실행 → 재시도 → 최종 결과까지 측정합니다. 겹쳐 실행한 구간은 시간선으로 봅니다.

전체 비용

모든 모델 호출의 실제 사용량·도구 비용을 합산합니다. 호출 실패 비용·캐시·실행일 단가·통화도 구분합니다.

모델 기록입력·출력 토큰
호출 횟수·모델 ID
실행 기록대기·도구·재시도
최종 완료 시각
보고 결과시나리오별 비용
지연·실패율 함께
단가·토큰을 가정해 계산했다면 예상 비용으로 표시합니다. 실제 사용량 측정값과 같은 열에 섞지 않습니다.
평균만으로 숨겨지는 느린 사례도 남깁니다. 동시 실행의 총 시간은 각 호출 시간을 단순히 더한 값과 다릅니다.
08 · 증빙 묶음

스크린샷 한 장에 재현 기록을 연결한다

이미지는 결과를 보여 주고, 입력·환경·로그는 그 결과를 다시 확인하게 합니다.

검토용 폴더 예시

evidence/
  README.md       # 목적·환경·명령·한계
  manifest.json   # 커밋·모델·문항 버전
  cases.jsonl     # 공유 가능한 시험 입력
  runs.jsonl      # 정제한 호출·도구 기록
  scores.csv      # 문항별 판정·이유
  screen.png      # 결과 화면

같은 실행으로 묶기

  • run_id·case_id로 입력·응답·점수 연결
  • 기대값과 실제값을 나란히 기록
  • 모의·실제·미실행 구분
  • 오답·실패의 대표 사례 포함
  • 처음부터 다시 할 실행 명령 안내
원본 저장이 제한되면 허용된 메타데이터·가린 화면으로 증빙합니다. API 키·토큰·비밀번호·불필요한 개인정보는 공개 자료에서 제외합니다.
형식·폴더 이름은 예시입니다. 참고: Auto-Healing 가이드 20쪽
