## 1. 원본 샘플과 직접 비교

### 기획서 (원본 DOCX SHA-256 `b29dac077bdd263b62ed3ae920a700784c85a8564bfd106e812627cb7d39bbab`)

원본에 실제로 있는 대항목/표는 다음과 같음:

1. **서비스 정의:** 구분·기재 내용(서비스명, 사용자, 해결 문제, 핵심 가치, MVP 범위) 2열 표
2. **기능 요구사항:** ID·기능·우선순위·수용 기준 표
3. **비기능 요구사항:** ID·영역·목표 표

V2는 세 대항목과 FR/NFR 형식을 갖추었으므로 **대항목 구조는 일치**한다. 그러나 사용자 가설·비선정 상태 설명이 장문으로 흩어져 **서비스 정의 첫눈 요약표**가 없음. 문제의 손해·기존 방식과의 정량 차이·실제 측정 계획을 사용자 측면에서 설득하기 어렵다.

추가 개선은 공식 대항목을 변경하지 않고 **서비스 정의의 하위 단락**으로 넣어야 한다. 가이드 `기획서_잘_쓰는_법`이 제안한 핵심 5질문 WHY/WHAT/HOW/WHEN-WHO/HOW WELL을 서비스 정의와 참조 표로 연결하되, 샘플을 위반해 5개 대항목으로 임의 변경하지 않는다.

### WBS (원본 DOCX SHA-256 `66c7687e99a9f54e819bbf01bb2fad7ef9510ce573cae6a710022325c5cc7cd7`)

원본에 실제로 있는 대항목/표는 다음과 같음:

1. **간트 차트(주차별 계획·실적):** 작업/담당 × 1~4주 × 상태, ■ 계획 / ● 실적을 구분
2. **일정 관리 규칙:** 주간 갱신, 실제 진척 기준, 지연·영향·변경일 기록
3. **작업 계획표:** ID·작업명·담당·기간·선행·산출물 표
4. **마일스톤:** M1~M4의 실제 결과물·목표일

V2는 대항목이 일치하나, **주제 결정까지의 운영표를 전체 개발 WBS 대신 보여주고 있음**. 현재 두 트랙 전략을 설명하는 목적은 충족하지만 강사 가이드의 100% 작업 분해·완료 기준·의존·핵심 경로·검토/버퍼 요건은 미충족. 11/21 결정을 선행 조건으로 하고, 선정 후 상세 재계획해야 하는 후속 작업은 **미정/조건부**를 유지하되, 전체 교육 마감의 산출물·기획·설계·검토·시연 준비는 WBS 상위 구조에 유지해야 한다.

제출 형태는 `AIO_1기_최종프로젝트_가이드.html`에 **GitHub Projects 화면 또는 시트를 글자가 잘 보이게 캡처해 제출**로 안내되어 있어 현재 Markdown 간트만으로는 충족하지 못함.

## 2. Step2 가이드의 실질 요구

### API: `Doc/Step2/API설계문서_작성법.html` (2026-11-18 원본 고정)

가이드의 문서 구성 6가지:
- 공통 정보·인증: 개발/배포 서버 URL, 인증, 공통 오류, 자동 문서(/docs), 변경 이력
- API 목록: Method/Path/인증/설명/요구사항
- 엔드포인트 상세: 호출 목적, 헤더, 경로/쿼리, 본문 필드/JSON, 검증/권한, 정상 응답, 오류, 실행 규칙 **8칸**
- 검증과 권한 규칙: 형식 vs 실행 권한·승인 분리
- Tool 정의·호출 흐름: 도구 입력/출력/성공·실패/서버의 실행 허가/호출 순서
- 실행 규칙: timeout·재시도·backoff·중복 실행 방지

현재 V2는 API-01~04의 경로 목록, 요청 예시와 주요 필드를 갖췄지만 **각 API별 완전한 8칸 계약이 없다.** `/docs` 위치, 버전 이력, 실제 사용할 Tool별 예시, 도구별 구체 실패 규칙도 빠져 있다. 백엔드를 실제 구현한 것이 아니므로 `미구현/설계값`으로 명확히 구분하되, **문서로 설계해야 하는 필드는 비워두는 것이 곧 가이드 충족이 아님**을 유의한다.

### DB: `Doc/Step2/DB스키마설계서_작성법.html`

가이드의 문서 구성 6가지:
- ERD + 관계 명세표
- 엔터티 정의(모든 컬럼의 타입·제약·의미)
- pgvector 문서/청크·벡터 스키마·인덱스
- RLS 역할별 SELECT/INSERT/UPDATE/DELETE
- JWT/Redis 세션·캐시 수명주기
- 인덱스·쿼리 최적화 및 검증

현재 V2는 ERD+테이블 요약과 인덱스 후보는 있으나 **열별 타입·제약표, 별도 관계 명세, 권한 정책표와 운영 설계가 없다.** 특히 'pgvector, Redis, RLS는 채택 미정'으로만 적으면 해당 가이드 항목의 설계/적용 여부·대안·결정 시점을 설명하지 못한다. 사용 범위·현재 조건·실제 선택 여부를 명시하고 **특정 기술을 사용하지 않을 경우 강사/매니저 확인 후 항목별 N/A 사유**로 처리한다. 교육의 기술 학습 목표를 임의로 제거하지 않는다.
