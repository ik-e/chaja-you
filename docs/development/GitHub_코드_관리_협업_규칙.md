- 담당: R01 (팀장)
- 상태: 초안

- 갱신일: 2026-11-10
- 근거: [킥오프 회의록 및 첨부 원본](../meetings/2026-11-10_킥오프_회의록.md), 팀장의 후속 운영 방향

## 1. 목적과 원칙

GitHub는 코드, 개발 문서, 커밋과 변경 이력을 관리하는 공용 공간으로 사용합니다. 팀은 담당자의 자율성과 개발 속도를 우선하며, 다른 팀원의 사전 승인이나 필수 코드 리뷰를 병합 조건으로 두지 않습니다. 각 담당자가 자기 변경의 최소 확인을 마치고 공유하는 방식으로 진행합니다.

## 2. 브랜치와 푸시

- 모든 팀원은 `main`에 직접 푸시할 수 있습니다.
- 개인 브랜치는 선택 사항이며 자유롭게 만들고 사용할 수 있습니다. 브랜치 이름과 작업 방식은 강제하지 않습니다.
- `main`에 직접 푸시하거나 개인 브랜치를 병합할 때 PR을 사용하지 않습니다. PR 승인 대기나 필수 리뷰 절차를 두지 않습니다.
- 다른 사람의 변경과 충돌할 가능성이 있는 공통 파일·API·DB 스키마·환경 설정은 관련 담당자에게 먼저 알리고 영향을 조율합니다. 이는 승인 절차가 아니라 작업 충돌을 줄이기 위한 알림입니다.
- 변경으로 `main`이 실행되지 않거나 핵심 흐름이 깨지면 변경한 담당자가 우선 수정하거나 되돌리고, 팀장에게 상황을 공유합니다.

## 3. 담당자의 최소 확인

각 담당자는 자신의 변경 범위에 맞는 최소한의 확인을 한 뒤 푸시합니다. 다른 팀원이 별도로 결과물을 검토하는 것은 필수 규칙이 아닙니다.

| 변경 유형 | 최소 확인 예시 |
|---|---|
| 백엔드/API | 변경한 API 또는 핵심 로직이 기본 입력에서 동작하는지 확인 |
| 프론트엔드 | 변경한 화면과 주요 사용자 흐름이 열리고 동작하는지 확인 |
| 데이터/DB | 적용·조회가 의도대로 되는지 확인하고 기존 데이터 영향 점검 |
| 인프라/설정 | 개발 환경의 실행, 연결 또는 상태 확인 |
| 문서 | 링크가 맞고 지시한 절차를 따라갈 수 있는지 확인 |

관련 자동 테스트가 이미 있으면 변경과 직접 관련된 테스트를 실행합니다. 테스트가 없거나 실행할 수 없으면 범위에 맞는 간단한 수동 확인으로 진행하고, 중요한 제한이나 남은 문제만 커밋 메시지 또는 관련 작업 기록에 남깁니다. 이 규칙은 모든 변경에 새 테스트를 만들도록 요구하지 않습니다.

## 4. 커밋과 변경 공유

- 커밋 메시지는 날짜만 쓰지 않고 변경 목적을 알 수 있게 작성합니다.
- 여러 목적의 변경은 가능하면 나눠 커밋합니다. 작은 작업은 과도하게 쪼개지 않습니다.
- 다른 담당자 작업에 영향을 주는 변경이나 `main`의 실행 상태를 깨뜨릴 수 있는 변경은 푸시 직후 Discord에 변경 내용과 영향을 간단히 알립니다.
- 커밋 메시지 형식은 강제하지 않습니다. 예시는 다음과 같습니다.

```text
화면: 검색 결과 요약 표시
fix: 빈 검색어 처리
docs: API 실행 방법 추가
```

## 5. 통합·QA·배포·릴리스

- 팀장 R01이 전체 통합, 통합 QA, 배포와 릴리스를 관리합니다.
- 각 담당자는 자기 변경과 확인 결과를 공유해 팀장이 전체 동작을 파악할 수 있게 합니다.
- 공식 시연·배포·릴리스 시점과 대상은 팀장이 정하고, 관련 내용을 `docs/meetings/` 또는 해당 산출물 문서에 기록합니다.
- 직접 푸시는 허용하지만, 공식 릴리스의 준비 상태 확인과 배포 진행 책임은 팀장에게 있습니다.

## 6. 보안과 저장소 공개 범위

- `.env`, API 키, 봇 토큰, 비밀번호, 개인 식별 정보는 커밋하지 않습니다. 설정 예시에는 실제 비밀값 없이 `.env.example`을 사용합니다.
- 비밀값을 잘못 커밋했다면 즉시 팀장에게 알리고 해당 자격 증명을 폐기·교체합니다. 단순히 파일을 삭제하는 것만으로 유출 대응을 끝내지 않습니다.
- 킥오프 회의록에는 저장소 공개 여부가 미확정으로 남아 있습니다. 공개 범위는 팀의 결정이 기록되기 전까지 임의로 바꾸지 않습니다.

## 7. 근거와 갱신

킥오프 회의록에는 `main` 직접 작업 허용 검토, 개인 브랜치 사용, PR 간소화 방향이 제안으로 적혀 있으며 세부 사항은 추가 합의 대상으로 표시되어 있습니다. 이 문서는 회의록의 미확정 항목을 현재 팀장이 설명한 운영 방향에 맞춰 구체화한 초안입니다. 팀 합의가 달라지면 이 기준 문서와 [개발 협업 README](README.md)를 함께 갱신합니다.
