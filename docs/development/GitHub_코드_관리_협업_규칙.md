## 1. 목적과 기본 원칙

GitHub는 코드·개발 문서·결정·계약·검증 결과와 변경 이력을 보존하는 정본 공간으로 사용하고, Discord는 협의·전달·알림에 사용합니다.

- `main`은 여러 사람이 동시에 개발하는 작업 공간이 아니라 **통합된 현재 상태**입니다.
- 담당자(TASK owner)는 합의된 작업 범위 안에서 구현 방법, 내부 테스트, 검증 근거와 완료 판단을 자율적으로 책임집니다.
- R01은 모든 변경의 승인자나 재검증자가 아니라 제품 경계·우선순위, cross-task 통합 기준, 핵심 E2E와 릴리스 판단을 담당합니다.
- PR과 검토는 변경의 의미·영향 범위에 비례하여 사용하며, 단순한 변경에 불필요한 승인 대기를 만들지 않습니다.

## 2. 브랜치·PR·main 반영

| 변경 범위 | 통합 방식 | 확인 책임 |
|---|---|---|
| 의미가 바뀌지 않는 오탈자·단순 문서 정리·생성 프로젝션 갱신 | `main` 직접 반영 가능; 별도 PR 강제 없음 | 변경 담당자 |
| TASK 내부의 의미 있는 기능 변경 | **TASK 단위 브랜치 + PR 기본** | TASK owner가 구현·검증·통합 판단 |
| 다른 TASK가 의존하는 API·DB 스키마·인터페이스·상태·계약 변경 | 브랜치 + PR 기본 | 관련 owner끼리 영향과 계약 확인 |
| 제품 범위·Must/Done·공통 구조·해결되지 않는 cross-task 충돌 | R01 결정 후 통합 | R01은 결정, 담당자는 구현·검증 |

- 의미 있는 변경에 PR을 기본으로 쓰지만, **모든 PR에 R01 승인이나 별도 필수 리뷰를 요구하지 않습니다.**
- 브랜치는 TASK 단위로 작업을 구분합니다. 세부 브랜치 이름이나 PR 서식 자체를 새로운 승인 요건으로 만들지 않습니다.
- 공통 파일·설정 등 다른 담당자의 작업에 영향을 주는 변경은 적용 전에 관련 owner와 조율합니다.
- 직접 반영이 허용되는 작은 변경도 해당 파일의 책임 범위와 현재 GitHub 접근·브랜치 규칙을 따릅니다.
- `main`의 핵심 흐름이 변경 후 깨지면 변경 담당자가 우선 수정·되돌리고 관련 owner 및 R01에게 영향을 공유합니다.

## 3. 책임 분산과 정본 편집

- **TASK 내부·저위험 변경:** TASK owner가 구현·테스트·완료 판단과 검증 근거를 책임집니다.
- **공유 계약 변경:** 관련 owner가 의존 관계·호환성·변경 영향을 함께 확인합니다.
- **프로젝트 범위·필수 요구사항·공통 구조 변경:** R01이 판단하고 근거 및 후속 조치를 기록합니다.
- **canonical TASK 원본:** 한 시점에 한 명의 책임자만 직접 수정합니다. 기본 책임자는 해당 TASK owner이며, 다른 사람은 자신의 기록·리뷰에서 근거와 수정안을 전달합니다. 소유권 변경이나 R01의 직접 수정이 필요하면 이를 명시하고 동시 편집을 피합니다.
- 막힘·일정 위험·cross-task 영향이 없는 정상 작업에는 R01의 매번 확인을 요구하지 않습니다.

## 4. 담당자의 최소 확인

각 담당자는 변경에 맞는 최소 확인을 한 뒤 통합합니다. 이미 있는 관련 자동 테스트는 실행하고, 테스트가 없거나 실행할 수 없다면 범위에 맞는 수동 확인으로 대체할 수 있습니다. **모든 변경에 새 테스트를 만들거나 R01 검토를 받도록 강제하지 않습니다.**

| 변경 유형 | 최소 확인 예시 |
|---|---|
| 백엔드/API | 변경한 API 또는 핵심 로직의 기본 입력 동작 확인 |
| 프론트엔드 | 변경한 화면과 주요 사용자 흐름 동작 확인 |
| 데이터/DB | 적용·조회 동작과 기존 데이터 영향 확인 |
| 인프라/설정 | 실행 환경·연결·설정 변경 영향 확인 |
| 문서 | 링크·설명·지시 절차의 정합성 확인 |

검증하지 못한 항목이나 남은 중요한 제한은 통과로 표시하지 않고 해당 TASK·커밋·검토 기록에 남깁니다.

## 5. 커밋과 변경 공유

- 일반 커밋 메시지는 `<종류>(<대상>): <실제 변경 요약>` 형식을 **권장**합니다. 예: `docs(TASK-004): record source constraints`, `fix(R05): handle missing input`, `docs(ops): sync collaboration rules`.
- 종류는 `docs`, `feat`, `fix`, `test`, `refactor`, `chore`, `merge` 등을 사용합니다. 가장 중요한 기준은 **실제 diff의 주된 변경과 메시지가 일치하는 것**이며, 형식·티켓 번호를 강제하지 않습니다.
- 서로 다른 목적의 변경은 가능하면 나누되, 작은 작업을 불필요하게 쪼개지 않습니다.
- 다른 담당자 작업이나 `main` 실행 상태에 영향을 주는 변경은 Discord에 변경 내용·영향·필요한 확인을 간단히 알립니다. 확정 결정과 검증 결과는 GitHub 정본에 남깁니다.

## 6. 통합·QA·릴리스

- R01은 제품 경계와 cross-task 통합 기준, **핵심 사용 흐름의 E2E 및 공식 릴리스 준비 상태**를 확인합니다.
- TASK owner는 자신의 작업과 검증 근거를 관리하며, 공유 계약의 변경은 관련 owner와 확인합니다.
- 공식 시연·배포·릴리스 시점과 대상은 R01이 결정하고 해당 회의·산출물·작업 문서에 기록합니다.
- PR을 통과했다고 제품 전체의 E2E 확인이 자동으로 완료된 것으로 간주하지 않습니다.

## 7. 보안과 기록 범위

- 이 저장소는 공개 저장소입니다. `.env`, 실제 API 키·토큰·비밀번호·개인 연락처·비공개 링크를 코드·문서·예시·로그·커밋에 포함하지 않습니다. 설정 예시는 비밀값 없이 `.env.example`로 관리합니다.
- 비밀값을 잘못 커밋하면 R01에게 알리고 해당 자격 증명을 즉시 폐기·교체합니다. 파일 삭제만으로 유출 대응을 끝내지 않습니다.
- 외부 자료와 Discord 메시지의 보존·사용 범위는 [공개 저장소 운영 안내](../public/공개_저장소_운영_안내.md)와 [AGENTS.md](../../AGENTS.md)를 따릅니다.
- GitHub에는 다음 작업에서 재사용할 **지속 상태·결정·계약·검증 결과**를 남기고, 실행 중 worker/retry/queue·임시 context 같은 일시적 runtime 상태를 프로젝트 정본과 혼합하지 않습니다.
